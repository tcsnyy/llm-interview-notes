# 38. 线上监控 / 灰度发布 / A/B 测试与安全审计

> **文件定位**：讲解模型上线后的监控、评测、灰度发布、A/B 测试、安全审计和数据闭环体系。本项目仅做了本地 vLLM 部署和压测，**未实现完整的线上监控、灰度发布、K8s 多节点部署、实时告警等生产级 DevOps 体系**。本章内容作为"如果项目走到生产化需要补充什么"的工程落地扩展方向，面试时需明确区分"已做"和"应做"。
>
> **核心原则**：实事求是，不夸大项目线上化程度。所有未实现的功能标注为"生产化扩展方向"。

---

## 面试 1 分钟 / 3 分钟回答版本

### 1 分钟版

> 模型上线后的工程体系包含四个层面：监控——通过 QPS、延迟分位数、TTFT、TPOT、GPU 利用率等 25+ 指标实时掌控系统健康；灰度发布——用 canary release 或 A/B 测试逐步验证新模型，医疗场景对灰度策略要更保守；安全审计——针对危险建议、禁忌症遗漏、用药错误、隐私泄露等医疗特有风险建立审计和告警机制；数据闭环——从用户反馈和低分回答中挖掘训练数据，驱动模型持续迭代。项目中我完成了 vLLM 本地部署和压测，验证了吞吐和延迟指标，但完整的线上监控和灰度体系需要在生产环境中补充。

### 3 分钟版

> LLM 应用上线的工程复杂度往往超过模型训练本身。我将这个体系分为四层来理解。
>
> 第一层是线上监控。核心指标分为三类：服务指标（QPS、错误率、p50/p95/p99 延迟）、LLM 特有指标（TTFT、TPOT、tokens/s 吞吐）、资源指标（GPU/CPU 利用率、显存、队列长度）。医疗场景还需关注：RAG 检索命中率、安全审查耗时、幻觉报告率、拒绝回答率。
>
> 第二层是灰度发布和 A/B 测试。canary release 先把 5-10% 流量切到新模型观察，关键指标稳定后逐步扩大到 50%、100%。医疗场景更保守——高风险样本需要单独评估，回滚条件预先定义（如错误率超过基线 2 个标准差即自动回滚）。
>
> 第三层是安全审计。医疗场景的特殊风险包括：给出危险建议、遗漏禁忌症提示、错误剂量推荐等。需要专门的审计算法检测这些模式，必要时自动熔断或人工接管。
>
> 第四层是数据闭环。用户反馈、低分回答、RAG 检索失败的 query、安全审查触发的高风险 case 都应被系统收集，经人工审核后反哺为新的训练数据。
>
> 我的项目目前处于"本地部署验证"阶段——用 vLLM 在 RTX 5090 上完成了单机部署，压力测试得出吞吐 877 tok/s、TTFT 42ms 的基线数据。完整线上化需要补充 K8s 部署、Prometheus + Grafana 监控、CI/CD 流水线、灰度路由网关等基础设施，这些都是我明确标记的下一步扩展方向。

## 1. 线上监控指标体系

### 1.1 服务层指标

| 指标 | 含义 | 告警阈值（参考） |
|------|------|---------------|
| QPS | 每秒请求数 | 超过容量 80% 告警 |
| 错误率 | 非 200 响应占比 | > 1% 严重, > 0.1% 警告 |
| 超时率 | 超过阈值时间的请求占比 | > 0.5% 告警 |
| p50/p95/p99 延迟 | 分位数延迟 | 比基线增加 50%/100% |

### 1.2 LLM 特有指标

| 指标 | 含义 | 关注点 |
|------|------|--------|
| **TTFT** | 从收到请求到首个 token | 用户体验核心，< 200ms 优秀 |
| **TPOT** | 每生成一个 token 的平均时间 | decode 效率，< 20ms/token 理想 |
| tokens/s | 总体生成速度 | 衡量吞吐能力 |
| Input/Output Tokens | token 数量分布 | 长 prompt 影响 prefill 延迟 |

### 1.3 RAG / 检索相关指标

| 指标 | 含义 |
|------|------|
| Cache Hit Rate | LLM 响应缓存命中率 |
| Retrieval Latency | 知识库向量检索耗时（应 < 50ms） |
| RAG Hit Rate | 检索是否返回相关文档 |
| No-Answer Rate / Refusal Rate | 模型无法/拒绝回答的比例 |
| Hallucination Report Rate | 用户/系统标记幻觉的比例 |

### 医疗数据日志注意事项

- 强制脱敏字段：用户真实姓名 → 哈希、身份证号 → 不记录、手机号 → 不记录
- 不可将原始 query 发送给第三方 API 做分析
- 审计日志需满足医疗合规要求（可追溯、不可篡改）
- 日志保留周期需满足法规要求（如不少于 1 年）

## 3. 灰度发布和 A/B 测试

### 概念总览

| 策略 | 说明 | 适用场景 |
|------|------|---------|
| **Canary Release** | 小比例流量逐步扩大（5%→25%→50%→100%） | 新模型逐步替换旧模型 |
| **Blue-Green Deployment** | 两套完整环境，流量一键切换 | 回滚只需切回蓝色环境 |
| **Shadow Traffic** | 新模型接收镜像流量，不返回给用户 | 高风险场景的安全预评估 |
| **A/B Testing** | 多版本并行服务，统计显著性对比 | 用于效果评估而非部署策略 |

### Canary Release 核心逻辑

1. 部署新模型到独立 vLLM 实例
2. 负载均衡层按比例切流：先切 5%
3. 观察指标 1-2 小时：延迟 p95、错误率、安全违规率
4. 逐步加大：5% → 20% → 50% → 100%
5. 任何指标异常 → 立即回滚

**医疗场景特殊点**：高风险请求（用药/急救/手术）只走 stable 版本——不参与灰度实验。

### Rollback 自动回滚条件

- 错误率 > 1% 或超过基线 2 个标准差
- p99 延迟翻倍（> 基线 × 2）
- 安全违规范例数增加 > 50%
- 连续 5 次健康检查失败

### A/B Testing 医疗特殊考量

- 不能只看点击率和用户满意度——用户满意不等于医学正确
- 安全指标一票否决：B 版本在任何安全指标上显著差于 A（p<0.05）→ 直接终止实验
- 流量切分按 user_id hash 保证用户一致性
- 高风险 query 始终先走 shadow traffic 静默评估

## 4. 安全审计

### 医疗特有安全风险

| 风险类别 | 典型表现 | 严重程度 |
|---------|--------|---------|
| Dangerous Advice | 建议高血压患者停药 | 极高 |
| Contraindication | 未提及药物禁忌症 | 极高 |
| Wrong Dosage | 推荐错误剂量 | 极高 |
| Delayed Emergency | 对心梗症状建议居家观察 | 极高 |
| Overdiagnosis | 将普通头痛暗示为脑瘤 | 高 |
| False Reassurance | 告诉患者"没事"但实际需就医 | 高 |
| Privacy Leakage | 回复中暴露个人信息 | 高 |
| Jailbreak / Prompt Injection | 越狱绕过安全限制 | 中 |

### 安全告警与熔断自动降级流程

```
1. SafetyMonitor 检测到高风险告警
2. 判断严重程度：
   ├─ CRITICAL (单个高风险) → 拦截此请求, 返回安全回复
   ├─ CRITICAL × 3 (1min内) → 触发熔断
   └─ EMERGENCY → 立即熔断
3. 熔断状态：
   ├─ 所有请求 → 安全降级回复
   ├─ 高风险请求 → 加入人工复核队列
   └─ 发送告警 → 值班工程师
4. 恢复流程：
   ├─ 工程师排查定位根因
   ├─ 修复问题 → 人工确认安全 → 解除熔断
   └─ 逐步恢复流量 (canary 5%→25%→...)
```

## 5. 数据闭环

### 数据来源

- 用户反馈：点赞/点踩、手动纠错、自由文本反馈、追问行为
- 低分回答：LLM-as-Judge 评分低、安全审查触发、检索失败/幻觉标注
- RAG 检索失败样本：检索相似度低于阈值、检索到但无法回答
- 高风险错误：安全告警触发、人工复核确认的错误、红队测试发现的漏洞

### 数据闭环流水线

```
线上 bad case
    │
    ▼
[自动归因分类]
  ├── 模型知识不足 → 标记"需补充RAG知识"
  ├── 回答不安全 → 标记"DPO rejected候选"
  ├── 回答质量差 → 标记"SFT训练候选"
  ├── 检索不准 → 标记"RAG优化候选"
  └── 用户无理取闹 → 过滤丢弃
    │
    ▼
[人工复审]（每周一次，筛选高价值样本）
    │
    ▼
[标注] SFT候选写好标准答案 / DPO候选写好chosen+rejected
    │
    ▼
[训练池积累到阈值 → 触发新一轮训练]
```

### 关键设计

- 人工复审环节不可省——自动归因可能误判
- 回流周期：每周收集 → 每两周标注 → 每月或积累 1000+ 条触发新训练
- 医疗场景：标注需要医学专业人员审核（而非 crowdsourcing）

## 7. 面试核心问答

### Q: 模型上线后监控什么？⭐⭐⭐⭐⭐

> "模型上线后的监控需要覆盖四个层面。第一层是服务层面：QPS、错误率、超时率、p50/p95/p99 延迟。第二层是 LLM 特有指标：TTFT、TPOT、input/output token 分布。第三层是资源层：GPU 利用率、显存、队列长度。第四层是业务安全层：RAG 检索命中率、安全审查触发率、幻觉报告率、拒绝回答率。我的项目完成了本地 vLLM 部署压测，拿到了吞吐 877 tok/s、TTFT 42ms 的基线数据。但完整的 Prometheus + Grafana 监控面板、告警规则、K8s 调度等生产化能力需要在后续迭代中补充。"

### Q: 线上反馈如何反哺训练？⭐⭐⭐⭐⭐

> "线上反馈反哺训练是一个闭环过程。第一步收集：用户点赞/点踩、手动纠错、系统自动标记的低分回答、安全告警触发、RAG 检索失败。第二步挖掘：从反馈中提取高价值训练数据候选——用户点踩+追问的 case、用户手动纠错提供的 chosen/rejected 对、检索失败的 query 提示知识库盲区。第三步审核：候选数据需要人工审核（医疗场景最好是医生审核）——不能直接把用户反馈当训练数据。第四步构造训练数据：SFT 对话格式或 DPO 偏好对。第五步重训+评测：用新数据增量训练，在扩展的评测集上验证指标，通过后走灰度发布。这个闭环我在项目文档中做了完整设计，但因为项目是小规模部署试点，还没有机会跑通完整的数据飞轮。"

## 8. 背诵版总结

### 核心概念速记

| 概念 | 一句话 | 本项目状态 |
|------|--------|-----------|
| QPS / Error Rate / p99 Latency | 最基础的服务健康三指标 | 本地压测有基线 |
| TTFT | 首 token 延迟，用户体验核心 | 项目测得 42ms |
| TPOT | 每 token 延迟，decode 效率 | vLLM 自动优化 |
| Canary Release | 小比例灰度→逐步扩大 | 未实现，需补充 |
| A/B Testing | 多版本并行服务，统计对比 | 未实现 |
| Circuit Breaker | 自动熔断保护 | 未实现 |
| Data Flywheel | 线上反馈驱动模型持续优化 | 设计完整，待落地 |

### 面试口诀

> "上线先看三指标：错误率、p99、首 token。灰度先走 5%，高风险不进实验流。安全告警三连发，熔断接管不能少。用户反馈不是免费数据，医生审核才能进训练池。数据闭环要跑通，模型越用越强大。"
