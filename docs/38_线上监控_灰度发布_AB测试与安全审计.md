## 面试 1 分钟 / 3 分钟回答版本

### 1 分钟版（电梯 pitch）

> 模型上线后的工程体系包含四个层面：监控——通过 QPS、延迟分位数、TTFT、TPOT、GPU 利用率等 25+ 指标实时掌控系统健康；灰度发布——用 canary release 或 A/B 测试逐步验证新模型，医疗场景对灰度策略要更保守；安全审计——针对危险建议、禁忌症遗漏、用药错误、隐私泄露等医疗特有风险建立审计和告警机制；数据闭环——从用户反馈和低分回答中挖掘训练数据，驱动模型持续迭代。项目中我完成了 vLLM 本地部署和压测，验证了吞吐和延迟指标，但完整的线上监控和灰度体系需要在生产环境中补充。

### 3 分钟版（含项目细节）

> LLM 应用上线的工程复杂度往往超过模型训练本身。我将这个体系分为四层来理解。
>
> 第一层是线上监控。核心指标分为三类：服务指标（QPS、错误率、超时率、p50/p95/p99 延迟）、LLM 特有指标（TTFT 首 token 延迟、TPOT 每 token 延迟、tokens/s 吞吐、input/output token 分布）、资源指标（GPU/CPU 利用率、GPU 显存、队列长度）。医疗场景还需关注安全相关指标：RAG 检索命中率、安全审查耗时、幻觉报告率、拒绝回答率。
>
> 第二层是灰度发布和 A/B 测试。canary release 先把 5-10% 流量切到新模型观察，关键指标稳定后逐步扩大到 50%、100%。医疗场景的灰度更保守——高风险样本（如涉及用药、急救、手术建议）需要单独评估，安全阈值比通用场景更严格。回滚条件也要预先定义（如错误率超过基线 2 个标准差即自动回滚）。
>
> 第三层是安全审计。医疗场景的特殊风险包括：给出危险建议、遗漏禁忌症提示、错误剂量推荐、延误紧急就医建议、过度诊断引发恐慌、虚假安慰延误治疗。需要专门的审计算法检测这些模式，发现风险时触发告警、记录审计日志、必要时自动熔断或人工接管。
>
> 第四层是数据闭环。用户点赞/点踩、低分回答、RAG 检索失败的 query、安全审查触发的高风险 case，都应该被系统收集，经人工审核后反哺为新的 SFT 数据、DPO preference pair、RAG 文档补充或 safety eval set 扩展。这样模型会越用越好。
>
> 我的项目目前处于"本地部署验证"阶段——用 vLLM 在 RTX 5090 上完成了单机部署，压力测试得出吞吐 877 tok/s、TTFT 42ms 的基线数据。完整线上化需要补充 K8s 部署、Prometheus + Grafana 监控、CI/CD 流水线、灰度路由网关等基础设施，这些都是我明确标记的下一步扩展方向。

## 1. 线上监控指标体系（25+ 指标详解）

### 1.1 服务层指标

| 指标 | 英文 | 含义 | 告警阈值（参考） |
|------|------|------|---------------|
| QPS | Queries Per Second | 每秒请求数 | 超过容量 80% 告警 |
| 请求总数 | Request Count | 累计请求量 | 用于流量分析和计费 |
| 错误率 | Error Rate | 非 200 响应占比 | > 1% 严重, > 0.1% 警告 |
| 超时率 | Timeout Rate | 超过阈值时间的请求占比 | > 0.5% 告警 |
| p50 延迟 | p50 Latency | 50% 请求的端到端延迟 | 比基线增加 50% |
| p95 延迟 | p95 Latency | 95% 请求的端到端延迟 | 比基线增加 50% |
| p99 延迟 | p99 Latency | 99% 请求的端到端延迟 | 比基线增加 100% |

### 1.2 LLM 特有指标

| 指标 | 英文 | 含义 | 关注点 |
|------|------|------|--------|
| **TTFT** | Time To First Token | 从收到请求到首个 token | 用户体验核心指标，< 200ms 优秀 |
| **TPOT** | Time Per Output Token | 每生成一个 token 的平均时间 | decode 效率，< 20ms/token 理想 |
| tokens/s | Tokens Per Second | 总体生成速度 | 衡量吞吐能力 |
| Input Tokens | 输入 token 数量分布 | 理解 prompt 长度分布 | 长 prompt 影响 prefill 延迟 |
| Output Tokens | 输出 token 数量分布 | 理解回答长度分布 | 长回答影响 decode 耗时 |

### 1.3 资源层指标

| 指标 | 含义 | 告警 |
|------|------|------|
| GPU Utilization | GPU 计算单元利用率 | > 95% 可能过载, < 50% 资源浪费 |
| GPU Memory | 显存使用量/百分比 | > 95% 有 OOM 风险 |
| CPU Utilization | CPU 利用率 | 关注预处理/data pipeline 是否成瓶颈 |
| Queue Length | 等待队列中请求数 | 持续增长说明容量不足 |

### 1.4 RAG / 检索相关指标

| 指标 | 含义 | 关注点 |
|------|------|------|
| Cache Hit Rate | LLM 响应缓存命中率（如 semantic cache） | 减少重复推理成本 |
| Retrieval Latency | 知识库向量检索耗时 | 影响 TTFT，应 < 50ms |
| Rerank Latency | 精排模型耗时 | 关注 reranker 是否成为瓶颈 |
| Generation Latency | LLM 纯生成时间 | decode 阶段耗时 |
| Safety Check Latency | 安全审查耗时 | 不应显著影响用户体验 |
| RAG Hit Rate | 检索是否返回相关文档 | 影响回答质量的核心前置条件 |
| No-Answer Rate | 模型无法回答的比例 | 过高说明知识库不足或路由错误 |
| Refusal Rate | 模型拒绝回答的比例 | 医疗场景中合理的拒绝是安全行为 |
| Hallucination Report Rate | 用户/系统标记幻觉的比例 | 核心安全指标 |
| User Feedback Rate | 用户主动反馈占比 | 反馈率本身反映用户参与度 |

### 2.2 医疗数据日志注意事项

```
【强制脱敏字段】
  - 用户真实姓名 → 哈希
  - 身份证号 → 不记录
  - 手机号 → 不记录
  - GPS 精确定位 → 粗粒度到城市级别
  - IP 地址 → 脱敏后保留 /24 子网

【医疗特有约束】
  - 日志中的病情描述、用药记录属于医疗数据，受《个人信息保护法》管辖
  - 不可将原始 query 发送给第三方 API 做分析
  - 审计日志需满足医疗合规要求（可追溯、不可篡改）
  - 日志保留周期需满足法规要求（如不少于 1 年）
  - 删除用户数据时需同步删除对应日志

【日志安全】
  - 日志系统本身需要访问控制和审计
  - writer 端和服务端分离（避免日志写入影响推理延迟）
  - 考虑异步写日志队列（如 Kafka → ELK）
```

### 3.2 Canary Release 路由伪代码

```python
import hashlib
import random
from dataclasses import dataclass
from typing import Dict, Optional


@dataclass
class ModelVersion:
    name: str
    endpoint: str
    weight: float  # 流量比例 0.0 ~ 1.0
    is_active: bool


class CanaryRouter:
    """
    Canary Release 流量路由器。
    根据当前灰度配置将请求分发到不同版本模型。
    
    策略：
    1. 高风险医疗请求 → 始终发往 stable 版本（保守策略）
    2. 其他请求 → 按流量比例随机路由
    3. 自动增量：如指标正常，每 N 分钟增加灰度比例
    """

    def __init__(self):
        self.versions: Dict[str, ModelVersion] = {}
        self.gray_scale_history = []  # 灰度变更记录，用于审计

    def register_version(self, version: ModelVersion):
        self.versions[version.name] = version

    def detect_risk_level(self, request: dict) -> str:
        """根据请求内容判断风险等级（医疗特有逻辑）"""
        query = request.get("query", "")
        high_risk_keywords = [
            "急救", "溶栓", "药物剂量", "手术",
            "过敏", "休克", "中毒", "新生儿",
            "化疗", "抗凝", "胰岛素",
        ]
        for kw in high_risk_keywords:
            if kw in query:
                return "high"
        return "low"

    def route(self, request: dict) -> str:
        """决定请求路由到哪个模型版本"""
        risk_level = self.detect_risk_level(request)

        # 高风险请求：只走 stable 版本（医疗场景保守策略）
        if risk_level == "high":
            stable_version = self._get_stable_version()
            if stable_version:
                return stable_version.endpoint

        # 用户级别哈希：同一用户始终路由到同一版本（保证体验一致）
        user_id = request.get("user_id", str(random.random()))
        user_hash = int(hashlib.md5(user_id.encode()).hexdigest(), 16) % 100

        # 按权重分配
        cumulative = 0
        for version in sorted(self.versions.values(),
                              key=lambda v: v.weight):
            cumulative += version.weight * 100
            if user_hash < cumulative and version.is_active:
                return version.endpoint

        # fallback: 返回 stable 版本
        stable = self._get_stable_version()
        return stable.endpoint if stable else list(self.versions.values())[-1].endpoint

    def _get_stable_version(self) -> Optional[ModelVersion]:
        """获取 stable 版本（权重最大且激活的）"""
        active = [v for v in self.versions.values() if v.is_active]
        if not active:
            return None
        return max(active, key=lambda v: v.weight)

    def auto_increment_weight(self, new_version: str, increment: float = 0.1):
        """自动增加灰度比例（需先验证指标正常）"""
        if new_version in self.versions:
            current_weight = self.versions[new_version].weight
            new_weight = min(current_weight + increment, 1.0)
            self.versions[new_version].weight = new_weight
            self.gray_scale_history.append({
                "timestamp": time.time(),
                "version": new_version,
                "old_weight": current_weight,
                "new_weight": new_weight,
            })
```

### 3.3 Rollback Condition 伪代码

```python
import statistics
from collections import deque
from dataclasses import dataclass, field
from typing import Deque, List


@dataclass
class RollbackConfig:
    """回滚条件配置"""
    error_rate_threshold: float = 0.01       # 错误率超过 1%
    error_rate_std_multiplier: float = 2.0   # 超过基线 2 个标准差
    p99_latency_increase_ratio: float = 2.0  # p99 延迟翻倍
    safety_violation_increase: float = 1.5   # 安全违规范例数增加 50%
    consecutive_failures: int = 5            # 连续 5 次健康检查失败
    observation_window_seconds: int = 300    # 观察窗口 5 分钟
    min_samples: int = 100                   # 最少样本量


class RollbackDecider:
    """自动回滚决策器"""

    def __init__(self, config: RollbackConfig = None):
        self.config = config or RollbackConfig()
        self.metrics_history: Deque[dict] = deque(maxlen=1000)

    def add_metrics(self, snapshot: dict):
        """添加一个时间窗口的指标快照"""
        self.metrics_history.append(snapshot)

    def should_rollback(self) -> tuple[bool, str]:
        """判断是否应该回滚
        Returns:
            (should_rollback: bool, reason: str)
        """
        if len(self.metrics_history) < self.config.min_samples:
            return False, "Not enough samples yet"

        # 获取最近观察窗口的指标
        recent = [
            m for m in self.metrics_history
            if m["timestamp"] > time.time() - self.config.observation_window_seconds
        ]
        if len(recent) < self.config.min_samples:
            return False, "Not enough samples in observation window"

        # 1. 检查错误率
        error_rates = [m["error_rate"] for m in recent]
        baseline_error = statistics.mean(error_rates[:10])  # 基线取前 10 个点
        current_error = statistics.mean(error_rates[-10:])  # 当前取后 10 个点

        if current_error > self.config.error_rate_threshold:
            return True, f"Error rate {current_error:.3%} exceeds threshold {self.config.error_rate_threshold:.3%}"

        if current_error > baseline_error + self.config.error_rate_std_multiplier * (
            statistics.stdev(error_rates) if len(error_rates) > 1 else 0
        ):
            return True, f"Error rate {current_error:.3%} significantly above baseline {baseline_error:.3%}"

        # 2. 检查延迟
        p99_latencies = [m["p99_latency_ms"] for m in recent]
        baseline_p99 = statistics.mean(p99_latencies[:10])
        current_p99 = statistics.mean(p99_latencies[-10:])

        if current_p99 > baseline_p99 * self.config.p99_latency_increase_ratio:
            return True, f"p99 latency {current_p99:.0f}ms increased {current_p99/baseline_p99:.1f}x over baseline {baseline_p99:.0f}ms"

        # 3. 检查安全违规范例（医疗特有）
        if "safety_violations" in recent[0]:
            violations = [m["safety_violations"] for m in recent]
            baseline_v = statistics.mean(violations[:10])
            current_v = statistics.mean(violations[-10:])
            if current_v > baseline_v * self.config.safety_violation_increase:
                return True, f"Safety violations increased from {baseline_v:.1f} to {current_v:.1f}"

        return False, "All metrics within normal range"

    def execute_rollback(self, new_version_name: str) -> dict:
        """执行回滚操作"""
        return {
            "action": "rollback",
            "target_version": new_version_name,
            "rollback_reason": "Automatic rollback triggered by RollbackDecider",
            "steps": [
                "1. Route all traffic back to stable version",
                "2. Drain in-flight requests on canary version",
                "3. Preserve canary version logs for investigation",
                "4. Send alert to on-call engineer",
                "5. Schedule post-mortem review",
            ],
            "recovery_time_estimate": "Immediate (traffic switch ~seconds)",
        }
```

### 3.4 A/B Testing 中的医疗特殊考量

```
【为什么不能只看点击率和用户满意度】
  - 医学 LLM 的"好回答"不等于"用户满意的回答"
  - 用户满意 ≠ 医学正确：模型可能给出用户想听但危险的建议
  - 点击率高可能只是模型更"讨好"用户（降低安全门槛）
  - 医疗场景必须额外评估：安全性、准确性、合规性

【医疗 A/B 测试安全约束】
  1. 高风险样本单独评估：
     - 涉及药物剂量、急救建议、手术决策的 query 单独统计
     - 这些样本上 B 版本必须不差于 A 版本才能通过
  2. 安全指标一票否决：
     - 如果 B 版本在安全指标上显著差于 A（p<0.05）→ 直接终止实验
     - 不需要等所有指标都跑完
  3. 流量切分保证用户一致性：
     - 同一用户的所有请求应发给同一版本（基于 user_id hash）
     - 避免用户先后得到不同模型回答的困惑
  4. 灰度比例与风险等级联动：
     - 低风险 query: 正常灰度 5%→25%→50%→100%
     - 高风险 query: 始终先走 shadow traffic（静默 5000+ 样本后人工审查）
```

### 3.5 A/B Routing 伪代码

```python
class ABRouter:
    """
    A/B 测试路由器。
    按用户 hash 稳定分流，保证同一用户始终见到同一版本。
    """

    def __init__(self, experiments: dict):
        """
        experiments = {
            "medical_style_v2": {
                "control": ModelVersion(name="v3.0", endpoint="...", weight=0.5),
                "treatment": ModelVersion(name="v3.1", endpoint="...", weight=0.5),
                "safety_constraints": {
                    "high_risk_only_control": True,  # 高风险只走对照组
                }
            }
        }
        """
        self.experiments = experiments

    def route(self, request: dict, experiment_name: str) -> str:
        exp = self.experiments[experiment_name]

        # 高风险请求：不走实验组
        if exp["safety_constraints"].get("high_risk_only_control"):
            if self._is_high_risk(request["query"]):
                return exp["control"].endpoint

        # 用户 hash 稳定分配
        user_id = request.get("user_id", "")
        bucket = int(hashlib.md5(user_id.encode()).hexdigest(), 16) % 100

        control_weight = exp["control"].weight * 100
        if bucket < control_weight:
            return exp["control"].endpoint
        else:
            return exp["treatment"].endpoint

    def _is_high_risk(self, query: str) -> bool:
        high_risk_patterns = [
            r"剂量|用量|吃几片|mg|ml",            # 用药剂量
            r"胸痛|呼吸困难|大出血|昏迷|抽搐",      # 急诊症状
            r"孕妇|哺乳期|新生儿|婴幼儿",            # 特殊人群
            r"手术|开刀|切除",                     # 手术建议
            r"过敏|过敏源|禁忌",                    # 过敏和禁忌
        ]
        import re
```

### 4.1 医疗特有安全风险

| 风险类别 | 典型表现 | 检测方法 | 严重程度 |
|---------|--------|---------|---------|
| Dangerous Advice | 建议高血压患者停药 | 规则 + Judge 二次审查 | 极高 |
| Contraindication | 未提及药物禁忌症 | 对照药品说明书知识库 | 极高 |

| Overdiagnosis | 将普通头痛暗示为脑瘤 | 概率性表述检测 | 高 |
| False Reassurance | 告诉患者"没事"但实际需就医 | 否定模式 + 风险校验 | 高 |
| Privacy Leakage | 回复中暴露训练数据中的个人信息 | PII 检测器 | 高 |
| Prompt Injection | 用户输入尝试越狱 | 输入安全检查 + 意图分类 | 中 |
| RAG Document Injection | 恶意 RAG 文档注入诱导错误回答 | 文档来源验证 + 内容审查 | 中 |

```python
class FeedbackCollector:
    """用户反馈收集系统"""

    def __init__(self, db_connection, feedback_queue):
        self.db = db_connection
        self.queue = feedback_queue  # 异步队列，避免阻塞推理

    def collect(self, request_id: str, feedback_type: str,
                feedback_detail: dict):
        """收集一条用户反馈"""
        feedback = {
            "request_id": request_id,
            "timestamp": time.time(),
            "type": feedback_type,  # "thumbs_up", "thumbs_down", "correction", "free_text"
            "detail": feedback_detail,
        }

        # 异步写入（不阻塞 API 返回）
        self.queue.put(feedback)

    def process_feedback_batch(self):
        """批量处理反馈队列（定期执行）"""
        batch = []
        while not self.queue.empty():
            batch.append(self.queue.get())

        if not batch:
            return

        for fb in batch:
            # 1. 持久化存储
            self.db.insert("feedback", fb)

            # 2. 更新指标计数器
            if fb["type"] == "thumbs_down":
                self._increment_counter("daily_dislike_count")

            # 3. 低分反馈自动入池待审核
            if fb["type"] in ["thumbs_down", "correction"]:
                self._add_to_review_pool(fb)

            # 4. 修正类反馈 → 直接标记为潜在 SFT 数据候选
            if fb["type"] == "correction":
                self._add_to_training_candidate_pool(fb)

    def _add_to_review_pool(self, feedback: dict):
        """将低质量回答加入人工审核池"""
        self.db.insert("review_pool", {
            "request_id": feedback["request_id"],
            "status": "pending_review",
            "priority": self._calculate_review_priority(feedback),
        })

    def _add_to_training_candidate_pool(self, feedback: dict):
        """将用户修正加入训练数据候选池"""
        self.db.insert("training_candidates_sft", {
            "source": "user_correction",
            "request_id": feedback["request_id"],
            "correction": feedback["detail"].get("correct_answer", ""),
            "status": "pending_doctor_review",  # 需医生审核
        })

    def _calculate_review_priority(self, feedback: dict) -> str:
        """根据反馈类型和 query 风险计算审核优先级"""
        risk = feedback["detail"].get("risk_level", "low")
        if feedback["type"] == "correction" or risk == "high":
            return "high"
        return "normal"
```

### 6.1 Latency Logging Middleware

```python
import time
import functools
from contextlib import contextmanager
from typing import Dict


class LatencyTracker:
    """请求延迟追踪中间件"""

    def __init__(self):
        self.metrics = {}

    @contextmanager
    def track(self, request_id: str):
        """上下文管理器：自动记录耗时"""
        tracker = {"start": time.time(), "breakdown": {}}
        try:
            yield tracker
        finally:
            total_ms = (time.time() - tracker["start"]) * 1000
            tracker["total_ms"] = total_ms
            self.metrics[request_id] = tracker

    def record_phase(self, tracker: dict, phase: str, phase_start: float):
        """记录单个阶段的耗时"""
        tracker["breakdown"][phase] = (time.time() - phase_start) * 1000


# ===== 使用示例 =====
tracker = LatencyTracker()

def process_medical_query(request_id: str, query: str):
    """处理医疗查询的完整流程"""
    with tracker.track(request_id) as t:
        # Phase 1: Safety pre-check
        t1 = time.time()
        safety_result = safety_check(query)
        tracker.record_phase(t, "safety_pre_check", t1)

        # Phase 2: Retrieval
        t2 = time.time()
        docs = retrieve_documents(query)
        tracker.record_phase(t, "retrieval", t2)

        # Phase 3: Rerank
        t3 = time.time()
        ranked_docs = rerank_documents(query, docs)
        tracker.record_phase(t, "rerank", t3)

        # Phase 4: Generation
        t4 = time.time()
        response = llm_generate(query, ranked_docs)
        tracker.record_phase(t, "generation", t4)

        # Phase 5: Safety post-check
        t5 = time.time()
        safety_post = safety_post_check(query, response)
        tracker.record_phase(t, "safety_post_check", t5)

        return response


def log_request_metrics(request_id: str, tracker: LatencyTracker):
    """输出单次请求的延迟分解日志"""
    metrics = tracker.metrics.get(request_id)
    if metrics:
        print(json.dumps({
            "request_id": request_id,
            "total_ms": metrics["total_ms"],
            "breakdown": metrics["breakdown"],
        }))
```

## 7. 面试核心问答

### 7.1 "模型上线后监控什么"标准回答

> "模型上线后的监控需要覆盖四个层面。
>
> 第一层是**服务层面**的通用指标：QPS、错误率、超时率、p50/p95/p99 延迟。这些是任何线上服务都需要的。
>
> 第二层是**LLM 特有指标**：TTFT（首 token 延迟，影响用户感知）、TPOT（每 token 平均时间，反映 decode 效率）、input/output token 分布（监控用户 prompt 长度变化趋势）。
>
> 第三层是**资源层**：GPU 利用率、GPU 显存、CPU 利用率、请求队列长度。需要关注是否有资源瓶颈或泄露——比如显存 slow leak 会导致运行数小时后 OOM。
>
> 第四层是**业务安全层**，对医疗场景尤其重要：RAG 检索命中率（检索失败的 query 无法保证回答质量）、安全审查触发率、幻觉报告率、拒绝回答率。这些指标直接反映模型在真实场景中是否可靠。
>
> 我的项目完成了本地 vLLM 部署压测，拿到了吞吐 877 tok/s、TTFT 42ms 的基线数据。但完整的 Prometheus + Grafana 监控面板、告警规则、K8s 调度等生产化能力需要在后续迭代中补充。"

### 7.2 "线上反馈如何反哺训练"标准回答

> "线上反馈反哺训练是一个闭环过程，我叫它'数据飞轮'。
>
> 第一步是**收集**：用户点赞/点踩、手动纠错、自由文本反馈，以及系统自动标记的低分回答（LLM-as-Judge 评分低）、安全告警触发的回答、RAG 检索失败的 query。
>
> 第二步是**挖掘**：从收集的反馈中提取高价值的训练数据候选。比如用户点踩+追问的 case 通常说明回答有问题；用户手动纠错提供了 chosen/rejected 对；检索失败的 query 提示知识库盲区。
>
> 第三步是**审核**：候选数据需要经过人工审核（医疗场景最好是医生审核）。不能直接把用户反馈当作训练数据——用户可能给出错误修正，或者用户的偏好不等于医学正确。
>
> 第四步是**构造训练数据**：审核通过的数据被格式化为 SFT 对话数据或 DPO 偏好对。RAG 检索盲区触发知识库文档补充。安全告警 case 加入 safety eval set。
>
> 第五步是**重训 + 评测**：用新数据增量训练模型，在扩展后的评测集上验证指标提升，通过后走灰度发布上线。
>
> 这样形成一个正向循环：模型上线 → 服务用户 → 收集反馈 → 改进模型 → 重新上线。每个 cycle 越短，模型进化越快。这个闭环我在项目文档中做了完整设计，但因为项目是小规模部署试点，还没有机会跑通完整的数据飞轮。"
