# 25 后训练算法对比总表

> 本文档按类别对比 25+ 种方法，覆盖从继续预训练到偏好对齐再到安全增强的完整后训练技术栈。
> 面试保守说法 = 你在面试中遇到"为什么不用 XX"类追问时应该使用的回答思路。

---

## 一、预训练延续与基础微调

| 方法 | 类别 | 核心思想 | 数据格式 | 需Teacher | 需Reward Model | 需Ref Model | On-Policy | 优点 | 缺点 | 适合场景 | 医学项目使用 | 面试保守说法 |
|------|------|------|------|:---:|:---:|:---:|:---:|------|------|------|:---:|------|
| **CPT** (继续预训练) | 训练阶段 | 在领域语料上继续做 next-token prediction，注入领域知识 | 原始文本序列 | 否 | 否 | 否 | 否 | 最直接的知识注入方式；无需标注数据 | 耗时/耗算力；可能导致灾难性遗忘(catastrophic forgetting)；需要大量高质量领域文本(>10B tokens) | 有海量领域文本且需要深度知识注入的场景(如法律/医学基座) | 未使用(数据量不够) | "CPT 需要至少几十亿 token 的领域文本才有意义，我们没有这个规模的纯医学文本数据。用 Teacher 模型做数据蒸馏更高效——它在 55K 数据上就实现了知识的有效迁移" |
| **IFT** (指令微调) | SFT | 在 instruction-response 数据上做监督微调 | (instruction, response) pair | 否(可人工撰写) | 否 | 否 | 否 | 简单直接；data efficient；训练稳定 | 依赖数据质量；容易过拟合；只学了"形式"不一定学到"能力" | 所有 LLM 后训练的基础阶段 | 是(本质就是 SFT) | "IFT 和 SFT 本质上是一回事，我们的 55K 数据就是 IFT 数据。我们对 response 部分的 loss 计算做了 standard 的 label masking" |
| **SFT** (监督微调) | SFT | 在高质量标注数据上最大化正确回答的似然 | (prompt, response) pair, 只计算 response 部分 loss | 可选(用 teacher 生成) | 否 | 否 | 否 | 后训练的基础步骤；决定模型的格式跟随和基本能力 | 缺乏偏好引导；可能继承数据中的 bias；只优化正样本不利用负样本 | 所有 LLM 后训练的基础阶段 | **使用**(55K 医疗数据, QLoRA) | "SFT 是后训练的基石——它建立了模型的基本对话能力和指令遵循。我们在它的基础上用 DPO 进行了偏好对齐" |

## 二、数据蒸馏与训练

| 方法 | 类别 | 核心思想 | 数据格式 | 需Teacher | 需Reward Model | 需Ref Model | On-Policy | 优点 | 缺点 | 适合场景 | 医学项目使用 | 面试保守说法 |
|------|------|------|------|:---:|:---:|:---:|:---:|------|------|------|:---:|------|
| **Teacher Distillation** (知识蒸馏 in LLM) | 数据生成 | 用大模型(teacher)生成高质量数据，用于训练小模型(student) | Teacher 生成的 (prompt, response) pair | 是 | 否 | 否 | 否 | 利用大模型的知识和能力生成高质量训练数据；cost-effective | Teacher 本身不完美(可能产生错误数据)；需要手动筛选/验证；可能限制 student 的认知天花板 | 数据匮乏的垂直领域、小模型 training | **使用**(DeepSeek-v4-pro → Qwen3-8B) | "我们用 Teacher 模型做数据蒸馏而不是 logit-level 知识蒸馏——数据蒸馏在 LLM 领域更实用，因为不同模型架构的 logit 对齐不直接" |
| **Rejection Sampling Fine-tuning** | 数据生成+SFT | 从当前策略采样多个候选，用 reward model 选最好的一个做 SFT | 采样 N 个 response + reward 打分 → 取最高分的 | 否 | 是(=scorer) | 否 | **是**(当前策略采样) | 比普通 SFT 数据质量更高；利用负样本信息(虽不直接训练，但用于筛选) | 需要 reward model；采样 + 筛选增加成本；可能偏向 reward model 的偏好 | 需要高质量正样本但不想直接做 RL 的场景 | 部分使用(LLM-as-Judge 打分筛选) | "我们在 DPO 数据构造中用到了类似的思路——多采样后用 LLM-as-Judge 打分排序，但目的是构造偏好对而非直接做 SFT" |
| **OPD** (Online Preference Distillation) | DPO+On-policy | 用当前策略 on-policy 采样生成数据, 用teacher/RM标注偏好, 然后做 DPO | 当前策略采样 + preference label → DPO data | 是(=scorer) | 可选 | 是 | **是** | 缩小分布偏移(distribution shift)；效果优于标准 DPO | 每轮都需要采样和标注，计算成本高(DPO 的 3-5x)；需要对 teacher/RM 有一定信任 | 追求 DPO 极致效果的场景 | 未使用(成本限制) | "OPD 确实比标准 DPO 更好——on-policy 采样缩小了分布偏移。但我们 10K 数据的规模和 RTX 5090 (32GB) 的算力限制下，标准 DPO 已经够用。如果扩大规模会优先考虑 iterative DPO 或 OPD" |

## 三、偏好优化 — DPO 家族

| 方法 | 类别 | 核心思想 | 数据格式 | 需Teacher | 需Reward Model | 需Ref Model | On-Policy | 优点 | 缺点 | 适合场景 | 医学项目使用 | 面试保守说法 |
|------|------|------|------|:---:|:---:|:---:|:---:|------|------|------|:---:|------|
| **DPO** (Direct Preference Optimization) | 偏好优化 | 从 BT 模型推导出 policy 的闭式解，直接在偏好数据上优化 policy | (prompt, chosen, rejected) triple | 否 | 否(隐式) | **是** | 否(标准)/可选(iterative) | 训练简单稳定；不需要显式 RM；计算成本低(一个 policy + 一个 frozen ref)；工程实现成熟(TRL库) | off-policy 数据分布偏移；容易过拟合(especially on small data)；可能 reward hacking | 中小规模偏好数据(1K-100K)、资源有限的场景、快速 prototyping | **使用**(10K DPO, β=0.1) | "DPO 适合我们的约束条件——10K 数据规模、RTX 5090 (32GB) 算力、有限的项目时间。它不需要维护 reward model 和 value model，训练稳定。但我也理解它可能不如 on-policy 方法效果好" |
| **IPO** (Identity Preference Optimization) | 偏好优化 | 在 DPO 基础上引入 identity mapping 约束，防止 policy 过度偏离 ref | 同 DPO | 否 | 否 | **是** | 否 | 更强的 KL 约束(平方 loss vs log-sigmoid)；理论上更不容易过拟合 | 实践中与 DPO 差距不大；约束过强可能欠拟合 | DPO 容易过拟合的小数据场景 | 未使用 | "IPO 的平方 loss 提供了更强的 KL 惩罚——理论上对防过拟合有帮助。但实践中在我们的数据规模下 DPO 的过拟合通过 early stopping(1 epoch)控制了，IPO 的额外收益不显著" |
| **KTO** (Kahneman-Tversky Optimization) | 偏好优化 | 不需要 pairwise 数据，只需单个样本的"好/坏"标签, 基于前景理论(Prospect Theory) | (prompt, response, label: good/bad) | 否 | 否 | **是** | 否 | 数据构造更简单(不需要 explicit pair)；可以利用更多数据(如用户"赞/踩"反馈) | 信息量不如 pairwise(没有直接对比)；理论假设更复杂 | 有大量 single-label preference 数据的场景(如用户反馈日志) | 未使用(我们有 pairwise data) | "KTO 的优势在于不需要显式的 chosen/rejected 对——这在有用户反馈的场景很实用。但我们有能力构造 pairwise 数据(pairwise 信息量更大)，所以选了 DPO" |
| **ORPO** (Odds Ratio Preference Optimization) | 偏好优化 | 在 SFT loss 上叠加 odds ratio 偏好损失，不需要 ref model | 同 DPO 但不需要 ref model | 否 | 否 | **否** | 否 | 省 ref model 显存(约 50%)；训练更快(单 forward pass)；效果在一些 benchmark 上接近 DPO | Odd ratio 的数学假设更强；不一定在所有场景下都稳定 | 显存极度受限的场景、对 ref model 开销敏感 | 未使用(DPO够用) | "ORPO 省 ref model 是一个亮点——但它本质上把 SFT 和偏好对齐混在一起训练，超参数(损失权重)的调优更复杂。我们用 DPO 的两阶段(SFT→DPO)更清晰可控" |
| **SimPO** (Simple Preference Optimization) | 偏好优化 | 用 average log probability 作为隐式 reward + target reward margin γ | 同 DPO(但不需要 ref model) | 否 | 否 | **否** | 否 | 省 ref model；用 avg log prob 对长度更鲁棒(不惩罚长回答)；理论简洁 | 去 ref 后缺少 KL 约束，可能在分布变化大的场景不稳定 | 偏好对齐、长度控制 | 未使用 | "SimPO 的去 ref model 设计确实简洁。但它用 avg log prob 替换 sum log prob 也有代价——在需要精确控制 token-level preference 的场景不够灵活。DRL 的 ref model 虽然多占显存，但提供了显式的 KL 约束锚点" |
| **CPO** (Contrastive Preference Optimization) | 偏好优化 | 不只用 chosen/rejected 对比，还用正确的 reference answer 做 contrastive | (prompt, chosen, rejected, gold_answer optional) | 否 | 否 | 可选 | 否 | 引入 contrastive learning；可以利用 gold answer | 需要额外的正确标注；实际效果存疑 | 有 ground truth 答案的场景(如数学/代码) | 未使用(医疗没有ground truth) | "CPO 需要一个明确的 gold answer——这在数学/代码场景很自然，但医疗问答大多没有唯一的'标准答案'。所以我们没有使用它" |

## 四、偏好优化 — RL 方法

| 方法 | 类别 | 核心思想 | 数据格式 | 需Teacher | 需Reward Model | 需Ref Model | On-Policy | 优点 | 缺点 | 适合场景 | 医学项目使用 | 面试保守说法 |
|------|------|------|------|:---:|:---:|:---:|:---:|------|------|------|:---:|------|
| **PPO** (Proximal Policy Optimization) | RL | 用 clipped objective 约束 policy 更新幅度，同时最大化 reward 并最小化 KL 散度 | 实时采样 + reward model 打分 | 否 | **是** | **是** | **是** | 训练灵活(可迭代多轮)；探索性强；经典 RL 算法经过大量验证 | 需要 4 个模型(policy/ref/reward/value)；训练极不稳定(需要大量调参)；显存巨大 | 大预算/大规模的对齐项目、需要多轮迭代优化的场景 | 未使用(资源+时间限制) | "PPO 是 RLHF 的经典方法——理论上效果上限比 DPO 高。但它需要同时维护 policy、reference、reward、value 四个模型，训练极不稳定。我们的资源和项目时期不支持 PPO 级别的调参成本。但我理解当数据规模和算力更充足时，PPO 是更好的选择" |
| **GRPO** (Group Relative Policy Optimization) | RL | 用 group 内 relative reward 替代 value model，去掉 critic | 同 PPO 但不需要 value model | 否 | **是** | **是** | **是** | 省掉 value model(减去 1/4 模型)；训练更稳定；DeepSeek-R1 的核心 RL 方法 | 仍需 reward model；group 内采样增加推理成本；reward 归一化假设需要谨慎设计 | 推理能力激发、预算中等场景 | 未使用(项目阶段太早) | "GRPO 是 DeepSeek-R1 成功的关键——去掉 value model 降低了工程复杂度，group relative reward 提供了有效的 baseline。但它仍然需要 reward model 和大量 on-policy 采样，在我们的 10K 数据规模下不经济" |
| **RLOO** (REINFORCE Leave-One-Out) | RL | 用 leave-one-out baseline 替代 value model | 每个 prompt 采样 K 个 response | 否 | **是** | 可选 | **是** | 不需 value model；baseline 计算简单(其他 K-1 个的平均 reward)；方差比普通 REINFORCE 小 | 仍需 reward model；baseline 质量依赖于 K(组内样本数)；K 小时方差大 | 中等规模的对齐、需要 on-policy RL 但不想维护 value model | 未使用 | "RLOO 比 PPO 简洁但比 GRPO 的 baseline 设计更直观(直接取其他样本均值的相反方向)。在我们的规模下，on-policy RL 的整体开销还是超过 DPO" |
| **REINFORCE++** | RL | 在 REINFORCE 基础上加入 PPO 的关键技术(clipping、KL 惩罚等) | 同 PPO | 否 | **是** | **是** | **是** | 比 PPO 更简洁的实现；但仍保留了 PPO 的核心优势 | 需要 reward model 和 ref model；相对较新，社区实践经验少 | 需要 on-policy RL 但想要更简洁实现 | 未使用 | "REINFORCE++ 是 PPO 的简化版——保留了 clipping 和 KL，但代码更简洁。作为 RL 方法仍然需要在数据规模和工程上有更多投入" |
| **DAPO** (Decoupled Alignment from Preference Optimization) | RL 改进 | 解耦 alignment 中"正确性"和"风格"两个维度，分别优化 | 需要 reward model 对多维度分别打分 | 否 | **是**(多维度) | 可选 | **是** | 解决 DPO 中 preference trade-off 难题(安全 vs 有用)；更细粒度的偏好控制 | 需要多维度 reward model(或分解)；训练和调试更复杂 | 需要精细控制多维度偏好的场景(如安全+有用+风格) | 未使用 | "DAPO 解决了一个深刻的 DPO 问题：DPO 的偏好是一维的，但实际对齐需求是多维的(安全 vs 有用 vs 风格)。我们在这个问题上做了 implicit 处理(用 Safety-RAG 补偿安全维度)，但 DAPO 提供了一个更 principled 的解法" |
| **RLVR** (RL with Verifiable Rewards) | RL | 在可验证任务上使用规则 reward(答案对错、代码通过率)而不是训练 RM | 可验证的 task + rule-based reward | 否 | **否**(用规则) | 可选 | 可选(但通常 on-policy) | 不需要 reward model(消除 reward hacking 的一个主因)；reward 信号绝对准确；DeepSeek-R1 使用 | 只适用于可验证任务(数学/代码/逻辑)；不适用于开放域对话 | 数学推理、代码生成、逻辑推理 | 未使用(医疗开放域) | "RLVR 在数学和代码上非常成功——原因是这些领域的 reward 是可验证的。但医学对话大多是开放域——没有唯一的正确答案。如果能设计出部分可验证的医疗 reward(如药物配伍禁忌)，可以作为 hybrid reward 的一部分" |

## 五、Reward 与验证模型

| 方法 | 类别 | 核心思想 | 数据格式 | 需Teacher | 需Reward Model | 需Ref Model | On-Policy | 优点 | 缺点 | 适合场景 | 医学项目使用 | 面试保守说法 |
|------|------|------|------|:---:|:---:|:---:|:---:|------|------|------|:---:|------|
| **Reward Model** (奖励模型) | 评分模型 | 在偏好 pair 上用 BT 模型训练一个打分模型 | (prompt, chosen, rejected) | 否 | 自训练 | 否 | 否 | 为 RL 提供 reward 信号；可复用(一次训练多次使用)；打分可解释 | 易 reward hacking(over-optimization)；泛化差(训练分布外打分不可靠)；训练成本高 | PPO/GRPO 类 on-policy RL 方法的必需品 | 隐式使用(DPO 隐式 RM) | "DPO 隐式利用了 reward model——它将 reward 表示为 policy 和 ref 的 log ratio，不需要显式训练。但如果我们后续要做 iterative DPO 或 GRPO，就需要显式训练 RM" |
| **PRM** (Process Reward Model) | 评分模型 | 对推理过程的每一步进行打分，而非仅对最终结果打分 | step-wise annotations for reasoning | 否 | 自训练 | 否 | 否 | 提供过程级监督；可用于纠正中间推理错误；对长链推理有帮助 | 标注成本极高(需要每步标注)；训练复杂；目前仅数学推理场景效果显著 | 长链推理(数学证明、代码)的精细监督 | 未使用(医学回答非长链推理) | "PRM 在数学推理中很有价值——因为它需要在 multi-step reasoning 的每一步提供信号。但医学问答通常是知识调配型的(2-3 步)，不需要 process-level reward" |
| **ORM** (Outcome Reward Model) | 评分模型 | 只对最终输出打分——即标准 RM | 同 Reward Model | 否 | 自训练 | 否 | 否 | 标注成本低(只需偏好标签)；是 RLHF 的标准组件 | 只告诉"对/错"不告诉"哪里错/为什么"；稀疏信号 | 通用 RLHF | 同 Reward Model | "ORM 就是我们通常说的 reward model——只给最终结果打分。PRM 给中间步骤打分。前者够用于大多数对齐场景，后者在长链推理中更有效" |
| **Verifier** | 验证模型 | 不打分而是做事实/安全验证——判断输出是否与知识一致 | (query, response, knowledge) → label(consistent/inconsistent) | 否 | 否 | 否 | 否 | 直接定位事实错误；与 RAG 天然互补；不需要偏好数据 | 需要知识库支持；验证范围受知识库覆盖度限制；误判风险 | RAG 系统、安全敏感的垂直领域 | **使用**(Safety-RAG Verifier, Qwen3-8B 微调) | "我们的 verifier 不同于 reward model——它不做偏好打分，而是做事实一致性判断(NLI 任务)。这是 Safety-RAG 的核心组件，用于检测模型是否编造了检索知识中不存在的信息" |

## 六、安全增强与检索增强

| 方法 | 类别 | 核心思想 | 数据格式 | 需Teacher | 需Reward Model | 需Ref Model | On-Policy | 优点 | 缺点 | 适合场景 | 医学项目使用 | 面试保守说法 |
|------|------|------|------|:---:|:---:|:---:|:---:|------|------|------|:---:|------|
| **RAG-enhanced SFT** | 训练+检索 | 在 SFT 训练数据中加入检索到的相关知识作为 context | (prompt + retrieved_context, response) | 可选 | 否 | 否 | 否 | 训练时就教会模型利用检索知识；比推理时才加 RAG 更 coherent | 训练数据构造复杂；可能与推理时的检索结果分布不一致 | 想在训练阶段就融入检索能力的场景 | 未使用(推理阶段加) | "我们没有在 SFT 阶段做 RAG 增强——因为这样模型会过度依赖训练时的检索结果，而推理时检索到的知识可能不同。我们选择在推理阶段动态做检索，保持灵活性" |
| **RAG as Safety Layer** | 推理安全 | 在推理时检索外部知识 + 验证模型输出与知识的一致性 | query → retrieval → verification → (correction if needed) | 否 | 否 | 否 | 否 | 不需要重新训练模型；外部知识可随时更新；提供可审计的安全 trace | 增加推理延迟(检索+验证)；依赖知识库质量；对无法检索的问题无效 | 医疗/法律/金融等安全敏感领域 | **使用**(Safety-RAG) | "这是 Safety-RAG 的核心设计——RAG 不仅用于增强回答质量，更作为安全验证层。检索知识 = ground truth anchor，verifier 确保生成内容不偏离" |

## 七、面试回答速查：为什么不用 XX 方法？

| 被问方法 | 回答要点 |
|------|------|
| **为什么不用 PPO/GRPO?** | DPO 在我们的约束(10K 数据, RTX 5090 (32GB), 有限时间)下是最优选择。PPO 需要 4 个模型+reward model training+大量 on-policy 调参，投入产出不成比例。但我理解其优势，如果规模扩大会考虑 **iterative DPO → GRPO** 的渐进升级路径 |
| **为什么不用 OPD?** | OPD 的 on-policy sampling 每轮需要重新生成和标注数据——成本是 DPO 的 3-5x。我们 DPO 1 epoch 约 4 小时，OPD 做 3 轮需要 60+ 小时。在项目时间约束下选择了性价比更高的方案 |
| **为什么不用 ORPO/SimPO?** | 我们选择 DPO 是因为它经过了最充分的社区验证(TRL 库有直接支持)，工程风险最低。ORPO/SimPO 的"省 ref model"在我们的硬件上不是瓶颈——ref model 是 frozen 的，只占 4GB(4bit)显存。如果未来显存更紧张，会考虑 |
| **为什么不用 RLVR?** | RLVR 的光芒在可验证 reward 领域(数学/代码)——而医学对话的 reward 很难用规则验证(不存在唯一正确答案)。但可以设计 hybrid reward：部分维度(药物配伍禁忌)可规则验证 + 其他维度用 RM |
| **为什么不用全量微调?** | 全量微调 8B 模型需要 ~192GB 显存，RTX 5090 (32GB) 只有 32GB。QLoRA 降到了 12GB。同时 8B 规模上 QLoRA vs 全量的差距只有 1-2%，性价比极高。如果资源足够我也会选全量 |
| **为什么不用纯 RAG?** | 纯 RAG(尤其是 naive RAG)没有验证层——它盲目信任检索到的内容。而我们发现检索到的知识也可能错/不完整/不相关。Safety-RAG 加入 verification layer 解决了这个盲点。同时 RAG 不改变模型的行为模式(格式/语气/安全意识)，这些需要 SFT+DPO |
| **为什么不用 Prompt Engineering 替代 Safety-RAG?** | Prompt 是软约束——模型可以不遵守(尤其在长对话中注意力衰减)。Safety-RAG 的验证是外部硬约束——无论模型怎么想，只要输出与检索知识不一致就会被检测和修正。两者互补而非互斥 |

## 八、方法选择决策树

```
你要做后训练对齐 →
│
├─ 有海量领域文本(>10B tokens)?
│  └─ YES → CPT(继续预训练) 注入领域知识
│
├─ 有高质量 SFT 数据?
│  └─ YES → SFT/IFT 建立基础对话能力
│     │
│     ├─ 数据从哪里来?
│     │  ├─ Teacher 模型生成 → Teacher Distillation + 人工筛选
│     │  └─ 人工撰写 → 人工确保质量(数据量通常少)
│     │
│     ├─ 显存够吗?
│     │  ├─ >200GB → 全量微调
│     │  ├─ 40-200GB → LoRA (r=8-64)
│     │  └─ <40GB → QLoRA (4bit NF4 + 双重量化)
│     │
│     └─ 需要偏好对齐吗?
│        │
│        ├─ 有少量偏好数据(1K-50K), 资源有限?
│        │  └─ → DPO(标准, β=0.05-0.5)
│        │     ├─ 有过拟合担忧? → IPO / 降低 β / 减少 epoch
│        │     └─ 想省 ref model? → ORPO / SimPO
│        │
│        ├─ 有中等偏好数据(50K-500K), 资源充裕?
│        │  └─ → Iterative DPO / OPD (on-policy)
│        │
│        ├─ 有大量数据(>500K), 大预算, 追求极致效果?
│        │  └─ → PPO / GRPO / RLOO (on-policy RL)
│        │     ├─ 可验证 reward? → RLVR
│        │     └─ 需多维度控制? → DAPO
│        │
│        └─ 安全敏感领域(医疗/法律/金融)?
│           └─ → 在 DPO/PPO 基础上 + Safety-RAG / Constitutional AI
```

## 背诵版总结

1. 共覆盖25种后训练相关方法，按6大类组织：基础训练类/蒸馏类/偏好对齐类/RL类/奖励模型类/RAG结合类
2. **我的项目使用的**：SFT + Teacher Distillation + DPO + RAG as safety layer（4种，必须能详细讲）
3. **面试必须了解的**：PPO(RLHF基础)、GRPO(当前最火)、RLVR(reasoning后训练)、OPD(on-policy新方向)
4. **只需知道存在的**：IPO/KTO/ORPO/SimPO/CPO/RLOO/REINFORCE++/DAPO/PRM/ORM
5. **核心区分**：offline(DPO, SFT)用静态数据 vs online(PPO, GRPO, OPD)需要实时生成数据
6. **面试被问到未实现的方法**："了解原理和适用场景，项目中未实现，后续可扩展" + 简单说1-2句原理
