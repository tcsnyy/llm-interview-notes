## 二、核心知识点 Q&A

### Q: 在线推理和离线推理有什么本质区别？⭐⭐⭐⭐

DPO训练阶段的rejected生成属于**离线推理**（offline/batch inference）：不需要考虑延迟，可以用大batch_size、高吞吐优先，甚至可以跑一晚上。部署后的用户问答是**在线推理**（online inference）：对延迟敏感，TTFT要求在毫秒级，需要做并发控制、流式输出。

离线推理的核心指标是**吞吐量**（tokens/s），在线推理的核心指标是**TTFT**（首token延迟）和**TPOT**（每token延迟）。离线可以开大batch放大吞吐，在线必须控制并发防止p99延迟爆炸。

**追问**："为什么rejected生成不直接在DPO训练时做？" DPO训练过程中每步需要chosen和rejected是固定pair，两者必须来自同一prompt。rejected通常在训练前离线生成好：用SFT模型在temperature=0.7条件下采样得到回答，和teacher的chosen答案组成pair。如果在训练时实时生成rejected，每步都要推理一次，速度太慢。

**项目结合**：我们的DPO rejected是用SFT模型在t=0.7下离线采样后存储为JSON文件，训练时直接加载。rejected离线生成为已实现；在线推理系统为部分实现（vLLM部署完成但缺完整在线链路）。

**易错点**：有人以为"推理就是推理"，不分在线/离线。面试一定要主动区分：离线重吞吐、在线重延迟。

### Q: RESTful API / OpenAI-compatible API / gRPC / WebSocket 有什么区别和适用场景？⭐⭐⭐⭐

| 协议 | 特点 | 适用场景 | 不适合 |
|------|------|---------|--------|
| RESTful API | HTTP+JSON，无状态，易调试 | 标准CRUD、管理接口 | 高频双向通信 |
| OpenAI-compatible | RESTful子集，兼容 `/v1/chat/completions` | 模型推理，对接现有生态 | 非LLM场景 |
| gRPC | Protobuf序列化，双向流，高性能 | 微服务内部通信 | 外部API（兼容性差） |
| WebSocket | 全双工长连接，服务端主动推送 | 实时对话、长连接场景 | 无状态的一次性请求 |

医学问答项目推荐：对外提供**OpenAI-compatible API**（用户对接成本最低，生态工具链完善），内部服务间用**gRPC**（低延迟，强类型）。流式输出用**SSE**（Server-Sent Events）而非WebSocket——SSE更简单，单向推送足够。

**追问**："为什么不用gRPC直接对外？" gRPC的Protobuf二进制序列化速度快，但对外部API有两个致命问题：调试困难（curl/postman不能直接调）和生态兼容性（大部分LLM工具链基于OpenAI兼容REST接口）。gRPC更适合内部微服务通信。

**项目状态**：vLLM的OpenAI-compatible API已实现；gRPC和WebSocket未实现。

### Q: 流式输出和非流式输出怎么实现？⭐⭐⭐⭐

非流式输出：客户端发请求，服务端生成完整个response后一次性返回。流式输出：用**SSE（Server-Sent Events）**协议，每次生成一个token就推送给前端，前端实时渲染。技术栈：FastAPI的`StreamingResponse` + `asyncio`异步生成器 + vLLM的`stream=True`参数。

异步接口的核心：推理请求处理中不阻塞主线程。FastAPI用`async def` + `await`实现协程并发。

**追问**："流式输出怎么保证最后一帧一定送到？中间断了怎么办？" SSE协议用`data: [DONE]`作为结束信号。中间断连：客户端维护重连机制，但LLM生成一般不需要续传——断连后重新请求即可。关键是在`finally`块里确保释放资源。

**项目状态**：流式输出已实现。断连重试机制未完整实现。

**易错点**：有人用WebSocket做流式推送——WebSocket是全双工，但LLM流式输出是单向的，SSE更轻量。

### Q: 如果线上出了一个bad case，你怎么通过日志排查？⭐⭐⭐⭐

每条请求至少记录以下字段，确保任何bad case都能根据request_id全链路追溯。核心日志结构包含：timestamp、request_id、user_id_hash、session_id、model_version/lora_version/kb_version/prompt_version、request/response摘要、latency_breakdown分段计时、rag_details（检索文档ID和分数）、safety_flags（安全检测结果）、error字段、client信息、GPU状态。

**追问**："这么多字段，日志量不会爆炸吗？" 分级采样策略：全量记录ERROR级别；latency_breakdown按10%采样；响应内容不存日志（隐私风险），只存finish_reason和token数；大流量的rag_details异步写入不阻塞主请求路径；用Elasticsearch ILM 30天后自动归档或删除。

**项目状态**：基础logging已实现。完整的结构化日志+采样+ILM未实现。

**易错点**：不要把完整请求内容和响应内容写入日志——这是隐私合规红线。messages_preview只存前100个字符。

### Q: 推理服务和RAG服务应该放在一起还是分开？⭐⭐⭐⭐

核心原则：**按瓶颈拆分，不按教科书拆分**。

| 模块 | 是否独立 | 原因 |
|------|---------|------|
| vLLM推理服务 | 独立 | GPU密集型，独占显存，必须独立 |
| 检索服务 | 独立 | CPU密集型，可用不同机型 |
| Embedding服务 | 独立（可选） | GPU需求但与推理不同 |
| Rerank服务 | 独立（可选） | 小模型，可和检索服务合并 |
| API网关 | 独立 | 鉴权/限流/路由/聚合 |

推荐的最小生产架构：推理服务（vLLM，独占GPU）+ 检索服务（向量检索+rerank，可CPU）+ API网关（FastAPI，聚合请求/日志/监控）。分开有3个好处：vLLM合并后Python GIL可能影响RAG检索并发性能；分开后可独立扩缩；故障隔离——检索挂了不影响纯文本对话（降级到无RAG模式）。

**项目状态**：当前所有模块运行在同一台RTX 5090上，未做服务拆分。

**易错点**：不要一上来就说"必须拆微服务"——微服务的通信开销和运维复杂度在小规模下可能得不偿失。3-5个服务是合理的最小拆分。

### Q: Docker / Docker Compose / K8s 的概念和适用场景？⭐⭐⭐

Docker：容器化工具，把应用和依赖打包成镜像，确保环境一致性。Docker Compose：单机多容器编排，一个YAML文件定义所有容器，一行命令全启动。Kubernetes：多机容器编排平台，管理多节点调度、自动扩缩容、滚动更新、服务发现。

**追问**："你的医学项目适合用K8s吗？" 当前不适合。RTX 5090单机部署，K8s的调度和网络开销反而拖慢推理。K8s的适用场景是：多节点GPU集群、需要自动扩缩容、高可用要求。当前Docker Compose是最适合的——简单、够用、运维成本低。

**项目状态**：项目当前为裸机Python运行。可快速迁移到Docker Compose。vLLM本身有官方Docker镜像。

**易错点**：面试官问K8s不是想听你背诵概念，而是想知道你能否判断"什么时候该用、什么时候不该用"。

## 三、代码实现（核心伪代码）

### FastAPI 服务结构

```python
# medical_api_server.py 核心结构
import asyncio, time, uuid
from fastapi import FastAPI, HTTPException, Request
from fastapi.responses import StreamingResponse, JSONResponse

app = FastAPI(title="Medical LLM API")

# 中间件：请求ID + 日志
@app.middleware("http")
async def add_request_id(request: Request, call_next):
    request_id = str(uuid.uuid4())[:8]
    request.state.request_id = request_id
    request.state.start_time = time.time()
    response = await call_next(request)
    elapsed = (time.time() - request.state.start_time) * 1000
    response.headers["X-Request-ID"] = request_id
    return response

# /health: 检查vLLM、RAG、向量库状态
# /chat: 主对话接口（隐私脱敏→风险识别→路由→RAG检索→vLLM推理→安全审查→流式返回）
# /rag_chat: 强制走RAG的对话接口
# /retrieve: 独立的检索接口（调试/预览用）
```

### 错误处理策略

- **全局异常处理**：HTTPException和通用Exception分别返回结构化错误
- **服务降级**：RAG检索失败→返回空上下文不阻断对话；vLLM推理失败→返回预设兜底回复
- **超时控制**：推理加30s超时保护，超时返回504

### Q: 用1分钟介绍项目的工程落地情况？⭐⭐⭐⭐⭐

我们这个医学LLM项目当前完成了从数据生成→SFT→DPO→Safety-RAG→vLLM部署的核心流程。部署方面，用vLLM在RTX 5090上运行，吞吐877 tok/s、TTFT 42ms。如果要真正服务化上线，需要补齐四个关键能力：第一是API网关做鉴权限流和参数校验，第二是结构化日志做全链路追踪，第三是检索缓存降低RAG延迟，第四是监控告警系统。架构上推荐Docker Compose管理3-4个容器（vLLM推理、RAG检索、向量库、Redis），当前不需要K8s。

### Q: 用3分钟介绍？⭐⭐⭐⭐⭐

（在1分钟基础上扩展三个维度）第一是训练侧的工程化：数据构造有三层过滤，SFT用QLoRA训练完保存adapter，DPO的rejected离线批量生成。第二是部署侧的考量：vLLM暴露OpenAI-compatible接口，FastAPI加一层网关，RAG和推理应拆成独立服务。日志每条请求要有request_id贯穿所有服务，记录latency_breakdown。版本管理覆盖模型/tokenizer/chat template/prompt/RAG知识库/Judge prompt。第三是当前定位：项目已完成后训练到部署的全链路技术可行性验证，但距离生产级还差网关、日志、监控、缓存、灰度发布等P0组件。

## 高频问题速记

| 问题 | 一句话核心 |
|------|-----------|
| 在线vs离线推理 | 离线重吞吐（batch大不在意延迟）；在线重TTFT和TPOT（要流式、要毫秒级） |
| REST vs gRPC vs WebSocket | 对外用OpenAI-compatible REST，内部微服务间用gRPC，流式用SSE不用WebSocket |
| 流式怎么实现 | FastAPI StreamingResponse + SSE协议 + vLLM stream=True |
| 日志怎么设计 | request_id串联全链路，latency_breakdown分段计时，不存完整对话内容（隐私） |
| 单体vs微服务 | 按瓶颈拆分：vLLM独立(GPU)、检索独立(CPU)、API网关聚合，3-4个服务足够 |
| Docker vs K8s | Docker Compose编排单机多容器，K8s管多机集群，单机项目不需要K8s |
| 医学项目部署架构 | Nginx→FastAPI网关→vLLM(GPU)+RAG(CPU)+ChromaDB+Redis，Docker Compose编排 |
| 版本管理 | 模型/tokenizer/chat template/prompt/RAG知识库/Judge prompt全部版本化 |
| 模型回滚 | 预构建镜像→改tag→重启容器，30秒完成；model lineage记录全血缘 |
| 生产差了啥 | P0: 网关/日志/监控/缓存；P1: 灰度/隐私脱敏/失败回流；P2: K8s/多副本 |
| 限流熔断降级 | 限流(令牌桶)→熔断(连续失败N次断)→降级(RAG挂了用纯模型回答) |
