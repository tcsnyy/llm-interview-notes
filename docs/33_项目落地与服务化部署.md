### 知识点1：在线推理 vs 离线推理

**面试官怎么问**："你做DPO的时候推理和部署后的推理，有什么本质区别？"

**考察什么**：是否理解离线批量推理和在线实时推理的不同约束条件。

**标准回答**：

> DPO训练阶段的rejected生成属于**离线推理**（offline/batch inference）：不需要考虑延迟，可以用大batch_size、高吞吐优先，甚至可以跑一晚上。部署后的用户问答是**在线推理**（online inference）：对延迟敏感，TTFT要求在毫秒级，需要做并发控制、流式输出。
>
> 离线推理的核心指标是**吞吐量**（tokens/s），在线推理的核心指标是**TTFT**（首token延迟）和**TPOT**（每token延迟）。离线可以开大batch放大吞吐，在线必须控制并发防止p99延迟爆炸。

**追问**："为什么rejected生成不直接在DPO训练时做？"

**追问回答**：

> DPO训练过程中每步需要chosen和rejected是固定pair，两者必须来自同一prompt。rejected通常在训练前离线生成好：用SFT模型在temperature=0.7条件下采样得到回答，和teacher的chosen答案组成pair。如果在训练时实时生成rejected，每步都要推理一次，速度会慢到不可接受。

**项目结合**：我们的DPO rejected是用SFT模型在t=0.7下离线采样后存储为JSON文件，训练时直接加载，不走实时推理。

**是否已实现**：rejected离线生成为已实现；在线推理系统为部分实现（vLLM部署完成但缺完整在线链路）。

**易错点**：有人以为"推理就是推理"，不分在线/离线。面试一定要主动区分：离线重吞吐、在线重延迟。

### 知识点2：RESTful API / OpenAI-compatible API / gRPC / WebSocket 区别

**面试官怎么问**："你的模型服务提供什么类型的API？为什么选这种？"

**考察什么**：是否理解不同API协议的设计哲学和适用场景。

**标准回答**：

| 协议 | 特点 | 适用场景 | 不适合 |
|------|------|---------|--------|
| RESTful API | HTTP+JSON，无状态，易调试 | 标准CRUD、管理接口 | 高频双向通信 |
| OpenAI-compatible | RESTful子集，兼容 `/v1/chat/completions` | 模型推理，对接现有生态 | 非LLM场景 |
| gRPC | Protobuf序列化，双向流，高性能 | 微服务内部通信 | 外部API（兼容性差） |
| WebSocket | 全双工长连接，服务端主动推送 | 实时对话、长连接场景 | 无状态的一次性请求 |

> 医学问答项目推荐：对外提供**OpenAI-compatible API**（用户对接成本最低，生态工具链完善），内部服务间用**gRPC**（低延迟，强类型）。流式输出用**SSE**（Server-Sent Events）而非WebSocket——SSE更简单，单向推送足够。

**追问**："为什么不用gRPC直接对外？gRPC不是更快吗？"

**追问回答**：

> gRPC的Protobuf二进制序列化速度快没错，但对外部API有两个致命问题：第一，调试困难——curl/postman不能直接调；第二，生态兼容性——大部分LLM工具链（LangChain、LlamaIndex等）都基于OpenAI兼容的REST接口。gRPC更适合作为内部微服务之间的通信协议。

**项目结合**：我们的vLLM默认暴露OpenAI-compatible接口（`/v1/chat/completions`），可直接用openai python包调用。

**是否已实现**：vLLM的OpenAI-compatible API已实现。gRPC和WebSocket未实现。

**易错点**：不要把gRPC当作"万能快方案"——它只在微服务内部通信时有优势，对外API用REST更实际。

### 知识点3：同步/异步接口、流式/非流式输出

**面试官怎么问**："流式输出和非流式输出，你在后端怎么实现的？"

**考察什么**：是否理解异步编程模型和SSE协议。

**标准回答**：

> 非流式输出：客户端发请求，服务端生成完整个response后一次性返回。简单但用户体验差——用户要干等。
>
> 流式输出：用**SSE（Server-Sent Events）**协议，每次生成一个token就推送给前端，前端实时渲染。技术栈：FastAPI的`StreamingResponse` + `asyncio`异步生成器 + vLLM的`stream=True`参数。
>
> 异步接口的核心：推理请求处理中不阻塞主线程。FastAPI用`async def` + `await`实现协程并发，一个请求在等vLLM生成时，主线程可以处理其他请求的健康检查、日志记录等。

**追问**："流式输出怎么保证最后一帧一定送到？中间断了怎么办？"

**追问回答**：

> SSE协议用`data: [DONE]`作为结束信号。中间断连：客户端维护重连机制，用`last_event_id`告诉服务器从哪里续传。但LLM生成一般不需要续传——断连后重新请求即可。关键是在`finally`块里确保释放资源（如vLLM的generation slot）。

**项目结合**：我们的`/chat`接口使用FastAPI的StreamingResponse实现逐token推送，vLLM backend设为`stream=True`。

**是否已实现**：流式输出已实现。断连重试机制未完整实现。

**易错点**：有人用WebSocket做流式推送——WebSocket是全双工，但LLM流式输出是单向的（服务端→客户端），SSE更轻量、实现更简单。

### 知识点6：单体服务 vs 微服务

**面试官怎么问**："你的推理服务和RAG服务是放在一起还是分开的？"

**考察什么**：是否理解服务拆分的工程原则。

**标准回答**：

> 我们当前的方案是"单体服务的微服务化演进"。核心原则：**按瓶颈拆分，不按教科书拆分**。

**服务拆分分析**：

| 模块 | 是否独立 | 原因 |
|------|---------|------|
| vLLM推理服务 | 独立 | GPU密集型，独占显存，必须独立 |
| 检索服务 | 独立 | CPU密集型，可用不同机型 |
| Embedding服务 | 独立（可选） | GPU需求但与推理不同，可共享GPU |
| Rerank服务 | 独立（可选） | 小模型，可和检索服务合并 |
| Judge服务 | 独立 | 离线评测用，在线可异步 |
| API网关 | 独立 | 鉴权/限流/路由/聚合 |

> 推荐的最小生产架构：
> - **推理服务**（vLLM）：独占GPU
> - **检索服务**（向量检索+rerank）：可CPU或共享GPU
> - **API网关**（FastAPI）：聚合请求、日志、监控

**追问**："三个服务怎么通信？"

**追问回答**：

> 内部服务间推荐用gRPC（低延迟+Protobuf强类型），而且服务发现用Consul或简单的DNS。但为简单起见，初期也可以用HTTP REST（每个服务一个内网端口），用Docker Compose的service name做服务发现。API网关收到请求后，并行调用检索服务和推理服务（检索完成→构造prompt→送推理），用asyncio并发以降低总延迟。

**项目结合**：当前所有模块运行在同一台RTX 5090上，未做服务拆分。具备拆分成微服务的技术基础。

**是否已实现**：未拆分，当前为单体部署。

**易错点**：不要一上来就说"必须拆微服务"——微服务的通信开销和运维复杂度在小规模下可能得不偿失。3-5个服务是合理的最小拆分。

### 知识点7：Docker / Docker Compose / Kubernetes 概念

**面试官怎么问**："你了解Docker和K8s吗？你的项目能用Docker部署吗？"

**考察什么**：容器化的基本概念和实际应用能力。

**标准回答**：

> Docker：容器化工具，把应用和依赖打包成镜像，确保环境一致性（训练环境=部署环境）。
>
> Docker Compose：单机多容器编排。一个YAML文件定义推理容器+检索容器+网关容器，一行命令`docker compose up`全启动。
>
> Kubernetes：多机容器编排平台。管理多节点上的容器调度、自动扩缩容、滚动更新、服务发现。对单机项目过量了。

**追问**："你的医学项目适合用K8s吗？"

**追问回答**：

> 当前不适合。RTX 5090单机部署，K8s的调度和网络开销反而拖慢推理。K8s的适用场景是：多节点GPU集群、需要自动扩缩容、高可用要求（一个节点挂了自动切）。如果未来扩展到多台GPU服务器做多副本推理，才考虑K8s。当前Docker Compose是最适合的——简单、够用、运维成本低。

**项目结合**：项目当前为裸机Python运行。可快速迁移到Docker Compose。

**是否已实现**：未容器化。vLLM本身有官方Docker镜像。

**易错点**：面试官问K8s不是想听你背诵概念，而是想知道你能否判断"什么时候该用、什么时候不该用"。一定加一句适用性判断。

### 知识点8：医学项目适合的轻量部署架构

**面试官怎么问**："如果让你把这个医学项目真正部署上线，你会怎么设计架构？"

**考察什么**：工程落地判断力——在约束条件下做合理的架构决策。

**标准回答**（医学项目轻量部署架构）：

```
                        ┌──────────────┐
                        │   用户请求    │
                        └──────┬───────┘
                               ▼
                        ┌──────────────┐
                        │   Nginx      │  反向代理 + SSL + 限流
                        │   :443       │
                        └──────┬───────┘
                               ▼
                    ┌──────────────────────┐
                    │   API Gateway        │  FastAPI :8000
                    │   鉴权/路由/聚合/日志  │
                    └──┬───────────────┬───┘
                       │               │
              ┌────────▼──────┐  ┌─────▼──────────┐
              │  vLLM Service │  │  RAG Service    │
              │  :8001 (GPU)  │  │  :8002 (CPU)    │
              │  RTX 5090独占  │  │  检索+rerank    │
              └───────────────┘  └─────┬───────────┘
                                       │
                              ┌────────▼──────────┐
                              │  Vector DB        │
                              │  ChromaDB/Milvus  │
                              │  :19530           │
                              └───────────────────┘

监控层: Prometheus + Grafana (指标采集+大盘)
日志层: Loki / ELK (结构化日志)
缓存层: Redis (检索缓存+限流计数)
```

> 核心设计原则：单机3-4个容器（vLLM + RAG + 向量库 + Redis），Docker Compose编排。GPU独占给vLLM，其他服务用CPU。Nginx做前置反向代理和SSL termination。

**追问**："为什么不把vLLM和RAG合并成一个服务？"

**追问回答**：

> 可以合并，但分开有3个好处：第一，vLLM是GPU密集型，合并后Python GIL可能影响RAG检索的并发性能；第二，分开后可以独立扩缩（检索压力大时可以对RAG Service做多副本）；第三，故障隔离——检索挂了不影响纯文本对话（降级到无RAG模式）。

**项目结合**：我们已经有了vLLM部署和RAG模块，差距在于API网关封装和服务编排。

**是否已实现**：核心模块就绪，服务编排/网关/监控未实现。

**易错点**：不要过度设计——单机3-5个容器足够，不需要服务网格（Istio）、不需要消息队列（Kafka），更不需要多AZ部署。

### 知识点9：生产级部署还需要哪些组件

**面试官怎么问**："你觉得你的项目离生产上线还差什么？"

**考察什么**：考察对生产系统的全局认知，以及实事求是的自我评估能力。

**标准回答**：

> 我们已完成：后训练、评测、Safety-RAG、LoRA merge、vLLM部署/压测。距生产级系统还差以下组件：

| 缺失组件 | 重要性 | 说明 |
|---------|--------|------|
| API网关（FastAPI封装） | P0 | 鉴权、限流、参数校验、日志聚合 |
| 结构化日志+全链路追踪 | P0 | request_id贯穿所有服务，排查bad case |
| 检索缓存（Redis） | P0 | 高频医学问题命中率预计40%+，显著降延迟 |
| 监控告警（Prometheus+Grafana） | P0 | GPU利用率、p99延迟、错误率 |
| 失败样本收集管道 | P1 | 用户反馈→标注→回流SFT/DPO |
| 灰度发布机制 | P1 | 5%→20%→50%→100%分阶段放量 |
| 隐私脱敏服务 | P1 | 用户输入中的姓名、身份证号等脱敏 |
| 版本管理平台 | P1 | 模型/知识库/prompt的版本记录和回滚 |
| 压测平台 | P1 | 自动化压测、性能回归检测 |
| 高可用（多副本） | P2 | vLLM单点故障→切备用实例，需多GPU |
| 多节点部署 | P2 | 需K8s或至少多台GPU服务器 |
| A/B测试框架 | P2 | 新老模型对比，需一定流量规模 |

**追问**："为什么要分成P0/P1/P2？"

**追问回答**：

> P0是"不加上去不能上线"——没有鉴权/限流用户可能滥用，没有监控出问题不知道怎么排查。P1是"上线后第一周必须加"——灰度发布降低事故风险，隐私脱敏是合规底线。P2是"有更大流量才需要"——高可用和多节点在小流量（<100 QPS）下过度投资。

**项目结合**：坦诚说明当前项目的边界——是算法验证+技术可行性验证，不是完整生产系统。

**是否已实现**：P0组件均未完整实现。当前项目定位为"后训练技术验证+可演示原型"。

**易错点**：不要说"我们啥都做完了"——面试官如果是工程出身，一听就知道你在吹牛。诚实列出差距反而加分，因为这证明你了解生产系统的全貌。

### 知识点10：版本管理（模型/知识库/prompt）

**面试官怎么问**："你训了好几个版本的模型，怎么管理版本？万一新版本出问题怎么回滚？"

**考察什么**：MLOps基础素养——模型不是训练完就完了，要有完整的生命周期管理。

**标准回答**：

**需要版本管理的组件**：

| 组件 | 版本内容 | 版本号示例 |
|------|---------|-----------|
| 基座模型 | Qwen3-8B checkpoint | `qwen3-8b-base` |
| LoRA adapter | SFT/DPO的adapter权重 | `sft-lora-v3`, `dpo-lora-v2.1` |
| Merged模型 | merge后的完整权重 | `medical-v2.1` |
| Tokenizer | tokenizer.json + special tokens | `tokenizer-v2` |
| Chat template | Jinja2模板字符串 | `chat-template-v3` |
| RAG知识库 | 15本PDF / chunks版本 | `kb-v3.2` |
| System prompt | 系统提示词 | `sys-prompt-v4` |
| Judge prompt | LLM-as-Judge评测prompt | `judge-prompt-v2` |

**Model Lineage（模型血缘）记录**：

```
medical-v2.1:
  base_model: qwen3-8b-base
  sft_adapter: sft-lora-v3 (trained on teacher-mimo-11K)
  dpo_adapter: dpo-lora-v2.1 (trained on preference-pairs-10K, β=0.1)
  merge_date: 2026-01-12
  eval_score: overall=4.96, safety=4.82
  rag_version: kb-v3.2
  prompt_version: sys-prompt-v4
  deployment_status: active
```

**回滚流程**：

```
① 发现bad case或监控告警（如幻觉率突升）
② 确认问题模型版本（通过request日志中的model_version字段）
③ 召回当前模型流量（API网关改路由权重）
④ 切回上一个stable版本（如 medical-v2.0）
⑤ 在新的staging环境复现问题
⑥ 修复后发布 medical-v2.2（按灰度流程上线）
```

**追问**："如果模型出问题，回滚要多久？"

**追问回答**：

> 如果有镜像预构建（Docker镜像包含merged模型），回滚可以在30秒内完成——改Docker Compose的镜像tag然后重启容器。如果没有镜像，需要手动加载权重到vLLM，可能需要2-5分钟。所以生产环境一定要预构建模型镜像，不能现场下权重。

**项目结合**：当前我们使用git管理训练代码和配置，模型权重用日期+配置标记文件名（如`qwen3-8b-dpo-lora-20260112`）。但没有正式的版本管理平台。

**是否已实现**：手动版本管理已实现（文件名标记）。自动化的血缘追踪和回滚机制未实现。

**易错点**：模型版本不只是模型权重版本——tokenizer、chat template、prompt都要纳入版本管理。一个常见事故：换了新prompt但忘了记录，导致"模型变差"但无从排查。

```python
@app.middleware("http")
async def add_request_id(request: Request, call_next):
    request_id = str(uuid.uuid4())[:8]
    request.state.request_id = request_id
    request.state.start_time = time.time()

    response = await call_next(request)

    elapsed = (time.time() - request.state.start_time) * 1000
    logger.info("request_completed",
        request_id=request_id,
        path=request.url.path,
        method=request.method,
        status_code=response.status_code,
        latency_ms=round(elapsed, 1)
    )
    response.headers["X-Request-ID"] = request_id
```

```python
@app.post("/chat")
async def chat(request: ChatRequest, http_request: Request):
    request_id = http_request.state.request_id
    start_time = time.time()

    # 1. 参数校验 + 隐私脱敏
    if not request.messages:
        raise HTTPException(status_code=400, detail="messages不能为空")

    user_input = request.messages[-1].get("content", "")
    user_input_clean = safety.redact_pii(user_input)  # 脱敏

    # 2. 风险识别
    risk_level = safety.assess_risk(user_input_clean)
    logger.info("risk_assessment",
        request_id=request_id,
        risk_level=risk_level,
        user_id_hash=request.medical_profile.user_id_hash
            if request.medical_profile else "anonymous"
    )

    # 3. 路由决策：低风险走fast path，高风险走Safety-RAG path
    use_rag = (
        request.rag.enable_rag if request.rag else False
    ) or risk_level in ("high_risk", "critical")

    # 4. 构造最终prompt
    rag_context = ""
    rag_latency = 0
    if use_rag:
        rag_start = time.time()
        try:
            rag_result = await rag.retrieve(
                query=user_input_clean,
                top_k=request.rag.top_k if request.rag else 5,
                rerank=request.rag.rerank_enabled if request.rag else True
            )
            rag_context = rag.format_context(rag_result)
        except Exception as e:
            logger.error("rag_failed", request_id=request_id, error=str(e))
            rag_context = "[检索服务暂时不可用，以下回答基于模型自身知识]"
        rag_latency = (time.time() - rag_start) * 1000

    final_messages = _build_messages(request.messages, rag_context)

    # 5. vLLM推理（流式）
    if request.stream:
        return StreamingResponse(
            _stream_generate(request_id, final_messages, request, start_time,
                             use_rag, rag_latency, risk_level),
            media_type="text/event-stream"
        )
    else:
        # 非流式
        result = await _non_stream_generate(
            request_id, final_messages, request, start_time,
            use_rag, rag_latency, risk_level
        )
        return JSONResponse(content=result)


async def _stream_generate(
    request_id, messages, request, start_time, use_rag, rag_latency, risk_level
) -> AsyncGenerator[str, None]:
    """流式生成SSE"""
    full_response = ""
    vllm_start = time.time()
    first_token_sent = False
    ttft = 0

    try:
        async for token_text in vllm.generate_stream(
            model=request.model,
            messages=messages,
            temperature=request.temperature,
            max_tokens=request.max_tokens
        ):
            if not first_token_sent:
                ttft = (time.time() - vllm_start) * 1000
                first_token_sent = True

            full_response += token_text
            yield f"data: {json.dumps({'token': token_text})}\n\n"

        # 后处理：安全审查
        post_start = time.time()
        safety_result = safety.check_response(full_response, risk_level)

        # 如果安全审查不通过，追加警告信息
        if not safety_result.passed:
            warning = safety_result.warning_message
            full_response += f"\n\n【安全提醒】{warning}"
            yield f"data: {json.dumps({'token': warning})}\n\n"

        post_latency = (time.time() - post_start) * 1000

        # 发送结束标记（含metadata）
        total_latency = (time.time() - start_time) * 1000
        yield f"data: {json.dumps({'done': True, 'metadata': {
            'request_id': request_id,
            'safety_level': safety_result.level,
            'rag_used': use_rag,
            'latency_ms': round(total_latency, 1),
            'ttft_ms': round(ttft, 1)
        }})}\n\n"
        yield "data: [DONE]\n\n"

    except Exception as e:
        logger.error("stream_error", request_id=request_id, error=str(e))
        yield f"data: {json.dumps({'error': str(e)})}\n\n"
        yield "data: [DONE]\n\n"
    finally:
        # 异步写日志（不阻塞响应）
        asyncio.create_task(_log_request(
            request_id=request_id,
            messages=messages,
            response_preview=full_response[:200],
            use_rag=use_rag,
            rag_latency=rag_latency,
            ttft=ttft,
            total_latency=(time.time() - start_time) * 1000,
            risk_level=risk_level,
            error=None
        ))
```

```python
@app.post("/retrieve")
async def retrieve(request: Request, http_request: Request):
    """独立的检索接口——用于调试、前端预览或第三方集成"""
    body = await request.json()
    query = body.get("query", "")
    top_k = body.get("top_k", 5)
    rerank_enabled = body.get("rerank", True)

    if not query:
        raise HTTPException(status_code=400, detail="query不能为空")

    request_id = http_request.state.request_id
    start = time.time()

    try:
        # Hybrid检索
        dense_results = await rag.dense_search(query, top_k * 2)
        sparse_results = await rag.sparse_search(query, top_k)

        # 合并去重（RRF: Reciprocal Rank Fusion）
        merged = rag.merge_results(dense_results, sparse_results, top_k * 2)

        # Rerank精排
        if rerank_enabled:
            merged = await rag.rerank(query, merged, top_k)

        latency = (time.time() - start) * 1000

        return JSONResponse(content={
            "request_id": request_id,
            "query": query,
            "results": [
                {
                    "chunk_id": r.chunk_id,
                    "content": r.content[:500],  # 截断预览
                    "score": round(r.score, 4),
                    "source": r.source,
                    "page": r.page
                }
                for r in merged[:top_k]
            ],
            "total_candidates": len(dense_results) + len(sparse_results),
            "latency_ms": round(latency, 1)
        })

    except Exception as e:
        logger.error("retrieve_error", request_id=request_id, error=str(e))
        raise HTTPException(status_code=500, detail=f"检索失败: {str(e)}")
```

```python
    """服务降级策略"""

    @staticmethod
    async def safe_rag_retrieve(query: str, top_k: int, request_id: str):
        """RAG检索降级：检索失败→返回空上下文，不阻断对话"""
        try:
            return await rag.retrieve(query, top_k)
        except Exception as e:
            logger.error("rag_degraded", request_id=request_id, error=str(e))
            return {"chunks": [], "status": "degraded"}

    @staticmethod
    async def safe_vllm_generate(messages, request_id, fallback_msg=None):
        """vLLM降级：推理失败→返回预设的兜底回复"""
        try:
            return await vllm.generate(messages)
        except Exception as e:
            logger.error("vllm_degraded", request_id=request_id, error=str(e))
            return fallback_msg or "系统暂时繁忙，请稍后重试。如为紧急医疗情况，请立即就医。"


# ---------- 超时控制 ----------
async def generate_with_timeout(messages, timeout_seconds=30):
    """推理加超时保护"""
    try:
        return await asyncio.wait_for(
            vllm.generate(messages),
            timeout=timeout_seconds
        )
    except asyncio.TimeoutError:
        logger.error("vllm_timeout", timeout=timeout_seconds)
        raise HTTPException(
            status_code=504,
            detail="推理超时，请尝试缩短问题或稍后重试"
        )
```

## 四、面试总结材料

### 面试1分钟回答

> 我们这个医学LLM项目当前完成了从数据生成→SFT→DPO→Safety-RAG→vLLM部署的核心流程。部署方面，用vLLM在RTX 5090上运行，吞吐877 tok/s、TTFT 42ms。如果要真正服务化上线，需要补齐四个关键能力：第一是API网关做鉴权限流和参数校验，第二是结构化日志做全链路追踪，第三是检索缓存降低RAG延迟，第四是监控告警系统。架构上推荐Docker Compose管理3-4个容器（vLLM推理、RAG检索、向量库、Redis），当前不需要K8s。

---

### 面试3分钟回答

> 我们这个医学LLM项目的工程落地，我从三个维度来讲。
>
> 第一是训练侧的工程化：数据构造阶段我们有三层过滤（规则→模型打分→人工抽检），SFT用QLoRA训练完保存adapter，DPO的rejected是离线批量生成的——和线上推理不同，离线重吞吐、在线重延迟。LoRA merge后用vLLM部署，选vLLM是因为PagedAttention的KV Cache分页管理可以让24GB显存支持更多并发。
>
> 第二是部署侧的考量：当前vLLM暴露OpenAI-compatible接口，可直接用openai库调用。如果封装成正式API服务，需要FastAPI加一层网关——做鉴权、限流、参数校验、SSE流式输出。RAG检索和vLLM推理应拆成独立服务，因为检索是CPU密集型、推理是GPU密集型，分开可以独立扩缩和故障隔离。RAG的延迟优化包括embedding缓存、检索结果缓存、并行hybrid检索。日志方面每条请求要有request_id贯穿所有服务，记录latency_breakdown（预处理/检索/rerank/首token/生成/后处理各段耗时），这样才能定位性能瓶颈。版本管理不能只管模型权重——tokenizer、chat template、system prompt、RAG知识库、judge prompt都要有版本号，确保任何时刻知道"线上跑的是什么组合"。
>
> 第三是我们当前的定位：项目已完成后训练、评测、Safety-RAG、LoRA merge、vLLM部署和压测，证明了从算法到部署的全链路技术可行性。但距离生产级系统还差API网关、结构化日志、监控告警、缓存、灰度发布等P0组件。我对此有清晰认知——项目当前是"后训练技术验证+可演示原型"，具备向服务化系统扩展的坚实基础。

### 高频问题速记

| 问题 | 一句话核心 |
|------|-----------|
| 在线vs离线推理 | 离线重吞吐（batch大，不在意延迟）；在线重TTFT和TPOT（要流式、要毫秒级） |
| REST vs gRPC vs WebSocket | 对外用OpenAI-compatible REST，内部微服务间用gRPC，流式用SSE不用WebSocket |

| 日志怎么设计 | request_id串联全链路，latency_breakdown分段计时，不存完整对话内容（隐私） |
| 单体vs微服务 | 按瓶颈拆分：vLLM独立(GPU)、检索独立(CPU)、API网关聚合，3-4个服务足够 |
| Docker vs K8s | Docker Compose编排单机多容器，K8s管多机集群，单机项目不需要K8s |
