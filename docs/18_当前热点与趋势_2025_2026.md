## 1. Reasoning Model 后训练、Long-CoT、RLVR、GRPO

### Q: 讲讲你对 DeepSeek-R1 训练流程和 GRPO 的理解？⭐⭐⭐⭐⭐

Reasoning Model 后训练是指让模型在回答前产生"长链思维"（Long Chain-of-Thought），通过强化学习让模型学会"思考"。代表工作：DeepSeek-R1、Kimi-k1.5、Qwen3思考模式。

**核心技术**：
- **Long-CoT**：模型生成数千 token 的推理链，包含自我反思、假设检验、排除法等人类解题策略。
- **RLVR**（Reinforcement Learning with Verifiable Rewards）：对数学/代码等有标准答案的任务，用规则验证器判断最终答案是否正确，将二值信号作为 reward，不需要人工标注偏好数据。
- **GRPO**（Group Relative Policy Optimization）：DeepSeek 提出的简化版 PPO，对每个问题采样一个组（如16个）答案，用组内平均分归一化每个答案的 advantage，从而不需要单独训练 critic 模型，节省一半显存。

**为什么火**：DeepSeek-R1 证明了纯 RL 训练后的小模型在数学推理上超越同规模 SFT 基线 20+ 个百分点；scaling law 从预训练转移到后训练（推理时更多 token = 更好答案）；成本极低（RLVR 不需要人工标注，GRPO 不需要 critic 模型，8B 模型单机 8 卡就能做 reasoning 训练）。

**和 SFT/DPO/RLHF 的关系**：SFT 做冷启动（让模型有基本的 CoT 格式），DPO 做偏好对齐，但两者都不能让模型"学会思考"——Long-CoT 的涌现需要 RL 的试错机制。RLVR/GRPO 是 RLHF 的变体：把"人类偏好 reward model"换成"规则验证器"，把"PPO+critic"换成"GRPO 组内归一化"。可以在 SFT→DPO 之后再叠加 GRPO 做 reasoning 增强。

**DeepSeek-R1 流程**：R1-Zero 直接用 RLVR+GRPO 训练，模型自己涌现 Long-CoT；但可读性差，所以 R1 先做少量 SFT 冷启动再 RL，提升可读性同时保持推理能力。

**GRPO vs PPO**：PPO 需要四个模型（policy+reference+critic+reward），GRPO 只需两个（policy+reference）。GRPO 用组内相对排名代替 critic 的绝对价值估计，减少了训练不稳定性和显存开销。

**医学项目关系**：医学诊断天然适合 reasoning——病例→症状分析→鉴别诊断→初步诊断→确诊。可以在现有 Teacher-DPO 模型基础上，对诊断类数据用 GRPO 做 reasoning 增强。但医学诊断的"标准答案"不如数学唯一，设计验证规则会更复杂。我们项目当前聚焦 SFT+DPO+Safety-RAG 的安全闭环，GRPO 是下一步方向。（了解原理，项目未实现）

## 2. PPO 回归与简化 RL (REINFORCE++/RLOO/DAPO/Dr. GRPO)

### Q: PPO 在 LLM 训练中有什么问题？现在有哪些简化方案？⭐⭐⭐⭐

2025 年出现了一波"简化 RL"浪潮：

- **REINFORCE++**：在经典 REINFORCE 基础上加 PPO 的 clip 机制但不训练 critic，用蒙特卡洛估计的 return 减去 baseline 计算 advantage。
- **RLOO**（REINFORCE Leave-One-Out）：对每个 prompt 采样 k 个 response，用"去掉自己后其他 k-1 个的均值"做 baseline，无 critic。
- **DAPO**：字节提出的去偏 PPO，解决 dynamic sampling 下长度 bias 和 reward hacking 问题。
- **Dr. GRPO**：GRPO 的改进版，解决组内归一化导致的"全体低分但组内仍有高分"问题，引入全局 baseline。

**为什么火**：PPO 太复杂（需要训练 critic、处理 GAE、调大量超参），简化版效果不输 PPO 甚至更好，显存友好（无 critic 方案让小模型训练门槛大幅降低）。

**PPO 的问题**：需要四个模型→显存大；critic 训练不稳定→需要精细调参；value head 只训练最后几层→可能不准确。

**RLOO 核心**：对同一个问题生成 k 个回答，第 i 个回答的 baseline 是其他 k-1 个回答 reward 的均值。如果这个回答比别的回答好，advantage 为正，反之负。

**医学项目关系**：DPO 已经能满足大部分偏好对齐需求。如果后续需要在线采样和更强的探索能力，RLOO 和 GRPO 是比 PPO 更务实的选择——单机即可训练，不需要维护额外 critic 模型。（了解原理，项目未实现）

## 3. DPO 家族 (IPO/KTO/ORPO/SimPO/CPO)

### Q: DPO 有什么核心问题？有哪些改进版本？⭐⭐⭐⭐⭐

DPO（Direct Preference Optimization）将 RLHF 的两步流程简化为一步。2024-2025 年出现大量变体：

- **IPO**：解决 DPO 对偏好数据过拟合问题，引入正则化使模型不过度远离 reference。
- **KTO**：不需要 pairwise 偏好对，只需单条数据的"好/坏"标签，适用于用户反馈等单边标注场景。
- **ORPO**：将 SFT loss 和偏好优化 loss 合并，一个阶段同时做指令跟随和偏好对齐，省掉 SFT 单独阶段。
- **SimPO**：用 reward 的差值做优化目标，不需 reference 模型，用长度归一化解决 length bias。
- **CPO**：强调 chosen 和 rejected 的对比学习，在 embedding 空间拉开距离。

**DPO 的核心问题**：对离 reference 较远的样本容易过拟合；chosen/rejected 差距小时梯度信号弱；需要 reference 模型增加显存；对 chosen/rejected 质量敏感。

**为什么选 DPO 没选别的**：医疗场景有明确的 chosen（teacher 答案）和 rejected（SFT 模型采样），pairwise 偏好对能充分体现安全改进方向。KTO 需要单边标注，我们的数据更适合 pairwise。ORPO 理论上可以省 SFT 但我们发现两阶段分开调参更可控。

**医学项目关系**：医疗偏好对构造是核心竞争力。如果扩大数据规模到 10 万+ 对，IPO 的正则化可能有用。KTO 适合医疗用户反馈场景。（DPO 已实现，变体未用，了解原理）

## 4. OPD / On-Policy Distillation

### Q: Teacher distillation 和 OPD 有什么区别？⭐⭐⭐⭐

On-Policy Distillation (OPD) 是在训练过程中由 teacher 模型对 policy 模型当前生成的样本进行实时标注和指导的方法。和传统"离线蒸馏"（用预先生成的 teacher 数据做 SFT）不同，OPD 在训练循环中动态调用 teacher。

**主要变体**：
- **Offline OPD (标准版)**：边训练边用 teacher 对 policy 当前输出打分/修正
- **Lightning OPD**：减少 teacher 调用次数，用"teacher 只在 policy 不确定时介入"
- **Stable OPD**：引入滑动平均或课程学习解决 teacher 信号不稳定
- **Multi-teacher OPD**：多个 teacher 模型共同蒸馏到一个 policy

**Teacher Distillation vs OPD**：传统蒸馏用 teacher 预先生成一批数据然后固定训练（offline, off-policy）；OPD 在训练过程中动态调用 teacher（online, on-policy）。区别在于 policy 的更新是否影响 teacher 的输入分布。

**为什么火**：弥补离线蒸馏的分布偏移；被 DeepSeek-R1 等顶会工作使用（R1 蒸馏阶段本质上就是 OPD）；API 成本下降使 OPD 可行。

**医学项目关系**：我们项目的 Teacher-MiMo 线路本质是 offline distillation。下一步如果做 OPD：用不确定性采样，只在 policy 输出"不安全/不确定"的医疗建议时调用 MiMo 做 online 修正。（了解原理，项目未实现）

## 5. Process Reward Model / Outcome Reward Model / Verifier

### Q: ORM 和 PRM 有什么区别？分别适用于什么场景？⭐⭐⭐⭐

- **ORM（Outcome Reward Model）**：对完整回答打分/判断好坏。传统 RLHF 的 reward model 就是 ORM。
- **PRM（Process Reward Model）**：对推理过程的每一步打分。可以识别"蒙对答案但推理错误"的情况。
- **Verifier**：规则验证器，只适用于有标准答案的任务。对就 1 分，错就 0 分。

三者关系：Verifier < ORM < PRM，从最粗糙到最精细，从最便宜到最贵。

**DeepSeek-R1 的策略**：R1 用 RLVR（规则 Verifier）而非 PRM。因为数学题的最终答案有明确对错，Verifier 就够了。但论文也指出 PRM 在可解释性和错误定位上有优势。

**医学用 PRM 的价值**：诊断过程步骤化——问诊→检查→诊断→治疗，每一步都有对错。PRM 可以识别"中间步骤危险但最终答案正确"的 case。

**医学项目关系**：我们的 LLM-as-Judge 8 维度评分已经有一定"过程评估"属性（不光看最终答案，还看相关性、完整性、安全性等中间维度）。但严格 PRM 需要逐步骤标注，当前项目未实现。PRM 的挑战是过程标注成本很高——医学推理的每一步对错需要专家标注。（了解原理，项目未实现）

## 6. Test-time Scaling / Self-consistency / Best-of-N / Rejection Sampling

### Q: 什么是 test-time scaling？和 train-time scaling 有什么区别？⭐⭐⭐⭐

- **Test-time Scaling**：推理时增加计算量以换取更好结果（更多采样、更长推理链、更复杂搜索策略）
- **Self-consistency**：对同一问题采样 N 个推理路径，取多数结果
- **Best-of-N**：采样 N 个完整回答，用 reward model 打分，选最高分的
- **Rejection Sampling**：采样 N 个回答，只保留满足质量门槛的（常用于构造高质量训练数据）

**Test-time vs Train-time**：Train-time scaling 是花更多算力训练更大的模型（预训练思维）；Test-time scaling 是推理时花更多算力（推理时思维）。后预训练时代，test-time scaling 是性价比更高的 scaling 方向。

**和 SFT/DPO/RLHF 的关系**：Rejection sampling 是 SFT 数据筛选的利器；Best-of-N 是部署侧技巧；DPO 的 rejected 可以通过多次采样取低分的来构造。

**医学项目关系**：DPO 中 rejected 的构造用了采样（temperature=0.7）。Safety-RAG 在检索阶段对多个检索结果做了 rerank 过滤器，类似 best-of-N 在检索环节的应用。部署时 best-of-N 不适合当前低延迟需求场景。（项目中以 rejection sampling 形式隐式使用）

## 7. Synthetic Data / Teacher Model Distillation

### Q: 合成数据会不会有"模型内循环"问题？质量怎么保证？⭐⭐⭐⭐⭐

**合成数据**是用模型生成训练数据而非人工标注，是 2025 年后训练的主流数据来源。**Teacher Model Distillation** 是用强模型（teacher）生成高质量数据训练弱模型（student）。

**为什么火**：人工标注太贵（55K 条医疗 SFT 数据如果人工专家标注，成本估算百万级）；强模型 API 降价使 teacher 蒸馏性价比极高；合适 prompt+过滤+验证的合成数据效果接近人工数据。

**模型内循环问题**：用合成数据训练→模型学会模仿 teacher 的风格和错误→再用这个模型生成数据→错误放大。解决方案：teacher 多样化（不用单一模型）、数据过滤和验证、引入真实数据（如 HuatuoGPT2 原始数据）、定期人工抽检。

**我们的蒸馏不同之处**：不是简单的"teacher 输出→SFT 训练"。而是形成闭环——teacher 生成→SFT→DPO→LLM-as-Judge 评估→发现幻觉→Safety-RAG 修复→验证。蒸馏数据是起点，后训练闭环是核心。

**医学项目关系**：项目的 Teacher-MiMo 线路是核心创新点之一。两阶段数据生成体现了合成数据在偏好对齐中的价值。从 reasoning 模型蒸馏 Long-CoT 到医学诊断是下一步方向。（核心方法）

## 8. Safety Alignment / Jailbreak Robustness

### Q: 你们项目怎么保证模型安全？DPO 在安全对齐上有什么风险？⭐⭐⭐⭐⭐

**Safety Alignment（安全对齐）**：让模型拒绝有害请求，输出安全内容。2025 年趋势：从"拒绝回答"走向"安全回答"——不是简单说不，而是给出安全的、有益的回应。

**我们的安全方案（核心亮点）**：多层防护——SFT 数据包含安全拒绝模板；DPO 安全偏好优化；LLM-as-Judge 四类评测中专门有 medical safety review；Safety-RAG 五层安全检测；rule-based 11 类安全规则过滤。不是单点防护，是纵深防御。

**DPO 的安全风险（核心发现）**：DPO 在常见医疗问题上表现好，但在长尾高风险场景（罕见病、复杂用药、危重症）会产生"过度自信"的幻觉。这是因为 DPO 偏好优化让模型学会"给看起来专业的答案"，但在知识薄弱的长尾区域，专业的外表下是错误内容。这就是我们引入 Safety-RAG 的根本原因。

**医学项目关系**：这是项目的核心亮点。DPO 幻觉发现→Safety-RAG 修复→66.7% 幻觉下降，形成了完整的安全闭环。相比单纯的"安全拒绝"，我们的方案是"安全回答"（通过 RAG 注入正确医学知识）。

## 9. RAG + Post-training 结合

### Q: RAG 和微调是互斥的吗？什么场景用 RAG 什么场景微调？⭐⭐⭐⭐⭐

RAG 和后训练不再是两个独立的技术栈，2025 年的趋势是深度融合。

**RAG 和微调不互斥**：微调让模型更好理解检索文档、更好遵循指令、更好组织回答；RAG 给模型提供实时、准确的外部知识。我们项目证明了两者的互补性——DPO 微调后的模型在常见医疗问题表现好，但长尾知识缺失，RAG 弥补了这一不足。

**我们的配合方式**：不是简单的"模型回答+RAG 纠正"的 pipeline 拼接。而是——训练阶段用 teacher 生成 SFT 和 DPO 数据；评测阶段发现 DPO 幻觉问题；部署阶段用 Safety-RAG 做实时安全增强。三个阶段的配合形成了安全闭环。

**医学项目关系**：这是项目核心亮点之二。

## 10. Agent Post-training / Tool-use Training

### Q: Agent 训练和普通对话训练有什么区别？你们医学项目有没有做 agent？⭐⭐⭐

**Agent Post-training**：训练模型作为 agent 行动——多轮决策、工具调用、环境交互。**Tool-use Training**：训练模型准确调用 API/函数/工具。

**Agent 训练的特殊性**：需要多轮交互数据、环境反馈、错误恢复。数据格式复杂（包含 tool call/result 的交替历史）。评测也难——不是判回答质量，是判任务完成度。

**为什么火**：模型从"对话"走向"行动"的商业价值；Tool-use 是小模型突破口；Medical Agent 是刚需（医生需要能查病历、看文献、写报告的工具型助手）。

**医学项目关系**：当前项目聚焦对话场景的安全对齐和知识增强，没有涉及 agent/tool-use 训练。但医学 agent 场景很清晰——模型接 EMR 系统查病历、接医学知识库查文献、接检查系统预约检查。Safety-RAG 中的检索模块可以看做一种特殊的 tool-use。（了解原理，项目未实现）

## 11. Multimodal Post-training / Small Model Specialization

### Q: 你们为什么只做纯文本？会不会太窄了？⭐⭐⭐

**为什么纯文本**：医学的核心决策是基于文本的（病历、检查报告、文献、指南）。医学影像诊断是另一个专门领域（放射科 AI），和我们做临床决策支持是互补的，硬揉在一起不一定效果好。

**小模型专精是核心主张**：Qwen3-8B 在通用对话比不过 GPT-4o，但在医学垂域通过精心设计的后训练可以达到接近效果。垂域小模型有商业价值：部署成本低、推理速度快、数据隐私可控（可本地部署）。

**后续方向**：如果要做多模态，最可能是"医学影像报告生成+临床决策整合"——影像模型提取特征→LLM 生成结构化报告→结合病史做综合诊断。但当前 8B 模型做多模态有些勉强。（了解原理，多模态项目未实现）

## 12. Eval-driven Post-training / Data-centric Post-training

### Q: 后训练中算法重要还是数据重要？你们项目是怎么做数据筛选的？⭐⭐⭐⭐⭐

**数据 > 算法**：在模型和算法架构趋同的今天，数据质量是后训练的核心区分器。

**Eval-driven Post-training**：以评测为导向的后训练——先定义评测标准，再针对性优化训练。和传统"训完再测"不同。

**Data-centric Post-training**：不改变模型架构/训练算法，重点关注数据质量。

**我们的 data-centric 实践**：SFT 数据用 teacher 自动打分+规则过滤，85,000 条过滤到 55,000 条（保留率 64.7%）；DPO 构造用 teacher 答案做 chosen、SFT 模型采样做 rejected（高质量偏好对）；安全性用 11 类规则筛选高风险 case。项目完全遵循 eval-driven+data-centric 范式。（核心方法论）

## 13. Scalable Oversight / LLM-as-Judge 可信性

### Q: LLM-as-Judge 真的可信吗？万一 Judge 也有 bias 怎么办？⭐⭐⭐⭐⭐

**LLM-as-Judge 可信性问题**：位置 bias（先出现的答案容易得高分）、长度 bias（长答案容易得高分）、自我偏好 bias（模型喜欢自己风格的答案）。

**我们的可信性保障（面试重点）**：不是单一评估，是四重交叉验证——Score-based 评估（8 维度精细打分，减少笼统评分的主观性）；Pairwise 评估（A/B 对比，比单独打分更客观）；Medical Safety Review（专门安全审查）；Rule-based（11 类硬规则，完全客观）。四重方法交叉验证，单一方法的 bias 被其他方法修正。Judge 的偏差可以通过评估框架设计来缓解。

**医学项目关系**：LLM-as-Judge 是项目评测体系的核心，面试重点准备。（核心亮点）

## 14. 医疗/法律/金融高风险垂域后训练

### Q: 医疗和其他垂域后训练的差异在哪？医学 LLM 最难的地方是什么？⭐⭐⭐⭐

高风险垂域（医疗、法律、金融）的后训练有特殊要求：错误代价极高（一次药物剂量错误可能致命）、知识密集且更新快、需要可解释性和可追溯性、监管合规要求。

**医疗的特殊性**：错误容忍度极低——数学题答案错了可以再算，药物剂量错了就完了；知识边界模糊——很多东西"医学界也没统一答案"；安全维度多——不只"是不是对的"，还包括"有没有免责声明""有没有建议就医""有没有考虑禁忌症"。

**最难的地方**：不是技术实现，是场景理解——需要深入理解医疗决策流程、医患沟通规范、安全边界定义，才能设计出合理的训练和评测方案。纯技术背景做不好医学 LLM。

## 15. vLLM / SGLang / TensorRT-LLM

### Q: 你们为什么选 vLLM 而不是 SGLang 或 TensorRT-LLM？⭐⭐⭐⭐

- **vLLM**：开源 LLM 推理框架，核心创新 PagedAttention。支持 continuous batching、prefix caching。
- **SGLang**：新一代推理框架，RadixAttention 比 PagedAttention 的 prefix sharing 更高效。
- **TensorRT-LLM**：NVIDIA 官方推理框架，对 NVIDIA GPU 有最优性能但灵活性不如开源方案。

**为什么选 vLLM**：生态成熟、社区活跃、文档完善、和 Qwen 模型兼容性好。我们的需求是低延迟（TTFT~42ms）、中等吞吐（~877 tok/s），vLLM 完全满足。SGLang 在特定场景可能有更好性能但我们暂未遇到瓶颈。

**PagedAttention 原理**：把 KV cache 分成固定大小的 page（类似 OS 内存分页），不要求连续存储。好处：减少显存碎片、可以复用 prefix 的 KV cache、可以灵活分配/回收显存。

**医学项目关系**：项目部署阶段使用 vLLM 0.21.0 + RTX 5090。（已使用）

## 16. OPD vs DPO / OPD vs GRPO（技术路线选择）

### Q: 你怎么看 OPD 和 DPO 的关系？如果让你选 OPD 还是 GRPO 做下一步？⭐⭐⭐⭐

**OPD 和 DPO 不互斥，是互补的**：OPD 解决"数据从哪来"的问题（在线 vs 离线），DPO 解决"怎么优化"的问题。我们的项目用 offline teacher distillation+DPO，如果升级就是 OPD+DPO。

**技术栈选择框架**：

| 场景 | 推荐方案 | 原因 |
|------|---------|------|
| 有标准答案（数学/代码） | GRPO+RLVR | 验证便宜，试错学习有效 |
| 有偏好数据（写作/对话） | DPO | 偏好对直接优化，稳定高效 |
| 需要在线探索 | RLOO/GRPO | 无critic，简单可行 |
| 需要安全知识增强 | DPO+RAG | 偏好对齐+知识补充 |
| teacher成本充足 | OPD+DPO | 在线蒸馏消除分布偏移 |
| teacher成本有限 | Offline Distill+SFT+DPO | 我们项目的方案 |

**下一步选 OPD 还是 GRPO**：如果是医学诊断推理提升→GRPO（用诊断准确性做验证信号）；如果是提升模型在分布外/长尾 query 上的泛化→OPD（动态 teacher 消除分布偏移）。根据项目现状（安全闭环已建立，下一步提升推理能力），GRPO 优先级略高于 OPD。

## 工程落地热点专题（17-41号工程热点）

### Q: 你们的 vLLM 部署配置和性能数据？⭐⭐⭐⭐⭐

我们选 vLLM 是因为部署最快、社区最活跃、和 Qwen 模型兼容性好。在 RTX 5090 上，设 max-num-seqs=16（饱和并发）、max-model-len=4096（控制 KV Cache）、gpu-memory-utilization=0.90（留 10% 缓冲）。PagedAttention 显存管理和 Continuous Batching 调度让我们在 16 并发下达到 877 tok/s 的吞吐，TTFT 100ms。（已使用）

### Q: SGLang 和 vLLM 有什么区别？什么场景用 SGLang 更好？⭐⭐⭐

SGLang 的核心差异化在于 RadixAttention——基于前缀树自动检测和共享所有请求的公共前缀，比 vLLM 的 block 级 prefix caching 粒度更细。在大量请求共享相同 system prompt 和检索文档的场景下，SGLang 可能比 vLLM 吞吐更好。但当前 vLLM 生态更完善。（了解原理，项目未使用）

### Q: 为什么不用 TensorRT-LLM？⭐⭐⭐

TensorRT-LLM 的性能确实更好（通常比 vLLM 快 20-50%），但部署门槛高——需要编译模型为 TensorRT engine、版本兼容性敏感、调试困难。对于 8B 模型在单张 RTX 5090 上，vLLM 的 877 tok/s 已经满足需求。而且 TensorRT-LLM 的某些优化需要企业卡（A100/H100）才能生效。（了解原理，项目未使用）

### Q: PagedAttention 和你了解的别的 KV Cache 优化有什么不同？⭐⭐⭐⭐

PagedAttention 本质上将操作系统的虚拟内存管理搬到了 KV Cache 管理上——page = block、page table = block table、demand paging = 按需分配。好处：近乎零碎片、按需分配和释放（完成即回收）、Copy-on-Write 共享（system prompt 只需存一份）。在 16 并发下，PagedAttention 帮我们节省了约 40-50% 的 KV Cache 显存。（已使用）

### Q: Continuous Batching 的调度逻辑是什么？⭐⭐⭐⭐

每个 step 动态决定 batch 的组成：检查是否有新请求→如有空闲 slot 则分配 KV block 加入 prefill；当前 batch = 所有 prefill 中的请求 + 所有 decode 中的请求；执行一次 model.forward()；完成的请求移出 batch，释放 KV block。prefill 和 decode 可以在一个 forward pass 中计算——通过正确处理 position 和 attention mask。16 并发时 GPU 利用率保持在 90% 以上，这就是 Continuous Batching 的效果。（已使用）

### Q: Prefix Caching 收益有多大？⭐⭐⭐

我们开启了 vLLM 的 `--enable-prefix-caching`。在医学教学场景中，system prompt（医学角色+安全约束）约 200 tokens，每个请求都共享这个前缀。压测显示开启 prefix caching 后 prefill 时间减少约 30%。（已使用）

### Q: Speculative Decoding 你们用了吗？⭐⭐

Speculative decoding 通过 draft-target 模型协作加速生成。在我们的场景中有两个限制：需要额外部署 draft model（增加显存开销，单卡 RTX 5090 不太友好）；医学回答需要高准确性，draft 模型的采样可能引入偏差。当前 877 tok/s 的吞吐已经足够。（了解原理，项目未使用）

### Q: Qwen3 的 GQA 对推理有什么好处？⭐⭐⭐

Qwen3-8B 使用 GQA，num_kv_heads=8，num_attention_heads=32。这意味着 KV Cache 大小是 MHA 的 1/4。单 token KV Cache 约 128KB，4096 token 上下文约 512MB。对比 MHA 的 2GB/序列，GQA 是我们能在 16 并发下运行的关键因素之一。（GQA 天然受益）

### Q: 你们为什么设 max-model-len=4096 而不是 32K？Long-context 和 RAG 哪个更好？⭐⭐⭐

设 max-model-len=4096 是工程权衡——医学教学场景的典型问答不需要超长上下文，4096 已经能容纳完整的 system prompt + RAG 检索文档 + 用户问题 + 模型回答。设太大意味着 KV Cache 显存开销成比例增长，并发数从 16 降到 2-3。long-context 和 RAG 也不是互斥的——对于需要查阅大量文献的任务，我们用 RAG 检索最相关的 top-3 文档拼接进上下文，效果不输全文直接塞入。（选用 4096 作为平衡点）

### Q: RAG 系统怎么部署的？延迟瓶颈在哪？⭐⭐⭐

当前 RAG 是和模型在同一台机器上部署的（本地向量库 FAISS + 本地 rerank 模型）。延迟拆解：embedding 计算约 50ms + FAISS 向量检索约 30ms + rerank 约 80ms + LLM 生成约 2000ms。LLM 生成是最大头。如果要做高并发，embedding 模型和 rerank 模型需要独立部署和扩展。（本地单机部署）

### Q: RAG 延迟怎么优化？⭐⭐⭐⭐

**三板斧**：第一板斧并行化（embedding 计算可与权限检查并行，多路检索可并行发出）；第二板斧多级缓存（L1-embedding 缓存命中率约 10-20%，L2-检索结果缓存约 20-30%，L3-LLM 回答缓存约 5-10%）；第三板斧 Fast path 路由（70% 的常见医学问题跳过 RAG 直接生成，TTFT ~50ms vs RAG path ~250ms）。综合三板斧，预期端到端延迟降低 40-60%。（方案已详细设计）

### Q: RAG 缓存怎么设计？医学知识更新了怎么办？⭐⭐⭐

三层缓存策略：第一层精确匹配 cache（相同问题直接返回缓存回答）；第二层语义相似度 cache（相似度 > 0.95 视为"同一问题"）；第三层检索结果 cache（相同检索 query 复用结果）。医学知识更新：常规回答缓存 7 天，药物/剂量相关缓存 1 天（更新更频繁），并有 invalidation 触发器——教材/指南更新时批量清除相关领域缓存。（部分实现）

### Q: Agentic RAG 你们支持吗？⭐⭐

当前实现的是单轮 RAG——检索一次 + 生成一次。但医学场景确实有 agentic 的需求——如"头痛、发烧、喉咙痛"的理想流程应该是多轮检索。Agentic RAG 的主要挑战是状态管理、超时控制、检索质量评估。（了解原理，项目规划中）

### Q: 多卡推理怎么做？Tensor Parallel 和 Pipeline Parallel 什么场景用哪个？⭐⭐⭐

多卡推理三种策略：Tensor Parallel（TP，将单层权重切到多卡，适合单卡放不下模型）、Pipeline Parallel（PP，不同层放不同卡，适合极深模型）、多副本（每卡独立运行完整模型，适合并发量大但模型不大）。对于 Qwen3-8B 在 RTX 5090 上——单卡能放下，多副本是最优方案。4 张 RTX 5090 多副本可达 ~3500 tok/s。（单卡部署，多副本方案已估算）

### Q: 你们服务有网关吗？怎么做限流和鉴权？⭐⭐

当前 vLLM 部署是直连模式，没有独立的网关层。在生产化设计中会加一层 LLM Gateway 提供：API key 认证、Rate limiting、请求路由、日志和监控。技术选型上可以用 LiteLLM 或自研 Gateway（FastAPI + Redis 做限流计数器）。（已规划设计，未实施）

### Q: LLMOps 在你们项目中怎么体现？⭐⭐⭐

我们使用 WandB 和 Git 做基础的实验管理。完整的 LLMOps 体系（模型注册中心、prompt 版本管理、线上监控）、CI/CD 自动化、灰度发布、线上监控告警、反馈闭环这些还停留在方案设计层面。实验阶段的 LLMOps 有实践，生产阶段的 LLMOps 还缺很多。（WandB+Git 基础已用）

### Q: 怎么保证模型上线后的安全？⭐⭐⭐⭐

多层安全机制：离线层面有 11 类 rule-based 安全规则和 LLM-as-Judge Safety Review。线上还需要补充实时安全监控（每个请求过安全规则引擎）、异常检测（安全触发率突增时告警）、安全仪表盘（每日报告）。离线评测已验证 11 类规则有效性，线上实时监控方案已规划。（离线安全评测已完成，线上监控方案已规划）

### Q: 怎么收集用户反馈来改进模型？Online Evaluation 怎么做？⭐⭐⭐

Online Evaluation 的核心是收集多维度用户信号：显式信号（有用/没用按钮、需要更多信息反馈）、隐式信号（是否复制回答、是否短时间内重新提问、停留时间和回访率）、自动评测（每次回答跑 LLM-as-Judge 8 维度评分）、抽检机制（每天随机抽 50 条线上对话做详细质量评估）。Bad case 自动入库作为下一轮训练数据补充。（方案已详细规划，未实施）

### Q: 新模型上线怎么保证不出问题？⭐⭐⭐⭐

三步走：第一步离线评测门禁（新模型必须通过全部离线评测）；第二步 Shadow Testing（新模型影子模式运行 1-2 天，收集对比数据）；第三步 Canary Release（5%→25%→50%→100% 逐步扩大，任一阶段出问题立即回滚）。医学场景 Canary 观察窗口应更长（至少 48 小时）。（方案已详细规划，未实施）

### Q: 医疗 AI 合规你们是怎么考虑的？⭐⭐⭐

医疗 AI 合规有多个层面：数据层面（使用公开合成数据和脱敏数据，不包含真实患者隐私）、模型层面（定位为"医学教学辅助"而非"临床诊断系统"，监管门槛相对较低）、部署层面（本地部署数据不出域）、可解释性（Safety-RAG 通过引用医学教材来源增强可追溯性）。正式的医疗器械认证（FDA/NMPA）需要专门合规团队和大量临床验证。（基础合规考虑已覆盖）

### Q: 数据飞轮怎么设计？线上 bad case 怎么回流到训练？⭐⭐⭐⭐

四步流程：第一步 Bad case 识别（从线上日志中通过用户点踩、重新生成、安全规则触发、低分等多信号识别）；第二步入库分类（打标签——幻觉/不安全/不完整/不相关/知识过时，安全类 > 幻觉类 > 质量类）；第三步数据修复（用 teacher 重新生成正确回答，组成新的偏好对）；第四步增量训练（积累到 500-1000 对后在最新 checkpoint 上做增量 DPO）。（方案已详细规划，未实施）

### Q: Human-in-the-Loop 的分级审核怎么设计？⭐⭐⭐

四级风险评估：L0 自动通过（低风险问题，安全评分 5/5，占 70-80% 请求）；L1 自动标记异步审核（中等风险，1-2 小时内审核）；L2 人工实时审核（高风险场景，安全评分低于阈值，等审核后再发送，占 5-10%）；L3 拒绝回答（明显超出 AI 能力边界，直接拒答建议就医）。（方案已详细规划，未实施）

### Q: 推理成本怎么算？怎么降低？⭐⭐⭐

成本优化的核心是"分层服务"：请求分级（简单问题走 fast path + 低 temperature）、Model Cascading（如果部署 1.5B 轻量版 + 8B 标准版，90% 简单问题走 1.5B 模型，成本低 4x）、缓存策略（命中率 15-25% 直接节省 15-25% GPU 时）、量化推理（INT8/INT4 吞吐提升 2-4x）。单张 RTX 5090 24h 运行，每日可处理约 38M tokens，估计每日成本约 $5-10。（设计已规划）

2. **已详细规划但未完整实现的设计**：RAG 延迟优化三板斧（并行化+缓存+fast path）、分层缓存（L1/L2/L3 + TTL）、数据飞轮（bad case → 回流 → 增量训练）、分级人工审核（L0-L3）、三步上线策略（离线门禁→Shadow→Canary）、LLM Gateway + 限流/鉴权、多副本负载均衡

3. **了解原理、展示视野的技术**：SGLang（RadixAttention）、TensorRT-LLM（编译优化）、Speculative Decoding（draft model）、Agentic RAG（多轮检索）、GRPO/RLVR（reasoning 训练）、OPD（online distillation）

4. **面试核心策略**：诚实区分"已实现"和"已规划"——强调"完整的工程思维"而非"完整的工程实现"。对于规划中的部分，可以详细阐述设计逻辑和技术选型考量，这本身就是工程能力的体现。

5. **被问"你这个也不懂那个也不会"时的回应**："这些方向我确实没有全部亲手做过，但我理解它们的核心原理和适用场景。我的项目聚焦医疗场景的安全对齐，SFT+DPO+Safety-RAG 是当前最合适的方案。新技术我会持续关注，选择最适合问题的方法而不是最热的方法。"
