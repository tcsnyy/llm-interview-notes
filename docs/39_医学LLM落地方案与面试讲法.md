```
用户输入问题
    │
    ▼
① 隐私脱敏 (PII Redaction)  →  正则+NER识别替换为[REDACTED]
    │
    ▼
② 风险识别 (Risk Assessment)  →  Keyword + 语义分类 → safe/low/medium/high/critical
    │
    ├─ 低风险 (safe/low) → Fast Path（纯模型回答）
    │
    └─ 高风险 (high/critical) → Safety-RAG Path
         │
         ├─ ③ RAG路由决策 → ④ Query重写 → ⑤ Hybrid检索(并行Dense+Sparse)
```

## F. 工程难点

| 难点 | 难度 | 为什么难 | 我们的应对 |
|------|------|---------|-----------|
| 医疗高风险安全 | ★★★★★ | 一个错误建议可能危及生命 | 5层Safety-RAG架构，安全规则硬拦截兜底 |
| DPO长尾幻觉 | ★★★★☆ | DPO让模型更自信但在知识薄弱区编造事实 | 实验发现→RAG补充外部知识→grounding校验 |
| RAG检索准确性 | ★★★★☆ | 医学问题需要找准精确段落 | Hybrid检索(dense+sparse)+rerank精排 |
| RAG延迟 | ★★★☆☆ | 检索+rerank+审查增加端到端延迟 | embedding缓存、检索结果缓存、并行检索 |
| 模型幻觉监控 | ★★★★☆ | 缺乏线上ground truth | grounding score + 用户反馈 + 引用校验 |

**DPO长尾幻觉是核心难点**：我在项目中自主发现DPO训练让模型在常见医疗问题上表现更好，但在脑溢血溶栓、甲状腺癌等长尾场景上，模型编造了不存在的临床数据和文献出处。根因分析：DPO的reward机制鼓励模型"自信回答"，但在知识薄弱区，这种自信变成了"自信地编造"——本质是reward hacking。

## G. 面试高频问答（50+ Q/A）

### Q1: 你的医学项目怎么部署的？⭐⭐⭐⭐⭐

> 训练完成后，通过PEFT的merge_and_unload把LoRA adapter合并到基座模型，得到一个完整的权重文件。然后用vLLM加载这个权重，暴露OpenAI-compatible的`/v1/chat/completions`接口。部署在RTX 5090上，吞吐877 tok/s，TTFT 42ms。

**避坑**：不要说"用HuggingFace的model.generate()开个Flask服务"——太慢，没并发优化。

### Q2: vLLM参数怎么选的？⭐⭐⭐⭐

> RTX 5090（32GB显存）上部署Qwen3-8B：max-model-len=8192（覆盖绝大多数场景）、gpu-memory-utilization=0.90（留10% buffer）、max-num-seqs=16（单卡8B模型的最佳并发）、dtype=float16。参数通过压测验证有具体数据支撑。

### Q3: 如何压测？token/s怎么解释？⭐⭐⭐⭐⭐

> 用Python并发请求模拟多用户同时调用vLLM的/completions接口。我们的877 tok/s是单并发下的decode吞吐。多并发（4路）下总吞吐约1200+ tok/s，因为Continuous Batching能更好地利用GPU算力。注意区分Prefill吞吐（计算密集型，高）和Decode吞吐（显存带宽密集型，低）。

### Q4: TTFT和TPOT是什么？⭐⭐⭐⭐

> TTFT（Time To First Token）：从发送请求到收到第一个token的时间，反映prefill阶段耗时。我们的TTFT约42ms。TPOT（Time Per Output Token）：生成阶段每个后续token的平均时间，反映decode阶段效率。用户体感延迟 = TTFT + 前几个token的生成时间。流式输出在TTFT后用户就开始看到内容，所以TTFT比总延迟更影响体验。

### Q5: RAG接入后为什么变慢？如何降低延迟？⭐⭐⭐⭐

> RAG增加了三个延迟来源：embedding推理、向量检索（约180ms）、rerank（约45ms），共约225ms。降低策略：动态路由（低风险走fast path省225ms）、检索缓存（Redis缓存高频问题，命中时<10ms）、并行检索（Dense和Sparse同时发起取max）、Rerank batch。

### Q6: Context太长怎么办？⭐⭐⭐

> 取top-3 chunk按rerank score排序，总长控制在约1500-2000 tokens。策略：截断+排序、Context compression（LLMLingua摘要压缩）、分层prompt、滑动窗口、Chunk大小调优。当前项目方案：top-3 chunk + system prompt + 问题 ≈ 2500-3000 tokens。

### Q7: 如何做RAG缓存？医疗问题能不能缓存？⭐⭐⭐⭐

> 四级缓存：检索结果缓存（Redis，高频命中率40%+）→ Embedding缓存 → 语义缓存 → 回答缓存。医疗缓存注意事项：知识类（"感冒的诊疗指南"）可缓存、用户特异性（"我头疼3天吃什么药"）不可缓存、安全提醒必须实时生成、PHI必须脱敏后才判断是否缓存。

### Q8: 如何解释项目尚未生产上线？⭐⭐⭐⭐⭐

> 坦白说这个项目当前是**后训练技术验证+可部署原型**，不是完整生产级系统。它完成的部分是后训练链路的核心闭环——从数据生成到vLLM部署，并且**发现并解决了安全对齐的核心问题**（DPO幻觉）。未完成的服务化组件（API网关、监控、缓存、灰度发布）我有清晰认知，它们是工程层面的补全而非算法层面的创新。

### Q9: 如何回答"你这只是demo吗"？⭐⭐⭐⭐⭐

> 如果demo是指"跑通一个开源代码"，那显然不是。核心价值在于：第一，我自己发现了DPO的医疗长尾幻觉问题——这不是调开源模型能得到的insight。第二，我设计了完整的解决方案并验证了效果。第三，我走通了从数据到部署的后训练全链路。第四，我对项目边界有清醒认知——哪些做了哪些没做，下一步该做什么。

### Q10: 医学LLM后训练项目的最大技术价值是什么？⭐⭐⭐⭐⭐

> 不是"我训出了一个好模型"。最大的技术价值是：**发现DPO的医疗长尾幻觉问题，并通过Safety-RAG验证了修复效果**。这证明了一个重要假设：DPO在常见场景提升性能的同时，可能在长尾高风险场景引入新的安全隐患。技术延伸意义：这个发现不仅适用于医疗——任何高风险垂域（法律、金融、工程）的DPO对齐都可能存在类似问题。

```
17. 灰度策略：5%→20%→50%→100%，幻觉率突升×1.2自动回滚

【面试技巧】
18. 诚实但不贬低：说清"做了什么vs没做什么"，展示对差距的认知
19. 突出独立发现：DPO幻觉不是"别人告诉我的"，是我自己设计和发现的
20. 工程思维展示：不仅知道怎么做，还知道为什么这么做、什么时候不该做
```
