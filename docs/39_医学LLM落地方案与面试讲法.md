# 39 医学LLM落地方案与面试讲法

> **文件定位**：把医学LLM Teacher项目包装成工程落地可讲版本。重点解决一个核心困境——项目不是完整生产系统，但面试中需要展示工程落地能力。本文教你如何"诚实但不贬低"地讲述项目边界。
>
> **核心原则**：承认边界（未完整上线），展示深度（对完整生产链路有清晰认知），突出优势（后训练全链路闭环+安全发现+可部署验证）。
>
> **使用方式**：先背下一句话介绍（5选1），再熟读1分钟/3分钟模板，最后逐条过一遍高频问答（至少50条）。面试前精读3遍。

| 压测 | 100% | 吞吐/延迟/并发基准测试 |

### A.2 未完成的模块（坦诚但不露怯）

| 模块 | 原因 | 当前替代方案 |
|------|------|------------|
| API网关（FastAPI封装） | 专注算法验证，API层不是重点 | vLLM原生OpenAI兼容接口 |
| 结构化日志/全链路追踪 | 单机部署不需要request_id串联 | Python logging |
| 监控告警（Prometheus/Grafana） | 无持续流量，监控意义有限 | 手动观察GPU利用率 |
| 灰度发布 | 需要至少2个模型版本同时在线 | 手动切换模型权重 |
| 检索缓存（Redis） | 低流量下缓存命中率有限 | 每次实时检索 |
| 隐私脱敏服务 | 为内部测试，无真实用户数据 | 测试数据已脱敏 |
| 反馈回流管道 | 需要在线收集用户反馈 | 离线bad case分析 |
| 多副本/高可用 | 单GPU无法多副本 | 单实例运行 |
| K8s编排 | 单机不需要K8s | Docker Compose（计划中） |
| A/B测试 | 需要流量规模 | 离线对比评测 |

### A.3 项目边界的正确表述

**推荐说法**（面试中用这个）：

> 这个项目是一个**后训练技术验证+可部署原型**。我完成了从数据构造到vLLM部署的完整后训练链路闭环，证明了技术可行性。项目具备向服务化系统扩展的基础——核心模块（推理、RAG、安全过滤）都已在单机上验证通过，补上API网关、监控和缓存后即可作为小规模试点上线。

**不推荐说法**（避免）：

> 我做了一个生产级医学AI系统。（夸大，会被追问K8s/多节点/灰度等未实现内容）
> 我这个只是demo/实验。（自我贬低，忽略了后训练的完整性和技术深度）

根据不同面试官背景和岗位侧重点，选择对应的版本：

### B.5 面试简洁版（HR/快速介绍）

> 我主导了医学大模型后训练项目：用Teacher模型生成数据→SFT微调→DPO偏好对齐→发现幻觉问题→设计RAG安全方案修复→vLLM部署上线。对后训练全链路有完整的实战经验。

## D. 3分钟项目落地介绍

> 适用场景：面试官说"详细讲讲你的项目"

```
我的医学LLM Teacher项目，从工程落地角度，我按时间线分六个阶段讲。

第一阶段：teacher数据生成。出发点是我发现开源医学SFT数据（HuatuoGPT2）
的答案质量参差不齐——部分GPT-4生成的回答泛化有余但医学严谨性不足。
我用MiMo-v2.5-pro重新生成答案，设计专业的医学system prompt，
temperature设0.2保证确定性。58K数据经过三层过滤——规则过滤（格式/长度）、
模型打分过滤、人工抽检（5%）——最终保留11393条，保留率73.6%。

第二阶段：SFT训练。选Qwen3-8B作为基座，QLoRA配置r=16/α=32，
在RTX 5090上训练。我做了三条对比线路：Base不微调、SFT-HuatuoGPT2原版数据、
SFT-Teacher-MiMo蒸馏数据，验证teacher蒸馏的有效性。

第三阶段：DPO偏好对齐。构造9841对偏好数据：chosen是teacher的标准答案，
rejected用SFT模型在temperature=0.7下采样得到。β=0.1训练1个epoch。
DPO后总分从4.93提升到4.96，但这里我注意到一个关键问题。

第四阶段：Safety-RAG安全增强。评测发现DPO在长尾医疗场景产生了幻觉——
比如在脑溢血溶栓、甲状腺癌、MRCNS感染这类不常见高风险的案例上，
模型会过度自信地给出错误建议。我设计了Safety-RAG：15本医学PDF教材
切分11707个chunk，5层检索架构（路由+过滤+向量+rerank+安全规则）。
最终在3个挑战案例上：整体+0.21，grounding+0.23，hallucination+0.15。

第五阶段：LoRA merge和vLLM部署。LoRA权重通过PEFT merge_and_unload
合并到基座，然后用vLLM在RTX 5090上部署。压测结果：吞吐877 tok/s，
TTFT 42ms，单卡支持3-5路并发。vLLM的关键优势是PagedAttention的
KV Cache分页管理，24GB显存能同时服务多个请求而不像传统方案那样内存碎片。

第六阶段：服务化扩展的规划。当前项目是完整的技术验证原型。
如果要生产上线，我会优先补齐四个P0组件：API网关做鉴权限流、
结构化日志做全链路追踪、Redis做RAG检索缓存（预计命中率40%+）、
Prometheus+Grafana做监控告警。架构上用Docker Compose编排3-4个容器——
vLLM推理(GPU独占)、RAG检索(CPU)、ChromaDB向量库、Redis缓存。
灰度发布按5%→20%→50%→100%的节奏放量，通过request日志中的
model_version字段监控新旧版本指标差异。失败样本通过用户反馈
收集后回流到训练数据池用于下轮SFT/DPO迭代，形成数据闭环。

这就是我整个项目的工程落地全貌——一个从数据到部署的后训练闭环，
当前是技术验证原型但具备向服务化系统扩展的完整基础。
```

## F. 工程难点

### F.1 难点总览

| 难点 | 难度 | 为什么难 | 我们的应对 |
|------|------|---------|-----------|
| 医疗高风险安全 | ★★★★★ | 一个错误建议可能危及生命，不能只靠概率 | 5层Safety-RAG架构，安全规则硬拦截兜底 |
| DPO长尾幻觉 | ★★★★☆ | DPO让模型更自信但在知识薄弱区编造事实 | 实验发现→RAG补充外部知识→grounding校验 |
| RAG检索准确性 | ★★★★☆ | 医学问题需要找准精确段落，语义相近不够 | Hybrid检索(dense+sparse)+rerank精排 |
| RAG延迟 | ★★★☆☆ | 检索+rerank+审查增加端到端延迟 | embedding缓存、检索结果缓存、并行检索 |
| Rerank成本 | ★★★☆☆ | Rerank模型每次对所有候选打分 | Rerank前先做粗排削减候选数、batch调用 |
| Context太长 | ★★★☆☆ | 注入过多RAG内容超出模型context window | Context compression, 截断+排序 |
| vLLM参数调优 | ★★★☆☆ | max_num_batched_tokens等参数影响吞吐/延迟 | 压测不同并发下的最优参数 |
| Chat template一致性 | ★★★☆☆ | 训练和推理的template不一致导致效果退化 | 训练时保存完整tokenizer_config.json，部署时复用 |
| 隐私合规 | ★★★☆☆ | 医疗对话含敏感信息，不能明文存储/传输 | 本地脱敏，hash用户标识，不存对话原文 |
| 模型幻觉监控 | ★★★★☆ | 缺乏线上ground truth，难以实时检测幻觉 | grounding score + 用户反馈 + 引用校验 |

### F.2 各难点深度分析

**难点1：医疗高风险安全**

医疗场景的容错率接近零。一个典型场景：用户描述头痛症状，如果模型误判为普通头痛而建议休息，但实际是脑溢血前兆，可能延误就医。普通NLP的"回答得好不好"在医疗领域不够——必须问"回答得安不安全"。

我们的方案：5层安全架构不做"事后审查"，而是在每个环节逐层拦截。最外层的风险路由判断问题风险等级；中间层的检索为模型提供循证知识；最内层的安全规则做硬拦截——比如"未建议就医"、"推荐未经批准的疗法"一律触发降级回复。

**难点2：DPO长尾幻觉**

这是我在项目中自主发现的问题。DPO训练让模型在常见医疗问题上表现更好（总分+0.03），但在脑溢血溶栓、甲状腺癌等长尾场景上，模型编造了不存在的临床数据和文献出处。根因分析：DPO的reward机制鼓励模型"自信回答"，但在知识薄弱区，这种自信变成了"自信地编造"——本质是reward hacking的一个表现形式。

**难点3：RAG检索准确性**

用户口语化的医疗问题（"我头疼3天了"）和教材中的标准化描述（"头痛持续超过72小时需考虑..."）存在语义gap。单一dense检索可能召回"养生建议"而非"诊疗指南"。解决方案：Hybrid检索（dense embedding + sparse BM25），前者捕捉语义相关，后者捕捉关键词精确匹配，RRF融合后送入rerank精排。

## G. 工程优化策略

### G.1 延迟优化全景

```
总延迟 = 网络 + 脱敏 + 风险识别 + RAG(检索+rerank) + vLLM(TTFT+生成) + 安全审查

优化策略（按优先级排列）：

┌─────────────────────────────────────────────────────────────────┐
│ P0 优化（效果最大）                                              │
├─────────────────────────────────────────────────────────────────┤
│ ① RAG动态路由     高风险走RAG，低风险fast path直接到vLLM        │
│ ② Hybrid检索并行   Dense和Sparse并行请求，不串行等待             │
│ ③ 检索结果缓存     高频医学问题(Q:"感冒怎么办？")40%+命中率，     │
│                    Redis缓存TTL=1小时，命中时延迟降到<10ms       │
│ ④ vLLM streaming   流式返回，TTFT=42ms后用户立即看到首token      │
├─────────────────────────────────────────────────────────────────┤
│ P1 优化（进一步优化）                                            │
├─────────────────────────────────────────────────────────────────┤
│ ⑤ Rerank batch     合并多个检索请求的rerank推理，降低GPU调度开销 │
│ ⑥ Embedding缓存    对query做embedding缓存，相同/相似query复用    │
│ ⑦ Context压缩      检索chunk过长时做摘要压缩再注入prompt         │
│ ⑧ 低风险fast path  纯模型回答（不用RAG），延迟减少180+45=225ms  │
├─────────────────────────────────────────────────────────────────┤
│ P2 优化（有流量规模后）                                          │
├─────────────────────────────────────────────────────────────────┤
│ ⑨ 灰度发布         5%/20%/50%/100%分阶段放量，降低新模型风险     │
│ ⑩ 失败样本回流     收集bad case，人工标注后回流SFT/DPO训练池     │
└─────────────────────────────────────────────────────────────────┘
```

### G.2 各策略详解

**RAG动态路由**：不是所有问题都需要RAG。"感冒了怎么办？"这类高频简单问题可用纯模型回答，延迟减少200ms+。路由规则基于风险分级——safe/low走fast path，medium及以上走RAG path。

**Hybrid检索并行**：dense检索和sparse检索不是串行（先dense再sparse），而是用asyncio.gather同时发起，总延迟=max(dense耗时, sparse耗时)+RRF融合耗时，而非两者之和。

**检索结果缓存**：高频医学问题（top 100个常见症状咨询）占据大量流量。对这类问题的检索结果做Redis缓存，TTL设置要考虑医学知识的半衰期（1小时到24小时，取决于知识类型）。

**Rerank batch**：当并发请求都需要rerank时，将多个rerank请求合并为一个batch送入模型，减少GPU调用次数和padding开销。

**Embedding缓存**：用户的query可以先算hash，如果hash命中缓存则直接用缓存的embedding向量，跳过embedding模型推理。

**Context压缩**：当检索到的chunks总长度超过一定阈值（如4096 tokens），先做摘要压缩再注入prompt。可以用一个小模型做extractive summarization，或者简单的按rerank score截断。

**vLLM streaming**：流式输出在TTFT=42ms后用户即感知到响应，端到端延迟虽然不变（总生成时间一样），但体感延迟大幅改善。

**灰度发布**：

```
阶段1: 5%流量 → 观察30分钟（看错误率、幻觉率、p99延迟）
阶段2: 20%流量 → 观察2小时
阶段3: 50%流量 → 观察4小时
阶段4: 100%流量 → 全量

每一阶段设自动回滚条件：
- 错误率 > 1%
- p99延迟 > 基线 × 1.5
- 幻觉率 > 基线 × 1.2
任一触发 → 自动切回旧版本
```

**失败样本回流**：

```
用户thumbs down / 内容被安全规则拦截
       │
       ▼
  [失败样本池] ──▶ 人工筛选/标注
       │
       ├── 模型知识不足 → 补充RAG知识库
       ├── 模型回答不安全 → 标注→加入DPO rejected
       ├── 模型回答质量差 → 标注→加入SFT训练数据
       └── 检索不准确 → 优化chunk切分/embedding模型
```

**Q4: vLLM参数怎么选的？**

**推荐回答**：
> 我在RTX 5090（32GB显存）上部署Qwen3-8B，经过压测后选择：
> - `max-model-len`: 8192（医疗对话通常不需要超长上下文，8192覆盖绝大多数场景）
> - `gpu-memory-utilization`: 0.90（留10% buffer防止OOM）
> - `max-num-seqs`: 16（单卡8B模型，16个并发是显存能支持的上限，实际测试中8-12时性能最佳）
> - `dtype`: float16（性能和精度的平衡，8B不需要bf16的额外精度）
>
> 参数调整方法：固定并发数（如4），从max-model-len=4096开始逐步上调，观察显存使用。然后在目标max-model-len下逐步提高并发，观察TTFT变化，找到TTFT开始显著恶化的拐点。

**不推荐回答**：用的默认参数。（显示对参数含义不理解）

**可引出技术点**：vLLM内存模型、KV Cache计算、TTFT vs 并发数的tradeoff

**Q5: 如何压测？token/s怎么解释？**

**推荐回答**：
> 压测工具：我用Python并发请求模拟多用户同时调用vLLM的/completions接口，统计不同并发量下的吞吐和延迟。
>
> token/s的含义：**吞吐量**——每秒生成的token总数。注意区分：
> - **Prefill吞吐**：处理prompt的token数/s（计算密集型，高吞吐）
> - **Decode吞吐**：生成输出的token数/s（显存带宽密集型，低吞吐）
> - 通常说的"token/s"指decode吞吐，vLLM报告的总吞吐包含了prefill+decode。
>
> 我们的877 tok/s是单并发下的decode吞吐。多并发（4路）下总吞吐约1200+ tok/s，因为Continuous Batching能更好地利用GPU算力。

**不推荐回答**：压测就是跑了个测试脚本看了下速度。（没有说明方法、并发设置、指标含义）

**可引出技术点**：prefill vs decode、Continuous Batching、GPU利用率与并发的关系

**项目真实边界**：压测已完成，有877 tok/s和42ms TTFT等实测数据。

**Q6: TTFT和TPOT是什么？**

**推荐回答**：
> TTFT（Time To First Token）：从发送请求到收到第一个token的时间。反映prefill阶段的耗时——主要是计算prompt的KV Cache。我们的TTFT约42ms，对用户体验来说是"秒回"级别。
>
> TPOT（Time Per Output Token）：生成阶段每个后续token的平均时间。反映decode阶段的耗时。TPOT = (总生成时间 - TTFT) / (completion_tokens - 1)。
>
> 用户体感延迟 = TTFT + 前几个token的生成时间。流式输出在TTFT后用户就开始看到内容，所以TTFT比总延迟更影响体验。

**不推荐回答**：就是首token延迟和每个token的速度。（过于简略，没解释原因和影响因素）

**可引出技术点**：prefill和decode的计算特点、KV Cache、流式输出对用户体验的影响

**项目真实边界**：TTFT 42ms有实测数据，TPOT需进一步测量。

**Q7: RAG接入后为什么变慢？如何降低延迟？**

**推荐回答**：
> RAG增加了三个延迟来源：embedding推理（query→向量）、向量检索（ANN搜索）、rerank（精排打分）。在我们的场景中，检索约180ms，rerank约45ms，加起来增加约225ms。
>
> 降低延迟的策略（按优先级）：
> 1. **动态路由**：低风险问题走fast path，不走RAG（省225ms）
> 2. **检索缓存**：Redis缓存高频问题的检索结果，命中时检索<10ms
> 3. **并行检索**：Dense和Sparse同时发起，取max而非sum
> 4. **Rerank batch**：合并多个请求的rerank任务，减少调度开销
> 5. **Embedding缓存**：对query做语义hash，相同/相似query复用embedding
>
> 目标：P50延迟从225ms降到<50ms（缓存命中时<10ms）

**不推荐回答**：RAG就是会慢，没办法。（暴露缺乏优化思维）

**可引出技术点**：检索延迟拆解、缓存策略、动态路由、并行化

**项目真实边界**：RAG延迟有实测数据，缓存和动态路由策略已设计但未完整实现。

**Q8: RAG哪些阶段可以并行？rerank太慢怎么办？**

**推荐回答**：
> 可并行的阶段：
> 1. Dense检索和Sparse检索可以用asyncio.gather同时发起，取max延迟而非sum
> 2. 如果你有多个知识库（不同医学教材），可以并行检索再合并
> 3. RAG检索可以和风险识别并行（风险识别不依赖检索结果）
>
> Rerank慢的优化：
> 1. 减少候选数：粗排（dense score）先筛到top-2K，再送给rerank
> 2. Batch rerank：用batch推理而非逐条推理，充分利用GPU并行
> 3. 模型选型：BGE-Reranker-v2-m3 比 v1 更快，或用cross-encoder的小蒸馏版本
> 4. 考虑"不rerank"策略：只在检索分数差异小（top-1和top-5分数差距<0.1）时才触发rerank

**不推荐回答**：rerank就是很慢，没办法。

**可引出技术点**：Hybrid检索并行化、Rerank模型选型、粗排+精排架构

**项目真实边界**：Dense+Sparse并行已实现，Rerank优化策略已设计但未完整实验。

### H.2 上下文与缓存（Q9-Q12）

**Q9: Context太长怎么办？**

**推荐回答**：
> 医学RAG的一个典型问题是：检索出5个chunk，每个500字，加上system prompt和对话历史，总长度可能超过10000 tokens，影响推理速度甚至超出模型max-model-len。
>
> 应对策略：
> 1. **截断+排序**：按rerank score从高到低取前N个chunk，保持总长在4096 tokens内
> 2. **Context compression**：对检索到的chunk用LLM做摘要压缩再注入prompt（LLMLingua等方法）
> 3. **分层prompt**：先把RAG chunks做一个轻量级的"信息摘要"，放到system message中，原始chunks不拼接
> 4. **滑动窗口**：对话历史超过一定轮次后，只保留最近3轮
> 5. **Chunk大小调优**：从500 tokens降到300 tokens，减少冗余但保持完整语义单元
>
> 我们项目当前方案：取top-3 chunk按rerank score排序，总长控制在约1500-2000 tokens，加上system prompt和问题，总prompt约2500-3000 tokens。

**不推荐回答**：多检索几个chunk拼进去，模型能处理。（忽视context window限制和长prompt的推理代价）

**可引出技术点**：Context compression、LLMLingua、prompt工程、chunk分割策略

**项目真实边界**：Chunk截断已实现，context compression等高级策略未实现。

**Q10: 如何做RAG缓存？**

**推荐回答**：
> RAG缓存分三级：
>
> **L1：检索结果缓存**（最有效）
> 对query做规范化（去标点、小写、核心词提取）后算hash，映射到Redis中的检索结果。高频问题命中率预计40%+。TTL=1小时（医学知识相对稳定）。
> 实现：`cache_key = hashlib.md5(normalize(query)).hexdigest()` → `redis.get(cache_key)`
>
> **L2：Embedding缓存**
> 对query的embedding向量做缓存。相同或极高相似度（cosine>0.95）的query复用embedding，跳过embedding模型推理。
>
> **L3：语义缓存**
> 不要求query完全相同，而是语义相似（cosine>0.9）就可以返回同样的检索结果。需要一个向量库做近似最近邻搜索。
>
> **缓存失效策略**：知识库更新（新教材加入）→ 清空所有缓存。定时失效（每日凌晨）→ 防止过期医学知识。

**不推荐回答**：RAG不需要缓存，每次都重新检索就行。

**可引出技术点**：多级缓存架构、缓存一致性、Redis应用、语义缓存

**项目真实边界**：缓存策略已设计，未实现（需要Redis基础设施）。

**Q11: 医疗问题能不能走fast path？如何做高风险路由？**

**推荐回答**：
> 可以走fast path，但必须有靠谱的路由机制。我的方案：
>
> **路由规则**（双轨判断）：
> 1. 关键词匹配：问题中包含"头疼/感冒/牙疼/肚子疼"等常见症状且无高危关键词（胸痛/呼吸困难/意识模糊/口眼歪斜等）→ low risk
> 2. 语义风险分类：用轻量级分类器（如一个fine-tuned的BERT或直接prompt LLM做安全分类）判断风险等级
>
> **Fast Path条件**：同时满足①风险等级=safe/low ②非首次提问（老用户已有病史记录）③非药物咨询（开药必须走RAG验证）
>
> **路由流程**：
> ```
> query → 关键词匹配(low)→ 语义分类(low)→ Fast Path → 直接用模型回答
> query → 关键词匹配(high)/语义分类(medium+)→ Safety-RAG Path → 检索+rerank+安全审查
> ```
>
> Fast Path延迟约1000ms左右（纯vLLM推理），RAG Path延迟约1250ms（增加检索+rerank+审查）。

**不推荐回答**：所有问题都走RAG最安全。（过度保守，没有优化意识）

**可引出技术点**：动态路由、风险分级、Fast/Slow Path设计、用户分层

**项目真实边界**：Safety-RAG已有风险关键词路由，但精细的语义分类路由未完整实现。

**Q12: 如何保护用户隐私？医疗问答是否可以缓存？**

**推荐回答**：
> 隐私保护核心策略：
> 1. **PII脱敏**：前端/API层用正则+NER识别姓名、身份证、手机号、地址等，替换为`[REDACTED]`
> 2. **用户标识hash**：用sha256(user_id+salt)做user_id_hash，不可逆
> 3. **不存对话原文**：日志只存token数、safety flags、latency_breakdown，不存message正文
> 4. **本地部署**：所有数据不出服务器，不经过第三方API
>
> 医疗问答的缓存需要特殊考量：
> - **知识类缓存**（如"感冒的诊疗指南"）→ 可以缓存，TTL=1-24小时
> - **用户特异性缓存**（如"我头疼3天了吃什么药"）→ 不可缓存，因为包含个体信息
> - **去隐私后的通用回答**→ 可以缓存部分回答模板，但要注入当前检索的最新知识
> - **安全提醒**→ 必须实时生成，不能缓存（如"请立即就医"需要根据当前question实时决策）

**不推荐回答**：所有请求都缓存一下就好了。（忽视医疗隐私的敏感性）

**可引出技术点**：数据合规、PII识别、缓存的隐私考量、本地推理优势

**Q14: 如何处理p99延迟过高？如何区分检索慢还是生成慢？**

**推荐回答**：
> p99延迟高的排查方法：
>
> 1. **看latency_breakdown**：每条请求记录了各阶段耗时，重点看p99请求的延迟分布
>    - 预处理>100ms → 隐私脱敏或参数校验慢
>    - 检索>500ms → embedding推理/ANN搜索/rerank慢
>    - vLLM TTFT>200ms → prefill慢（prompt太长或排队）
>    - vLLM生成>2s → decode慢（生成长度大或并发高）
>    - 后处理>100ms → 安全审查逻辑复杂
>
> 2. **区分检索慢 vs 生成慢**：
>    - 检索慢的特征：TTFT正常（42ms），但总延迟显著高于预期（检索快则总延迟≈TTFT+生成时间）
>    - 生成慢的特征：TTFT变高（排队等待），每个token的生成时间也变高
>
> 3. **常见原因和修复**：
>    检索慢 → 缓存命中率低，检查缓存策略；ANN索引需要重建
>    生成慢 → 并发过高，降低max-num-seqs；prompt过长，做context compression
>    排队慢 → 请求波峰，增加max-num-seqs或加多副本

**不推荐回答**：看日志时间戳就行。（没有系统化的延迟拆解思路）

**可引出技术点**：latency breakdown、p99分析、排队论、性能调优方法论

**项目真实边界**：延迟拆解设计已做，结构化日志未完整实现。

**Q15: 如何监控幻觉率？**

**推荐回答**：
> 线上幻觉率监控的核心挑战是缺乏ground truth——用户问的真实答案我们不知道。
>
> 我们的监控策略：
> 1. **Grounding score**（在线）：用Safety-RAG中的独立打分模块，对生成内容和检索知识做一致性比对。grounding_score < 0.5 标记为疑似幻觉。
> 2. **用户反馈**（在线）：thumbs down的比例，特别是标记为"信息不准确"的反馈。
> 3. **引用可验证性**（在线）：模型回答中引用的文献出处是否能在RAG知识库中找到——找不到的引用标记为幻觉。
> 4. **定期人工评测**（离线）：每周从线上采样100条回答，由医学专家或高质量Judge做幻觉审查。
> 5. **Golden set回归**（离线）：预置100条有标准答案的医疗问题，每日跑一遍看幻觉率变化。
>
> 告警阈值：连续5分钟的疑似幻觉率 > 5% → 告警 → 检查是否模型版本/RAG知识库版本变动导致。

**不推荐回答**：幻觉监控暂无好办法。（暴露不知道这个领域的核心难题）

**可引出技术点**：grounding score、用户反馈闭环、幻觉检测方法、SelfCheckGPT

**项目真实边界**：离线评测的幻觉检测（grounding_score）已实现，实时在线幻觉监控未实现。

**Q16: 如何收集失败样本回流传SFT/DPO？**

> ```
> 线上bad case（thumbs down / 安全拦截 / 用户举报）
>       │
>       ▼
> [自动归因分类]
>   ├── 模型知识不足 → 标记"需补充RAG知识"

>   ├── 回答质量差 → 标记"SFT训练候选"

**Q17: 检索服务/vLLM服务挂了怎么办？**

**推荐回答**：
> 高可用策略分两层：
>
> **检索服务挂了（降级策略）**：
> ```python
> try:
>     rag_result = await rag_service.retrieve(query)
> except RAGServiceUnavailable:
>     # 降级：用纯模型回答，不注入RAG上下文
>     # 在回答末尾追加免责声明
>     response = await vllm.generate(query)
>     response += "\n\n【提示】知识检索服务暂不可用，以上回答基于模型自身知识，" \
>                 "请参考权威医学资料确认。如有紧急情况请立即就医。"
> ```
>
> **vLLM服务挂了（无降级余地）**：
> - 返回503 + 友好提示："系统暂时繁忙，请稍后重试。紧急情况请立即就医。"
> - 如果有备用vLLM实例（多副本），Nginx自动切换到健康实例
> - 单机部署下只能返回503，这也是为什么多副本对医疗系统很重要
>
> **熔断机制**：
> - 连续N次请求检索服务超时 → 熔断（open circuit）→ 后续请求直接走降级路径
> - 半开恢复：每隔30s发送一个探测请求，成功则关闭熔断

**不推荐回答**：挂了大不了重启。（没有SRE意识）

**Q18: 如何控制GPU利用率？单卡vs多卡？多副本vs张量并行？**

**推荐回答**：
>
> **GPU利用率控制**：
> - vLLM的gpu-memory-utilization: 0.90（留10% buffer）
> - 监控GPU利用率不是100%就好——100%说明已达瓶颈，新请求会排队
> - 理想利用率：70-85%（有buffer处理突发流量）
>
> **单卡 vs 多卡**：
> - Qwen3-8B在FP16下约16GB模型参数，RTX 5090(32GB)单卡足够
> - 8B模型张量并行（tensor parallelism）性价比低——通信开销 > 并行收益
> - 多卡适合：模型放不进单卡（70B+）或需要高并发多副本
>
> **多副本 vs 张量并行**：
> - 多副本（Data Parallel）：多张卡各自跑完整模型，Nginx/API网关做负载均衡
>   - 优势：简单、容错好、线性扩展吞吐
>   - 劣势：每张卡都要装完整模型
> - 张量并行（Tensor Parallel）：一张卡装不下，切分模型到多张卡
>   - 优势：能跑大模型
>   - 劣势：卡间通信开销、单卡故障影响全局
> - Qwen3-8B适合多副本（2-4卡各跑一个vLLM实例，Nginx轮询）

**不推荐回答**：GPU利用率越高越好，100%才好。

**可引出技术点**：张量并行、数据并行、GPU利用率调优、vLLM参数调优

**项目真实边界**：单卡部署已验证，多副本方案已规划。

**Q19: 如何限流/熔断/降级？**

**推荐回答**：
> 三层流量管控：
>
> **限流（Rate Limiting）**：
> - 令牌桶算法：每用户每秒N个请求，超出返回429 Too Many Requests
> - 在API网关层实现（Nginx limit_req 或 FastAPI中间件）
> - 分用户等级：普通用户5 req/s，VIP用户20 req/s
>
> **熔断（Circuit Breaker）**：
> - 连续失败阈值：检索服务连续5次超时/错误 → 熔断
> - 半开探测：每30s放一个请求试探，成功则关闭熔断
> - 熔断后走降级路径
>
> **降级（Degradation）**：
> | 故障场景 | 降级策略 |
> |---------|---------|
> | RAG检索超时 | 用纯模型回答+免责声明 |
> | vLLM超载 | 返回预设的静态回复模板 |
> | 向量库不可用 | 跳过检索，模型直接回答 |
> | 安全审查超时 | 放行（宁可漏判不能阻塞） |
> | 日志系统故障 | 丢弃日志，不影响主链路 |
>
> 降级的核心原则：**安全审查不能降级**——宁可慢也不能跳过安全检查。其他辅助模块可降级。

**不推荐回答**：暂时不需要限流，流量很小。（缺乏工程前瞻性）

**可引出技术点**：令牌桶、滑动窗口限流、服务降级分级、优先级队列

**项目真实边界**：限流/熔断/降级策略已设计，代码框架已有但未完整部署。

**Q20: 如何避免流式输出危险内容？**

**推荐回答**：
> 流式输出场景下的安全挑战：内容是逐token推送的，前几个token可能是安全的但后续转向危险内容——不能等生成完再审查。
>
> 策略：
> 1. **前置高风险拦截**：高风险问题（风险识别阶段判定critical）不走流式，走非流式先审查后返回
> 2. **实时关键词监控**：每个token在推送前过一遍安全关键词黑名单，命中则截断
> 3. **流式缓冲+窗口审查**：每生成N个token（如32），暂停推送，对缓冲区做一次快速安全扫描，通过则继续推送，不通过则截断
> 4. **句子级拦截**：以句号/换行为边界，每个句子完成后审查再推送
> 5. **安全水印**：在system prompt中注入安全约束（"你绝对不能给出以下类型的建议..."），从源头降低风险
> 6. **流式后追加安全提醒**：即使内容已推送，在生成结束的[DONE]之前追加一条安全提醒

**不推荐回答**：流式比非流式快，直接流式就行。（忽视安全控制）

**可引出技术点**：流式安全控制、实时内容审核、安全prompt工程

**项目真实边界**：Safety-RAG已有后置安全审查（非流式），实时流式安全控制未完整实现。

> 3. **Safety-RAG也做A/B测试**：对比不同RAG策略的效果——dense-only vs hybrid、rerank vs no-rerank、不同chunk大小——找到安全性和延迟的最佳权衡。
>
> 这些问题不影响项目的核心发现（DPO引入幻觉→RAG可修复），但能让实验更系统、结论更可靠。

**不推荐回答**："我觉得做得挺好的，没什么要改的。"

**可引出技术点**：实验设计改进、A/B测试、评测体系设计、RLHF vs DPO

**项目真实边界**：改进方向都是合理的技术讨论，不需要实现过。

**Q26: 你觉得医学LLM落地最大的挑战是什么？**

> 技术挑战（幻觉、延迟、检索精度）都有工程手段可以缓解——RAG降低幻觉、缓存降低延迟、hybrid检索提升精度。但安全边界是一个"治不了"的问题：

**Q27-Q34: 快问快答**

**Q27: 你的模型和直接调用GPT-4o有什么区别？**
> 本地部署可控、可微调、医疗数据不出域。GPT-4o API涉及数据出境合规风险，且不能针对医学场景做定制化微调。

**Q28: 为什么不直接用更大模型？70B的效果比8B好。**
> 落地约束：RTX 5090 32GB显存放不下70B（即使用4bit量化也紧张）。8B是"实用尺寸"——能训练能部署，且医学对话不需要复杂推理，8B足够覆盖。效果差距用teacher蒸馏+RAG填补。

**Q29: LoRA merge后模型大小变化了吗？**
> LoRA merge前后参数量相同——merge把adapter权重加到原有权重上再保存，总参数不变。变化的是：训练时是base_model + lora_adapter两个文件，merge后是一个完整的单一权重文件。

**Q30: 你的RAG用了什么embedding模型？**
> BGE-large-zh-v1.5，1024维向量。选择原因是中文医学领域评测效果好，且社区有大量中文优化。

**Q31: 为什么用ChromaDB而不是Milvus？**
> 轻量选择：ChromaDB嵌入式部署，零运维。11707个chunk的规模ChromDB完全够用。Milvus适合百万级以上大规模向量库。

**Q32: 你的模型能处理多长的对话？**
> SFT训练时max_seq_len=2048，vLLM部署时max-model-len=8192。多轮对话建议控制在10轮以内，否则早期信息会被稀释。

**Q33: 模型会不会泄露训练数据中的患者信息？**
> 训练数据来自公开的HuatuoGPT2和teacher生成，不包含真实患者数据。部署的数据隐私策略在H.4的Q12中详述。

**Q34: 有没有考虑多模态医学能力？**
> 当前是纯文本。医学影像（X光/CT/病理切片）的多模态分析需要视觉encoder+专门的医学影像数据，是下一步的扩展方向但不是当前后训练项目范围。

### H.5 扩展技术深度（Q35-Q50+）

**Q35: 如何做A/B测试两个模型版本？**

**推荐回答**：
> A/B测试框架设计：
> ```
> 用户请求 → API网关
>                │
>                ├── (user_id_hash % 100) < 50 → Model A (稳定版)
>                └── (user_id_hash % 100) >= 50 → Model B (实验版)
> ```
>
> 关键设计：
> - 按user_id做一致性hash分流（同一用户始终打到一个模型，避免体验不一致）
> - 两个模型返回结果中不注明是A还是B（双盲）
> - 监控核心指标：thumbs up ratio、幻觉率、安全拦截率、p99延迟
> - 实验周期：至少1周，收集足够样本量确保统计显著性
> - 实验结果：统计检验（如卡方检验比较两个模型的错误率差异是否显著）

**可引出技术点**：A/B测试框架、统计显著性、在线实验设计
**真实边界**：A/B框架已设计，未实现（需流量规模）。

**Q36: 如何保证chat template训练和推理一致？**

**推荐回答**：
> 这是部署时容易忽视的细节。训练时tokenizer的chat template存储在`tokenizer_config.json`中，部署时必须用同一份。
>
> 不一致的后果：训练时用了带system prompt格式的template，推理时用了不带格式的，模型行为完全不同——可能导致"模型变傻"。
>
> 最佳实践：训练完成后，把完整的`tokenizer_config.json`、`tokenizer.json`、`special_tokens_map.json`和merged模型一起打包。vLLM加载时指定`--tokenizer ./merged-model`，确保使用的是训练时的tokenizer。

**可引出技术点**：tokenizer一致性、chat template Jinja2、特殊token处理
**真实边界**：训练时保存了完整tokenizer配置，部署时复用了。

**Q37: DPO的rejected为什么用temperature=0.7而不是0？**

**推荐回答**：
> temperature=0（贪婪解码）生成的rejected是"同一性"回答——每次都一样，缺乏多样性。temperature=0.7产生的rejected包含更多样的"次优"回答，让DPO学到的偏好更鲁棒——不仅学会"拒绝坏答案"，还学会"拒绝不同类型的坏答案"。
>
> 但也注意：temperature太高（>1.0）会产生随机噪声，rejected质量不可控。

**可引出技术点**：temperature采样原理、DPO偏好对构造、多样性vs质量
**真实边界**：temperature=0.7是实验中实际使用的参数。

**Q38: vLLM的Continuous Batching具体怎么工作的？**

**推荐回答**：
> vLLM在每个decode step动态决定batch中的请求组成：
> 1. 新请求到达 → 立即调度prefill
> 2. Prefill完成后 → 请求转为decode状态
> 3. 请求生成完 → 离开batch
> 4. 任何时候都有请求在做prefill、有请求在做decode
>
> 相比静态batching（等整个batch全部完成才能加新请求），Continuous Batching大幅降低了GPU空闲时间。

**可引出技术点**：Continuous Batching、prefill-decode调度、GPU利用率
**真实边界**：vLLM内置实现，部署时使用默认调度策略。

---

**Q39: 什么是KV Cache预分配浪费？PagedAttention怎么解决的？**

**推荐回答**：
> 传统框架为每个请求预分配max_seq_len长度的连续KV Cache空间——即使用户只生成50个token，也预留了2048个token的空间。PagedAttention把KV Cache切成固定大小的block（类似OS中的内存页），按需分配，通过block table做逻辑到物理的映射。多个请求的相同prefix（如system prompt）可共享同一份block。

**可引出技术点**：PagedAttention、显存碎片化、虚拟内存类比
**真实边界**：vLLM自动管理，部署时无需手动调KV Cache。

---

**Q40: 模型推理时GPU利用率不高怎么办？**

**推荐回答**：
> GPU利用率低通常在decode阶段——每次只处理1个token，计算量小，大部分时间花在从显存读取KV Cache上（显存带宽瓶颈）。提高利用率的办法：
> 1. 提高并发（Continuous Batching让多个请求同时decode）
> 2. 增大max-num-seqs（允许更多请求进batch）
> 3. 使用FlashAttention（减少显存读写）
> 4. 如果利用率仍然低，说明不是计算瓶颈而是显存带宽瓶颈——这是decode阶段的固有特性

**可引出技术点**：GPU利用率分析、compute-bound vs memory-bound、FlashAttention
**真实边界**：压测时观察了GPU利用率，有实测数据。

**Q41: 模型的量化方案是什么？推理时量化了吗？**

**推荐回答**：
> 训练时：QLoRA 4bit NF4量化（降低训练显存）。
> 推理时：FP16，未量化。原因是：
> - RTX 5090 32GB放8B FP16（约16GB）足够
> - FP16推理质量无损，量化(AWQ/GPTQ)可能带来轻微精度下降
> - 如果未来换70B模型，推理时会考虑4bit量化以装入单卡

**可引出技术点**：QLoRA、AWQ、GPTQ、推理量化选型
**真实边界**：训练用QLoRA 4bit，推理FP16，实际部署配置。

**Q42: 为什么不把Chat Template存在代码里？**

**推荐回答**：
> Chat template应该跟随模型权重和tokenizer一起保存，而不是硬编码在应用代码中。原因：
> 1. 不同模型版本的template可能不同——代码硬编码无法追溯版本
> 2. 回滚模型时如果忘了改代码中的template，会导致不一致
> 3. tokenizer_config.json是模型包的一部分，vLLM可以自动读取
>
> 最佳实践：代码中不写任何template逻辑，完全依赖vLLM从模型目录加载。

**可引出技术点**：MLOps实践、配置管理、模型打包标准
**真实边界**：使用vLLM自动加载tokenizer配置。

**Q43: 为什么检索不能只看相似度分数？**

**推荐回答**：
> 高相似度不等于高相关性——向量相似度衡量的是语义邻近，但"语义邻近的医学内容"可能是"一般健康科普"而非"权威诊疗指南"。
>
> 例如：用户问"脑溢血溶栓治疗"，embedding检索可能返回"脑溢血的日常护理"（语义相关但学术权威性不足），而不是"急性脑出血溶栓治疗指南"（BM25关键词匹配更精确）。
>
> 这就是为什么需要hybrid检索（dense+sparse）+ rerank + 安全规则的多层过滤。

**可引出技术点**：语义相似度 vs 事实相关性、dense vs sparse检索、rerank的价值
**真实边界**：Hybrid检索已在Safety-RAG中实现。

**Q44: 你的Safety-RAG为什么是5层？不能3层吗？**

**推荐回答**：
> 5层每一层解决不同维度的问题，不能合并：
> - 第1层（风险路由）→ 决定是否走RAG，低风险跳过后4层
> - 第2层（文档过滤）→ 粗筛，排除明显不相关的文档
> - 第3层（向量检索）→ 语义召回，dense+sparse hybrid
> - 第4层（rerank精排）→ 对候选精排，筛选最相关的
> - 第5层（安全规则）→ 硬拦截，过滤不安全/不权威的内容
>
> 如果做成3层（路由+检索+安全规则），就缺失了粗排（效率）和精排（精度）的分层优化。每一步都有明确的工程目的。

**可引出技术点**：多层架构设计、效率与精度的分层思想
**真实边界**：5层架构已在Safety-RAG中完整设计并实现。

**Q45: 知识库的chunk怎么划分的？为什么是11707个？**

**推荐回答**：
> Chunk划分策略：
> - 每个chunk约300-500 tokens
> - 按段落边界切分（保持语义完整性）
> - 相邻chunk有50 tokens的overlap（防止关键信息被切断）
> - 每个chunk保留metadata：来源文献、页码、章节标题
>
> 11707是15本医学教材自然切分的结果——不是刻意为之。如果未来加入更多教材，chunk数自然增长。

**可引出技术点**：chunk策略、overlap设计、PDF解析、Embedding模型
**真实边界**：11707 chunks是实际数据，chunk策略已在实际中使用。

**Q46: 你觉得RAG能完全消除幻觉吗？**

**推荐回答**：
> 不能。RAG给模型提供了外部知识，显著降低了"不知道而编造"的幻觉——但引入了新的幻觉类型：
> 1. **retrieval错误**：检索到不相关的内容，模型基于错误信息生成
> 2. **attribution错误**：检索对了但模型误用了（张冠李戴引用）
> 3. **over-reliance**：检索知识的权威性不足但模型盲目采信
>
> RAG是把幻觉从"编造"降级为"基于不可靠引用"，是一个量级的改善但不是质的消除。这也是为什么我们保留了安全规则层做硬拦截。

**可引出技术点**：RAG幻觉新类型、attribution、retrieval质量
**真实边界**：对RAG局限性的清醒认知，是面试中的加分项。

> 排查步骤：
> 1. **检查版本一致性**：线上的model_version、prompt_version、KB_version是否和离线评测一致
> 2. **检查prompt是否正确注入**：RAG上下文是否被正确拼接到prompt中（有时换行/编码问题导致prompt畸形）
> 3. **检查tokenizer配置**：chat template是否一致
> 4. **分析幻觉分布**：是集中在某种问题类型（如罕见疾病）还是均匀分布
> 5. **对比线上问题vs评测问题分布**：线上用户问的问题可能和评测集分布不同（评测集偏常见病，线上可能有更多长尾问题）
> 6. **检查检索质量**：线上的RAG检索结果质量是否和离线一致
> 7. **抽样人工审查**：拿线上100个bad case和离线评测100个sample做人工比对
>
> 最可能的原因：线上问题分布不同（长尾问题比例更高）导致DPO的幻觉问题被放大。修复方向：扩充知识库覆盖更多长尾疾病、提高检索召回率。

**可引出技术点**：系统化排查方法论、线上vs离线gap分析
**真实边界**：排查思路的完整性体现工程素养。
