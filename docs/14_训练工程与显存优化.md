## 1. Batch Size / Micro Batch Size / Gradient Accumulation / Effective Batch Size

### 1.1 概念关系

```
Effective Batch Size = Micro Batch Size × Gradient Accumulation Steps
```

```
示例（本项目 SFT）:
micro_batch_size = 2      # 每次前向处理的样本数（受显存限制）
gradient_accumulation = 8  # 累积 8 个 micro batch 的梯度再做一次 optimizer step
effective_batch_size = 2 × 8 = 16  # 等效于一次性处理 16 个样本
```

### 1.2 为什么需要梯度累积

RTX 5090 只有 32GB 显存，无法一次放 16 条长序列样本同时前向。梯度累积让每一次 optimizer step 的"有效批次"变大，同时保持显存占用不变：

```
每个 micro batch:
  forward → 计算 loss → backward → 累加梯度到 .grad

每 gradient_accumulation steps:
  optimizer.step() → 更新权重
  optimizer.zero_grad() → 清零梯度 → 开始下一轮累计
```

**数学本质**：梯度累积等价于用更大的 batch size 计算平均梯度。

> **面试金句**："梯度累积是一种用时间换空间的技术——通过多次 forward/backward 再更新一次参数，在显存受限的情况下实现等效大批次训练，提升训练稳定性。"

### 1.3 超参数选择建议

| 场景 | micro_batch_size | grad_accum | effective_bs |
|------|-----------------|------------|-------------|
| QLoRA SFT | 1-2 | 4-16 | 8-32 |
| 全参 SFT | 1 | 32-128 | 32-128 |
| DPO | 1 | 4-8 | 4-8 |
| 预训练 | 很大（GPU多） | 1 | 千万级tokens |

## 2. Mixed Precision (BF16/FP16)、Loss Scaling

### 2.1 混合精度训练原理

训练时模型主体用半精度（BF16/FP16）计算加速和节省显存，但某些关键操作（如 loss 计算、某些归一化层）保持 FP32 精度：

```
权重存储: FP32 (master weights)
前向计算: BF16 (自动转换)
梯度累积: FP32 (精度保证)
优化器更新: FP32 → 转回 BF16
```

### 2.2 BF16 vs FP16

| 特性 | FP16 | BF16 |
|------|------|------|
| 尾数位 | 10-bit | 7-bit |
| 指数位 | 5-bit | 8-bit |
| 动态范围 | [-65504, 65504] | ≈[-3.4e38, 3.4e38] |
| 溢出风险 | 高（需要 loss scaling） | 低（几乎不需要） |
| 硬件支持 | 广泛 | 需要 A100+ / RTX 30 系列+ |

**本项目用 BF16**，因为：
1. RTX 5090 原生支持 BF16。
2. 不需要 loss scaling，训练更稳定。
3. Qwen3 原始训练用 BF16，精度一致。

### 2.3 Loss Scaling（FP16 场景需要）

FP16 的指数位只有 5-bit，小梯度可能 underflow 到 0：

```python
# 伪代码：FP16 混合精度 + loss scaling
scaler = torch.cuda.amp.GradScaler()

with torch.cuda.amp.autocast(dtype=torch.float16):
    loss = model(input)  # FP16 前向

scaler.scale(loss).backward()     # 放大梯度
scaler.step(optimizer)            # 更新（含 unscale）
scaler.update()                   # 动态调整 scale 因子
```

**BF16 不需要 loss scaling**：因为其 8-bit 指数与 FP32 相同，动态范围足够大。

> **面试金句**："BF16 通过牺牲尾数精度换取更大的指数范围，使得它拥有和 FP32 相同的动态范围，因此训练时几乎不需要 loss scaling 就能避免梯度下溢。这是 BF16 在 LLM 训练中比 FP16 更受欢迎的核心原因。"

## 3. Gradient Checkpointing、Gradient Clipping

### 3.1 Gradient Checkpointing（梯度检查点/重计算）

**问题**：反向传播需要前向的中间激活值。全保存激活值显存开销巨大（对于 Qwen3-8B 可能超过 100GB）。

**解决方案**：前向时不保存所有中间激活，反向时**重新计算**需要的部分。

```
无 checkpointing:
  x → Layer1 → a1 → Layer2 → a2 → Layer3 → a3 → loss
                     所有 a 都保存（显存爆炸）

gradient_checkpointing=True:
  x → Layer1 → a1 → Layer2 → a2 → Layer3 → a3 → loss
                     ↑ 只保存 checkpoint 节点
  反向时: a2 = Layer2(Layer1(x))  # 重新计算
```

**代价**：多一次前向计算（约 20-30% 额外计算时间），但显存节省 50-70%。

**QLoRA 场景**：由于 LoRA adapter 本身参数很少，激活值显存是主要瓶颈，强烈建议开启。

```python
# HuggingFace Trainer 中启用
from transformers import TrainingArguments
args = TrainingArguments(
    gradient_checkpointing=True,
    gradient_checkpointing_kwargs={"use_reentrant": False},
)
```

### 3.2 Gradient Clipping（梯度裁剪）

防止梯度爆炸，将梯度的范数裁剪到指定阈值：

```python
# 在 Trainer 中设置
args = TrainingArguments(
    max_grad_norm=1.0,  # 梯度 L2 范数超过 1.0 则等比缩放
)
```

**公式**：
```
if ||g|| > max_grad_norm:
    g = g × (max_grad_norm / ||g||)
```

典型值：`max_grad_norm=1.0` 是通用安全值，QLoRA 训练常设 `0.3~1.0`。

## 4. Warmup、Cosine Scheduler、Weight Decay、AdamW

### 4.1 Learning Rate Warmup

训练初期学习率从 0（或一个极小值）线性/余弦增长到目标学习率：

```
lr = target_lr × min(step / warmup_steps, 1.0)
```

**为什么需要 warmup**：
- 随机初始化的模型/新初始化的 LoRA adapter 梯度方向不稳定。
- 大学习率直接上会导致参数剧烈震荡。
- warmup 给优化器一个"探索"阶段，让梯度统计量（如 Adam 的一阶/二阶矩）逐渐建立。

```python
# 典型配置
warmup_steps=100       # 或 warmup_ratio=0.03 (占总步数 3%)
lr_scheduler_type="cosine"
```

### 4.2 Cosine Scheduler

学习率从 target_lr 余弦衰减到最小值：

```
lr(step) = lr_min + 0.5 × (lr_max - lr_min) × (1 + cos(π × step / total_steps))
```

**优势**：
- 初始阶段：lr 较高，快速收敛。
- 末期：lr 缓慢递减，细致优化。
- 比 step decay 更平滑，不易陷入局部最优。

### 4.3 Weight Decay

L2 正则化的实现方式（在 AdamW 中与 L2 正则化等价但实现不同）：

```python
# AdamW 中 weight decay 直接在权重上施加衰减
θ = θ - lr × (∇L + λ × θ)  # λ 即 weight_decay
```

**QLoRA 训练中**：通常只对 LoRA adapter 参数施加 weight decay，base model 的 4-bit 权重不更新（不对其施加）。

```python
# 典型值
weight_decay=0.01  # 适中
weight_decay=0.0   # 无正则化（易过拟合）
weight_decay=0.1   # 强正则化（欠拟合风险）
```

### 4.4 AdamW 优化器

Adam + Decoupled Weight Decay：

```
m_t = β₁ × m_{t-1} + (1-β₁) × g_t          # 一阶矩（动量）
v_t = β₂ × v_{t-1} + (1-β₂) × g_t²         # 二阶矩（自适应学习率）
m̂_t = m_t / (1-β₁^t)                        # 偏差修正
v̂_t = v_t / (1-β₂^t)
θ_t = θ_{t-1} - lr × (m̂_t / (√v̂_t + ε) + λ × θ_{t-1})
                                               ↑ weight decay 独立于梯度
```

> **面试金句**："AdamW 把 weight decay 从 Adam 的 L2 正则化中解耦出来，使 weight decay 不受自适应学习率缩放的影响，正则化效果更稳定。"

## 5. Paged Optimizer (QLoRA 中使用 paged_adamw_8bit)

### 5.1 问题

QLoRA 中 base model 不更新（4bit），只有 LoRA adapter 需要更新（通常是 16-bit）。但原始 LoRA 参数较少（~0.1%-1% 总参数量），优化器状态（Adam 的 m 和 v）也占用显存。

当使用 8-bit 优化器状态时，如果 GPU 显存紧张，优化器状态可能触发 OOM。

### 5.2 Paged Optimizer 原理

将优化器状态（m, v）**换出到 CPU 内存**，只在需要更新时才换入 GPU：

```
GPU 显存:
  模型权重 + LoRA 参数 + 激活值 → GFX 算力
  优化器状态 m, v → 不在 GPU！存在 CPU RAM

需要 optimizer.step() 时:
  CPU → PCIe → GPU: 搬运一页优化器状态
  更新对应参数
  GPU → PCIe → CPU: 写回（如需要）
```

**本质**：利用 CPU RAM（远大于 GPU 显存）来存优化器状态，自动分页搬运。

### 5.3 在 QLoRA 中使用

```python
import bitsandbytes as bnb

optimizer = bnb.optim.PagedAdamW8bit(
    model.parameters(),
    lr=2e-4,
    weight_decay=0.01,
)
```

或通过 TrainingArguments：

```python
from transformers import TrainingArguments
args = TrainingArguments(
    optim="paged_adamw_8bit",
)
```

> **面试金句**："Paged Optimizer 和 PagedAttention 异曲同工——都用分页思想打破物理显存的连续分配限制。Paged Optimizer 把优化器状态卸载到 CPU，需要时自动分页换入。"

## 6. DeepSpeed ZeRO-1/2/3、FSDP、DDP（概念层面）

### 6.1 数据并行 (DDP, Distributed Data Parallel)

```
GPU0: model replica + batch[0:N/2]   → forward → backward → all-reduce gradients
GPU1: model replica + batch[N/2:N]   → forward → backward → all-reduce gradients
```

每张 GPU 持有一份完整模型副本，各自处理不同的数据。梯度通过 all-reduce 同步后各自更新。

**问题**：每张 GPU 存完整模型 → 当模型很大时放不下。

### 6.2 ZeRO-1: 优化器状态分片

```
GPU0: model full + optimizer states[0:N/2]
GPU1: model full + optimizer states[N/2:N]
```

每张 GPU 只存一部分优化器状态（m, v），更新时 all-gather 获取完整状态。

**显存节省**：~4x（Adam 的 m+v 约占模型权重的 2x）。

### 6.3 ZeRO-2: 优化器状态 + 梯度分片

```
GPU0: model full + optimizer states[0:N/2] + gradients[0:N/2]
GPU1: model full + optimizer states[N/2:N] + gradients[N/2:N]
```

梯度也在每张 GPU 上分片存储，backward 时用 reduce-scatter 而非 all-reduce。

**显存节省**：~8x。

### 6.4 ZeRO-3: 优化器状态 + 梯度 + 参数全分片

```
GPU0: model[0:N/2] + optimizer states[0:N/2] + gradients[0:N/2]
GPU1: model[N/2:N] + optimizer states[N/2:N] + gradients[N/2:N]
```

模型权重本身也被分片。前向/反向时需要时 all-gather。

**显存节省**：正比于 GPU 数量（N 张 GPU → 每张节省 N 倍）。

**代价**：大量通信，对网络带宽要求高。

### 6.5 FSDP (Fully Sharded Data Parallel)

PyTorch 原生实现，类似 ZeRO-3 概念：

```python
from torch.distributed.fsdp import FullyShardedDataParallel as FSDP
model = FSDP(model, sharding_strategy="FULL_SHARD")
```

### 6.6 本项目为什么不需要

RTX 5090 单卡，不需要分布式。但如果面试官追问：

> "8B 模型在单卡上跑 QLoRA（base model 4-bit 只占 ~4GB，LoRA 参数很少，加上激活和优化器总共不超 28GB），单卡 32GB 足以容纳。分布式在本场景下引入 NVLink/PCIe 通信开销反而降低效率。"

## 7. OOM 排查流程

### 7.1 OOM 类型诊断

```
1. CUDA out of memory. Tried to allocate X.XX GiB
   GPU 0 has a total capacity of 32.00 GiB of which X.XX GiB is free.
```

**系统化排查步骤**：

```python
# 步骤1: 查看显存快照
import torch
print(torch.cuda.memory_summary())

# 步骤2: 定位最大显存消耗者
# 在训练代码中插入
torch.cuda.reset_peak_memory_stats()
outputs = model(**batch)  # forward
loss = outputs.loss
print(f"Peak after forward: {torch.cuda.max_memory_allocated() / 1e9:.2f} GB")

loss.backward()
print(f"Peak after backward: {torch.cuda.max_memory_allocated() / 1e9:.2f} GB")

optimizer.step()
print(f"Peak after optimizer: {torch.cuda.max_memory_allocated() / 1e9:.2f} GB")
```

### 7.2 常见 OOM 原因及解决

| 原因 | 诊断信号 | 解决方案 |
|------|---------|---------|
| batch size 太大 | OOM 在 forward 阶段 | 减小 micro_batch_size |
| 序列太长 | 报错时有 max_seq_len 信息 | 截断/过滤长序列 |
| 激活值太大 | OOM 在 backward 阶段 | 开启 gradient_checkpointing |
| 优化器状态 | OOM 在 optimizer.step() | 用 paged_adamw_8bit |
| KV Cache 爆 | 推理 OOM | 减小 max_model_len |
| 显存碎片 | OOM 时 free 显存看似够 | 设置 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` |

### 7.3 OOM 排查决策树（面试口述版）

```
OOM 了怎么办？
  ├─ 先看报错发生在哪个阶段
  │   ├─ forward 阶段 → batch size 或 seq_len 问题 → 减 batch / 截断长序列
  │   ├─ backward 阶段 → 激活值问题 → 开 gradient checkpointing
  │   └─ optimizer.step() → 优化器状态问题 → 换 paged_adamw_8bit
  │
  ├─ 如果减到 batch_size=1 还 OOM
  │   ├─ 检查是否有模型副本（如 DPO 的 reference model）
  │   ├─ 检查是否意外加载了不需要的组件
  │   └─ 考虑切换更低精度（NF4 → INT4 → 更小模型）
  │
  └─ 如果显存使用 < 90% 但 OOM
      └─ 可能是碎片化 → 设 PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True
```

## 8. Loss NaN 排查流程

### 8.1 NaN 来源

```python
# 可能原因
1. 学习率过大 → 梯度爆炸 → 参数溢出 → NaN
2. 数据中有 NaN/Inf → 传播到 loss
3. 数值不稳定操作（如 log(0)）
4. FP16 溢出（BF16 很少）
5. attention mask 错误 → 对 padding 做 attention → NaN
```

### 8.2 排查步骤

```python
# 步骤1: 检查输入数据
for batch in dataloader:
    for k, v in batch.items():
        if torch.isnan(v).any() or torch.isinf(v).any():
            print(f"NaN/Inf in input: {k}")

# 步骤2: 检查中间激活
with torch.autograd.detect_anomaly():
    loss = model(**batch).loss
    loss.backward()  # 会在产生 NaN 的第一步报错并打印 trace

# 步骤3: 降低学习率重试
lr = current_lr / 10

# 步骤4: 检查 loss 曲线
# 如果 loss 突然从正常值跳变到 NaN → 大概率是学习率问题
# 如果 loss 从第一步就是 NaN → 数据问题或初始化问题
```

### 8.3 典型解决

| 现象 | 解决方案 |
|------|---------|
| loss 突然 NaN（训练中途） | 降 lr、增大 warmup、检查是否有异常样本 |
| loss 第一步 NaN | 检查数据、检查 chat template 是否正确 tokenize |
| loss 波动大后 NaN | gradient clipping 太小？增大 max_grad_norm |
| 确定某 batch 导致 NaN | skip 该 batch（设置 `skip_bad_batch=True`）|

## 9. Checkpoint 保存、Resume Training、save_total_limit

### 9.1 Checkpoint 保存策略

```python
from transformers import TrainingArguments

args = TrainingArguments(
    output_dir="./qlora_checkpoint",
    save_strategy="steps",          # 按步数保存
    save_steps=200,                 # 每 200 步保存
    save_total_limit=3,             # 只保留最近 3 个 checkpoint（自动删旧）
    save_safetensors=True,          # 使用 safetensors 格式（安全、快速）
    save_only_model=False,          # 保存 optimizer/scheduler 以便 resume
)
```

### 9.2 Resume Training

```python
from transformers import Trainer

trainer = Trainer(
    model=model,
    args=training_args,
    train_dataset=train_dataset,
)

# 从最近 checkpoint 恢复
trainer.train(resume_from_checkpoint=True)
# 或指定 checkpoint
trainer.train(resume_from_checkpoint="./qlora_checkpoint/checkpoint-600")
```

**关键**：resume 需要 checkpoint 中包含 optimizer state 和 scheduler state，所以 `save_only_model=False`。

### 9.3 最佳实践

```
output_dir/
  ├── checkpoint-200/
  │   ├── adapter_model.safetensors   # LoRA 权重
  │   ├── optimizer.pt                # 优化器状态
  │   ├── scheduler.pt                # 学习率调度器状态
  │   ├── trainer_state.json          # 训练进度
  │   └── rng_state.pth               # 随机数状态（保证可复现）
  ├── checkpoint-400/
  └── checkpoint-600/
```

> **面试金句**："训练的最佳实践是 `save_total_limit=3` + `save_strategy=steps`。这样既能应对训练中断从容恢复，又不会吃光硬盘空间。"

## 10. DPO 为什么比 SFT 更吃显存

### 10.1 DPO 的核心计算

DPO loss 公式：

```
L_DPO = -E[log σ(β × (log π_θ(y_w|x) - log π_ref(y_w|x)
                      - log π_θ(y_l|x) + log π_ref(y_l|x)))]
```

需要**同时**计算：

1. **Policy model (π_θ)** forward: 对 chosen 和 rejected 各一次。
2. **Reference model (π_ref)** forward: 对 chosen 和 rejected 各一次。

**总计：4 次 forward pass**（SFT 只需 1 次）。

### 10.2 显存对比

| 阶段 | SFT (1样本) 显存 | DPO (1样本, 1对 chosen+rejected) 显存 |
|------|-----------------|--------------------------------------|
| Base Model (NF4) | ~4 GB | ~4 GB |
| LoRA Adapter | ~0.05 GB | ~0.05 GB |
| Policy Forward (×1) | ~8 GB 激活 | — |
| Policy Forward (×2: chosen+rejected) | — | ~16 GB 激活 |
| Reference Forward (×2) | — | ~16 GB 激活（+reference 权重 ~4GB） |
| Optimizer States | ~0.5 GB | ~0.5 GB |
| **总计** | **~12.5 GB** | **~32+ GB** |

**核心原因**：
1. DPO 每样本需要 4 次 forward，SFT 只需 1 次。
2. Reference model 虽然不更新，但仍需加载到显存中做前向。
3. Chosen + Rejected 两个 response 的 log-prob 都需要计算。

> **面试金句**："DPO 比 SFT 更吃显存的根本原因是需要同时加载 policy model 和 reference model 两个模型，且每个样本需要 4 次前向传播来分别计算 chosen 和 rejected 的对数概率。这导致激活值和模型副本的显存需求大幅增加。"

## 11. Reference Model 省显存的几种方法

### 11.1 方法一：Pre-compute Reference Log-probs（推荐）

训练前用 reference model 对所有数据做一次批量推理，算好 `log π_ref(y|x)` 存到磁盘：

```python
# 推理阶段（只需做一次）
for batch in dataloader:
    with torch.no_grad():
        ref_logps_chosen = compute_logprobs(reference_model, batch["chosen"])
        ref_logps_rejected = compute_logprobs(reference_model, batch["rejected"])
    # 存入 dataset
    batch["ref_logps_chosen"] = ref_logps_chosen.cpu()
    batch["ref_logps_rejected"] = ref_logps_rejected.cpu()

# 训练时从 dataset 读取即可，不需要 reference model
```

**优点**：训练时完全不需要加载 reference model，显存需求与 SFT 相同。
**缺点**：如果继续训练多轮/eval 的数据变了，需要重新 pre-compute。

### 11.2 方法二：CPU Offload

Reference model 放在 CPU，需要时临时搬运到 GPU：

```python
reference_model = reference_model.to("cpu")

# 训练 loop 中
with torch.no_grad():
    ref_output = reference_model.to("cuda")(input_ids).logits
    reference_model.to("cpu")  # 用完立即移回 CPU
```

**优点**：不用 pre-compute，灵活。
**缺点**：每次搬运有 PCIe 延迟，训练慢。

### 11.3 方法三：Reference Model 也用 4-bit

```python
from transformers import BitsAndBytesConfig

bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_compute_dtype=torch.bfloat16,
    bnb_4bit_quant_type="nf4",
)
reference_model = AutoModelForCausalLM.from_pretrained(
    "Qwen/Qwen3-8B",
    quantization_config=bnb_config,
)
```

### 11.4 方法四：LoRA Merge 后 Pruning

如果 reference model 只需要做 log-prob 计算（不需要生成），可以 merge LoRA 后只保留需要的层。

### 11.5 本项目采用的方法

结合方案一和方案三：reference model 使用 4-bit 加载，pre-compute 所有 reference log-probs 并存入数据集，训练时只加载 policy model。

## 12. QLoRA 显存构成

### 12.1 显存解剖

```
┌──────────────────────────────────────┐
│          RTX 5090 (32 GB)            │
├──────────────────────────────────────┤
│  Base Model (NF4)           ~4.0 GB  │  ← 8B 参数 × 0.5 bytes
│  + 反量化 overhead          ~0.5 GB  │  ← 计算时临时提升到 BF16
├──────────────────────────────────────┤
│  LoRA Adapter (BF16)       ~0.05 GB  │  ← r=16, α=32, 所有 attention 层
│  LoRA Optimizer States     ~0.10 GB  │  ← m+v, 8bit paged
├──────────────────────────────────────┤
│  Activations (SFT, bs=2)   ~12-15 GB │  ← 前向/反向中间激活
│  (with gradient ckpt)       ~6-8 GB  │  ← 开启后约减半
├──────────────────────────────────────┤
│  CUDA Context / 碎片       ~1-2 GB   │
├──────────────────────────────────────┤
│  总计 (SFT, bs=2, grad_ckpt) ~18 GB │
│  总计 (DPO, bs=1, grad_ckpt) ~26 GB │
└──────────────────────────────────────┘
```

### 12.2 各组成部分详解

| 组件 | 大小估算公式 | 本项目 | 备注 |
|------|------------|--------|------|
| Base Model (NF4) | params × 0.5 bytes | ~4 GB | QLoRA 核心节省 |
| LoRA Weights | r × 2 × d_model × num_target_layers × 2 | ~50 MB | 极小 |
| Optimizer States | 2 × lora_params × 1 byte (8bit) | ~100 MB | paged 可卸载 |
| Activations | 取决于 batch, seq_len, hidden_size | 6-15 GB | 可压缩 |
| Gradients | 同 LoRA params | ~50 MB | 只有 LoRA 有梯度 |

## 13. RTX 5090 单卡训练怎么讲（面试回答模板）

> **面试官**："你们在什么硬件上训练的？为什么用单卡？"

**回答框架**：

"我们使用一张 RTX 5090 (32GB) 完成全部训练。选择消费级显卡的原因是项目预算有限，但也恰好体现了 QLoRA 的魅力——让 8B 级别模型的训练在消费级硬件上成为可能。

训练配置：

- **SFT**：batch_size=2, grad_accum=8, effective_batch=16, max_seq_len=2048, QLoRA NF4 + BF16 计算。开启 gradient checkpointing 和 paged_adamw_8bit。显存峰值约 18GB，单 epoch 约 2-3 小时。

- **DPO**：batch_size=1, grad_accum=8, effective_batch=8。比 SFT 更吃显存，因为需要额外加载 reference model 做 log-prob 计算。我们预先计算了 reference log-probs 存入数据集，训练时不再加载 reference model，显存峰值约 22-24GB。

关键优化点：
1. NF4 4-bit 量化把 base model 从 16GB 压缩到 4GB。
2. Gradient checkpointing 让激活值显存减半。
3. Paged AdamW 8bit 优化器状态从 2×LoRA_params×4bytes 降到 2×LoRA_params×1byte，同时支持 CPU offload。
4. Pre-compute reference log-probs 消除 DPO 的 reference model 显存开销。
5. 过滤超长序列保证 max_seq_len=2048，控制 KV Cache 和激活值。

如果面试官问'为什么不加卡'，我会回答：单卡训练避免了分布式通信开销，代码更简单，调试更方便。8B 级别的 QLoRA 训练本身就是设计为单卡可跑的。"

## 15. Eval Double Base-Load 问题怎么避免

### 15.1 问题场景

```python
# 典型评估代码（有 bug）
base_model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen3-8B", load_in_4bit=True)
model_ckpt1 = PeftModel.from_pretrained(base_model, "./ckpt_epoch1")
eval(model_ckpt1)

# 加载第二个 checkpoint 时
base_model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen3-8B", load_in_4bit=True)
# ↑ 此时显存中有两份 base model！(旧的和新的)
model_ckpt2 = PeftModel.from_pretrained(base_model, "./ckpt_epoch2")
```

**根因**：Python GC 没有立即释放第一个 base_model，导致两份 4-bit 模型同时在显存中。

### 15.2 解决方案

```python
import gc
import torch

def safe_load_peft(base_name, ckpt_path):
    """安全加载 PEFT 模型，确保旧模型被释放"""
    # 清理上一个模型
    gc.collect()
    torch.cuda.empty_cache()
    torch.cuda.synchronize()

    base_model = AutoModelForCausalLM.from_pretrained(
        base_name,
        load_in_4bit=True,
        device_map="auto",
    )
    model = PeftModel.from_pretrained(base_model, ckpt_path)
    return model

# 或使用上下文管理器
class ModelLoader:
    def __init__(self):
        self.model = None

    def load(self, base_name, ckpt_path):
        self.unload()
        self.model = safe_load_peft(base_name, ckpt_path)

    def unload(self):
        if self.model is not None:
            del self.model
            gc.collect()
            torch.cuda.empty_cache()
```

**更推荐的做法**：用一个脚本跑一个 checkpoint 的评估，不同 checkpoint 用不同脚本实例，彻底隔离。

## 16. Rejected Generation Batch Inference 怎么优化

### 16.1 问题

DPO 需要 rejected responses。如果用 policy model 逐条生成 rejected response（batch_size=1），几千条数据可能需要数小时。

### 16.2 优化方案

**方案一：批量推理**：把数据分批（如 batch_size=16），一次性推理生成所有 rejected responses：

```python
from vllm import LLM, SamplingParams

# 批量推理 rejected responses
llm = LLM(model="./merged_qwen3_8b", dtype="bfloat16")

sampling_params = SamplingParams(
    temperature=0.8,        # 略高温度产生多样性
    top_p=0.95,
    max_tokens=512,
)

prompts = [item["prompt"] for item in dpo_dataset]
outputs = llm.generate(prompts, sampling_params)

for item, output in zip(dpo_dataset, outputs):
    item["rejected"] = output.outputs[0].text
```

**方案二：预先准备 5 个 candidate，挑最差的**: 每个 prompt 生成多个 responses，用 reward model 打分，选分数最低的作为 rejected。

```python
sampling_params.n = 5  # 每个 prompt 生成 5 个
outputs = llm.generate(prompts, sampling_params)
# 用 reward model / LLM-as-Judge 打分，选最佳为正例、最差为反例
```

**方案三：混合 rejected 来源**: 部分来自其他模型（如更小的模型），部分来自当前模型的高温度采样：

```python
rejected_sources = {
    "qwen3_4b_t08": "./rejected_from_smaller_model.json",
    "current_model_t09": "./rejected_from_current_model.json",
}
```

> **面试金句**："Rejected generation 的优化关键是批量推理——用 vLLM 等推理框架一次性跑完所有 prompts，比逐条生成快 10-50 倍。"

## 背诵版总结

### 核心概念速记

| 概念 | 一句话 |
|------|--------|
| Gradient Accumulation | 多次 forward/backward 再更新，时间换空间的等效大批次 |
| Mixed Precision (BF16) | 前向反向用半精度加速，master weight 用 FP32 保精度 |
| BF16 vs FP16 | BF16 指数位同 FP32，不用 loss scaling；FP16 需要 |
| Gradient Checkpointing | 不存中间激活，反向时重算，省 50-70% 显存 |
| Gradient Clipping | 梯度范数超过阈值时等比缩放，防梯度爆炸 |
| AdamW | Adam + 解耦 weight decay，正则化不受自适应 lr 影响 |
| Paged Optimizer | 优化器状态分页存在 CPU，需要时换入 GPU |
| ZeRO-3/FSDP | 模型/优化器/梯度全分片，每卡只存 1/N |
| QLoRA 显存构成 | Base(4GB NF4) + LoRA(50MB) + Optim(~100MB) + Activations(6-15GB) |
| DPO 多耗显存 | 需 reference model 前向 + chosen/rejected 各算 log-prob |

### 高频面试问答

**Q: 为什么用 QLoRA 而不是全参微调？**
A: 单卡 RTX 5090 32GB 无法承载 8B 模型的全参训练（需要 ~64GB+）。QLoRA 通过 NF4 量化 + 只训练 LoRA adapter，把显存需求降到 18GB 左右，让消费级显卡也能训练。

**Q: DPO 训练 OOM 了怎么处理？**
A: 首先 pre-compute reference log-probs 消除 reference model 加载；其次 batch_size=1 + gradient_checkpointing；如果还不够，减少 max_seq_len 或降低 LoRA rank。

**Q: gradient checkpointing 为什么能省显存？**
A: 因为反向传播需要的中间激活值不保存，而是在反向时重新计算一遍。相当于用 20-30% 的额外计算时间换取 50-70% 的显存节省。

**Q: BF16 和 FP16 训练哪个好？为什么？**
A: BF16 更好。它的 8-bit 指数位与 FP32 相同，动态范围更大，不容易梯度下溢，不需要 loss scaling，训练更稳定。FP16 需要精细调 loss scale，不稳定因素更多。

## 17. DDP (Distributed Data Parallel) 原理简述和代码示例

### 17.1 DDP 核心原理

```
DDP 将同一份模型复制到每张 GPU 上，每张 GPU 处理不同的数据子集：

GPU 0: model_replica + batch[0:N/G]  → forward → backward → all-reduce gradients
GPU 1: model_replica + batch[N/G:2N/G] → forward → backward → all-reduce gradients
GPU 2: model_replica + batch[2N/G:3N/G] → forward → backward → all-reduce gradients

All-Reduce: 所有 GPU 的梯度求平均 → 每张 GPU 得到相同的平均梯度 → 各自更新
```

**关键**：DDP 要求每张 GPU 都能完整放下模型 + 优化器状态 + 中间激活。所以对于大模型（>13B），单卡通常放不下。

### 17.2 DDP 代码示例

```python
import torch
import torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP
from torch.utils.data import DataLoader, DistributedSampler

# 1. 初始化分布式环境
dist.init_process_group(backend="nccl")  # NCCL 用于 GPU 通信
local_rank = int(os.environ["LOCAL_RANK"])
torch.cuda.set_device(local_rank)

# 2. 模型包装
model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen3-8B")
model = model.to(local_rank)
model = DDP(model, device_ids=[local_rank])

# 3. 数据分发（DistributedSampler 确保每张 GPU 拿到不重叠的数据）
sampler = DistributedSampler(dataset, shuffle=True)
dataloader = DataLoader(dataset, batch_size=4, sampler=sampler)

# 4. 训练循环
for epoch in range(epochs):
    sampler.set_epoch(epoch)  # 确保每 epoch 数据 shuffle 不同
    for batch in dataloader:
        outputs = model(batch["input_ids"].to(local_rank))
        loss = outputs.loss
        loss.backward()  # DDP 自动做 all-reduce 同步梯度
        optimizer.step()
        optimizer.zero_grad()

# 启动命令
# torchrun --nproc_per_node=4 train.py  # 4 卡 DDP
```

### 17.3 DDP 显存需求

```
每张 GPU 需要存储：
- 完整模型权重：16 GB (8B BF16)
- 完整优化器状态：32 GB (Adam m+v, FP32)
- 完整梯度：16 GB
- 中间激活：根据 batch_size，约 10-30 GB
------------------------------
总计：~74-94 GB (远超 RTX 5090 32GB)
```

**这就是为什么 QLoRA 是必要的**——全参 DDP 训练 8B 模型需要 A100 80GB 级别的显卡。

## 18. FSDP (Fully Sharded Data Parallel) 参数分片原理

### 18.1 FSDP 核心思想

FSDP 将模型参数、梯度、优化器状态**分片**到多张 GPU 上：

```
DDP (每张 GPU 有完整模型):
GPU0: [======== 完整模型 16GB ========] + [优化器 32GB] + [梯度 16GB]
GPU1: [======== 完整模型 16GB ========] + [优化器 32GB] + [梯度 16GB]

FSDP (每张 GPU 只存一部分模型):
GPU0: [模型 1/N] + [优化器 1/N] + [梯度 1/N]  ← 每卡 ~64/N GB
GPU1: [模型 1/N] + [优化器 1/N] + [梯度 1/N]
GPU2: [模型 1/N] + [优化器 1/N] + [梯度 1/N]
GPU3: [模型 1/N] + [优化器 1/N] + [梯度 1/N]
```

**工作流程**：
- 前向传播：需要某层权重时，all-gather 获取完整该层 → 计算 → 释放
- 反向传播：同理，all-gather → 计算梯度 → reduce-scatter 分片存储
- 优化器更新：每张 GPU 只更新自己负责的参数分片

### 18.2 FSDP 代码示例

```python
from torch.distributed.fsdp import (
    FullyShardedDataParallel as FSDP,
    MixedPrecision,
    ShardingStrategy,
)

# FSDP 配置
fsdp_config = {
    "sharding_strategy": ShardingStrategy.FULL_SHARD,  # ZeRO-3 级别全分片
    "mixed_precision": MixedPrecision(
        param_dtype=torch.bfloat16,
        reduce_dtype=torch.bfloat16,
        buffer_dtype=torch.bfloat16,
    ),
    "use_orig_params": True,  # 对 HF Trainer 兼容
}

model = FSDP(model, **fsdp_config)
```

### 18.3 FSDP vs DDP 显存对比

| 配置 | 每卡参数 | 每卡优化器 | 每卡梯度 | 总计/卡 |
|------|---------|-----------|---------|--------|
| DDP (1卡8B) | 16GB | 32GB | 16GB | ~64GB+ |
| FSDP (4卡8B) | 4GB | 8GB | 4GB | ~16GB+ |

> **面试金句**："FSDP 是 PyTorch 原生实现的 ZeRO-3，将模型/优化器/梯度全分片到所有 GPU 上，每张 GPU 的显存需求与 GPU 数量成反比。4 卡 FSDP 训练 8B 模型，每卡显存只需 ~16GB，RTX 5090 完全够用。"

## 20. DPO 显存构成的完整拆解

### 20.1 DPO 训练时显存详细分析

```
DPO 训练时 GPU 显存中的全部组件：

┌─────────────────────────────────────────────────────┐
│              DPO 显存构成 (bs=1)                      │
├─────────────────────────────────────────────────────┤
│ 1. Base Model (Policy, NF4)              ~4.0 GB    │
│    - 8B 参数 × 0.5 bytes (4-bit)                     │
│    - 反量化临时 overhead                 ~0.5 GB     │
├─────────────────────────────────────────────────────┤
│ 2. LoRA Adapter Weights (BF16)           ~0.05 GB   │
│    - r=16, α=32, target_modules=all_linears          │
├─────────────────────────────────────────────────────┤
│ 3. LoRA Gradients                        ~0.05 GB   │
│    - 只有 LoRA 参数有梯度                            │
├─────────────────────────────────────────────────────┤
│ 4. Optimizer States (Paged AdamW 8bit)   ~0.10 GB   │
│    - m + v, 每参数 1 byte (8-bit)                    │
│    - Paged 模式下可在 CPU/GPU 间分页                  │
├─────────────────────────────────────────────────────┤
│ 5. Activations (Policy Forward ×2)       ~8-12 GB   │
│    - Chosen response 一次前向                         │
│    - Rejected response 一次前向                       │
│    - 每次前向需要存中间激活供反向传播                  │
├─────────────────────────────────────────────────────┤
│ 6. Reference Model (如加载)              ~4.0 GB    │
│    - Reference forward ×2 (chosen + rejected)        │
│    - 如 pre-compute 则不需要                          │
├─────────────────────────────────────────────────────┤
│ 7. Reference Activations (如加载)        ~4-6 GB    │
│    - no_grad 模式，仅前向，激活不用于反向传播         │
│    - 但 vmap/flash_attention 仍占用临时显存           │
├─────────────────────────────────────────────────────┤
│ 8. CUDA Context / cuBLAS workspace       ~1-2 GB    │
├─────────────────────────────────────────────────────┤
│ 总计 (有 ref model 在线)                 ~21-29 GB  │
│ 总计 (pre-compute ref logprobs)          ~13-19 GB  │
└─────────────────────────────────────────────────────┘
```

### 20.2 最大显存消耗者的排名

1. **Policy Forward Activations**：8-12GB，最大头。chosen 和 rejected 各需要一次前向 + 反向传播。开启 gradient checkpointing 可减半到 4-6GB。
2. **Reference Model Weights**：4GB。如果 pre-compute 则完全消除。
3. **Reference Forward Activations**：4-6GB。如果 pre-compute 则完全消除。
4. **Base Model (NF4)**：4GB。这是 QLoRA 的核心优势，已经最小化了。

## 21. Reference Model 显存优化方法（完整版）

在原有"Pre-compute / CPU Offload / 4-bit"基础上补充：

### 21.4 方法四：使用更小的 Reference Model

```python
# 用一个 1.5B/0.5B 的小模型做 reference（牺牲精度换显存）
reference_model = AutoModelForCausalLM.from_pretrained(
    "Qwen/Qwen2.5-1.5B",  # 比 8B 小 5 倍
    load_in_4bit=True,
)
```

**优缺点**：显存从 4GB 降到 0.75GB，但 reference logprobs 的分布与 8B 模型不同，可能影响 DPO 优化质量。一般不建议，除非极端显存受限。

### 21.5 方法五：Layer-by-Layer Reference Computation

```python
# 逐层计算 reference logprobs，每层用完即释放
# 伪代码：
for layer_idx in range(num_layers):
    load_layer_to_gpu(reference_model, layer_idx)  # 只加载这一层
    compute_partial_logprobs(layer_idx)             # 计算部分 logprobs
    free_layer(reference_model, layer_idx)          # 立即释放
```

**优缺点**：显存降到 ~0.5GB/层，但实现复杂，推理速度极慢（与 disk I/O 相当）。不推荐，除非显存极度紧张且不能 pre-compute。

### 21.6 本项目的最终方案（推荐）

**三步组合**：
1. Pre-compute reference logprobs（训练前跑一次，存到数据集）
2. Reference model inference 时用 4-bit 加载（节省推理显存）
3. 训练时完全不加载 reference model（显存降到 SFT 级别）

```python
# 步骤1：Pre-compute（只需跑一次）
reference_model = AutoModelForCausalLM.from_pretrained(
    "Qwen/Qwen3-8B", load_in_4bit=True, device_map="auto"
)
for batch in tqdm(dataloader):
    with torch.no_grad():
        chosen_logps = compute_logprobs(reference_model, batch["chosen_input_ids"])
        rejected_logps = compute_logprobs(reference_model, batch["rejected_input_ids"])
    batch["ref_logps_chosen"] = chosen_logps.cpu()
    batch["ref_logps_rejected"] = rejected_logps.cpu()
# 保存 pre-computed dataset
torch.save(dataset_with_ref, "./dpo_dataset_with_ref.pt")

# 步骤2：训练时直接使用 pre-computed logprobs
# 不需要加载 reference model！
```

## 22. QLoRA 单卡训练扩展到多卡的方案

### 22.1 三种扩展路线

## 23. OOM 排查流程图（决策树文字版，增强版）

在原有 OOM 排查基础上补充更完整的决策树：

```
OOM 发生了什么？
├─ 推理时 OOM
│   ├─ 减小 max-model-len（控制 KV Cache 上限）
│   ├─ 减小 max-num-seqs（减少并发序列数）
│   ├─ 降低 gpu-memory-utilization（如 0.90 → 0.85）
│   └─ 检查是否加载了多余模型组件（如两份 reference model）
│
├─ SFT 训练时 OOM
│   ├─ forward 阶段 OOM → batch_size 或 seq_len 过大
│   │   ├─ 减 micro_batch_size（如 2→1）
│   │   ├─ 截断 max_seq_len（如 4096→2048）
│   │   └─ 过滤训练数据中的超长样本
│   │
│   ├─ backward 阶段 OOM → 激活值过大
│   │   ├─ 开启 gradient_checkpointing=True
│   │   ├─ 使用 flash_attention_2（如支持）
│   │   └─ 减小 batch_size（即使 forward 不 OOM，backward 也需要更多显存）
│   │
│   └─ optimizer.step() 时 OOM → 优化器状态过大
│       ├─ 换 paged_adamw_8bit
│       ├─ 减小 LoRA rank（减少可训练参数量）
│       └─ 开启 CPU offload（optimizer_offload=True）
│
├─ DPO 训练时 OOM
│   ├─ 第一步：pre-compute reference logprobs（消除 ref model 显存开销）
│   ├─ 第二步：micro_batch_size=1（最小化每步激活值）
│   ├─ 第三步：gradient_checkpointing=True
│   ├─ 第四步：max_seq_len 降低到 1536 或 1024
│   ├─ 第五步：reference model 用 4-bit + CPU offload（如果不能 pre-compute）
│   └─ 第六步：降低 LoRA rank（r=16→r=8）
│
└─ 如果 micro_batch_size=1 仍然 OOM
    ├─ 检查是否有两份模型在显存中（如 eval double-load 问题）
    ├─ 检查是否设置了多余的 torch.compile / fullgraph
    ├─ torch.cuda.empty_cache() + gc.collect() 彻底清理
    ├─ 设置 PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True 减少碎片
    └─ 最后的最后：换更小模型（8B→3B），或用更激进量化（NF4→INT4）
```

## 27. "单卡5090怎么训练8B"完整回答

> **面试官**："你们在单张 RTX 5090 上怎么训练 8B 模型的？"

**推荐回答**：

"我们通过四个层面的优化，让单张 32GB 显存的 RTX 5090 完成了 Qwen3-8B 的全流程训练：

**第一层：QLoRA 量化**。Base model 用 NF4 4-bit 量化，从 16GB 压缩到约 4GB。LoRA adapter（rank=16, alpha=32）参数仅约 50MB。这样模型权重 + LoRA + 优化器状态总计约 4.2GB，远小于全参训练的 64GB+。

**第二层：激活显存优化**。开启 gradient checkpointing，前向时不保存所有中间激活，反向时重新计算。激活显存从 12-15GB 降到 6-8GB。这是最有效的单卡显存优化手段。

**第三层：优化器优化**。使用 paged_adamw_8bit——优化器状态用 8-bit 存储（而非 FP32 的 4 bytes），同时支持分页换出到 CPU。LoRA 的优化器状态从 ~400MB 降到 ~100MB。

**第四层：DPO 专项优化**。DPO 最吃显存的是 reference model。我们采用 pre-compute 策略——训练前用 reference model 对所有数据算好 log-probs 存入数据集，训练时完全不加载 reference model。DPO 显存从 32GB+ 降到 ~22GB。

**最终效果**：SFT 显存峰值 ~18GB，DPO 显存峰值 ~22-24GB，均在 RTX 5090 的 32GB 内有余量。"

> **如果面试官追问**："那如果 batch_size=1 还 OOM 呢？"

**答**："我会继续缩小 max_seq_len（2048→1536→1024），过滤掉超长样本。极端情况下还可以降低 LoRA rank（16→8），减少可训练参数量和对应的激活值。如果这些都做了还 OOM，说明需要换更大的 GPU 或者用多卡 FSDP。"

## 背诵版总结（工程补充）

### 新增工程核心概念

- **DDP**：每卡完整模型副本，all-reduce 同步梯度。需要每卡能装下完整模型。
- **FSDP**：PyTorch 原生 ZeRO-3，参数/梯度/优化器全分片，每卡只存 1/N。
- **ZeRO-1/2/3**：分别分片优化器/优化器+梯度/全部，显存分别节省 4x/8x/Nx。
- **DPO 显存构成**：Policy Forward Activations（8-12GB）是最大头，Reference Model（4GB）第二。
- **Reference Model 最优方案**：Pre-compute logprobs + 4-bit 加载做一次推理 + 训练时不加载 ref model。
- **单卡到多卡路线**：QLoRA+DDP → LoRA+FSDP → Full FT+ZeRO-3，显存需求逐步降低但通信成本逐步增加。
- **8 卡扩展方向**：QLoRA→全参、batch 翻倍、seq_len 翻倍、并行实验。
- **Checkpoint 最佳实践**：save_strategy=steps, save_total_limit=3, save_safetensors=True, save_only_model=False(DPO 需要 optimizer state)。

### 加量版高频问答

**Q: DDP 和 FSDP 的核心区别？**
A: DDP 每张 GPU 存完整模型，显存需求是 N 倍单卡；FSDP 将模型分片到所有 GPU，每卡显存是 1/N。DDP 通信少速度快但只能训小模型，FSDP 通信多但能训大模型。

**Q: DPO 训练什么最吃显存？**
A: Policy 模型的 forward activations（chosen+rejected 各一次，8-12GB）是最大消耗者，其次是 reference model（4GB）。开启 gradient checkpointing 可以让激活减半，pre-compute ref logprobs 可以完全消除 ref model 开销。

**Q: 从单卡 QLoRA 到多卡全参微调怎么过渡？**
A: 分三步走——第一步保持 QLoRA 但用 DDP 多卡加速；第二步去掉 4-bit 量化，用 FSDP 分片 BF16 模型 + LoRA；第三步去掉 LoRA，用 ZeRO-3 做全参微调。每一步的显存需求和通信成本逐步增加，根据硬件条件选择。

**Q: 单卡 5090 训练 8B 的秘诀是什么？**
A: 四个关键——NF4 4-bit 量化压 model weights、gradient checkpointing 压 activations、paged_adamw_8bit 压 optimizer states、pre-compute ref logprobs 压 DPO overhead。四管齐下，32GB 显存刚好够用。
