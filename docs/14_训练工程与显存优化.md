### Q: Batch Size/Gradient Accumulation 的关系是什么？

```
Effective Batch Size = Micro Batch Size × Gradient Accumulation Steps
```

```
示例（本项目 SFT）:
micro_batch_size = 2      # 每次前向处理的样本数（受显存限制）
gradient_accumulation = 8  # 累积 8 个 micro batch 的梯度再做一次 optimizer step
effective_batch_size = 2 × 8 = 16  # 等效于一次性处理 16 个样本
```

**为什么需要梯度累积：** RTX 5090 只有 32GB 显存，无法一次放 16 条长序列样本同时前向。梯度累积让每一次 optimizer step 的"有效批次"变大，同时保持显存占用不变：

```
每个 micro batch: forward → 计算 loss → backward → 累加梯度到 .grad
每 gradient_accumulation steps: optimizer.step() → 更新权重 → optimizer.zero_grad()
```

**数学本质**：梯度累积等价于用更大的 batch size 计算平均梯度。

> **面试金句**："梯度累积是一种用时间换空间的技术——通过多次 forward/backward 再更新一次参数，在显存受限的情况下实现等效大批次训练，提升训练稳定性。"

**超参数选择建议：**

| 场景 | micro_batch_size | grad_accum | effective_bs |
|------|-----------------|------------|-------------|
| QLoRA SFT | 1-2 | 4-16 | 8-32 |
| 全参 SFT | 1 | 32-128 | 32-128 |
| DPO | 1 | 4-8 | 4-8 |
| 预训练 | 很大（GPU多） | 1 | 千万级tokens |

### Q: 混合精度训练 BF16/FP16 和 Loss Scaling 怎么理解？

训练时模型主体用半精度（BF16/FP16）计算加速和节省显存，但某些关键操作（如 loss 计算、某些归一化层）保持 FP32 精度：

```
权重存储: FP32 (master weights)
前向计算: BF16 (自动转换)
梯度累积: FP32 (精度保证)
优化器更新: FP32 → 转回 BF16
```

**BF16 vs FP16：**

| 特性 | FP16 | BF16 |
|------|------|------|
| 尾数位 | 10-bit | 7-bit |
| 指数位 | 5-bit | 8-bit |
| 动态范围 | [-65504, 65504] | ≈[-3.4e38, 3.4e38] |
| 溢出风险 | 高（需要 loss scaling） | 低（几乎不需要） |
| 硬件支持 | 广泛 | 需要 A100+ / RTX 30 系列+ |

**本项目用 BF16**，因为：RTX 5090 原生支持 BF16；不需要 loss scaling，训练更稳定；Qwen3 原始训练用 BF16，精度一致。

**Loss Scaling（FP16 场景需要）：** FP16 的指数位只有 5-bit，小梯度可能 underflow 到 0。

```python
scaler = torch.cuda.amp.GradScaler()
with torch.cuda.amp.autocast(dtype=torch.float16):
    loss = model(input)  # FP16 前向
scaler.scale(loss).backward()     # 放大梯度
scaler.step(optimizer)            # 更新（含 unscale）
scaler.update()                   # 动态调整 scale 因子
```

**BF16 不需要 loss scaling**：因为其 8-bit 指数与 FP32 相同，动态范围足够大。

> **面试金句**："BF16 通过牺牲尾数精度换取更大的指数范围，使得它拥有和 FP32 相同的动态范围，因此训练时几乎不需要 loss scaling 就能避免梯度下溢。这是 BF16 在 LLM 训练中比 FP16 更受欢迎的核心原因。"

### Q: Gradient Checkpointing 和 Gradient Clipping 是什么？

**Gradient Checkpointing（梯度检查点/重计算）：** 反向传播需要前向的中间激活值。全保存激活值显存开销巨大（对于 Qwen3-8B 可能超过 100GB）。解决方案：前向时不保存所有中间激活，反向时**重新计算**需要的部分。

```
无 checkpointing:
  x → Layer1 → a1 → Layer2 → a2 → Layer3 → a3 → loss
                     所有 a 都保存（显存爆炸）

gradient_checkpointing=True:
  反向时: a2 = Layer2(Layer1(x))  # 重新计算
```

**代价**：多一次前向计算（约 20-30% 额外计算时间），但显存节省 50-70%。QLoRA 场景下强烈建议开启。

```python
args = TrainingArguments(
    gradient_checkpointing=True,
    gradient_checkpointing_kwargs={"use_reentrant": False},
)
```

**Gradient Clipping（梯度裁剪）：** 防止梯度爆炸，将梯度的范数裁剪到指定阈值。

```python
args = TrainingArguments(max_grad_norm=1.0)  # 梯度 L2 范数超过 1.0 则等比缩放
```

公式：`if ||g|| > max_grad_norm: g = g × (max_grad_norm / ||g||)`。典型值：`max_grad_norm=1.0` 是通用安全值，QLoRA 训练常设 `0.3~1.0`。

### Q: Warmup/Cosine Scheduler/Weight Decay/AdamW 怎么配置？

**Learning Rate Warmup：** 训练初期学习率从 0 线性/余弦增长到目标学习率。

```
lr = target_lr × min(step / warmup_steps, 1.0)
```

为什么需要：随机初始化的模型/新初始化的 LoRA adapter 梯度方向不稳定；大学习率直接上会导致参数剧烈震荡；warmup 给优化器一个"探索"阶段。

```python
warmup_steps=100       # 或 warmup_ratio=0.03 (占总步数 3%)
lr_scheduler_type="cosine"
```

**Cosine Scheduler：** 学习率从 target_lr 余弦衰减到最小值。优势：初始阶段 lr 较高快速收敛，末期 lr 缓慢递减细致优化，比 step decay 更平滑。

**Weight Decay：** L2 正则化的实现方式（在 AdamW 中直接对权重施加衰减）。QLoRA 训练中通常只对 LoRA adapter 参数施加 weight decay。典型值 0.01。

**AdamW 优化器：** Adam + Decoupled Weight Decay。

```
m_t = β₁ × m_{t-1} + (1-β₁) × g_t          # 一阶矩（动量）
v_t = β₂ × v_{t-1} + (1-β₂) × g_t²         # 二阶矩（自适应学习率）
θ_t = θ_{t-1} - lr × (m̂_t / (√v̂_t + ε) + λ × θ_{t-1})
                                               ↑ weight decay 独立于梯度
```

> **面试金句**："AdamW 把 weight decay 从 Adam 的 L2 正则化中解耦出来，使 weight decay 不受自适应学习率缩放的影响，正则化效果更稳定。"

### Q: Paged Optimizer (QLoRA 中使用 paged_adamw_8bit) 是什么？

**问题：** QLoRA 中 base model 不更新（4bit），只有 LoRA adapter 需要更新。但优化器状态（Adam 的 m 和 v）也占用显存。当使用 8-bit 优化器状态时，如果 GPU 显存紧张，优化器状态可能触发 OOM。

**Paged Optimizer 原理：** 将优化器状态（m, v）**换出到 CPU 内存**，只在需要更新时才换入 GPU。

```
GPU 显存: 模型权重 + LoRA 参数 + 激活值 → GFX 算力
优化器状态 m, v → 不在 GPU！存在 CPU RAM

需要 optimizer.step() 时: CPU → PCIe → GPU: 搬运一页优化器状态 → 更新 → 写回
```

```python
import bitsandbytes as bnb
optimizer = bnb.optim.PagedAdamW8bit(model.parameters(), lr=2e-4, weight_decay=0.01)
# 或通过 TrainingArguments: optim="paged_adamw_8bit"
```

> **面试金句**："Paged Optimizer 和 PagedAttention 异曲同工——都用分页思想打破物理显存的连续分配限制。Paged Optimizer 把优化器状态卸载到 CPU，需要时自动分页换入。"

### Q: DeepSpeed ZeRO / FSDP / DDP 区别是什么？

**DDP (Distributed Data Parallel)：** 每张 GPU 持有一份完整模型副本，各自处理不同的数据。梯度通过 all-reduce 同步后各自更新。**问题**：每张 GPU 存完整模型 → 当模型很大时放不下。

**ZeRO-1**：优化器状态分片。每张 GPU 只存一部分优化器状态（m, v），更新时 all-gather 获取完整状态。显存节省 ~4x。

**ZeRO-2**：优化器状态 + 梯度分片。梯度也在每张 GPU 上分片存储，backward 时用 reduce-scatter 而非 all-reduce。显存节省 ~8x。

**ZeRO-3**：优化器状态 + 梯度 + 参数全分片。模型权重本身也被分片，前向/反向时需要时 all-gather。显存节省正比于 GPU 数量（N 张 GPU → 每张节省 N 倍）。**代价**：大量通信。

**FSDP (Fully Sharded Data Parallel)：** PyTorch 原生实现，类似 ZeRO-3 概念。

```python
from torch.distributed.fsdp import FullyShardedDataParallel as FSDP
model = FSDP(model, sharding_strategy="FULL_SHARD")
```

**本项目为什么不需要分布式：** RTX 5090 单卡，不需要分布式。如果面试官追问：

> "8B 模型在单卡上跑 QLoRA（base model 4-bit 只占 ~4GB，LoRA 参数很少，加上激活和优化器总共不超 28GB），单卡 32GB 足以容纳。分布式在本场景下引入 NVLink/PCIe 通信开销反而降低效率。"

### Q: OOM 怎么排查？

**系统化排查步骤：**

```python
# 步骤1: 查看显存快照
import torch
print(torch.cuda.memory_summary())

# 步骤2: 定位最大显存消耗者
torch.cuda.reset_peak_memory_stats()
outputs = model(**batch)  # forward
print(f"Peak after forward: {torch.cuda.max_memory_allocated() / 1e9:.2f} GB")
loss.backward()
print(f"Peak after backward: {torch.cuda.max_memory_allocated() / 1e9:.2f} GB")
optimizer.step()
print(f"Peak after optimizer: {torch.cuda.max_memory_allocated() / 1e9:.2f} GB")
```

**常见 OOM 原因及解决：**

| 原因 | 诊断信号 | 解决方案 |
|------|---------|---------|
| batch size 太大 | OOM 在 forward 阶段 | 减小 micro_batch_size |
| 序列太长 | 报错时有 max_seq_len 信息 | 截断/过滤长序列 |
| 激活值太大 | OOM 在 backward 阶段 | 开启 gradient_checkpointing |
| 优化器状态 | OOM 在 optimizer.step() | 用 paged_adamw_8bit |
| KV Cache 爆 | 推理 OOM | 减小 max_model_len |
| 显存碎片 | OOM 时 free 显存看似够 | 设置 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` |

**OOM 排查口诀：**

> "前向报错减 batch，后向报错开 ckpt，优化器报错换 paged，碎片报错改 alloc。DPO 先杀 ref model，减了 batch 再减 len，rank 降低是后手，都不行就换小模型。"

### Q: Loss NaN 怎么排查？

**NaN 来源：** 学习率过大 → 梯度爆炸 → 参数溢出 → NaN；数据中有 NaN/Inf → 传播到 loss；数值不稳定操作（如 log(0)）；FP16 溢出（BF16 很少）；attention mask 错误 → 对 padding 做 attention → NaN。

**排查步骤：**

```python
# 步骤1: 检查输入数据
for batch in dataloader:
    for k, v in batch.items():
        if torch.isnan(v).any() or torch.isinf(v).any():
            print(f"NaN/Inf in input: {k}")

# 步骤2: 检查中间激活
with torch.autograd.detect_anomaly():
    loss = model(**batch).loss
    loss.backward()  # 会在产生 NaN 的第一步报错并打印 trace

# 步骤3: 降低学习率重试
lr = current_lr / 10
```

**典型解决：**

| 现象 | 解决方案 |
|------|---------|
| loss 突然 NaN（训练中途） | 降 lr、增大 warmup、检查是否有异常样本 |
| loss 第一步 NaN | 检查数据、检查 chat template 是否正确 tokenize |
| loss 波动大后 NaN | gradient clipping 太小？增大 max_grad_norm |
| 确定某 batch 导致 NaN | skip 该 batch（设置 `skip_bad_batch=True`）|

### Q: Checkpoint 保存和 Resume 怎么做？

```python
from transformers import TrainingArguments

args = TrainingArguments(
    output_dir="./qlora_checkpoint",
    save_strategy="steps",          # 按步数保存
    save_steps=200,                 # 每 200 步保存
    save_total_limit=3,             # 只保留最近 3 个 checkpoint（自动删旧）
    save_safetensors=True,          # 使用 safetensors 格式（安全、快速）
    save_only_model=False,          # 保存 optimizer/scheduler 以便 resume
)
```

**Resume Training：**

```python
trainer.train(resume_from_checkpoint=True)
# 或指定 checkpoint
trainer.train(resume_from_checkpoint="./qlora_checkpoint/checkpoint-600")
```

**关键**：resume 需要 checkpoint 中包含 optimizer state 和 scheduler state，所以 `save_only_model=False`。

```
output_dir/
  ├── checkpoint-200/
  │   ├── adapter_model.safetensors   # LoRA 权重
  │   ├── optimizer.pt                # 优化器状态
  │   ├── scheduler.pt                # 学习率调度器状态
  │   ├── trainer_state.json          # 训练进度
  │   └── rng_state.pth               # 随机数状态（保证可复现）
```

> **面试金句**："训练的最佳实践是 `save_total_limit=3` + `save_strategy=steps`。这样既能应对训练中断从容恢复，又不会吃光硬盘空间。"

### Q: DPO 为什么比 SFT 更吃显存？

DPO loss 公式需要**同时**计算：
1. **Policy model (π_θ)** forward: 对 chosen 和 rejected 各一次
2. **Reference model (π_ref)** forward: 对 chosen 和 rejected 各一次

**总计：4 次 forward pass**（SFT 只需 1 次）。

**显存对比：**

| 阶段 | SFT (1样本) 显存 | DPO (1样本) 显存 |
|------|-----------------|--------------------------------------|
| Base Model (NF4) | ~4 GB | ~4 GB |
| Policy Forward | ~8 GB 激活 | ~16 GB 激活 (chosen+rejected) |
| Reference Forward | — | ~16 GB 激活（+reference 权重 ~4GB） |
| Optimizer States | ~0.5 GB | ~0.5 GB |
| **总计** | **~12.5 GB** | **~32+ GB** |

**核心原因：**
1. DPO 每样本需要 4 次 forward，SFT 只需 1 次
2. Reference model 虽然不更新，但仍需加载到显存中做前向
3. Chosen + Rejected 两个 response 的 log-prob 都需要计算

> **面试金句**："DPO 比 SFT 更吃显存的根本原因是需要同时加载 policy model 和 reference model 两个模型，且每个样本需要 4 次前向传播来分别计算 chosen 和 rejected 的对数概率。"

### Q: Reference Model 怎么省显存？

**方法一：Pre-compute Reference Log-probs（推荐）**

训练前用 reference model 对所有数据做一次批量推理，算好 `log π_ref(y|x)` 存到磁盘。

```python
# 推理阶段（只需做一次）
for batch in dataloader:
    with torch.no_grad():
        ref_logps_chosen = compute_logprobs(reference_model, batch["chosen"])
        ref_logps_rejected = compute_logprobs(reference_model, batch["rejected"])
    batch["ref_logps_chosen"] = ref_logps_chosen.cpu()
    batch["ref_logps_rejected"] = ref_logps_rejected.cpu()
```

优点：训练时完全不需要加载 reference model，显存需求与 SFT 相同。缺点：如果数据变了需要重新 pre-compute。

**方法二：CPU Offload**——Reference model 放在 CPU，需要时临时搬运到 GPU，用完立即移回。缺点：每次搬运有 PCIe 延迟，训练慢。

**方法三：Reference Model 也用 4-bit**——进一步压缩 reference model 显存。

**本项目采用的方法：** 结合方案一和方案三——reference model 使用 4-bit 加载，pre-compute 所有 reference log-probs 并存入数据集，训练时只加载 policy model。

### Q: QLoRA 的显存构成是怎样的？

```
┌──────────────────────────────────────┐
│          RTX 5090 (32 GB)            │
├──────────────────────────────────────┤
│  Base Model (NF4)           ~4.0 GB  │  ← 8B 参数 × 0.5 bytes

├──────────────────────────────────────┤
│  LoRA Adapter (BF16)       ~0.05 GB  │  ← r=16, α=32, 所有 attention 层

├──────────────────────────────────────┤

│  (with gradient ckpt)       ~6-8 GB  │  ← 开启后约减半
├──────────────────────────────────────┤
│  CUDA Context / 碎片       ~1-2 GB   │
├──────────────────────────────────────┤
│  总计 (SFT, bs=2, grad_ckpt) ~18 GB │
│  总计 (DPO, bs=1, grad_ckpt) ~26 GB │
└──────────────────────────────────────┘
```

### Q: RTX 5090 单卡训练怎么讲？

> **面试官**："你们在什么硬件上训练的？为什么用单卡？"

**回答框架：**

"我们使用一张 RTX 5090 (32GB) 完成全部训练。选择消费级显卡的原因是项目预算有限，但也恰好体现了 QLoRA 的魅力——让 8B 级别模型的训练在消费级硬件上成为可能。

训练配置：

- **SFT**：batch_size=2, grad_accum=8, effective_batch=16, max_seq_len=2048, QLoRA NF4 + BF16 计算。开启 gradient checkpointing 和 paged_adamw_8bit。显存峰值约 18GB，单 epoch 约 2-3 小时。

- **DPO**：batch_size=1, grad_accum=8, effective_batch=8。比 SFT 更吃显存，因为需要额外加载 reference model 做 log-prob 计算。我们预先计算了 reference log-probs 存入数据集，训练时不再加载 reference model，显存峰值约 22-24GB。

关键优化点：
1. NF4 4-bit 量化把 base model 从 16GB 压缩到 4GB
2. Gradient checkpointing 让激活值显存减半
3. Paged AdamW 8bit 优化器状态降低并支持 CPU offload
4. Pre-compute reference log-probs 消除 DPO 的 reference model 显存开销
5. 过滤超长序列保证 max_seq_len=2048

如果面试官问'为什么不加卡'，我会回答：单卡训练避免了分布式通信开销，代码更简单，调试更方便。8B 级别的 QLoRA 训练本身就是设计为单卡可跑的。"

### Q: DPO OOM 怎么解决？

**完整排查和解决路径：**

```
DPO OOM!
├─ 第一步：把 micro_batch_size 降到 1
├─ 第二步：开启 gradient_checkpointing
├─ 第三步：减少 max_seq_len（截断 prompt+response）
├─ 第四步：Pre-compute reference log-probs（消除 reference model）
├─ 第五步：reference model 用 4-bit + CPU offload
├─ 第六步：增大 grad_accum（补偿有效 batch size）
└─ 第七步：减少 LoRA rank (r=16 → r=8)，减少可训练参数量
```

**本项目实际采用的方案：**

```python
# DPO 训练配置
per_device_train_batch_size=1      # 最小 micro batch
gradient_accumulation_steps=8       # 累积补偿
max_seq_length=2048                 # 截断长度
gradient_checkpointing=True         # 激活重计算
optim="paged_adamw_8bit"            # 优化器省显存
bf16=True                           # 半精度
# Reference model: 训练前 pre-compute log-probs
```

### Q: Eval Double Base-Load 问题怎么避免？

**问题场景：**

```python
# 典型评估代码（有 bug）
base_model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen3-8B", load_in_4bit=True)
model_ckpt1 = PeftModel.from_pretrained(base_model, "./ckpt_epoch1")
eval(model_ckpt1)

# 加载第二个 checkpoint 时
base_model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen3-8B", load_in_4bit=True)
# ↑ 此时显存中有两份 base model！(旧的和新的)
```

**根因**：Python GC 没有立即释放第一个 base_model。

**解决方案：**

```python
import gc
import torch

def safe_load_peft(base_name, ckpt_path):
    gc.collect()
    torch.cuda.empty_cache()
    torch.cuda.synchronize()
    base_model = AutoModelForCausalLM.from_pretrained(base_name, load_in_4bit=True, device_map="auto")
    model = PeftModel.from_pretrained(base_model, ckpt_path)
    return model
```

### Q: Rejected Generation 批量推理怎么优化？

DPO 需要 rejected responses。如果用 policy model 逐条生成（batch_size=1），几千条数据可能需要数小时。

**方案一：批量推理**——把数据分批（如 batch_size=16），用 vLLM 一次性推理：

```python
from vllm import LLM, SamplingParams

llm = LLM(model="./merged_qwen3_8b", dtype="float16")
sampling_params = SamplingParams(temperature=0.8, top_p=0.95, max_tokens=512)

prompts = [item["prompt"] for item in dpo_dataset]
outputs = llm.generate(prompts, sampling_params)
```

**方案二：预先准备 5 个 candidate，挑最差的**——每个 prompt 生成多个 responses，用 reward model 打分，选分数最低的作为 rejected。

**方案三：混合 rejected 来源**——部分来自其他模型（如更小的模型），部分来自当前模型的高温度采样。

> **面试金句**："Rejected generation 的优化关键是批量推理——用 vLLM 等推理框架一次性跑完所有 prompts，比逐条生成快 10-50 倍。"

### Q: DDP (分布式数据并行) 的原理是什么？

```
DDP 将同一份模型复制到每张 GPU 上，每张 GPU 处理不同的数据子集：

GPU 0: model_replica + batch[0:N/G]  → forward → backward → all-reduce gradients
GPU 1: model_replica + batch[N/G:2N/G] → forward → backward → all-reduce gradients

All-Reduce: 所有 GPU 的梯度求平均 → 每张 GPU 得到相同的平均梯度 → 各自更新
```

**关键**：DDP 要求每张 GPU 都能完整放下模型 + 优化器状态 + 中间激活。所以对于大模型（>13B），单卡通常放不下。

**DDP 显存需求：** 每张 GPU 需要存储完整模型权重（16 GB 8B BF16）+ 完整优化器状态（32 GB Adam m+v）+ 完整梯度（16 GB）+ 中间激活（10-30 GB）= 总计 ~74-94 GB（远超 RTX 5090 32GB）。**这就是为什么 QLoRA 是必要的。**

---

### Q: FSDP 参数分片原理是什么？

FSDP 将模型参数、梯度、优化器状态**分片**到多张 GPU 上：

```
DDP (每张 GPU 有完整模型):
GPU0: [======== 完整模型 16GB ========] + [优化器 32GB] + [梯度 16GB]

FSDP (每张 GPU 只存一部分模型):
GPU0: [模型 1/N] + [优化器 1/N] + [梯度 1/N]  ← 每卡 ~64/N GB
```

工作流程：前向传播时 all-gather 获取完整该层 → 计算 → 释放；反向传播同理；优化器更新时每张 GPU 只更新自己负责的参数分片。

**FSDP vs DDP 显存对比：**

| 配置 | 每卡参数 | 每卡优化器 | 每卡梯度 | 总计/卡 |
|------|---------|-----------|---------|--------|
| DDP (1卡8B) | 16GB | 32GB | 16GB | ~64GB+ |
| FSDP (4卡8B) | 4GB | 8GB | 4GB | ~16GB+ |

> **面试金句**："FSDP 是 PyTorch 原生实现的 ZeRO-3，将模型/优化器/梯度全分片到所有 GPU 上，每张 GPU 的显存需求与 GPU 数量成反比。4 卡 FSDP 训练 8B 模型，每卡显存只需 ~16GB，RTX 5090 完全够用。"

### Q: DeepSpeed ZeRO-1/2/3 对比

| 特性 | ZeRO-1 | ZeRO-2 | ZeRO-3 |
|------|--------|--------|--------|
| **分片内容** | 仅优化器状态 | 优化器 + 梯度 | 优化器 + 梯度 + 参数 |
| **每卡显存节省** | ~4x | ~8x | Nx (N=GPU数) |
| **通信量** | 低 | 中 | 高 |
| **适用模型规模** | 10-30B | 30-100B | 100B+ |
| **训练速度** | 最快 | 较快 | 稍慢（通信开销） |

### Q: DPO 显存构成的完整拆解

```
DPO 训练时 GPU 显存中的全部组件：

1. Base Model (Policy, NF4)              ~4.0 GB    (8B 参数 × 0.5 bytes)
2. LoRA Adapter Weights (BF16)           ~0.05 GB   (r=16, α=32)
3. LoRA Gradients                        ~0.05 GB   (只有 LoRA 参数有梯度)
4. Optimizer States (Paged AdamW 8bit)   ~0.10 GB   (m + v, 8-bit)
5. Activations (Policy Forward ×2)       ~8-12 GB   (Chosen + Rejected)
6. Reference Model (如加载)              ~4.0 GB    (如 pre-compute 则不需要)
7. Reference Activations (如加载)        ~4-6 GB    (如 pre-compute 则不需要)
8. CUDA Context / cuBLAS workspace       ~1-2 GB

总计 (有 ref model 在线)                 ~21-29 GB
总计 (pre-compute ref logprobs)          ~13-19 GB
```

**最大显存消耗者排名：** Policy Forward Activations (8-12GB) > Reference Model Weights (4GB) > Reference Forward Activations (4-6GB) > Base Model NF4 (4GB)。

### Q: "单卡5090怎么训练8B"完整回答

> "我们通过四个层面的优化，让单张 32GB 显存的 RTX 5090 完成了 Qwen3-8B 的全流程训练：
>
> **第一层：QLoRA 量化**。Base model 用 NF4 4-bit 量化，从 16GB 压缩到约 4GB。LoRA adapter（rank=16, alpha=32）参数仅约 50MB。这样模型权重 + LoRA + 优化器状态总计约 4.2GB，远小于全参训练的 64GB+。
>
> **第二层：激活显存优化**。开启 gradient checkpointing，前向时不保存所有中间激活，反向时重新计算。激活显存从 12-15GB 降到 6-8GB。
>
> **第三层：优化器优化**。使用 paged_adamw_8bit——优化器状态用 8-bit 存储，同时支持分页换出到 CPU。LoRA 的优化器状态从 ~400MB 降到 ~100MB。
>
> **第四层：DPO 专项优化**。DPO 最吃显存的是 reference model。我们采用 pre-compute 策略——训练前用 reference model 对所有数据算好 log-probs 存入数据集，训练时完全不加载 reference model。DPO 显存从 32GB+ 降到 ~22GB。
>
> **最终效果**：SFT 显存峰值 ~18GB，DPO 显存峰值 ~22-24GB，均在 RTX 5090 的 32GB 内有余量。"

## 训练稳定性

### Q: 大模型训练中 loss spike 是什么？原因和应对？star:4

**Loss spike**：训练过程中 loss 突然飙升（从 ~0.5 跳变到几十甚至 NaN）。

**常见原因**：
1. **数据异常**：某条样本包含异常 token、过长序列或乱码
2. **学习率过大**：optimizer 跳过最优点进入发散区
3. **梯度爆炸**：某步梯度 norm 远超正常值（>100）
4. **混合精度溢出**：FP16 范围有限（±65504），大梯度值溢出 → 不用 FP16 改用 BF16（范围更大，±3.4e38）

**应对流程**：
1. 开启 gradient clipping（max_norm=1.0）
2. 检测到 loss spike → 跳过该 batch → 从上一个 checkpoint 恢复
3. 降低学习率（×0.1）重新训练
4. 检查 spike 前一步的输入数据是否有异常
5. BF16 替代 FP16——BF16 的指数位更多，不易溢出

**和项目结合**：我的 QLoRA 训练中未遇到 loss spike（使用 BF16 + gradient clipping + cosine scheduler），但 MiniMind 训练中验证过 loss NaN 排查流程。

### Q: 混合精度训练中 FP16 和 BF16 怎么选？star:3

| | FP16 | BF16 |
|---|------|------|
| 指数位 | 5 bit | 8 bit |
| 尾数位 | 10 bit | 7 bit |
| 数值范围 | ±65504 | ±3.4e38 |
| 精度 | 更高（尾数多） | 略低 |
| 溢出风险 | 高（范围小） | 低（范围大） |
| 适用场景 | 老GPU(V100) | 新GPU(A100/5090+) |

**为什么大模型训练几乎都用 BF16？** 范围大不容易溢出，不需要 loss scaling。大模型训练中梯度爆炸比精度损失更致命。BF16 的 7 位尾数在 LLM 场景下精度足够。

### Q: 梯度裁剪(gradient clipping)的作用是什么？star:2

限制梯度的最大 norm：$\text{if } \|g\| > c, \text{ then } g = g \cdot c / \|g\|$

防止单个 batch 的大梯度更新破坏训练稳定性。典型值 max_norm=1.0。不能解决数据质量或学习率问题——只是"安全阀"，不是"根本解"。

## 背诵版总结

### 核心概念速记

| 概念 | 一句话 |
|------|--------|
| Gradient Accumulation | 多次 forward/backward 再更新，时间换空间的等效大批次 |
| Mixed Precision (BF16) | 前向反向用半精度加速，master weight 用 FP32 保精度 |
| BF16 vs FP16 | BF16 指数位同 FP32，不用 loss scaling；FP16 需要 |
| Gradient Checkpointing | 不存中间激活，反向时重算，省 50-70% 显存 |
| Gradient Clipping | 梯度范数超过阈值时等比缩放，防梯度爆炸 |
| AdamW | Adam + 解耦 weight decay，正则化不受自适应 lr 影响 |
| Paged Optimizer | 优化器状态分页存在 CPU，需要时换入 GPU |
| ZeRO-3/FSDP | 模型/优化器/梯度全分片，每卡只存 1/N |
| QLoRA 显存 | Base(4GB NF4) + LoRA(50MB) + Optim(~100MB) + Activations(6-15GB) |
| DPO 多耗显存 | 需 reference model 前向 + chosen/rejected 各算 log-prob |

### 高频面试问答

**Q: 为什么用 QLoRA 而不是全参微调？**
A: 单卡 RTX 5090 32GB 无法承载 8B 模型的全参训练（需要 ~64GB+）。QLoRA 通过 NF4 量化 + 只训练 LoRA adapter，把显存需求降到 18GB 左右。

**Q: DPO 训练 OOM 了怎么处理？**
A: 首先 pre-compute reference log-probs 消除 reference model 加载；其次 batch_size=1 + gradient_checkpointing；如果还不够，减少 max_seq_len 或降低 LoRA rank。

**Q: gradient checkpointing 为什么能省显存？**
A: 因为反向传播需要的中间激活值不保存，而是在反向时重新计算一遍。相当于用 20-30% 的额外计算时间换取 50-70% 的显存节省。

**Q: BF16 和 FP16 训练哪个好？为什么？**
A: BF16 更好。它的 8-bit 指数位与 FP32 相同，动态范围更大，不容易梯度下溢，不需要 loss scaling，训练更稳定。

**Q: DDP 和 FSDP 的核心区别？**
A: DDP 每张 GPU 存完整模型，显存需求是 N 倍单卡；FSDP 将模型分片到所有 GPU，每卡显存是 1/N。DDP 通信少速度快但只能训小模型，FSDP 通信多但能训大模型。

**Q: 单卡 5090 训练 8B 的秘诀是什么？**
A: 四个关键——NF4 4-bit 量化压 model weights、gradient checkpointing 压 activations、paged_adamw_8bit 压 optimizer states、pre-compute ref logprobs 压 DPO overhead。四管齐下，32GB 显存刚好够用。
