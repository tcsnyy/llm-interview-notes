## 三、2分钟自我介绍模板

> 适用场景：面试官说"详细介绍一下你自己"

```
面试官您好，我叫[姓名]，[学校/专业]。我目前的研究方向是大模型后训练与安全对齐，有一个主项目和一个小辅助项目，想和您分享一下。

【主项目：医学 LLM Teacher】我做了一个完整的医学对话后训练项目。基座模型用的 Qwen3-8B——选择它是基于三点考量：GQA 推理效率高、中文能力 SOTA、硬件约束可控。

整个项目的 pipeline 分为五个阶段：

第一阶段是数据生成。我用 Qwen3-72B 作为 Teacher，构造了不同场景的 prompt 模板，生成 55K 条医疗 SFT 数据。数据质量控制包括：知识库交叉验证、去重、安全过滤和人工抽检 10%。

第二阶段是 SFT 训练。使用 QLoRA r=16/α=32，覆盖 attention 和 FFN 的所有线性层，在 2 张 4090 上训练 3 个 epoch。关键经验是 learning rate 从 2e-4 调到 5e-5 才使 loss 稳定收敛。

第三阶段是 DPO 偏好对齐。我从三个来源构造了 10K 偏好数据：同 prompt 不同 temperature 的采样对比、SFT 模型 vs Teacher 对比、以及 500 条人工标注。β=0.1 训练 1 epoch，reward accuracy 达到 0.78。

第四阶段是评测和分析。我用 Qwen3-72B 作为 LLM-as-Judge，设计了医学准确性、安全性、完整性三维度评测。和人工标注对标后，accuracy 维度 Spearman 达 0.78。但评测中我发现了一个重要现象——DPO 后模型在长尾医疗问题上出现了明显的幻觉：会编造不存在的临床数据和文献出处。我分析这是 reward hacking——DPO 的训练偏好使得模型在不确定时倾向于"自信编造"而非"诚实表达不确定性"。

第五阶段是 Safety-RAG 的提出和验证。我构建了包含 50 万条结构化知识的医疗知识库，在推理时检索 top-5 相关知识，用一个独立的 verifier 比对生成内容和检索知识是否一致，如果不一致就用检索知识修正。在 3 个典型幻觉案例上测试，全部修复。

最后用 vLLM 部署了 API 服务，单卡 4090 支持 10+ 并发。

【辅助项目：MiniMind】我从零训练了一个 26M 参数的小模型，自己实现了 GQA、RoPE、RMSNorm、SwiGLU 等架构组件，完整走完了 tokenizer 训练 → 预训练 → SFT → DPO 的全流程。这个项目让我真正理解了 LLM 的每个底层细节。

我现在申请的岗位是大模型后训练算法实习。我认为后训练的核心在于"如何用有限数据让模型学会人类偏好"——这涉及数据策略、训练方法选择、安全对齐和评测体系设计。我在项目中实践了这整个链路，期待在贵团队继续深入这个方向。
```

## 五、医学 LLM 项目 -- 3分钟版本

```
【背景和动机】
这个项目要构建一个能安全回答医疗问题的对话模型。核心约束是：不能让模型给出错误医疗建议，也不能编造不存在的医学信息。我们需要平衡"有用性"和"安全性"。

【数据阶段】
第一步是构造训练数据。我用 Qwen3-72B 作为 Teacher 模型，设计了涵盖问诊、检查解读、用药咨询、健康科普四类场景的 prompt 模板。为了保证数据多样性，我用了不同 temperature 采样和多 prompt 模板生成。最终收集了 55K 条数据，经过知识库交叉验证、语义去重、安全关键词过滤和 10% 人工抽检后入库。

【SFT 训练】
训练阶段用 QLoRA，rank=16，alpha=32。之所以不用全量微调，是因为 8B 模型的全量微调需要约 192GB 显存，而我们的硬件是 2 张 4090（共 48GB）。QLoRA 把基座量化到 4bit NF4，只训练 1% 的参数，加上双重量化和分页优化器，总显存约 12GB。训练 3 个 epoch，learning rate 5e-5 cosine schedule，effective batch size 16。

【DPO 训练与关键发现】
SFT 之后，我做了 DPO 偏好对齐。10K 偏好数据来自三路：多采样对比、模型 vs teacher 对比、人工标注 500 条高风险场景。β=0.1 训练 1 个 epoch。

训练完后用 LLM-as-Judge 评测——我设计了三维度（准确性/安全性/完整性），用 Qwen3-72B 做 judge。发现一个有意思的现象：DPO 后模型在常见问题上表现更好，但在医疗长尾问题上出现了新的幻觉——模型会编造具体的文献出处、临床试验数据来让回答显得更专业。比如问"某抗生素对某菌的效果"，模型会编造"一项三期临床招募 2347 例患者，有效率达 87.3%"，但其实这个临床试验根本不存在。

【Safety-RAG 设计】
我分析了这个现象的原因：DPO 的 reward 信号倾向于"确定自信"的回答风格——chosen 回答通常比 rejected 更完整、更确定。模型学会了：在不确定时，与其说"我不确定"可能被标为 rejected，不如编造一个看似专业的回答更像 chosen。这是典型的 reward hacking。

为了解决这个问题，我设计了 Safety-RAG——一个带验证层的 RAG 系统。核心改动是：不光检索知识然后让模型生成，而是先生成、再验证、必要时修正。具体来说：1）构建了 50 万条医疗知识库，用 bge-large-zh-v1.5 向量化；2）推理时检索 top-5；3）一个专门的 verifier 比对生成内容和检索知识的事实一致性；4）如果不一致，以检索知识为准生成修正后的回答。

【效果与部署】
在 3 个 DPO 后出现的典型幻觉案例上，Safety-RAG 全部修复。虽然 3 个案例样本量太少不能做统计显著性检验，但至少验证了 Safety-RAG 的有效性方向。最后用 vLLM 部署了 API 服务，支持 10+ 并发请求。

【Reflection】
这个项目如果重新做，我会：1）扩大安全评测的样本量；2）DPO 后做一轮 iterative DPO 验证；3）引入专业的医学 reranker 替代简单向量检索。目前整体完成度约 80%——研究探索 + 工程落地的组合。
```

## 六、医学 LLM 项目 -- 5分钟版本（扩展内容）

> 在 3 分钟版本基础上扩展以下内容：

### 补充 1：Teacher 数据生成的更多细节

```
在 Teacher 数据生成阶段，核心问题是"如何让 Teacher 生成既正确又多样化的医疗数据"。

正确性方面：设计了"生成-检索-验证"循环——Teacher 生成一条问答后，自动检索知识库中最相关的片段，与生成内容做语义相似度比对。如果一致性低于阈值（0.7），这条数据被标记为低质量并重新生成或丢弃。

多样性方面：用了 4 种策略——1）不同 temperature（0.1/0.5/0.9）生成不同风格的 response；2）多 prompt 模板轮换（20+ 种变体）；3）场景配额控制——四类场景各占约 25%；4）按疾病大类采样（呼吸/消化/心血管等 12 大类）。

最终从约 85K 原始生成中筛选出 55K 高质量数据，过滤率约 27%。
```

### 补充 2：DPO 数据构造的更多细节

```
DPO 数据的核心挑战是保证 chosen/rejected pair 的"subtle but meaningful"——差异太明显学不到细粒度偏好，差异太模糊没有信号。

策略是做一条"梯度"：对于每个 prompt，用 temperature=0.1/0.5/0.9 采样 3 个 response，让 LLM-as-Judge 打分。通常 t=0.1 最安全但最保守，t=0.9 最丰富但可能出错。把 t=0.1 和 t=0.9 的输出比较，如果两者分数差在 1-2 分（5 分制），就是一组好 pair。如果分数差太大（>3 分），说明 t=0.9 的答案有明显错误，pair 太简单，舍弃。

加上人工标注的 500 条高风险 case，最终 10K DPO 数据。
```

### 补充 3：安全评测体系的更多细节

```
评测体系从三个层面设计：

1）自动评测（LLM-as-Judge）：准确性(40%) + 安全性(35%) + 完整性(25%)，Qwen3-72B 打分。和 200 条人工标注对标，accuracy 维度 Spearman 0.78，safety 维度 0.62——说明 LLM 对安全性的判断还不够可靠。

2）安全 benchmark 测试：用 DangerousQA 测试违规回答率，补充 adversarial 场景。

3）人工抽检：每周随机抽 50 条输出，标注安全等级和是否有幻觉。

特别关注了"安全 vs 有用性"的 trade-off。benign query 拒答率控制在 5% 以下，adversarial query 拒答率 90% 以上。
```

### 补充 4：Safety-RAG 设计的思考过程

```
Safety-RAG 的设计经过了几次迭代：

v1：简单在 prompt 里拼接检索结果 → 模型有时忽略检索结果，仍按照自己的"记忆"编造内容。
v2：加了一个"先检索再生成"的硬约束 prompt → 模型会关注检索结果了，但检索到的知识也可能是错的或不完整的。
v3（最终版）：三步闭环——检索 → 生成 → 验证 → （如需要）修正。Verifier 不是简单的文本比对，而是用微调过的 Qwen3-8B 做医疗事实 NLI 任务。Verifier 的训练数据是 5K 条人工标注的（query, response, knowledge, label）四元组。

这个设计真正实现了知识库和模型的双向校验——不盲目信任任何一方。
```

## 九、面试官追问"项目最大难点"回答

```
这个项目最大的难点不是某个技术点的实现，而是一个"发现问题"的过程。

DPO 训练完之后，如果只看 loss 和 reward accuracy 曲线——一切似乎很好。但当我做深度 case study 时，发现了一个在表面指标上看不到的问题：模型在回答"某抗生素对某菌的耐药率"时，居然编造了具体的临床数据、文献引用和作者名字。

这个发现的难点在于：1）它不在常规评测指标（loss/reward accuracy）的监测范围内；2）它只在长尾医疗问题中出现，不是普遍现象；3）需要医学领域知识才能识别出模型在编造。

分析原因后发现这是一个深层的算法问题——DPO 的 implicit reward 模型学会了偏好"确定自信"的回答风格，而"诚实表达不确定性"被隐式地 penalized。这是 reward hacking 在医疗场景的具体体现。

解决这个问题的 Safety-RAG 方案虽然技术实现不难，但"找到问题"和"分析原因"的过程才是真正的难点——它需要跨领域的判断力（算法 + 医疗），以及对训练 dynamics 的深入理解。
```

## 十、面试官追问"项目创新点"回答

```
我认为这个项目的创新点分为两层：

第一层是技术方案层面的创新——Safety-RAG 的"验证-修正闭环"。标准 RAG 是检索后直接拼接生成，而我们的 Safety-RAG 多了验证层：用 verifier 对生成内容和检索知识做事实一致性检查，不一致就修正。这个设计解决了标准 RAG 的两个盲点：1）检索到的知识可能不相关或不完整；2）模型可能忽略检索结果而依赖自己的"记忆"。

第二层是方法论层面的创新——"从发现问题到解决问题"的完整算法思维链。DPO 训练后用常规指标看着很好，但我通过深度 case study 发现了幻觉问题，分析了 reward hacking 的机制，提出了 Safety-RAG 方案，并做了实验验证。这个"观察 → 假设 → 方案 → 验证"的闭环是我认为最有价值的。

诚实地说：Safety-RAG 作为一种"检索验证"思路并非全新发明——它站在了 RAG 和 RLHF safety 两条线的交叉点上。我的贡献是在医疗这个垂直场景中，识别出了"DPO 后幻觉增加"的具体问题，并将验证机制设计为一个完整的闭环系统。
```

## 十一、面试官追问"项目不足"回答

```
这个项目有几个明确的不足：

第一，评测样本量不足。Safety-RAG 的效果只在 3 个典型幻觉案例上验证了，样本量太小，不能做统计显著性检验。如果重新做，我会设计一个包含 100+ 条样本的系统性评测集。

第二，没有真实用户反馈闭环。这是一个研究探索项目，没有线上部署和真实用户的 feedback。vLLM 的 API 是可用的，但缺少用户侧的数据来验证模型在实际场景中的表现。

第三，知识库覆盖不全面。50 万条知识主要覆盖常见疾病和药物，对于罕见病、新药、前沿疗法覆盖不足。

第四，Safety-RAG 增加了推理延迟。检索+验证+可能的重新生成，总共增加了约 500ms 的延迟。

第五，没有做消融实验来严格证明 Safety-RAG 各组件各自的贡献。

我认为认识不足和正视不足本身也是能力的一部分，这些不足也意味着明确的改进方向。
```

```
我认为我适合后训练算法实习是因为三方面的匹配：

第一，我有完整的后训练实践经历。不是只做过 SFT 或只做过 DPO，而是走通了 data → SFT → DPO → evaluation → safety → deployment 全流程。我可以快速上手团队的 training pipeline。

## 十八、医学项目工程落地 -- 3分钟讲法

```
【训练与 Merge】
训练完成后，把 QLoRA adapter 合并到基座模型。Merge 的公式是 W' = W + (α/r) × BA，merge 后就是一个独立的完整模型，可以直接用 vLLM 加载，不需要额外推理开销。Merge 脚本用 PEFT 的 merge_and_unload() 方法，合并后模型大小从 4bit 恢复到 bf16（约 16GB）。

【vLLM 部署与压测】
部署选择了 vLLM——PagedAttention 和 Continuous Batching 在并发场景下吞吐优势明显。启动参数：max-model-len=4096, gpu-memory-utilization=0.9, dtype=bfloat16, max-num-seqs=32。硬件 RTX 5090 32GB——模型 bf16 占约 16GB，KV cache 按 4096 context + 32 并发估算约 10-12GB，总计 26-28GB，刚好在 32GB 显存内。

压测用 Python asyncio + OpenAI client 模拟并发请求，从 1 并发逐步增加到 64 并发。关键发现：32 并发前 TTFT 稳定在 40-50ms，吞吐线性增长到 877 tok/s；超过 32 并发后 TTFT 开始显著上升（排队效应），这是系统的饱和点。单用户场景 TTFT 42ms、TPOT ~15ms，用户体验流畅。

【RAG 延迟拆解与优化】
端到端 RAG pipeline 延迟拆解：query embedding ~8ms → FAISS 向量检索 ~30ms → prompt构建 ~1ms → vLLM prefill ~50ms → vLLM decode（avg 100 tokens）~1.5s → Safety-RAG verifier ~300ms。总延迟约 1.9s。Generation 是最大头（~80%），verifier 次之（~15%）。

优化思路：1）generation 用 streaming，TTFT 后用户立即看到 token；2）verifier 做动态路由——简单/低风险问题走 light-RAG 省去 verifier，预计平均延迟降低 20-40%；3）多路召回用 asyncio.gather 并行化，延迟取 max 而非 sum。

【缓存和容灾设计（设计方案，未实施）】
对生产级 RAG 的工程设计有完整方案：四层缓存体系（query/embedding/retrieval/rerank cache），用 Redis 做缓存存储；动态路由规则引擎区分急症/用药/常识三类场景；Nginx 反向代理 + 多 vLLM 副本做负载均衡；Prometheus + Grafana 监控；熔断降级策略。

虽然没有真实的线上环境，但我完成了从训练到部署到压测到优化的完整工程链路，并且对生产级系统需要什么（监控/灰度/容灾/缓存/路由）有清晰的理解和方案设计。
```

## 二十、"你有并行训练经验吗"回答模板

> 关键原则：诚实承认只有单卡 QLoRA 实践，但展示对分布式训练原理的理解

```
我的训练实践是基于单卡/双卡 QLoRA 完成的——医学 LLM 项目的 SFT 和 DPO 都在 2×4090 上使用 QLoRA 训练，不需要多机多卡的分布式训练。但我对分布式训练的原理和工具链有系统性的学习。

DDP (DistributedDataParallel)：每个 GPU 有完整模型副本，处理不同 micro-batch，backward 时自动触发 all-reduce 同步梯度。适用于模型能放进单卡显存的场景。

FSDP (Fully Sharded Data Parallel)：参数分片到各 GPU，前向/反向时按需 gather，省大量显存。和 DeepSpeed ZeRO-3 原理类似。

DeepSpeed ZeRO 三阶段：ZeRO-1 分片优化器状态，ZeRO-2 加上梯度分片，ZeRO-3 加上参数分片。ZeRO-3 理论上显存降到 1/N。

我的现状是：小型实验用 QLoRA 单/双卡完全够用（QLoRA 只占 ~13GB 显存），所以没有机会实践真正的分布式训练。但如果需要做全量微调或更大规模模型（如 70B），我理解需要 ZeRO-3/FSDP + 多机多卡，并且我有足够的原理基础可以快速上手。
