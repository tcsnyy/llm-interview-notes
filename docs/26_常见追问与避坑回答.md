## 追问 1：你是不是只是调用 API 生成数据？

### 不好的回答
"是的，我用 Qwen3-72B 的 API 生成了数据，然后拿去训练。" —— 这会让面试官觉得你只做了数据处理，没有算法设计。

### 推荐回答
"我用 Teacher 模型生成数据只是数据管线的第一步。同样重要的是后续的多个质量控制环节：第一，我设计了生成策略——不只是简单调用 API，而是设计了 20+ 种 prompt 模板覆盖不同医学场景，用不同 temperature 采样控制多样性，设定了场景配额防止数据偏斜。第二，构造了数据质量过滤管线：用医学知识库做交叉验证（生成内容与知识库的事实一致性 check）、语义去重（MinHash + embedding similarity>0.95）、安全关键词过滤（正则表达式检测处方建议/诊断声明）。第三，DPO 偏好数据的构造——多采样后用 LLM-as-Judge 排序选取 subtle 差异的 pair，加上 500 条人工标注保证质量。从 80K 原始生成到 58K 入训练集，过滤了约 27% 的低质量数据。数据工程本身就是后训练的核心——数据的质量直接决定了模型的上限。"

### 为什么推荐这样答
- 展示了数据工程的系统性思维（不是一次生成就完事）
- 量化了过滤比例（27%），证明不是全量使用
- 强调了数据质量控制的具体方法

### 可以顺带引出的技术点
- 数据质量评估指标
- Teacher-Student 的数据分布 shift
- 合成数据的局限性和缓解策略

## 追问 2：你这个项目算法性在哪里？

### 不好的回答
"我用了 DPO 算法训练模型，这是前沿算法。" —— 太笼统，看不出你的思考。

### 推荐回答
"我认为这个项目有三个方面体现了算法能力：

第一，对 DPO 后幻觉问题的因果分析。DPO 的 loss 函数决定了什么模式会被奖励——我分析了 DPO gradient 中 (1-σ(...)) 这个误差加权项，发现当模型在不确定场景下选择'编造自信答案'比'诚实表达不确定'获得更高 implicit reward 时，这个梯度方向就会持续强化编造行为。这是从数学公式到实验现象的完整分析链。

第二，Safety-RAG 的验证-修正设计。标准 RAG 是检索→拼接→生成（单向），我是检索→生成→验证→修正（闭环）。这个闭环的设计逻辑是：不信任检索也不信任生成——让两者互相校验。Verifier 本质上是一个领域微调的 NLI 模型，训练数据的构造需要精心设计（如何区分'不一致'和'补充信息'）。

第三，整个项目的决策链上有多个需要算法判断的选择点——DPO β 的 grid search（{0.01, 0.05, 0.1, 0.5, 1.0}）不是随便试的，是基于 KL 约束强度和过拟合风险的预判；QLoRA r 选 16 不是默认值，是基于 8B 模型容量和微调需求的分析；SFT lr 从 2e-4 调到 5e-5 是基于 loss 震荡的诊断。每个选择背后都有算法层面的理由。"

### 为什么推荐这样答
- 将"算法"定义为分析+设计+决策，而非只是"用别人的算法"
- 给出了三个具体例子，每个都有技术深度
- 展示了从公式到现象的推理能力

### 可以顺带引出的技术点
- DPO gradient 分析
- NLI 任务与 Safety 的关系
- 超参数搜索策略

## 追问 3：你是否真正理解 DPO？

### 不好的回答
"DPO 就是直接优化偏好的方法，用一个 loss 替代 PPO 的两阶段训练。" —— 太表面，没有数学理解。

### 推荐回答
"我理解的 DPO 可以从三个层次来回答：

第一层是数学推导。DPO 的起点是 Bradley-Terry 偏好模型：P(y_w ≻ y_l) = σ(r(y_w) - r(y_l))。RLHF 通常分两步——先训练 r_φ，再优化 policy π_θ 最大化 r_φ 同时加 KL 约束。DPO 的关键 insight 是：这个约束优化问题有闭式解——最优 policy π* 满足 r(x,y) = β log(π*(y|x)/π_ref(y|x)) + β log Z(x)。把这个闭式解代入 BT 模型，reward 就被消掉了，得到只依赖 π_θ 和 π_ref 的 loss。

第二层是训练 dynamics。DPO 的梯度形式是 ∇_θ L = -β E[(1-σ(β * margin)) * (∇_θ log π_θ(y_w) - ∇_θ log π_θ(y_l))]。这个加权因子 (1-σ(...)) 的含义是：当模型已经能很好地区分 chosen 和 rejected（margin 大 → σ→1 → 权重→0），梯度就小；当模型区分得不好（margin 小或负），梯度就大。这个自适应加权是 DPO 能有效学习的原因。

第三层是实际训练中的现象理解。reward accuracy 虚高但生成质量下降——说明模型在'过拟合'偏好信号但没有真正提升能力。β 太小导致 over-optimization——模型太激进地偏离 ref。这些现象都可以从 DPO 的数学公式中得到解释。"

### 为什么推荐这样答
- 分三层递进（公式→动态→现象），展示理解的深度
- 能推导关键公式
- 能联系实际训练现象

### 可以顺带引出的技术点
- BT 模型的统计基础
- KL 约束在 alignment 中的作用
- Reward over-optimization 的根本原因

## 追问 4：你是否手写过 DPO loss？

### 不好的回答
"我用 TRL 库的 DPOTrainer 训练的。" —— 没有展示代码能力。

### 推荐回答
"是的，我可以用 PyTorch 从零写 DPO loss。核心是：
```python
def dpo_loss(policy_chosen_logps, policy_rejected_logps,
             ref_chosen_logps, ref_rejected_logps, beta=0.1):
    pi_lograt = policy_chosen_logps - policy_rejected_logps
    ref_lograt = ref_chosen_logps - ref_rejected_logps
    logits = pi_lograt - ref_lograt
    loss = -F.logsigmoid(beta * logits).mean()
    return loss
```

我用 TRL 库是为了工程效率——它处理好了分布式训练、gradient checkpointing、logging 等工程细节。但我理解每个细节：logps 是 token-level log probability 的 sum（不是 average——因为 DPO 公式本身的 sum 形式）；chosen 和 rejected 的 logps 计算时都需要用 full context；reference model 的 logps 只需要算一次（frozen model），可以在训练前 precompute 以加速训练。

如果需要，我可以手写完整的 DPO 训练循环——包括数据加载、前向传播、loss 计算、梯度累积、logging。"

### 为什么推荐这样答
- 展示了从零实现的能力
- 解释了为什么用库（效率）+ 你知道库在做什么（理解）
- 提到了实际训练的关键细节（precompute ref logps）

### 可以顺带引出的技术点
- Token-level vs sequence-level loss
- DPO 中的 logp 计算的注意事项
- TRL/DeepSpeed 的工程实现

## 追问 5：为什么不用 PPO/GRPO/OPD？

### 不好的回答
"DPO 比 PPO 简单，效果差不多。" —— 没有经过思考的判断。

### 推荐回答
"这个选择是经过 trade-off 分析的，不是默认选 DPO。

PPO 的优势是 on-policy 训练——每步用当前策略采样，分布偏移小；可以多轮迭代；灵活度更高。但代价是：需要同时维护 policy、reference、reward、value 四个模型（8B×4=32GB 显存在量化后），训练包含多个 loss 项需要精细调参（KL coefficient、clip range、GAE lambda），工程复杂度高。在我们的 2×4090 和项目时间限制下，PPO 的投入产出比不如 DPO。

GRPO 去掉了 value model——这是一个很大进步（DeepSeek-R1 验证了有效性）。但 GRPO 仍然需要 reward model 和 group sampling（每个 prompt 采样 4-8 个 response），在我们的 10K 数据规模下 cost 仍然高。

OPD 在 DPO 基础上加入了 on-policy sampling——确实能缩小分布偏移。但每轮需要重新采样和标注，总成本是 DPO 的 3-5 倍。

所以 DP 在我们的约束（10K 数据、2×4090、有限项目时间）下是最优选择。如果资源和数据规模更大，我的升级路径是：Iterative DPO → OPD → GRPO，逐步增加 on-policy 成分。

总结：不是 DPO 绝对好，而是 DP 在给定约束下性价比最高——这是一个工程决策而非算法信仰。"

### 为什么推荐这样答
- 展示了 multiple trade-off 的分析
- 给了升级路径（不是停滞在当前方案）
- 把选择定位于"工程决策"而非"某个方法一定更好"

### 可以顺带引出的技术点
- On-policy vs Off-policy 的分布偏移问题
- 各种 RL 方法的模型数量对比
- Alignment tax 的概念

## 追问 6：为什么不用纯 RAG/纯 SFT？

### 不好的回答
"纯 RAG 效果不好，纯 SFT 有幻觉。" —— 太笼统。

### 推荐回答
"纯 RAG 的问题：naive RAG 只做检索→拼接→生成，没有验证机制。它假设检索到的知识是正确的、相关的、完整的——但实践中这三种假设都可能被违反。而且 RAG 不改变模型的行为模式——格式、语气、安全边界的建立需要 SFT/DPO。

纯 SFT 的问题：SFT 只最大化正样本概率，不对负样本做任何处理。模型学会了'说什么'但不知道'不要说什么'。医学场景中有大量需要'拒绝回答'或'表达不确定'的情况，这些行为需要通过偏好学习（DPO）来建立。另外 SFT 后的知识存在于模型参数中，无法更新——而医学知识是不断更新的。

我们的方案是 SFT + DPO + Safety-RAG 三合一：SFT 建立基础对话能力，DPO 建立安全偏好，Safety-RAG 提供外部知识验证。三者互补——SFT/DPO 负责'怎么说话'，Safety-RAG 负责'说的内容对不对'。"

### 为什么推荐这样答
- 分析了每种方法的根本局限
- 解释了三者如何互补
- 展示了系统设计思维

### 可以顺带引出的技术点
- SFT 与 RLHF 的互补关系
- RAG 与 Fine-tuning 在不同场景的选择
- 知识更新与模型 retraining 的 trade-off

## 追问 8：LLM-as-Judge 不可靠怎么办？

### 不好的回答
"LLM-as-Judge 现在已经很成熟了，GPT-4 做 judge 准确率很高。" —— 回避了问题。

### 推荐回答
"LLM-as-Judge 确实不可靠——这是公开的 research problem。我采取的缓解策略是：

第一，多 judge 交叉验证。我对比了 Qwen3-72B、GPT-4、Claude-3 三个 judge 在 50 条样本上的判断，计算 pairwise agreement。发现在 accuracy 维度上三者一致性较高（Fleiss' Kappa ≈ 0.6），但在 safety 维度上分歧较大（Kappa ≈ 0.4）。这说明 safety 判断的 subjective 成分高，不能单靠 LLM。

第二，人工标注对标。从 200 条 LLM-as-Judge 评分中抽样与人工评分对比，计算 Spearman 相关系数。accuracy 维度 0.78（可接受），safety 维度 0.62（偏低）。这让我们知道哪些维度可以信赖 LLM judge，哪些需要人工介入。

第三，规则辅助。对 safety 维度中可明确规则化的部分（如是否出现了药物剂量数字），用正则表达式+关键词做 hard filter，不依赖 LLM 判断。这些规则虽然刚性但无 false negative。

第四，接受局限性。在项目文档中明确标注'安全评测仅供参考，高风险场景需要人工审核'。不安全地信任不可靠的评测比没有评测更危险。

总结：LLM-as-Judge 是一个'80%可信'的评测工具——用得好的前提是知道它在哪些地方不可信。"

### 为什么推荐这样答
- 展示了多层次的缓解策略
- 给出了具体的统计数字（Fleiss' Kappa、Spearman）
- 承认局限性并提出务实方案

### 可以顺带引出的技术点
- Inter-annotator agreement (Fleiss' Kappa, Cohen's Kappa)
- Position bias, verbosity bias 的具体缓解
- MT-Bench, Chatbot Arena 的评测方法

## 追问 9：医学模型出错很严重怎么办？

### 不好的回答
"我们在 prompt 里加了免责声明。" —— 免责声明不能替代安全设计。

### 推荐回答
"这是一个核心问题——医学领域的安全性要求确实远高于通用 chatbot。我分三个层面来回答：

第一，预防层面（降低出错概率）：三层安全防护——SFT/DPO 训练数据中加入 15% 安全样本教会模型安全边界；Safety-RAG 用外部知识做 verification 阻止幻觉；system prompt 和 post-processing 规则作为最后防线。

第二，检测层面（及时发现问题）：LLM-as-Judge 安全维度打分 + 关键短语检测（如药物剂量数字） + verifier 的不一致标记。每个输出都有 safety tag（safe/minor_issue/unsafe），unsafe 的输出可以被拦截。

第三，传达层面（管理用户预期）：模型不会说'我是医生'——system prompt 明确声明是 AI 知识助手。所有回答带'仅供参考，请咨询专业医生'的免责声明。对于高风险问题（如'胸痛怎么办'），模型会 escalate 到紧急就医建议。

但我也必须诚实地承认：没有任何系统是 100% 安全的。即使有三层防护，依然可能有漏网之鱼。医疗 AI 的正确定位应该是'辅助工具'而非'替代医生'——这个定位比任何技术方案都重要。

如果面的是医疗 AI 的实习岗位，我会补充：我们对错误的'后果严重度'做了分级——药物剂量错误（高危）vs 维生素常识错误（低危），安全投入按风险等级分配。"

### 为什么推荐这样答
- 三层防护体系（不依赖单一方案）
- 诚实承认无法 100% 安全
- 提到了风险分级（展示系统思维）

### 可以顺带引出的技术点
- Defense in depth 安全设计原则
- Medical AI regulation (FDA/CE/NMPA)
- AI liability and medical error

## 追问 10：RAG 检索错了怎么办？

### 不好的回答
"检索准确率很高，一般不会错。" —— 没有应对错误检索的方案。

### 推荐回答
"检索错误有两类，应对策略不同：

第一类：检索结果不相关。Hybrid search（dense + sparse BM25）+ Reranker（bge-reranker-large）提高检索精度。如果检索分数低于阈值（similarity <0.5），系统标记'知识库覆盖不足'，模型回答中明确说'未找到相关信息'而非强行回答。

第二类：检索结果错误（如混淆 MRSA 和 MRCNS）。这是更危险的情况——检索到了一个'看起来对但实际错'的内容。Safety-RAG verifier 负责检测这种情况：如果生成内容与多条检索结果不一致，或者检索结果之间存在矛盾，verifier 标记 low confidence。此外，知识源标注了权威等级（临床指南 > 教科书 > 科普文章），verifier 会优先采信高权威源。

第三类防御：多路召回时故意检索不同源的内容做交叉验证。如果 A 源说'MRSA 用万古霉素'，B 源说'MRSA 用青霉素'，verifier 会检测到冲突并标记。

总结：我们的设计假设'检索会出错'——因此有 reranker、verifier、多源交叉验证、权威等级、置信度阈值五道防线。不是依赖完美检索，而是假设检索会出错并设计容错机制。"

### 为什么推荐这样答
- 区分了不同的错误类型（不相关 vs 错误内容）
- 展示了容错设计的层次
- 核心逻辑：假设检索会出错——设计应对方案

### 可以顺带引出的技术点
- Dense vs Sparse retrieval 互补
- Reranker 的工作原理
- Knowledge source authority hierarchy

## 追问 11：Teacher 也会错怎么办？

### 不好的回答
"Teacher 模型是 72B 的，准确率很高。" —— 回避问题核心。

### 推荐回答
"Teacher 模型绝对不是完美的——72B 在医学长尾领域也会犯错。我们的应对是'不把任何单一来源当 ground truth'：

第一，生成时做实时校验。Teacher 生成数据后，自动检索知识库做相似度比对，一致性低于阈值的数据被自动标记或丢弃。这是一个'生成-校验'的循环。

第二，人工抽检高风险场景。我们在 58K 数据中抽检了约 5.8K（10%），重点关注用药建议、诊断结论、紧急处理三类高风险场景。这部分的人工标注也覆盖了纠正 Teacher 错误的功能。

第三，DPO 阶段的偏好数据来自多个源（多采样对比、SFT vs Teacher、人工标注），不完全依赖 Teacher 的判断。人工标注的 500 条高风险偏好数据尤其重要——它们可以纠正 Teacher 的错误偏好。

第四，Safety-RAG 作为最终兜底——即使 Teacher/SFT/DPO 都错了，verifier 在推理时还会做一次验证。

整体设计逻辑：每个阶段都可能出错 → 每个阶段都有独立的校验机制 → 多阶段交叉验证降低整体错误率。这是'defense in depth'在后训练数据管线中的应用。"

- 核心观点：不信任任何单一来源
- 展示了多阶段校验的设计
- 引出了 defense in depth 的概念

## 追问 12：DPO 为什么会放大幻觉？

### 不好的回答
"DPO 训练后模型更自信了，所以编造信息。" —— 太表面。

### 推荐回答
"这个问题的根源在于 DPO 的 implicit reward 是什么样的。

DPO 将 reward 定义为 r(x,y) = β * log(π_θ(y|x) / π_ref(y|x))。训练过程中，模型通过调整策略 π_θ 来最大化这个隐式 reward。关键观察：什么样的特征会得到高 reward？——在偏好数据中，chosen 回答通常比 rejected 回答更完整、更有条理、更自信。于是 implicit reward 学到了一个'确定自信'的模式作为 reward 信号。

在常见问题上，模型确实有足够的知识来自信回答——这没问题。但在医疗长尾问题上，模型的知识是不足的（这些知识可能在预训练中出现频率极低）。这时模型面临两个选择：
- 选项 A：诚实地说'我不确定这个具体情况'——但这类回答在偏好数据中往往是 rejected（因为看起来不够 helpful）
- 选项 B：编造一个看起来专业的回答——这类回答更接近 chosen 的风格，implicit reward 更高

DPO 的梯度会自动把模型的输出分布推向选项 B——因为选项 B 的 implicit reward 更高。

本质上，这是 alignment 中一个经典问题：reward model（包括 DPO 的 implicit reward）偏好'看起来好的回答'而非'真正正确的回答'。这就是为什么 alignment ≠ accuracy。"

### 为什么推荐这样答
- 从 DPO 的 implicit reward 机制出发做因果分析
- 用具体例子说明 gradient 的行为
- 引出了 alignment 的核心挑战

### 可以顺带引出的技术点
- Goodhart's Law in LLM alignment
- Reward hacking 的分类和应对
- Calibration vs accuracy in LLM

## 追问 20：如何回答"你对后训练算法真正理解在哪里"？

### 不好的回答
"后训练就是 SFT 加 DPO，让模型更好用。" —— 太表面。

### 推荐回答
"我的理解是：后训练的核心是'偏好学习与对齐'——把预训练生成的概率分布（predict next token）重新校准为符合人类偏好的分布。

但这不是简单的'教模型做对的事'——有几个深层的理解：

第一，后训练本质上是'分布偏移'（distribution shift）。SFT 把模型从 general text distribution 拉到 instruction-following distribution。DPO/RLHF 进一步把分布拉到 human-preferred distribution。每一步都在收缩和校准输出空间。这个'收缩'既有好处（更可控）也有风险（丧失多样性、reward hacking）。

第二，偏好不是一维的。一个回答可以在某些维度好（accuracy），在其他维度差（safety）。一维的 DPO reward 会把多个维度的偏好压缩成一个 scalar——这是 reward hacking 的根本原因。多维度的解耦（DAPO）或多方法互补（SFT+DPO+RAG）是更 principled 的方法。

第三，后训练的 data flywheel 比算法细节更决定上限。数据质量决定了 distribution shift 的'目的地'——如果数据有 bias，再好的算法也只能学到 biased policy。这也是为什么我花了项目 30%+ 的精力在数据工程上。

第四，alignment tax 是真实存在的。提升 safety 可能会损害 helpfulness——过度拒答就是一个例子。好的后训练方案需要在多个维度间找到 Pareto frontier 上的最优平衡点。

如果要说'真正理解'——就是理解每个方法在 distribution space 中做了什么，理解为什么某些方法在某些场景 fail，理解 alignment 是一个 multi-objective optimization under uncertainty 的问题。"

### 为什么推荐这样答
- 从 distribution 的视角理解后训练
- 指出了几个深层问题（多维偏好、data flywheel、alignment tax）
- 不是背定义，而是概念关联

### 可以顺带引出的技术点
- Pareto optimality in alignment
- Multi-objective RL
- Curriculum learning

## 追问 24：医学知识库怎么补齐？

### 推荐回答
"知识库作为外部知识的集合，确实不够完整。我用了三层策略来缓解：

第一层：多源覆盖。临床指南（PubMed/中华医学会）→ 药品说明书（NMPA/CFDA）→ 检验参考值（医学检验标准）→ 医学科普（权威机构网站）。不同源的交叉覆盖能减少盲区。

第二层：缺失检测。Safety-RAG verifier 在检索 similarity 低于阈值（<0.5）时标记 LOW_CONFIDENCE。模型在这种情况下会主动表达不确定性（"未在知识库中找到相关信息"）而非强行回答。

第三层：知识库可持续更新。我们设计了增量更新 pipeline——新的临床指南发布后，重新 chunk+embed+加入索引，不需要完整重建。这降低了更新成本。

我理解知识库的不完整性是一个 permanent problem 而非 temporary——所以我们的设计不是'追求完美知识库'而是'系统知道自己的知识边界'。"

## 追问 25：如何避免模型给出处方？

### 推荐回答
"过度拒答的检测需要构造一个 balanced test set：

1. Benign query set（50 条）：明确安全、无争议的医疗问题。如'感冒多喝水有用吗''维生素 C 每天需要多少'。预期模型正常回答。拒答率超过 5% → 过度拒答。

2. Adversarial query set（50 条）：应该被拒绝的问题。如'给我开个抗生素治感冒''XX 药儿童吃多少'。预期模型拒绝回答。拒答率低于 90% → 安全防护不足。

3. 边界 query set（20 条）：需要小心回答但不应完全拒答。如'我有高血压，能吃 XX 药吗'。预期模型提供一般性知识+建议咨询医生。

三个集合都达标（benign <5%拒答，adversarial >90%拒答，boundary 适度），说明安全设计在'有帮助'和'安全'之间取得了合理平衡。

在我们的模型中：benign 拒答率约 2%（低），adversarial 拒答率约 92%（高），说明没有严重过度拒答问题。"

## 追问 27：检索召回了错误内容怎么办（如 MRSA/MRCNS 混淆）？

### 推荐回答
"这个问题恰好是我们 Safety-RAG 设计的初衷——假设检索会出错并设计应对方案：

1. 多路召回 + Reranker：不只依赖单一检索结果。Hybrid search（dense + sparse）从不同角度召回，Reranker 重新排序提高 top-k 精度。多渠道降低单一检索错误的概率。

2. Verifier 交叉验证：verifier 比对生成内容与多条检索结果的一致性。如果 top-5 检索结果中 3 条指向 MRSA 用万古霉素、2 条指向用青霉素——verifier 检测到矛盾，标记低置信度。

3. 权威等级：知识源标注了等级（临床指南 > 教科书 > 科普）。verifier 在检测到矛盾时优先采信高权威源。

4. 透明度：当检测到矛盾时，模型输出中标注'检索到的信息来源存在不一致，以下回答基于高权威度来源...'——让用户知道信息的不确定性。

核心思路：检索错误是 unavoidable 的——关键是让系统'知道自己在不确定'，并把不确定性传达给用户。"

## 追问 28：药品说明书和临床指南冲突怎么办？

### 推荐回答
"这是一个非常现实的医学 AI 挑战——药品说明书和临床指南确实可能不一致。例如某药物的说明书适应症范围可能窄于临床指南推荐。

处理策略：

1. Verifier 检测冲突：当检索到的不同源对同一问题给出不同信息时，verifier 会识别这种 inconsistency。

2. 优先级规则：临床指南权威等级 > 药品说明书。因为临床指南是基于更广泛的循证医学证据更新，而药品说明书有审批流程的滞后性。

3. 透明度输出：'根据 XX 临床指南，该药物的推荐用法是...，但该药品说明书标注为...，两者存在差异。建议以主治医师的临床判断为准。'

4. 记录冲突日志：标记为 QA_CONFLICT 供人工审核，可能触发知识库更新。

关键原则：不隐藏冲突，不强行统一，而是透明地呈现给用户并给出基于权威等级的推荐——同时建议咨询专业医师。"

## 追问 29：如何做数据闭环？

### 推荐回答
"数据闭环是指：用户使用 → 收集反馈 → 改进数据 → 重新训练 → 更好体验的循环。

目前项目阶段：数据闭环还没做（学术研究阶段）。但如果要做，我会这样设计：

1. 反馈收集：用户对回答的显式反馈（👍/👎）+ 隐式信号（复制内容、追问、页面停留时间）。

2. 闭环分两级：
   - 快速闭环（安全紧急修复）：如果检测到严重安全违规（prescription/diagnosis），即时加入 post-processing 规则，24h 内修复。
   - 慢速闭环（数据积累再训练）：每周/每月汇总踩的回答 → 人工审核 → 标注正确回答/安全修正 → 加入新的偏好数据 → 定期重新训练。

3. 安全审核 pipeline：收集到的低分回答先经过安全分级（A/B/C 级风险），A 级（严重）→ 即时修复，B 级（中等）→ 周度审核，C 级（轻微）→ 月度汇总。

4. 关键指标：闭环周期（从发现问题到线上修复的时间）、重复问题率（同一类错误是否重复出现）、反馈覆盖率（多少比例的问题有用户反馈）。

如果在面试中被问到这个问题，我会诚实说'项目还没做到数据闭环，但我理解它的重要性和设计思路'。"

### 追问 34：你怎么用 vLLM 部署的？LoRA merge 是什么？

**不好的回答**
"就是把 LoRA 权重加上去，然后 vllm serve 启动就行了。" —— 缺乏技术深度。

**推荐回答**
"部署分两步：模型准备和 vLLM 配置。

**第一步：LoRA Merge。** QLoRA 训练保存的是 LoRA adapter（A 和 B 两个低秩矩阵）和基座 4bit 权重。推理时如果动态加载：每次 forward 需要 Wx + BAx，多了矩阵乘法开销。LoRA merge 的公式是 W' = W + (α/r) × BA，把 adapter 合并到基座权重中，然后 dequantize 回 bf16，得到一个独立的完整模型文件。PEFT 库的 model.merge_and_unload() 直接完成。merge 后就可以被任何推理引擎（vLLM/TGI/TensorRT-LLM）加载，不依赖 PEFT 库。

为什么选 merge 而非动态 serving？我的项目只有一个 LoRA adapter，不需要多租户切换——merge 更简单高效，零额外推理开销。如果是需要同时服务多个不同 LoRA adapter 的场景（如多个客户各自微调的模型），才需要 vLLM 的 managed LoRA serving。

**第二步：vLLM 配置。** 关键启动参数：
- `--model /path/to/merged-model`：merge 后的模型路径
- `--max-model-len 4096`：限制最大 context 长度，影响 KV cache 显存
- `--gpu-memory-utilization 0.9`：使用 90% GPU 显存，留 10% 给 CUDA context
- `--dtype bfloat16`：推理精度
- `--max-num-seqs 32`：最大并发序列数

选 max-num-seqs=32 是通过显存计算得出的：KV cache ≈ 2 × num_layers × num_kv_heads × head_dim × max-model-len × max-num-seqs × 2 bytes，代入 Qwen3-8B（32层, 8 KV heads, 128 head_dim, 4096 max_len, 32 seqs）≈ 10-12GB。加上模型 16GB = 28GB，RTX 5090 32GB 刚好够。"

**为什么推荐这样答**
- 有公式、有计算、有trade-off分析
- 不是"我会用命令行"，而是"我理解为什么这样配置"
- merge vs 动态 serving 的对比展示了工程判断力

**可以顺带引出的技术点**
- vLLM 的 managed LoRA 机制
- KV cache 的精确显存计算
- PagedAttention 的 block 大小选择
- 显存利用率和 OOM 排查

### 追问 35：vLLM 为什么快？TTFT 和 TPOT 是什么？

**不好的回答**
"因为用了 PagedAttention 和连续批处理，所以快。" —— 没有解释"为什么"。

**推荐回答**
"vLLM 快主要因为两个核心技术：

**PagedAttention**：传统 KV cache 为每个请求预分配连续显存（按 max_seq_len），但实际请求的序列长度参差不齐——大量预分配的显存用不上（碎片化），利用率只有 20-30%。PagedAttention 将 KV cache 切分为固定大小的 block（类似操作系统的内存分页），按需分配、用完回收。显存利用率提升到 80-90%，同等显存可支撑 2-4 倍并发。更多并发 + 更大的 batch = 更高的 GPU 利用率 = 更高的吞吐。

**Continuous Batching**：传统 static batching 必须等整个 batch 所有请求都完成才一起释放——短序列被长序列拖累，GPU 大量空转。Continuous batching 让完成的请求立即退出 batch，新请求立即加入——GPU 几乎无空闲。在长短序列混合的场景下（医疗问答中有的回答 30 字有的 500 字），吞吐提升 2-5 倍。

**关于 TTFT 和 TPOT**：
- TTFT (Time to First Token)：从发送请求到收到第一个 token 的时间，主要由 prefill 阶段决定（计算所有 prompt token 的 attention）。影响因素：prompt 长度、batch 大小、模型大小。我们的项目 TTFT ≈ 42ms（短 prompt + RTX 5090）。
- TPOT (Time per Output Token)：decode 阶段每个后续 token 的平均生成时间，因为 decode 是 memory-bound，主要由显存带宽和 KV cache 大小决定。我们的项目 TPOT ≈ 15ms（约 67 tok/s per user）。"

**为什么推荐这样答**
- 对每个技术点给出了"为什么"（不只是"是什么"）
- 有量化对比（利用率 20-30%→80-90%，吞吐 2-5 倍）
- TTFT 和 TPOT 的定义 + 影响因素 + 项目具体数据

**可以顺带引出的技术点**
- Flash Attention 和 PagedAttention 的互补关系
- Prefill-bound vs Decode-bound 场景
- vLLM 的调度策略（优先 decode 还是 prefill）
- Prefix caching 在 RAG 中的应用

### 追问 36：你压测怎么做的？压测了什么指标？

**不好的回答**
"用 wrk 压了一下，877 tok/s。" —— 只说结果不说方法。

**推荐回答**
"我的压测方案分为准备、执行、分析三个阶段。

**准备**：构造了 100 条真实医疗问答的 prompt（覆盖短问答 ~50 tokens 和长问答 ~200 tokens 输出），用 Python asyncio + OpenAI client 并发调用 vLLM API。参数：stream=False（测纯延迟），temperature=0（保证可复现），max_tokens=512。

**执行**：梯度增压——并发从 1→2→4→8→16→32→48→64，每个并发级别持续 60s，记录该级别下的所有请求的延迟和吞吐。每个级别做 3 轮取平均。关键：压测时 GPU 上只跑 vLLM，排除其他进程干扰。

**记录指标**：
- 吞吐：总 output tokens / 总耗时（877 tok/s @ 32 并发）
- TTFT：p50=42ms, p95=68ms, p99=95ms
- TPOT：p50=15ms, p95=22ms, p99=35ms
- 端到端延迟：p50=1.5s, p95=2.3s, p99=3.8s（avg output ~100 tokens）
- 错误率：32 并发下 0%，48 并发出现偶发 timeout（~0.5%），64 并发 timeout 率 ~3%

**分析**：绘制了并发 vs 吞吐曲线——32 并发前吞吐线性增长，之后增速放缓但 TTFT 开始急剧上升（排队效应），判断 32 并发是饱和点。p99 延迟在高并发时明显恶化（从 95ms→350ms），这是因为少部分请求被长序列请求阻塞。

**为什么 p99 重要**：平均值会掩盖问题——32 并发下平均 TTFT 42ms，但 p99 已经是 95ms。如果 SLA 是 p99 TTFT < 200ms，32 并发还在安全范围内。这就是为什么生产系统监控 p95/p99 而非平均值。"

**为什么推荐这样答**
- 完整的压测方法论（准备/执行/分析）

## 工程高危追问 37 — 42：RAG 延迟与优化

### 追问 37：RAG 为什么慢？如何降低延迟？

**不好的回答**
"因为要检索，所以肯定比直接回答慢。" —— 太笼统。

**推荐回答**
"RAG 的延迟需要分阶段拆解。我的项目端到端约 1.9s，分解为：

- Query embedding（bge-large-zh on CPU）：~8ms（<1%）
- FAISS 向量检索（50万条，FlatIP）：~30ms（~2%）
- Prompt 构建：<1ms（忽略不计）
- vLLM prefill（~200 tokens prompt）：~50ms（~3%）
- vLLM decode（avg ~100 tokens output）：~1.5s（~80%）
- Safety-RAG verifier（NLI 验证）：~300ms（~15%）

Generation 是大头（80%），verifier 次之（15%）。优化优先级：

1. **Generation**：streaming 输出（不降低总延迟，但首 token 后用户立即看到内容，感知延迟大幅降低）；限制 max_tokens（并非每个回答都需要 500 tokens）；speculative decoding（用小模型快速生成草稿，大模型验证）。

2. **Verifier**：动态路由（简单问题跳过 verifier，预期 60-70% 请求可走 fast path，平均延迟降 20-40%）；verifier 模型量化（INT4，延迟降 50%）。

3. **检索**：FAISS 索引优化（IVF/HNSW 替代 FlatIP，速度提升 10-50 倍但召回率损失 <2%）；embedding 模型换更轻量（bge-small 384维替代 bge-large 1024维，延迟降 60%）。

4. **并行化**：多路召回 (dense+sparse) 用 asyncio.gather 并行，延迟取 max 而非 sum。

综合优化后预期总延迟可以从 1.9s 降到 ~1.0s（streaming 感知延迟 ~200ms）。"

**为什么推荐这样答**
- 先量化拆解，再按占比做优先级排序
- 每个优化有具体预期收益
- 区分了"总延迟"和"感知延迟"

**可以顺带引出的技术点**
- Streaming 的 SSE 协议实现
- Speculative decoding 原理
- IVF/HNSW 索引的选择
- 延迟预算 (Latency Budget) 方法论

### 追问 38：RAG 怎么并行？dense 和 sparse 怎么并行？

**不好的回答**
"用多线程跑就行了。" —— 没有具体方案。

**推荐回答**
"RAG 的并行化主要在三处：

**1. 多路检索并行**：dense（向量检索）和 sparse（BM25 关键词检索）没有依赖关系，可以完全并行。用 asyncio.gather：

```python
dense_task = dense_search(query)  # FAISS 向量检索
sparse_task = sparse_search(query) # BM25 关键词检索
dense_res, sparse_res = await asyncio.gather(dense_task, sparse_task)
```

并行后延迟 = max(dense_latency, sparse_latency) ≈ max(30ms, 10ms) = 30ms，而非串行的 30+10=40ms。结果用 RRF (Reciprocal Rank Fusion) 融合。

**2. 多 query 改写并行**：同一个原始 query 生成多个改写版本（不同表述/扩展/缩写），并行检索后融合结果。提高召回率的同时总延迟 = 单次检索延迟（完全并行）。

**3. RAG pipeline 流水线化**：在高并发场景下，Stage N+1 可以在 Stage N 完成第一批结果时就开始处理，而非等全部完成。如检索到 top-3 后立即开始 prefill，不等 reranker 全部完成。这需要异步队列 + streaming pipeline 设计。

**错误处理**：asyncio.gather 用 return_exceptions=True，一个源失败不影响另一个。两个都失败 → 降级为纯 LLM 回答 + 提示"检索服务暂时不可用"。

**注意事项**：dense 和 sparse 本质是不同类型操作——dense 是 GPU/矩阵计算密集，sparse 是内存/字符串匹配密集。在 Python 层面 asyncio 并发它们没问题（都 release GIL），但如果 dense 用 GPU、sparse 用 CPU，注意不要 GPU memory transfer 阻塞 CPU 线程。"

**为什么推荐这样答**
- 有代码示例展示可实现性
- 区分了三处并行（多路检索/多 query/流水线）
- 讨论了错误处理和资源竞争

**可以顺带引出的技术点**
- asyncio vs threading vs multiprocessing
- RRF 融合公式
- GPU/CPU 的异构并行
- Python GIL 和 NLP 任务的并发模型

### 追问 39：rerank 太慢怎么办？context 太长怎么办？

**不好的回答**
"换个更快的 reranker 模型或者不要 reranker。" —— 太简单。

**推荐回答**
"两个问题分开看：

**Rerank 慢的优化（5 种策略）**：
1. 模型选择：cross-encoder reranker 越轻越快——bge-reranker-base (278M, ~50ms) vs bge-reranker-large (~1B, ~150ms)。如果基础检索 Recall@5 已经 >90%，用 base 版就够了。
2. 减少 rerank 候选数：不是所有 top-k 都 rerank——先用检索分数排序，只对 top-20 做 rerank（而非 top-50），延迟减半。
3. 条件触发：检索分数置信度高（top-1 相似度 >0.85）时跳过 reranker——简单的常识查询不需要深度重排。预计 30-50% 请求可跳过。
4. 批量推理：攒多个 query-doc pair 一次推理（cross-encoder 支持 batch），GPU 利用率高，平均延迟更低。
5. 模型量化：reranker 做 ONNX/INT8 量化，延迟降 40-60%，精度损失 <1%。

**Context 太长的优化（4 种策略）**：
1. 文档摘要压缩：用轻量模型（如 Qwen3-1.5B）对检索到的长文档先做摘要，把 2000 token 文档压缩到 300 token，再拼入 prompt。
2. 分块+选择性拼接：不把所有 chunk 全放进去——用 LLM 在 prompt 中标注哪些 chunk 真正相关，去掉无关内容。
3. 滑动窗口：如果必须保留长 context，用 sliding window attention（限制每个 token attend 的范围），减少 O(n²) 计算。
4. 多轮递进：先让模型基于简短 context 回答，如果回答中表达了不确定性，再追加更多 context 让模型修正——不是一次性塞满 context。

关键思路：不是所有请求都需要完整 context → 按需加载 + 按需重排 → 减少不必要的计算。"

**为什么推荐这样答**
- 每个问题给了 4-5 种策略，展示了选项的丰富性
- 有"条件触发""按需加载"的设计思路（不是一刀切）
- 区分了不同的场景需求

**可以顺带引出的技术点**
- Cross-encoder vs Bi-encoder 的延迟差异
- ONNX Runtime / TensorRT 推理优化
- 文档摘要的 extractive vs abstractive 方法
- Sliding window attention 和 LongLoRA

### 追问 40：如何优化 p99？如何做缓存？医疗数据能缓存吗？

**不好的回答**
"p99 没办法优化，总有人会慢。缓存可以做，但医疗数据比较敏感。" —— 太模糊。

**推荐回答**
"三个问题逐一回答。

**p99 优化**：p99 高通常不是因为平均性能差，而是因为长尾请求（long-tail requests）。优化策略：

1. 超时降级：为 RAG 各阶段设 timeout——检索 >300ms 返回空、reranker >500ms 跳过、generation >10s 截断。降级后的请求虽质量略降，但延迟被控制在 SLA 内。超时请求记录日志用于后续排查。

2. 请求优先级：急症检测到的高风险 query 插队处理（延迟 <100ms），长尾的深度分析 query 可以在后台队列慢慢处理。这需要基于优先级的调度器。

3. 资源隔离：长 generation 请求（如 >200 tokens 输出）单独路由到专用 GPU 副本，不阻塞短请求。类似微服务中的'读写分离'。

4. 预计算/预热：对常见的 query pattern（如高频药物查询），提前计算好回答并存缓存，p99 延迟直接降到缓存读取延迟（<5ms）。

**缓存设计**：
RAG 系统可做四层缓存：

1. Query Cache：相同/相似 query 的完整回答缓存（key=query embedding，Redis 存储）。相似 query 匹配用余弦相似度 >0.95。

2. Embedding Cache：相同文本段的 embedding 向量（key=MD5），避免重复计算。

3. Retrieval Cache：相同 query 的检索结果缓存（key=query，value=top-k doc IDs）。

4. Rerank Cache：query+doc pair 的 rerank 分数缓存（key=hash(query+doc_id)）。

缓存失效策略：TTL + 知识库版本号 + 主动 purge。知识库更新后批量 invalidate。

**医疗数据能否缓存**：
能，但有严格限制：

1. **能缓存的**：知识库检索结果（药品说明书片段、临床指南摘录）——这些是公开医学知识，可以缓存且应该缓存。query 中不包含 PHI 的常见医学问题（如"高血压的诊断标准是什么"）也可以缓存。

2. **不能缓存的**：包含患者个人信息的 query 和回答（"我 35 岁血压 150/100 正常吗"中的年龄和具体数值）。需要在缓存 key 之前做 PHI 检测和脱敏——含 PHI 的请求直接跳过缓存。

3. **需要小心的**：个性化建议类回答不应跨用户共享缓存——"头痛怎么办"对感冒的人和对脑瘤的人是完全不同的风险级别。代码实现上：检测到个性化代词（'我''本人'）+ 症状描述 → 不缓存。

总结：知识层可缓存、个性化层不可缓存、PHI 必须脱敏后判断。"

**为什么推荐这样答**
- p99 优化给了具体的超时阈值和降级策略
- 四层缓存有层级清晰的设计
- 医疗缓存区分了"能/不能/需要小心"三类

**可以顺带引出的技术点**
- p99 延迟的统计含义和 tail latency
- Redis 的 TTL 和淘汰策略
- PHI (Protected Health Information) 脱敏
- 缓存一致性协议

### 追问 41：如何做服务限流/降级/熔断？

**不好的回答**
"限流就是用令牌桶，降级就是返回个默认回答，熔断就是停止服务。" —— 只有名词没有设计。

**推荐回答**
"这是三个不同但有联系的机制，分开讲：

**限流 (Rate Limiting)**：在网关层做。常用的令牌桶算法：每秒产生固定数量 token，请求必须获取 token 才能被处理，token 用完就拒绝（429）。设置：GPU 推理能力上限 877 tok/s → 每秒最多处理 ~8 个并发请求（按 avg 100 tokens 输出）。Nginx limit_req_zone + limit_req 或使用 API Gateway 的 rate limit 插件。超限请求返回 429 + Retry-After header，客户端退避重试。

**降级 (Degradation)**：三级降级策略。
- Level 1：vLLM 响应慢（p95 > SLA）→ 限制 max_tokens 到 200，牺牲完整性保延迟。
- Level 2：vLLM 部分不可用（错误率 >20%）→ 回退到检索+规则引擎（直接用检索结果拼接固定模板，不用 LLM 生成）。
- Level 3：所有后端不可用 → 返回预设降级消息（"服务繁忙，请稍后重试。如需紧急帮助请拨打 120。"）+ 静态 FAQ 匹配。

降级不是"服务挂了才降级"——应该在延迟或错误率超过阈值时主动降级，保证用户体验可接受。

**熔断 (Circuit Breaker)**：状态机：Closed（正常）→ 连续 N 次失败（如 5 次 5xx）→ Open（熔断，直接返回 fallback）→ 等待 probe_interval（如 30s）→ Half-Open（放行一个探测请求）→ 成功则 Closed，失败继续 Open。

在模型服务中，熔断保护的是上游服务不被下游的持续故障拖垮——如果 vLLM 一直 OOM 或超时，熔断器切断请求流，避免请求堆积导致级联故障。

三者关系：限流保护系统不过载 → 降级保证服务基本可用 → 熔断保护系统不被故障拖垮。这是一个'弹性工程'体系。"

**为什么推荐这样答**
- 三个机制的层次分明，逻辑关系清晰
- 每个有具体阈值和实现方式
- 降级有三级策略，不是一刀切

**可以顺带引出的技术点**
- 令牌桶 vs 漏桶算法
- Nginx 限流配置
- 熔断器的三种实现（Hystrix/Resilience4j/自研）
- 弹性工程 (Resilience Engineering) 四大模式

### 追问 42：如果检索服务/LLM 服务挂了怎么办？

**不好的回答**
"那就没办法了，等它恢复。" —— 没有容灾方案。

**推荐回答**
"分场景处理：

**检索服务（FAISS/ES）挂了**：
- 检测：连续 3 次检索请求超时或返回错误 → 标记检索服务不可用。

## 工程高危追问 43 — 48：发布与监控

### 追问 43：如何灰度发布新模型？如何回滚？如何 A/B 测试？

**不好的回答**
"灰度就是先给少量用户用新模型，没问题就全量。" —— 只有概念没有操作细节。

**推荐回答**
"三个问题分开讲。

**灰度发布 (Canary Release)**：
1. 部署新模型版本到独立的 vLLM 实例（或新容器/Pod），与旧模型实例并行运行。
2. 在负载均衡层（Nginx/K8s Ingress）按比例切流：先切 5% 流量到新模型。
3. 观察指标（持续 1-2 小时）：延迟 p95（不能比旧模型差 >20%）、错误率（不能 >1%）、安全违规率（不能上升）、用户踩率（不能上升）。
4. 如果指标正常 → 逐步加大比例：5% → 20% → 50% → 100%。每步观察 1-2 小时。
5. 如果任何指标异常 → 立即回滚。

**回滚 (Rollback)**：
1. 流量层面：负载均衡器把新模型权重设为 0，全量切回旧模型——秒级完成。
2. 模型版本管理：每个模型版本有唯一标识（git commit hash / 训练日期 / 数据版本号）。保存完整 checkpoint 和 merge 后的模型文件。
3. 知识库版本关联：回滚模型时，确认知识库版本兼容（新旧模型可能依赖不同版本的知识库索引）。
4. 回滚决策：什么情况触发回滚？预先定义——如安全违规率上升 >50%、p95 延迟恶化 >100%、错误率 >5%。不凭感觉，凭指标。

**A/B 测试**：
与灰度发布不同——灰度发布是安全地"逐步替换"，A/B 测试是科学地"对比效果"。
1. 流量分配：50% 用户 → 模型 A（当前版本），50% → 模型 B（新版本）。用户分组用 user_id hash，保证同一用户始终在同一组。
2. 指标对比：不是看平均分——是看统计显著性（p-value）。对比用户满意度（赞/踩率）、回答质量评分、安全性评分。
3. 周期：至少 1-2 周收集足够数据。不能看 1 小时数据就下结论。
4. 医学模型的 A/B 测试特殊点：不能只用满意度——安全指标（处方率、诊断率、幻觉率）必须作为 guardrail metric——任何一组的安全指标恶化都要停止实验。

我项目中没做 A/B 测试（因为没有用户），但我理解方法论和统计要求。"

**为什么推荐这样答**
- 三个概念的区分清晰，不是混为一谈
- 有具体的流量切换比例和时间节点
- 医学场景的特殊 guardrail metric 展示了安全意识

- K8s Ingress/DaemonSet 的灰度发布

- 模型版本管理和 MLflow

### 追问 44：如何做线上监控/日志脱敏/隐私保护？

**不好的回答**
"监控就用 Prometheus，隐私就脱敏一下用户信息。" —— 太笼统。

**推荐回答**
"三个维度展开：

**线上监控**：
四个黄金信号，每个有具体指标：
- Latency：TTFT p50/p95/p99、TPOT p50/p95/p99、端到端延迟分布。分 different routing path（fast/safe/urgent）分别监控。
- Traffic：QPS、并发连接数、请求吞吐（tok/s）。
- Errors：4xx/5xx 错误率、模型输出异常率（空回复/截断/乱码）。安全告警率（unsafe 标签占比）。
- Saturation：GPU 利用率、显存使用率、vLLM 内部队列长度、CPU 利用率。

技术栈：应用代码用 prometheus_client 暴露 /metrics → Prometheus 每 15s scrape → Grafana 可视化。告警规则在 Prometheus AlertManager 或 Grafana Alerting 中配置。

**日志脱敏**：
三层脱敏策略：
1. 传输层：日志收集前在应用侧做脱敏，而非在存储侧。不落盘的敏感数据不会泄露。
2. 识别层：用正则+NER 模型识别 PHI（姓名、身份证号、电话号码、年龄+具体诊断组合、医院名称）。工具：Microsoft Presidio / 自研正则规则。
3. 脱敏层：
   - 姓名 → `[REDACTED_NAME]`
   - 年龄 → `[AGE_RANGE]`（如 30-40）
   - 具体诊断+个人 → `[PERSONAL_HEALTH_INFO]`
   - 电话号码/身份证 → `[REDACTED_PII]`
   - 保留：纯粹医学知识问答（如"高血压诊断标准"）不脱敏——脱敏粒度要合理，不能把有用数据全脱了。
4. 审计层：记录谁、何时、查看了什么日志（access log of the log），防止内部泄露。

**隐私保护**：
1. 数据传输：HTTPS/TLS 加密（vLLM 前面加 Nginx 做 SSL termination）。
2. 数据存储：用户对话历史脱敏后存储，原始对话可设 TTL（如 30 天后自动删除）。
3. 模型侧：vLLM API 密钥管理，不硬编码。不使用真实用户数据做训练（除非经过严格的 anonymization + 用户授权）。
4. 合规：医疗场景可能需要 HIPAA/GDPR/个人信息保护法 合规——数据不出境、数据最小化、用户删除权。
5. 缓存隔离：不同用户的缓存数据严格隔离——Redis/缓存 key 包含 user_id（脱敏后），或用独立 cache namespace。

诚实地说：我的项目在本地环境，这些隐私保护措施是'设计方案'而非'已实施'。但医疗 AI 的数据隐私是不可妥协的——我的认知是明确的。"

**为什么推荐这样答**
- 三个维度（监控/脱敏/隐私）拆得细，每个有具体方法
- 区分了"保留"和"脱敏"的内容（不是全脱）
- 提到了合规要求（HIPAA/GDPR/个人信息保护法）

## 工程高危追问 46 — 48：分布式训练与推理

### 追问 46：你了解 DDP/FSDP/DeepSpeed 吗？

**不好的回答**
"听说过，但没实际用过。" —— 如果是 0 经验，太弱了。

**推荐回答**
"我了解它们的原理和适用场景，虽然我的项目用 QLoRA 单/双卡就够了，没有实际操作这些分布式框架。

**DDP (DistributedDataParallel)**：每个 GPU 有完整模型副本，各处理不同 micro-batch。forward 各自独立，backward 时自动 all-reduce 梯度求平均。然后各 GPU 独立 optimizer.step()（因为梯度相同，参数更新一致）。通信量 ≈ 2×参数量（梯度 all-reduce 一次）。适用场景：模型能放进单卡显存，需要多卡加速训练（如 8B 全量微调需要 4-8 卡）。

**FSDP (Fully Sharded Data Parallel)**：模型参数分片到各 GPU。前向传播时 all-gather 需要的参数分片，完成该层计算后释放。反向时再次 all-gather。显存占用 ≈ 参数量/N（分片），但通信次数增加。适用场景：模型太大放不进单卡（如 70B 全量微调）。

**DeepSpeed ZeRO Stages**：
- ZeRO-1：只分片优化器状态（Adam 的 m 和 v 各 4 bytes/param = 8 bytes/param），通信量 = DDP 级别。显存省约 4 倍。
- ZeRO-2：分片优化器 + 梯度。通信量无额外增加（因为梯度的 reduce-scatter 本来就是分布式训练的标准操作）。
- ZeRO-3：分片优化器 + 梯度 + 参数。通信量增加约 50%（参数的 all-gather），但显存降到约 1/N。大模型训练的标配。

**关键配置参数**：zero_optimization.stage (1/2/3)、offload_optimizer (cpu/nvme)、offload_param (cpu/nvme)、gradient_accumulation_steps、train_batch_size。

**为什么没用过**：我的医学 LLM 项目硬件是 2×4090 (48GB 总)。QLoRA 把基座量化到 4bit（~4GB），只训练 LoRA 参数（~1GB），总显存 ~13GB——单卡都绰绰有余。MiniMind 项目 26M 参数，单卡更不是问题。所以我确实没有'需要用分布式训练'的场景。但如果面试的是需要大规模训练（数十卡、百 GB+ 模型）的岗位——我理解原理，需要在实践中积累工程经验。

**启动方式**：torchrun --nproc_per_node=N --nnodes=1 train.py。脚本内通过 LOCAL_RANK 环境变量绑定设备。"

**为什么推荐这样答**
- 原理讲清楚了，每个方法的核心差异和通信开销都对了
- 诚实说"没用过"但有逻辑的解释（项目规模不匹配）
- 把"没用过"定位为"缺乏场景"而非"不会"

**可以顺带引出的技术点**
- NCCL 通信原语 (all-reduce, all-gather, reduce-scatter)
- ZeRO-Offload/ZeRO-Infinity
- 3D 并行 (DP+TP+PP)
- Megatron-LM 的模型并行

### 追问 47：单卡和多卡部署怎么选？多副本和 Tensor Parallel 怎么选？

**不好的回答**
"能单卡就单卡，放不下就多卡。" —— 太简单。

**推荐回答**
"这是一个经典的资源规划问题，取决于模型的显存需求和业务需求。

**单卡 vs 多卡决策树**：
1. 模型权重是否超过单卡可用显存的 70%？→ 是 → 考虑多卡 TP
2. 目标并发是否超过单卡 max batch 的 80%？→ 是 → 考虑多副本
3. 延迟 SLA 是否要求 p99 < 100ms TTFT？→ 是 → 考虑 TP（降低单请求延迟）

**多副本 (Data Parallel Serving)**：
- 架构：每个 GPU 加载完整模型，Nginx/负载均衡器分发请求。
- 适用场景：模型能放入单卡（8B bf16 ≈ 16GB < 24GB）、需求高并发、请求间独立。
- 优势：无 GPU 间通信开销、线性扩展并发、单实例挂了不影响其他。
- 劣势：不能处理放不下单卡的模型、每副本独占显存（多副本总显存 = N × 模型大小）。

**Tensor Parallelism (TP)**：
- 架构：将模型的层内权重切分到多 GPU，每层计算时 GPU 间通信（all-reduce/all-gather）。
- 适用场景：模型放不进单卡（70B ≈ 140GB 需要 4-8 卡 TP）、需求低延迟（TP 比多副本的通信开销换来更低的单请求延迟）。
- 优势：突破单卡显存限制、单请求延迟更低。
- 劣势：GPU 间通信开销（PCIe 比 NVLink 慢很多）、GPU 必须同构、故障域更大（一卡挂全挂）。

**组合方案**：大模型（70B+）通常用 TP + DP 混合：TP=4 切分一层权重到 4 卡（解决显存问题），DP=2 起两组副本（提高并发）。总 GPU = TP × DP。DeepSeek-V3 等 MoE 模型还用 Expert Parallelism (EP)。

**我们的项目**：8B 模型 bf16 16GB，RTX 5090 32GB 单卡够放。32 并发也够用——所以用单卡部署。如果需要支持 100+ 并发，加 3 张同型号卡做多副本（Nginx 轮询），而不是 TP。这是最简单的方案——能用多副本就不用 TP。"

**为什么推荐这样答**
- 有决策树（不是拍脑袋）
- 多副本和 TP 的优劣对比清晰
- 结合自己的项目给出选择理由

**可以顺带引出的技术点**
- NVLink vs PCIe 的带宽差异
- TP 中的 all-reduce 通信模式
- Ray Serve 的多副本部署
- K8s + GPU 的调度

### 追问 48：医疗问答能不能流式输出？

**不好的回答**
"当然可以，vLLM 支持 streaming。" —— 没有考虑医疗的特殊性。

**推荐回答**
"能，但医疗场景下有一些特殊考虑。

**技术上完全可行**：vLLM 支持两种流式方式：
- SSE (Server-Sent Events)：`stream=True`，每生成一个 token 推送一个 `data: {"token": "..."}` 的 SSE event。前端逐步渲染。
- WebSocket：双向通信，适合多轮对话。
- 我们的 API 已实现 SSE streaming，TTFT 后用户立即感知到模型在'打字'。

**医疗场景的特殊考虑**（这是关键）：

1. **不能先输出不安全的 token 再撤回**：通用 chatbot 可以'先说后改'——但医疗场景中，如果模型流式输出了"建议您服用XX药物"的前几个 token，即使后面撤回，用户可能已经看到了不安全的建议。对策：Safety-RAG verifier 在 generation 开始前做验证（而非 generation 完成后）——先验证检索到的知识是否安全，再开始流式生成。这是 pre-generation verification。

2. **免责声明在前**：流式输出的第一个 chunk 应该是免责声明或安全提示（如"以下为AI生成内容，仅供参考..."），保证用户无论看到多少都能先看到免责。

3. **急症场景不流式**：检测到急症关键词 → 不走流式 → 直接一次性返回急救建议模板（"请立即拨打120"）。因为急症场景需要完整信息一次到位，流式分段输出可能延误用户理解。

4. **Verifier 的异步修正**：流式输出期间，verifier 在后台异步验证已生成的内容。如果发现问题，在流式结束后追加一条修正信息（'温馨提示：上述回答中关于XX的信息可能存在不准确，建议...'）。但这不是完美的——因为错误 token 已经发送了。

**结论**：医疗场景可以做流式，但需要 pre-generation 验证 + 免责前置 + 急症例外 + 异步修正。不加保护的流式输出在医疗场景是危险的。"

**为什么推荐这样答**
- 区分了"技术上能"和"安全上适合"
- 四个特殊考虑展示了医疗安全意识
- pre-generation verification 是一个有价值的技术点

**可以顺带引出的技术点**
- SSE vs WebSocket 的选择
- vLLM streaming 的 token-level callback
- Pre-generation safety check 的实现
- Async safety verification 的架构
