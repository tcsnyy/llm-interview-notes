## 追问 2：你这个项目算法性在哪里？⭐⭐⭐⭐⭐

"我认为这个项目有三个方面体现了算法能力：

第一，对 DPO 后幻觉问题的因果分析。DPO 的 loss 函数决定了什么模式会被奖励——我分析了 DPO gradient 中 (1-σ(...)) 这个误差加权项，发现当模型在不确定场景下选择'编造自信答案'比'诚实表达不确定'获得更高 implicit reward 时，这个梯度方向就会持续强化编造行为。这是从数学公式到实验现象的完整分析链。

## 追问 3：你是否真正理解 DPO？⭐⭐⭐⭐⭐

"我理解的 DPO 可以从三个层次来回答：

第一层是数学推导。DPO 的起点是 Bradley-Terry 偏好模型：P(y_w ≻ y_l) = σ(r(y_w) - r(y_l))。RLHF 通常分两步——先训练 r_φ，再优化 policy π_θ 最大化 r_φ 同时加 KL 约束。DPO 的关键 insight 是：这个约束优化问题有闭式解——最优 policy π* 满足 r(x,y) = β log(π*(y|x)/π_ref(y|x)) + β log Z(x)。把闭式解代入 BT 模型，reward 就被消掉了，得到只依赖 π_θ 和 π_ref 的 loss。

第二层是训练 dynamics。DPO 的梯度形式是 ∇_θ L = -β E[(1-σ(β * margin)) * (∇_θ log π_θ(y_w) - ∇_θ log π_θ(y_l))]。加权因子 (1-σ(...)) 的含义是：当模型已经能很好地区分 chosen 和 rejected（margin 大 → σ→1 → 权重→0），梯度就小；当模型区分得不好（margin 小或负），梯度就大。

第三层是实际训练中的现象理解。reward accuracy 虚高但生成质量下降——说明模型在'过拟合'偏好信号但没有真正提升能力。β 太小导致 over-optimization——模型太激进地偏离 ref。这些现象都可以从 DPO 的数学公式中得到解释。"

**避坑**：不要只说"DPO 就是直接优化偏好的方法"——太表面，没有数学理解。

## 追问 4：你是否手写过 DPO loss？⭐⭐⭐⭐⭐

"是的，我可以用 PyTorch 从零写 DPO loss。核心是：

```python
def dpo_loss(policy_chosen_logps, policy_rejected_logps,
             ref_chosen_logps, ref_rejected_logps, beta=0.1):
    pi_lograt = policy_chosen_logps - policy_rejected_logps
    ref_lograt = ref_chosen_logps - ref_rejected_logps
    logits = pi_lograt - ref_lograt
    loss = -F.logsigmoid(beta * logits).mean()
    return loss
```

我用 TRL 库是为了工程效率——它处理好了分布式训练、gradient checkpointing、logging 等工程细节。但我理解每个细节：logps 是 token-level log probability 的 sum（不是 average——因为 DPO 公式本身的 sum 形式）；chosen 和 rejected 的 logps 计算时都需要用 full context；reference model 的 logps 只需要算一次（frozen model），可以在训练前 precompute 以加速训练。

如果需要，我可以手写完整的 DPO 训练循环——包括数据加载、前向传播、loss 计算、梯度累积、logging。"

**避坑**：不要说"我用 TRL 库的 DPOTrainer 训练的"——没有展示代码能力。

**延伸技术点**：Token-level vs sequence-level loss、DPO 中的 logp 计算的注意事项、TRL/DeepSpeed 的工程实现

## 追问 5：为什么不用 PPO/GRPO/OPD？⭐⭐⭐⭐⭐

"这个选择是经过 trade-off 分析的，不是默认选 DPO。

PPO 的优势是 on-policy 训练——每步用当前策略采样，分布偏移小；可以多轮迭代；灵活度更高。但代价是：需要同时维护 policy、reference、reward、value 四个模型，训练包含多个 loss 项需要精细调参，工程复杂度高。在我们的 2×4090 和项目时间限制下，PPO 的投入产出比不如 DPO。

GRPO 去掉了 value model——这是一个很大进步（DeepSeek-R1 验证了有效性）。但 GRPO 仍然需要 reward model 和 group sampling（每个 prompt 采样 4-8 个 response），在我们的 10K 数据规模下 cost 仍然高。

OPD 在 DPO 基础上加入了 on-policy sampling——确实能缩小分布偏移。但每轮需要重新采样和标注，总成本是 DPO 的 3-5 倍。

所以 DPO 在我们的约束（10K 数据、2×4090、有限项目时间）下是最优选择。如果资源和数据规模更大，我的升级路径是：Iterative DPO → OPD → GRPO，逐步增加 on-policy 成分。

总结：不是 DPO 绝对好，而是 DPO 在给定约束下性价比最高——这是一个工程决策而非算法信仰。"

**避坑**：不要说"DPO 比 PPO 简单，效果差不多"——没有经过思考的判断。

## 追问 6：为什么不用纯 RAG/纯 SFT？⭐⭐⭐⭐

"纯 RAG 的问题：naive RAG 只做检索→拼接→生成，没有验证机制。它假设检索到的知识是正确的、相关的、完整的——但实践中这三种假设都可能被违反。而且 RAG 不改变模型的行为模式——格式、语气、安全边界的建立需要 SFT/DPO。

纯 SFT 的问题：SFT 只最大化正样本概率，不对负样本做任何处理。模型学会了'说什么'但不知道'不要说什么'。医学场景中有大量需要'拒绝回答'或'表达不确定'的情况，这些行为需要通过偏好学习（DPO）来建立。另外 SFT 后的知识存在于模型参数中，无法更新——而医学知识是不断更新的。

我们的方案是 SFT + DPO + Safety-RAG 三合一：SFT 建立基础对话能力，DPO 建立安全偏好，Safety-RAG 提供外部知识验证。三者互补——SFT/DPO 负责'怎么说话'，Safety-RAG 负责'说的内容对不对'。"

## 追问 8：LLM-as-Judge 不可靠怎么办？⭐⭐⭐⭐

"LLM-as-Judge 确实不可靠——这是公开的 research problem。我采取的缓解策略是：

第一，多 judge 交叉验证。我对比了 Qwen3-72B、GPT-4、Claude-3 三个 judge 在 50 条样本上的判断，计算 pairwise agreement。发现在 accuracy 维度上三者一致性较高（Fleiss' Kappa ≈ 0.6），但在 safety 维度上分歧较大（Kappa ≈ 0.4）。这说明 safety 判断的 subjective 成分高，不能单靠 LLM。

第二，人工标注对标。从 200 条 LLM-as-Judge 评分中抽样与人工评分对比，计算 Spearman 相关系数。accuracy 维度 0.78（可接受），safety 维度 0.62（偏低）。这让我们知道哪些维度可以信赖 LLM judge，哪些需要人工介入。

第三，规则辅助。对 safety 维度中可明确规则化的部分（如是否出现了药物剂量数字），用正则表达式+关键词做 hard filter，不依赖 LLM 判断。

第四，接受局限性。LLM-as-Judge 是一个'80%可信'的评测工具——用得好的前提是知道它在哪些地方不可信。"

## 追问 9：医学模型出错很严重怎么办？⭐⭐⭐⭐⭐

"这是一个核心问题——医学领域的安全性要求确实远高于通用 chatbot。我分三个层面来回答：

第一，预防层面（降低出错概率）：三层安全防护——SFT/DPO 训练数据中加入 15% 安全样本教会模型安全边界；Safety-RAG 用外部知识做 verification 阻止幻觉；system prompt 和 post-processing 规则作为最后防线。

第二，检测层面（及时发现问题）：LLM-as-Judge 安全维度打分 + 关键短语检测（如药物剂量数字）+ verifier 的不一致标记。每个输出都有 safety tag（safe/minor_issue/unsafe），unsafe 的输出可以被拦截。

第三，传达层面（管理用户预期）：模型不会说'我是医生'——system prompt 明确声明是 AI 知识助手。所有回答带'仅供参考，请咨询专业医生'的免责声明。对于高风险问题（如'胸痛怎么办'），模型会 escalate 到紧急就医建议。

但我也必须诚实地承认：没有任何系统是 100% 安全的。即使有三层防护，依然可能有漏网之鱼。医疗 AI 的正确定位应该是'辅助工具'而非'替代医生'——这个定位比任何技术方案都重要。"

**避坑**：不要说"我们在 prompt 里加了免责声明"——免责声明不能替代安全设计。

## 追问 10：RAG 检索错了怎么办？⭐⭐⭐⭐

"检索错误有两类，应对策略不同：

第一类：检索结果不相关。Hybrid search（dense + sparse BM25）+ Reranker（bge-reranker-large）提高检索精度。如果检索分数低于阈值（similarity <0.5），系统标记'知识库覆盖不足'，模型回答中明确说'未找到相关信息'而非强行回答。

第二类：检索结果错误（如混淆 MRSA 和 MRCNS）。这是更危险的情况——检索到了一个'看起来对但实际错'的内容。Safety-RAG verifier 负责检测这种情况：如果生成内容与多条检索结果不一致，或者检索结果之间存在矛盾，verifier 标记 low confidence。此外，知识源标注了权威等级（临床指南 > 教科书 > 科普文章），verifier 会优先采信高权威源。

第三类防御：多路召回时故意检索不同源的内容做交叉验证。如果 A 源说'MRSA 用万古霉素'，B 源说'MRSA 用青霉素'，verifier 会检测到冲突并标记。

总结：我们的设计假设'检索会出错'——因此有 reranker、verifier、多源交叉验证、权威等级、置信度阈值五道防线。"

## 追问 11：Teacher 也会错怎么办？⭐⭐⭐⭐

"Teacher 模型绝对不是完美的——72B 在医学长尾领域也会犯错。我们的应对是'不把任何单一来源当 ground truth'：

第一，生成时做实时校验。Teacher 生成数据后，自动检索知识库做相似度比对，一致性低于阈值的数据被自动标记或丢弃。这是一个'生成-校验'的循环。

第二，人工抽检高风险场景。我们在 58K 数据中抽检了约 5.8K（10%），重点关注用药建议、诊断结论、紧急处理三类高风险场景。

第三，DPO 阶段的偏好数据来自多个源（多采样对比、SFT vs Teacher、人工标注），不完全依赖 Teacher 的判断。人工标注的 500 条高风险偏好数据尤其重要——它们可以纠正 Teacher 的错误偏好。

第四，Safety-RAG 作为最终兜底——即使 Teacher/SFT/DPO 都错了，verifier 在推理时还会做一次验证。

整体设计逻辑：每个阶段都可能出错 → 每个阶段都有独立的校验机制 → 多阶段交叉验证降低整体错误率。这是'defense in depth'在后训练数据管线中的应用。"

## 追问 12：DPO 为什么会放大幻觉？⭐⭐⭐⭐⭐

"这个问题的根源在于 DPO 的 implicit reward 是什么样的。

DPO 将 reward 定义为 r(x,y) = β * log(π_θ(y|x) / π_ref(y|x))。训练过程中，模型通过调整策略 π_θ 来最大化这个隐式 reward。关键观察：什么样的特征会得到高 reward？——在偏好数据中，chosen 回答通常比 rejected 回答更完整、更有条理、更自信。于是 implicit reward 学到了一个'确定自信'的模式作为 reward 信号。

在常见问题上，模型确实有足够的知识来自信回答——这没问题。但在医疗长尾问题上，模型的知识是不足的。这时模型面临两个选择：
- 选项 A：诚实地说'我不确定这个具体情况'——但这类回答在偏好数据中往往是 rejected（因为看起来不够 helpful）
- 选项 B：编造一个看起来专业的回答——这类回答更接近 chosen 的风格，implicit reward 更高

DPO 的梯度会自动把模型的输出分布推向选项 B——因为选项 B 的 implicit reward 更高。

本质上，这是 alignment 中一个经典问题：reward model（包括 DPO 的 implicit reward）偏好'看起来好的回答'而非'真正正确的回答'。这就是为什么 alignment ≠ accuracy。"

## 追问 13：你的项目和普通微调项目有什么区别？⭐⭐⭐⭐

"跟普通微调项目相比，我觉得有三个本质区别：

第一，完整性。不是只做了 SFT——而是从数据生成策略到训练到评测到安全到部署的完整链路。这让我理解了后训练每个阶段之间的关系和 trade-off。

第二，问题驱动。不是'我会 DPO 所以做 DPO'——而是 SFT 后发现了安全需求，于是做 DPO；DPO 后发现了幻觉问题，于是设计 Safety-RAG。每个阶段的选择都是由前一个阶段的发现驱动的。这是一个真正的 research loop。

第三，安全意识。普通微调项目通常关注 accuracy/helpfulness，我也关注这些——但额外关注了 safety。我识别了 reward hacking 在医疗场景的具体表现，设计了针对性的安全方案。

如果要说本质区别：普通微调项目证明了'我会用工具'，这个项目试图证明'我能发现问题、分析问题、设计解决方案'。"

## 追问 16：如何解释评测分数提升不大？⭐⭐⭐

"如果评测分数提升不大（比如从 3.5/5 到 3.7/5），我会诚实地说：

首先，这个提升幅度在我们的方法下是合理的——DPO 主要改变的是偏好的细腻度（输出风格、安全性、完整性），而不是准确性的大幅变化。准确性更多由 SFT 数据质量决定。

其次，我认为不能只看 aggregate score——要看在不同维度上的分布变化。比如安全分数从 2.8 提升到 3.6（+28%），但准确性只从 3.9 到 4.0（+2%），这反映了 DPO 的核心价值在安全维度而非 accuracy 维度。

关键：不夸大不显著的结果，但也不 dismiss 自己做的 work——分析分数背后的含义。"

## 追问 20：如何回答"你对后训练算法真正理解在哪里"？⭐⭐⭐⭐⭐

"我的理解是：后训练的核心是'偏好学习与对齐'——把预训练生成的概率分布（predict next token）重新校准为符合人类偏好的分布。

但这不是简单的'教模型做对的事'——有几个深层的理解：

第一，后训练本质上是'分布偏移'（distribution shift）。SFT 把模型从 general text distribution 拉到 instruction-following distribution。DPO/RLHF 进一步把分布拉到 human-preferred distribution。每一步都在收缩和校准输出空间。这个'收缩'既有好处（更可控）也有风险（丧失多样性、reward hacking）。

第二，偏好不是一维的。一个回答可以在某些维度好（accuracy），在其他维度差（safety）。一维的 DPO reward 会把多个维度的偏好压缩成一个 scalar——这是 reward hacking 的根本原因。多维度的解耦（DAPO）或多方法互补（SFT+DPO+RAG）是更 principled 的方法。

第三，后训练的 data flywheel 比算法细节更决定上限。数据质量决定了 distribution shift 的'目的地'——如果数据有 bias，再好的算法也只能学到 biased policy。

第四，alignment tax 是真实存在的。提升 safety 可能会损害 helpfulness——过度拒答就是一个例子。好的后训练方案需要在多个维度间找到 Pareto frontier 上的最优平衡点。

如果要说'真正理解'——就是理解每个方法在 distribution space 中做了什么，理解为什么某些方法在某些场景 fail，理解 alignment 是一个 multi-objective optimization under uncertainty 的问题。"

### 追问 34：你怎么用 vLLM 部署的？LoRA merge 是什么？⭐⭐⭐⭐

"部署分两步：模型准备和 vLLM 配置。

第一步：LoRA Merge。公式是 W' = W + (α/r) × BA，把 adapter 合并到基座权重中，然后 dequantize 回 bf16。PEFT 库的 model.merge_and_unload() 直接完成。merge 后就可以被任何推理引擎加载，不依赖 PEFT 库。

为什么选 merge 而非动态 serving？我的项目只有一个 LoRA adapter，不需要多租户切换——merge 更简单高效，零额外推理开销。

第二步：vLLM 配置。关键启动参数：--max-model-len 4096（限制最大 context 长度，影响 KV cache 显存）、--gpu-memory-utilization 0.9（使用 90% GPU 显存）、--dtype bfloat16、--max-num-seqs 32。

选 max-num-seqs=32 是通过显存计算得出的：KV cache ≈ 2 × num_layers × num_kv_heads × head_dim × max-model-len × max-num-seqs × 2 bytes ≈ 10-12GB。加上模型 16GB = 28GB，RTX 5090 32GB 刚好够。"

### 追问 35：vLLM 为什么快？TTFT 和 TPOT 是什么？⭐⭐⭐⭐

"vLLM 快主要因为两个核心技术：

PagedAttention：传统 KV cache 预分配连续显存，利用率只有 20-30%。PagedAttention 将 KV cache 切分为固定大小的 block，按需分配、用完回收，利用率提升到 80-90%，同等显存可支撑 2-4 倍并发。

Continuous Batching：传统 static batching 必须等整个 batch 所有请求都完成才一起释放。Continuous batching 让完成的请求立即退出 batch，新请求立即加入——GPU 几乎无空闲。在长短序列混合的场景下，吞吐提升 2-5 倍。

TTFT (Time to First Token)：从发送请求到收到第一个 token 的时间，主要由 prefill 阶段决定。我们的项目 TTFT ≈ 42ms（短 prompt + RTX 5090）。

TPOT (Time per Output Token)：decode 阶段每个后续 token 的平均生成时间，因为 decode 是 memory-bound。我们的项目 TPOT ≈ 15ms。"

### 追问 36：你压测怎么做的？压测了什么指标？⭐⭐⭐⭐⭐

"我的压测方案分为准备、执行、分析三个阶段。

准备：构造了 100 条真实医疗问答的 prompt，用 Python asyncio + OpenAI client 并发调用 vLLM API。参数：stream=False（测纯延迟），temperature=0（保证可复现），max_tokens=512。

执行：梯度增压——并发从 1→2→4→8→16→32→48→64，每个并发级别持续 60s，每个级别做 3 轮取平均。

记录指标：
- 吞吐：总 output tokens / 总耗时（877 tok/s @ 32 并发）
- TTFT：p50=42ms, p95=68ms, p99=95ms
- TPOT：p50=15ms, p95=22ms, p99=35ms
- 端到端延迟：p50=1.5s, p95=2.3s, p99=3.8s
- 错误率：32 并发下 0%，48 并发偶发 timeout ~0.5%，64 并发 ~3%

分析：32 并发前吞吐线性增长，之后增速放缓但 TTFT 开始急剧上升（排队效应），判断 32 并发是饱和点。p99 延迟在高并发时明显恶化，因为少部分请求被长序列请求阻塞。

为什么 p99 重要：平均值会掩盖问题——32 并发下平均 TTFT 42ms，但 p99 已经是 95ms。如果 SLA 是 p99 TTFT < 200ms，32 并发还在安全范围内。"

## 工程高危追问 37-42：RAG 延迟与优化

### 追问 37：RAG 为什么慢？如何降低延迟？⭐⭐⭐⭐

"RAG 的延迟需要分阶段拆解。我的项目端到端约 1.9s，分解为：

- Query embedding：~8ms（<1%）
- FAISS 向量检索：~30ms（~2%）
- vLLM prefill：~50ms（~3%）
- vLLM decode（avg 100 tokens）：~1.5s（~80%）
- Safety-RAG verifier：~300ms（~15%）

Generation 是大头（80%），verifier 次之（15%）。优化优先级：

1. Generation：streaming 输出（首 token 后用户立即看到内容，感知延迟大幅降低）；限制 max_tokens。

2. Verifier：动态路由（简单问题跳过 verifier，预计 60-70% 请求可走 fast path，平均延迟降 20-40%）；verifier 模型量化（INT4）。

3. 检索：FAISS 索引优化（IVF/HNSW 替代 FlatIP）；embedding 模型换更轻量。

4. 并行化：多路召回 (dense+sparse) 用 asyncio.gather 并行，延迟取 max 而非 sum。

综合优化后预期总延迟可以从 1.9s 降到 ~1.0s（streaming 感知延迟 ~200ms）。"

---

### 追问 38：RAG 怎么并行？dense 和 sparse 怎么并行？⭐⭐⭐

"RAG 的并行化主要在三处：

1. 多路检索并行：dense 和 sparse 没有依赖关系，用 asyncio.gather 完全并行。并行后延迟 = max(30ms, 10ms) = 30ms，而非串行的 40ms。结果用 RRF (Reciprocal Rank Fusion) 融合。

2. 错误处理：asyncio.gather 用 return_exceptions=True，一个源失败不影响另一个。两个都失败 → 降级为纯 LLM 回答 + 提示"检索服务暂时不可用"。

3. 多 query 改写并行：同一个原始 query 生成多个改写版本，并行检索后融合结果。提高召回率的同时总延迟 = 单次检索延迟。

4. 注意事项：dense 和 sparse 本质是不同类型操作——dense 是 GPU/矩阵计算密集，sparse 是内存/字符串匹配密集。在 Python 层面 asyncio 并发它们没问题。"

### 追问 39：rerank 太慢怎么办？context 太长怎么办？⭐⭐⭐

**Rerank 慢的优化（5 种策略）**：
1. 模型选择：bge-reranker-base (278M, ~50ms) vs bge-reranker-large (~1B, ~150ms)
2. 减少 rerank 候选数：只对 top-20 做 rerank
3. 条件触发：检索分数置信度高（top-1 相似度 >0.85）时跳过 reranker
4. 批量推理：攒多个 query-doc pair 一次推理
5. 模型量化：ONNX/INT8 量化，延迟降 40-60%

**Context 太长的优化（4 种策略）**：
1. 文档摘要压缩：用轻量模型对长文档做摘要
2. 分块+选择性拼接：去掉无关内容
3. 滑动窗口 attention：限制每个 token attend 的范围
4. 多轮递进：先基于简短 context 回答，不确定时再追加 context

### 追问 40：如何优化 p99？如何做缓存？医疗数据能缓存吗？⭐⭐⭐⭐

**p99 优化**：
1. 超时降级：为 RAG 各阶段设 timeout——检索 >300ms 返回空、reranker >500ms 跳过、generation >10s 截断
2. 请求优先级：急症检测到的高风险 query 插队处理
3. 资源隔离：长 generation 请求单独路由到专用 GPU 副本
4. 预计算/预热：高频 query pattern 提前计算并存缓存

**缓存设计（四层）**：
1. Query Cache：相同/相似 query 的完整回答缓存
2. Embedding Cache：相同文本段的 embedding 向量缓存
3. Retrieval Cache：相同 query 的检索结果缓存
4. Rerank Cache：query+doc pair 的 rerank 分数缓存

**医疗数据能否缓存**：
- 能缓存的：知识库检索结果（公开医学知识）、不含 PHI 的常见医学问题
- 不能缓存的：包含患者个人信息的 query 和回答
- 需要小心的：个性化建议类回答不应跨用户共享缓存

### 追问 41：如何做服务限流/降级/熔断？⭐⭐⭐

"限流（Rate Limiting）：在网关层用令牌桶算法。Nginx limit_req_zone + limit_req。超限请求返回 429 + Retry-After header。

降级（Degradation）：三级策略。Level 1：vLLM 响应慢 → 限制 max_tokens 到 200。Level 2：vLLM 错误率 >20% → 回退到检索+规则引擎。Level 3：所有后端不可用 → 返回预设降级消息 + 静态 FAQ。

熔断（Circuit Breaker）：状态机 Closed→Open→Half-Open。连续 N 次失败 → Open（直接返回 fallback）→ 等待 probe_interval → Half-Open（放行探测请求）→ 成功则 Closed，失败继续 Open。

三者关系：限流保护系统不过载 → 降级保证服务基本可用 → 熔断保护系统不被故障拖垮。"

### 追问 42：如果检索服务/LLM 服务挂了怎么办？⭐⭐⭐

"分场景处理：

检索服务挂了：降级方案 1 → 跳过检索，LLM 基于自身训练知识直接回答，强制加提示'知识检索服务暂时不可用'。降级方案 2 → 切换到备用检索服务（ES 备份）。定期健康检查，服务恢复后自动切回正常 pipeline。

vLLM 服务挂了：降级方案 1 → 启动备用轻量 CPU 模型。降级方案 2 → 直接用检索到的知识库片段 + 固定模板拼接回答。降级方案 3 → 返回静态 FAQ。进程管理工具（systemd/supervisor）检测到进程退出后自动重启 vLLM。

核心原则：'任何服务都可能挂' → 设计时假设它会挂 → 准备好降级路径。这比依赖服务 100% 可靠更务实。"

## 工程高危追问 43-48：发布与监控

### 追问 43：如何灰度发布新模型？如何回滚？如何 A/B 测试？⭐⭐⭐⭐

**灰度发布 (Canary Release)**：
1. 部署新模型版本到独立 vLLM 实例
2. 在负载均衡层按比例切流：先切 5% 流量
3. 观察指标：延迟 p95（不能比旧模型差 >20%）、错误率（不能 >1%）、安全违规率（不能上升）
4. 正常 → 逐步加大：5% → 20% → 50% → 100%。每步观察 1-2 小时
5. 任何指标异常 → 立即回滚

**回滚 (Rollback)**：
1. 流量层面：负载均衡器把新模型权重设为 0，全量切回旧模型——秒级完成
2. 模型版本管理：每个版本有唯一标识，保存完整 checkpoint 和 merge 后的模型文件
3. 回滚决策：预先定义——安全违规率上升 >50%、p95 延迟恶化 >100%、错误率 >5%

**A/B 测试**：
与灰度发布不同——灰度是安全地"逐步替换"，A/B 是科学地"对比效果"。50% 用户 → A 版本，50% → B 版本（user_id hash 保证同一用户始终在同一组）。医学模型特殊点：安全指标必须作为 guardrail metric——任何一组的安全指标恶化都要停止实验。

> 我项目中没做 A/B 测试（因为没有用户），但我理解方法论和统计要求。

### 追问 44：如何做线上监控/日志脱敏/隐私保护？⭐⭐⭐⭐

**线上监控**：四个黄金信号——Latency（TTFT/TPOT p50/p95/p99）、Traffic（QPS、并发数）、Errors（4xx/5xx 错误率、安全告警率）、Saturation（GPU 利用率、显存使用率）。技术栈：prometheus_client → Prometheus → Grafana。

**日志脱敏**（三层策略）：
1. 识别层：用正则+NER 识别 PHI（姓名、身份证号、电话号码、年龄+具体诊断组合）
2. 脱敏层：姓名 → [REDACTED_NAME]，年龄 → [AGE_RANGE]，电话号码 → [REDACTED_PII]
3. 保留：纯粹医学知识问答不脱敏——脱敏粒度要合理

**隐私保护**：
1. 数据传输：HTTPS/TLS 加密
2. 数据存储：用户对话历史脱敏后存储，可设 TTL
3. 合规：医疗场景可能需要 HIPAA/GDPR/个人信息保护法合规
4. 缓存隔离：不同用户的缓存数据严格隔离

> 诚实地说：我的项目在本地环境，这些隐私保护措施是'设计方案'而非'已实施'。但医疗 AI 的数据隐私是不可妥协的——我的认知是明确的。

### 追问 45：如何把线上反馈反哺训练？⭐⭐⭐

"数据闭环（Data Flywheel）分四个阶段：

1. 反馈收集：显式反馈（赞/踩/举报）+ 隐式反馈（追问/转人工/浏览时间）+ 安全反馈

2. 反馈审核和标注：自动分级（Safety-RAG verifier 再做安全检查）→ 标记风险等级（A/B/C）→ 人工抽检

4. 模型更新：定期重新训练（月/季度）→ 灰度发布 → 监控安全指标 → 如果改善则全量

> 诚实说明：我的项目没有线上系统，数据闭环是设计方案而非实践。但我理解它的核心价值——没有数据闭环，模型上线后就是'一次性交付'。"

## 工程高危追问 46-48：分布式训练与推理

### 追问 46：你了解 DDP/FSDP/DeepSpeed 吗？⭐⭐⭐⭐

"我了解它们的原理和适用场景，虽然我的项目用 QLoRA 单/双卡就够了，没有实际操作这些分布式框架。

DDP：每个 GPU 有完整模型副本，backward 时自动 all-reduce 梯度。通信量 ≈ 2×参数量。适用场景：模型能放进单卡显存，需要多卡加速训练。

FSDP：模型参数分片到各 GPU，前向/反向时按需 all-gather。显存占用 ≈ 参数量/N。适用场景：模型太大放不进单卡。

DeepSpeed ZeRO Stages：
- ZeRO-1：只分片优化器状态，显存省约 4 倍
- ZeRO-2：分片优化器 + 梯度，显存省约 8 倍
- ZeRO-3：分片优化器 + 梯度 + 参数，显存省约 N 倍，通信量增加约 50%

为什么没用过：我的医学 LLM 项目硬件是 2×4090，QLoRA 把基座量化到 4bit（~4GB），只训练 LoRA 参数（~1GB），总显存 ~13GB——单卡都绰绰有余。我确实没有'需要用分布式训练'的场景。但如果面试的是需要大规模训练的岗位——我理解原理，需要在实践中积累工程经验。"

**避坑**：不要只说"听说过，但没实际用过"——如果是 0 经验，太弱了。要展示原理理解。

### 追问 47：单卡和多卡部署怎么选？多副本和 Tensor Parallel 怎么选？⭐⭐⭐⭐

"决策树：
1. 模型权重是否超过单卡可用显存的 70%？→ 是 → 考虑多卡 TP
2. 目标并发是否超过单卡 max batch 的 80%？→ 是 → 考虑多副本
3. 延迟 SLA 是否要求 p99 < 100ms TTFT？→ 是 → 考虑 TP

多副本 (Replica Parallel)：每个 GPU 加载完整模型，Nginx 分发请求。零通信开销、线性扩展、高可用。前提是模型能放进单卡。

Tensor Parallelism (TP)：将层内权重切分到多 GPU。突破单卡显存限制，但有 GPU 间通信开销。对消费级 PCIe 显卡，TP 可能使 decode 延迟恶化。

我们的项目：8B 模型 bf16 16GB，RTX 5090 32GB 单卡够放。32 并发也够用——用单卡部署。如果需要支持 100+ 并发，加多副本（Nginx 轮询），而不是 TP。这是最简单的方案——能用多副本就不用 TP。"

### 追问 48：医疗问答能不能流式输出？⭐⭐⭐⭐

"能，但医疗场景下有一些特殊考虑。

技术上完全可行：vLLM 支持 SSE streaming，每生成一个 token 立即推送。

医疗场景的特殊考虑：
1. 不能先输出不安全的 token 再撤回：医学场景中，如果模型流式输出了"建议您服用XX药物"的前几个 token，即使后面撤回，用户可能已经看到了不安全的建议。对策：Safety-RAG verifier 在 generation 开始前做验证（pre-generation verification）。

2. 免责声明在前：流式输出的第一个 chunk 应该是免责声明或安全提示。

3. 急症场景不流式：检测到急症关键词 → 不走流式 → 直接一次性返回急救建议模板。

4. Verifier 的异步修正：流式输出期间，verifier 在后台异步验证已生成的内容。如果发现问题，在流式结束后追加修正信息。

结论：医疗场景可以做流式，但需要 pre-generation 验证 + 免责前置 + 急症例外 + 异步修正。不加保护的流式输出在医疗场景是危险的。"
