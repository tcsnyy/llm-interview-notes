## 面试 1 分钟 / 3 分钟回答版本

### 1 分钟版（电梯 pitch）

> 大模型训练的并行策略分为四类：数据并行（每卡一份模型副本，不同数据）、张量并行（单层切分到多卡）、流水线并行（不同层放不同卡）、序列并行（长序列切分）。显存优化方面，ZeRO-1/2/3 分别对优化器状态、梯度、参数做分片，FSDP 是 PyTorch 原生实现。混合精度训练（BF16/FP16+FP32 master weights）、梯度检查点（用计算换显存）、梯度累积（用时间换大批次）是单卡场景的核心技巧。我的项目在 RTX 5090 单卡上用 QLoRA 完成了 8B 模型的 SFT 和 DPO 训练，如果扩展到 8 卡，我会使用 FSDP + gradient checkpointing + BF16 混合精度做全参数微调。

### 3 分钟版（含项目细节）

> 并行训练要解决的核心问题是"单卡放不下"。8B 模型全参数 BF16 训练需要约 64GB 显存（参数 16GB + 梯度 16GB + 优化器 32GB），远超单卡 32GB 上限。解决方案有四条路径。
>
> 第一，数据并行（DDP/DataParallel）。DataParallel 单机多卡在主卡聚合梯度，负载不均衡且 Python GIL 影响性能；DDP 每卡独立进程，用 all-reduce 通信，性能远优于 DP。关键概念包括 rank（全局进程序号）、world_size（总进程数）、local_rank（单机内 GPU 序号）、DistributedSampler 做数据分配。
>
> 第二，模型并行。张量并行（TP）把一个矩阵乘法切成多块分到多卡并行计算再合并，通信量极大，适合卡间 NVLink 高速互联；流水线并行（PP）把模型按层切分，存在"气泡"空闲问题。
>
> 第三，ZeRO/FSDP。ZeRO-1 分片优化器状态（省 4x），ZeRO-2 加分片梯度（省 8x），ZeRO-3 连参数都分片（省 N 倍）。FSDP 是 PyTorch 原生实现。
>
> 第四，混合精度与显存优化。BF16 前向反向 + FP32 master weights，gradient checkpointing 省 50-70% 激活显存，gradient accumulation 用多次 forward/backward 换等效大批次。
>
> 在我的项目中，由于使用 QLoRA（4bit 量化 + 仅训 LoRA），base model 只需约 4GB，总显存在 18-24GB 范围内，单卡 RTX 5090 即可完成。这是经过计算后的技术选型，不是"只有一张卡"的妥协——对于 QLoRA 级别的训练，单卡避免了通信开销。但我也掌握了分布式训练的理论知识，如果面试官问"8 卡怎么扩展"，我能给出具体的配置方案和通信策略设计。

## 1. 为什么大模型训练需要并行

### 1.1 四大瓶颈

| 瓶颈类型 | 具体表现 | 8B 模型示例 |
|---------|--------|------------|
| **显存瓶颈** | 单卡放不下模型+优化器+激活 | BF16 全参训练需 ~64GB，单卡 32GB 不够 |
| **计算瓶颈** | 单卡算力不够导致训练时间不可接受 | 8B 全参训练单卡可能需要数月 |
| **通信瓶颈** | 多卡间梯度同步成为延迟主要来源 | all-reduce 在大 batch 下通信量可达 GB 级 |
| **数据加载瓶颈** | CPU 预处理跟不上 GPU 消费 | tokenization 成为 pipeline 瓶颈 |

### 1.2 显存需求定量分析

```
全参数 BF16 训练 8B 模型的显存需求:
  模型参数 (Φ):        8B × 2 bytes = 16 GB
  梯度:                8B × 2 bytes = 16 GB
  优化器状态 (AdamW):  8B × 8 bytes = 64 GB  (m:4 bytes + v:4 bytes)
  激活值:              取决于 batch_size × seq_len, 通常 20-80 GB
  ─────────────────────────────────────────
  总计:                             116+ GB

对比 QLoRA (r=16, NF4):
  模型参数 (NF4):      8B × 0.5 bytes =  4 GB
  LoRA 权重 (BF16):    ~5.4M × 2     ≈  0.01 GB
  优化器状态 (8bit):   ~5.4M × 2     ≈  0.01 GB
  激活值 (grad ckpt):                 ~8-12 GB
  ─────────────────────────────────────────
  总计:                               ~18 GB  ← 单卡 32GB 可跑
```

## 2. 数据并行：DataParallel vs DDP

### 2.1 DataParallel (DP, torch.nn.DataParallel)

```
GPU0 (master):  model replica + batch[0:N/2] → forward → backward
                ↑ 聚合所有 GPU 的梯度
GPU1:           model replica + batch[N/2:N] → forward → backward
                ↑ 梯度发回 GPU0
```

**问题**：
1. **单主卡瓶颈**：GPU0 需要聚合所有梯度，负载不均衡。
2. **Python GIL 影响**：多线程（非多进程），受 Python 全局解释器锁限制。
3. **通信效率差**：每次前向都需要 broadcast 模型参数。
4. **不支持多机**：仅限单机多卡。

**本项目不使用 DP**。如果单机双卡推理会用，但训练不用。

### 2.2 DistributedDataParallel (DDP, torch.nn.parallel.DistributedDataParallel)

```
GPU0 (独立进程):  model replica + batch[0:N/2] → forward → backward → all-reduce gradients
GPU1 (独立进程):  model replica + batch[N/2:N] → forward → backward → all-reduce gradients
                  ↑ 每个 GPU 的梯度通过 all-reduce 同步后各自更新
```

**核心区别**：
- DP 用多线程 + 主卡聚合，DDP 用多进程 + all-reduce。
- DDP 每张卡独立进行 optimizer.step()，参数始终保持一致（因为 all-reduce 后梯度相同）。
- DDP 支持多机多卡，使用 NCCL 后端通信。

### 2.3 DDP 训练伪代码

```python
# ddp_training.py
import torch
import torch.distributed as dist
import torch.multiprocessing as mp
from torch.nn.parallel import DistributedDataParallel as DDP
from torch.utils.data import DataLoader, DistributedSampler


def setup(rank, world_size):
    """初始化分布式进程组"""
    # rank: 全局进程编号 (0 ~ world_size-1)
    # world_size: 总 GPU 数量
    dist.init_process_group(
        backend="nccl",           # NVIDIA NCCL，GPU 通信最优
        init_method="env://",     # 从环境变量读取 MASTER_ADDR/MASTER_PORT
        rank=rank,
        world_size=world_size,
    )
    torch.cuda.set_device(rank)  # 绑定当前进程到对应 GPU


def cleanup():
    dist.destroy_process_group()


def train_one_epoch(model, dataloader, optimizer, rank):
    """单 epoch DDP 训练"""
    model.train()
    # DDP 自动处理梯度同步
    for batch_idx, batch in enumerate(dataloader):
        # 数据已在 DistributedSampler 层面分配好
        input_ids = batch["input_ids"].to(rank)
        labels = batch["labels"].to(rank)

        outputs = model(input_ids=input_ids, labels=labels)
        loss = outputs.loss

        optimizer.zero_grad()
        loss.backward()
        # DDP 在 backward 时自动 all-reduce 梯度（通过 hook）
        optimizer.step()

        # 只在 rank 0 打印，避免重复输出
        if rank == 0 and batch_idx % 100 == 0:
            print(f"Step {batch_idx}, Loss: {loss.item():.4f}")


def main_worker(rank, world_size):
    setup(rank, world_size)

    # 标准模型加载
    from transformers import AutoModelForCausalLM
    model = AutoModelForCausalLM.from_pretrained(
        "Qwen/Qwen3-8B",
        torch_dtype=torch.bfloat16,
    ).to(rank)

    # 用 DDP 包装模型
    model = DDP(model, device_ids=[rank])

    # DistributedSampler：确保每个 GPU 处理不重叠的数据
    from torch.utils.data import TensorDataset
    # 假设 dataset 已构建好
    dataset = TensorDataset(...)
    sampler = DistributedSampler(
        dataset,
        num_replicas=world_size,  # 总 GPU 数
        rank=rank,                # 当前 GPU 编号
        shuffle=True,
        seed=42,
    )
    dataloader = DataLoader(
        dataset,
        batch_size=2,       # per-GPU batch size
        sampler=sampler,    # 用 sampler 替代 shuffle
        num_workers=4,      # 数据加载子进程数
        pin_memory=True,    # 加速 CPU→GPU 数据传输
    )

    optimizer = torch.optim.AdamW(model.parameters(), lr=2e-4)

    train_one_epoch(model, dataloader, optimizer, rank)

    cleanup()


if __name__ == "__main__":
    world_size = torch.cuda.device_count()
    mp.spawn(main_worker, args=(world_size,), nprocs=world_size)
```

## 3. 模型并行：张量并行 (TP) 与流水线并行 (PP)

### 3.1 张量并行 (Tensor Parallelism, TP)

将单个 Transformer 层的矩阵计算切分到多张 GPU 上并行计算：

```
原始计算:
  Y = X @ W    (W ∈ R^{4096×4096})

张量并行 (按列切 W):
  GPU0: W[:, 0:2048]  →  Y0 = X @ W_col0
  GPU1: W[:, 2048:4096] → Y1 = X @ W_col1
  合并: Y = concat(Y0, Y1)

张量并行 (按行切 W):
  GPU0: W[0:2048, :] × X → 需要先分 X 或用 all-reduce
```

**特点**：
- 通信量极大：每次前向都要在 GPU 间传递中间激活。
- 适合 NVLink 高速互联（如单机 8 卡）。
- Megatron-LM 是经典实现。
- 本项目不需要（单卡训练，无 TP 需求）。

### 3.2 流水线并行 (Pipeline Parallelism, PP)

将模型按层切分到不同 GPU：

```
GPU0: Embedding + Layer 0-7    → 前向 → 传激活给 GPU1
GPU1: Layer 8-15               → 前向 → 传激活给 GPU2
GPU2: Layer 16-23              → 前向 → 传激活给 GPU3
GPU3: Layer 24-31 + LM Head    → 前向 → 计算 loss

反向时逆序回传梯度。
```

**"气泡"问题**：

```
时间轴 → (F=forward, B=backward, .=idle)

GPU0: F0 F1 F2 F3 B3 B2 B1 B0
GPU1: .. F0 F1 F2 F3 B3 B2 B1 B0
GPU2: .... F0 F1 F2 F3 B3 B2 B1 B0
GPU3: ...... F0 F1 F2 F3 B3 B2 B1 B0
       ↑ 气泡：GPU2/GPU3 在等待 GPU0/GPU1 完成前向
```

优化技术：GPipe（按 micro-batch 流水）、1F1B（one-forward-one-backward）调度。

### 3.3 3D 并行

Megatron-LM 提出的组合方案：

```
3D 并行 = TP (卡内) × PP (层间) × DP (数据间)

例如: 256 张 GPU
  TP=8  (单机 8 卡做张量并行)
  PP=4  (4 台机器做流水线并行)
  DP=8  (8 组做数据并行)
  总卡数 = 8 × 4 × 8 = 256
```

## 4. ZeRO / FSDP / DeepSpeed

### 4.1 ZeRO-1/2/3 逐级对比

| ZeRO 阶段 | 分片内容 | 每卡显存节省 | 通信量 | 实现复杂度 |
|-----------|---------|-------------|--------|-----------|
| ZeRO-1 | 优化器状态 (m, v) | ~4x | 低 | 低 |
| ZeRO-2 | 优化器状态 + 梯度 | ~8x | 中 | 中 |
| ZeRO-3 | 优化器状态 + 梯度 + 参数 | ~N 倍 (N=GPU数) | 高 | 高 |

```
ZeRO-1 工作原理:
  GPU0: 完整模型 + 优化器状态[0:N/2]
  GPU1: 完整模型 + 优化器状态[N/2:N]
  更新时: all-gather 优化器状态 → 各自更新 → 不需要同步参数（各自持有完整副本）

ZeRO-2 工作原理:
  GPU0: 完整模型 + 优化器状态[0:N/2] + 梯度[0:N/2]
  backward 时做 reduce-scatter (而非 all-reduce)，每卡只保留自己那部分梯度

ZeRO-3 工作原理:
  GPU0: 模型参数[0:N/2] + 优化器状态[0:N/2] + 梯度[0:N/2]
  前向时: all-gather 需要的参数片段 → 用完释放
  反向时: all-gather 需要的参数 → 计算梯度 → reduce-scatter
```

### 4.3 FSDP 训练伪代码

```python
import torch
import torch.distributed as dist
from torch.distributed.fsdp import (
    FullyShardedDataParallel as FSDP,
    MixedPrecision,
    ShardingStrategy,
    BackwardPrefetch,
    StateDictType,
    FullStateDictConfig,
)
from torch.distributed.fsdp.wrap import (
    transformer_auto_wrap_policy,
    size_based_auto_wrap_policy,
)
from transformers.models.qwen2.modeling_qwen2 import Qwen2DecoderLayer
import functools


def fsdp_training_setup(model, rank):
    """FSDP 训练配置"""

    # 混合精度策略
    mixed_precision_policy = MixedPrecision(
        param_dtype=torch.bfloat16,    # 参数存储为 BF16
        reduce_dtype=torch.bfloat16,   # 梯度 reduce 用 BF16
        buffer_dtype=torch.bfloat16,   # buffer 用 BF16
    )

    # FSDP 分片策略
    # FULL_SHARD → ZeRO-3 级别（参数+梯度+优化器全分片）
    # SHARD_GRAD_OP → ZeRO-2 级别
    # HYBRID_SHARD → 节点内全分片 + 节点间数据并行
    sharding_strategy = ShardingStrategy.FULL_SHARD

    # 自动包装策略：每个 Transformer 层作为一个 FSDP unit
    auto_wrap_policy = functools.partial(
        transformer_auto_wrap_policy,
        transformer_layer_cls={Qwen2DecoderLayer},
    )

    model = FSDP(
        model,
        auto_wrap_policy=auto_wrap_policy,
        sharding_strategy=sharding_strategy,
        mixed_precision=mixed_precision_policy,
        backward_prefetch=BackwardPrefetch.BACKWARD_PRE,  # 预取下一层参数
        device_id=torch.cuda.current_device(),
        cpu_offload=False,  # 设为 True 可将参数 offload 到 CPU
        limit_all_gathers=True,  # 限制 all-gather 并发，节省显存
    )

    return model


def save_fsdp_checkpoint(model, rank, save_path):
    """FSDP checkpoint 保存（需要先收集完整 state_dict）"""
    from torch.distributed.fsdp import FullStateDictConfig, StateDictType

    save_policy = FullStateDictConfig(offload_to_cpu=True, rank0_only=True)
    with FSDP.state_dict_type(model, StateDictType.FULL_STATE_DICT, save_policy):
        state_dict = model.state_dict()
        if rank == 0:
            torch.save(state_dict, save_path)

# model = fsdp_training_setup(model, local_rank)
# ... 训练 loop 与 DDP 相同
```

### 4.4 ZeRO-Offload

将优化器状态和梯度卸载到 CPU 内存，进一步降低 GPU 显存：

## 5. FP32 / FP16 / BF16 / INT8 / INT4 与 AMP

### 5.1 数值精度对比

| 精度 | 总位数 | 符号 | 指数 | 尾数 | 动态范围 | 典型用途 |
|------|--------|------|------|------|---------|---------|
| FP32 | 32 | 1 | 8 | 23 | ~10^38 | 训练 master weights |
| BF16 | 16 | 1 | 8 | 7 | ~10^38 | 训练前向/反向计算（主流） |
| FP16 | 16 | 1 | 5 | 10 | ~65504 | 推理加速 |
| INT8 | 8 | 1 | — | 7 | 256 级 | 推理量化 |
| INT4 | 4 | — | — | — | 16 级 | 训练量化（QLoRA）/ 推理 |

### 5.2 AMP (Automatic Mixed Precision) 代码

```python
import torch
import torch.cuda.amp as amp


def amp_training_step_fp16(model, batch, optimizer):
    """FP16 AMP 训练（需要 loss scaling）"""
    scaler = amp.GradScaler()

    with amp.autocast(device_type="cuda", dtype=torch.float16):
        outputs = model(**batch)
        loss = outputs.loss

    optimizer.zero_grad()
    scaler.scale(loss).backward()   # 放大梯度
    scaler.unscale_(optimizer)       # 还原梯度（用于 clipping）
    torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
    scaler.step(optimizer)           # 更新参数（自动 skip 无效更新）
    scaler.update()                  # 动态调整 scale 因子

    return loss.item()


def amp_training_step_bf16(model, batch, optimizer):
    """BF16 AMP 训练（不需要 loss scaling）"""
    with amp.autocast(device_type="cuda", dtype=torch.bfloat16):
        outputs = model(**batch)
        loss = outputs.loss

    optimizer.zero_grad()
    loss.backward()
    torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
    optimizer.step()

    return loss.item()
```

**本项目使用 BF16**：RTX 5090 原生支持 BF16 Tensor Core 计算，BF16 的 8 位指数与 FP32 相同，不需要 loss scaling，训练更稳定。

### 5.3 为什么 BF16 比 FP16 更适合训练

> "FP16 的指数位只有 5 位，动态范围 [-65504, 65504]，小梯度容易 underflow 为 0。需要用 loss scaling 把梯度放大到 FP16 可表示的范围内，然后在更新前还原。这个过程引入了额外的复杂度——scale 因子需要动态调整，调不好训练就不稳定。BF16 用 8 位指数（和 FP32 一样），动态范围约 10^38，小梯度不会 underflow，训练不需要 loss scaling，代码更简洁，训练更稳定。代价是尾数精度从 10 位降到 7 位，但实践证明这对深度学习训练的收敛基本没有影响。"

## 6. Gradient Checkpointing / Gradient Accumulation / Gradient Clipping

### 6.1 Gradient Accumulation 代码

```python
def training_loop_with_grad_accum(model, dataloader, optimizer,
                                   grad_accum_steps=8):
    """梯度累积训练循环"""
    model.train()
    optimizer.zero_grad()

    for step, batch in enumerate(dataloader):
        outputs = model(**batch)
        loss = outputs.loss

        # 缩放 loss（因为要累积多个 micro batch）
        # 如果 loss 是 mean reduction，需要除以 grad_accum_steps
        # 才能保持 effective batch 的 loss 与直接大 batch 等价
        loss = loss / grad_accum_steps
        loss.backward()

        # 每 grad_accum_steps 步更新一次
        if (step + 1) % grad_accum_steps == 0:
            torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
            optimizer.step()
            optimizer.zero_grad()

            print(f"Step {step + 1}: Effective batch update completed")

    # 处理最后不完整的累积
    if (step + 1) % grad_accum_steps != 0:
        optimizer.step()
        optimizer.zero_grad()
```

## 7. 显存分解：参数 / 梯度 / 优化器状态 / 激活值

### 7.1 显存估算伪代码

```python
def estimate_memory(
    num_params: int,          # 总参数量
    num_trainable_params: int, # 可训练参数量（QLoRA 中很小）
    batch_size: int,
    seq_len: int,
    hidden_size: int,
    num_layers: int,
    dtype_bytes: int = 2,     # BF16 = 2 bytes
    optimizer: str = "adamw",
    use_qlora: bool = False,
    use_grad_ckpt: bool = True,
):
    """估算训练显存"""
    memory = {}

    # 1. 模型参数
    if use_qlora:
        # QLoRA: base model 用 4bit（0.5 bytes/param）
        memory["base_model_4bit"] = (num_params - num_trainable_params) * 0.5
        # 反量化 overhead（块量化常数）
        memory["quant_constants"] = memory["base_model_4bit"] * 0.127  # ~12.7%
    else:
        memory["model_params"] = num_params * dtype_bytes

    # 2. 可训练参数 (LoRA adapter)
    memory["trainable_params"] = num_trainable_params * dtype_bytes

    # 3. 梯度（只对可训练参数）
    memory["gradients"] = num_trainable_params * dtype_bytes

    # 4. 优化器状态
    if optimizer == "adamw":
        # AdamW: m (moment1) + v (moment2), 各 FP32
        if use_qlora:
            # paged_adamw_8bit: 1 byte per state
            memory["optimizer_states"] = num_trainable_params * 2 * 1
        else:
            memory["optimizer_states"] = num_trainable_params * 2 * 4  # FP32

    # 5. 激活值（粗略估算）
    tokens_per_batch = batch_size * seq_len
    bytes_per_token_per_layer = hidden_size * dtype_bytes * 2  # ~forward+backward
    if use_grad_ckpt:
        # 只保存 checkpoint 节点的激活
        memory["activations"] = tokens_per_batch * bytes_per_token_per_layer * \
                                (num_layers ** 0.5) * 0.6
    else:
        memory["activations"] = tokens_per_batch * bytes_per_token_per_layer * \
                                num_layers

    # 6. KV Cache (主要是推理，训练也有部分)
    # 训练时 KV Cache 通常不被显式保留（Teacher Forcing 并行计算）
    # 但在 DPO 的 reference 前向时会临时占用
    memory["kv_cache"] = 0  # 训练期间 KV 不持久缓存的实现
    memory["cuda_overhead"] = 1.5 * 1e9  # ~1.5 GB CUDA context

    total = sum(memory.values())
    memory["total_gb"] = total / 1e9

    return memory


# ==== 示例计算 ====

    num_params=8_000_000_000,
    num_trainable_params=8_000_000_000,
    batch_size=2, seq_len=2048, hidden_size=4096, num_layers=32,
    use_qlora=False, use_grad_ckpt=True,
)
print(f"全参训练: {result_full['total_gb']:.1f} GB")
# 输出 ≈ 60-80 GB

# Qwen3-8B QLoRA 训练 (r=16)

    num_params=8_000_000_000,
    num_trainable_params=5_400_000,  # ~5.4M LoRA params
    batch_size=2, seq_len=2048, hidden_size=4096, num_layers=32,

# 输出 ≈ 16-20 GB
```

## 8. QLoRA 为什么省显存（与分布式对比视角）

### 8.1 四条省显存路径的对比

| 方法 | 原理 | 显存节省 | 代价 |
|------|------|---------|------|
| **QLoRA (本项目)** | 4bit 量化 + 只训 adapter | 约 5x | 精度略降，表达能力有限 |
| **ZeRO-3** | 参数/梯度/优化器全分片 | 约 N 倍 | 大量通信，需要高速互联 |
| **Gradient Checkpointing** | 不存激活值，反向重算 | 约 2x (激活部分) | 20-30% 额外计算 |
| **CPU Offload** | 优化器/参数放 CPU | 随 CPU 内存而定 | PCIe 带宽瓶颈 |

### 8.2 项目选择 QLoRA 的原因

> "单卡 + QLoRA 组合不是因为'只有一张卡'，而是经过计算的合理技术选型。8B 级别的 QLoRA 训练，单卡显存已足够，引入分布式反而增加了通信开销和代码复杂度。这体现了'用合适的工具解决合适的问题'的工程思维。如果扩展到 70B 模型或全量微调，分布式就是必需的。"

## 9. DPO 为什么比 SFT 更吃显存

### 9.1 标准回答

> "DPO 的核心 loss 需要同时计算 4 次前向传播：policy model 对 chosen response 的前向、policy model 对 rejected response 的前向、reference model 对 chosen response 的前向、reference model 对 rejected response 的前向。而 SFT 只需要 1 次前向（policy model 对 chosen response）。这导致两个关键问题：第一，激活值翻约 4 倍（如果 reference model 也常驻显存）；第二，reference model 本身需要额外显存加载。因此 DPO 的显存峰值通常是 SFT 的 1.5-2 倍。"

### 9.2 DPO 显存计算

```
DPO 单步显存需求:
  Base Model (NF4)          4 GB      [共享]
  Reference Model (NF4)     4 GB      [额外！SFT 没有]
  激活值 (4× forward)     ~16 GB      [SFT 只需 ~4 GB]
  LoRA 参数 + 优化器     ~0.05 GB
  ─────────────────────────────────
  总计                    ~24 GB      [SFT 约 12-14 GB]

解决策略（本项目采用）:
  1. Pre-compute reference log-probs → 消除 reference model 加载
  2. micro_batch_size=1 → 最小激活值
  3. gradient_checkpointing=True → 激活重计算
  4. max_seq_length=2048 → 控制序列长度
```

## 10. Training Throughput 统计代码

```python
import time
import torch
from collections import deque


class ThroughputTracker:
    """训练吞吐量统计"""

    def __init__(self, window_size=100):
        self.start_time = time.time()
        self.step_times = deque(maxlen=window_size)
        self.total_tokens = 0

    def update(self, batch_size, seq_len, step_time=None):
        """记录每个 step 的吞吐"""
        if step_time is None:
            step_time = time.time() - self.start_time
            self.start_time = time.time()

        tokens = batch_size * seq_len
        self.total_tokens += tokens
        self.step_times.append((tokens, step_time))

    def get_stats(self):
        """计算吞吐统计"""
        if not self.step_times:
            return {}

        total_tokens = sum(t for t, _ in self.step_times)
        total_time = sum(s for _, s in self.step_times)
        elapsed = time.time() - self.start_time

        return {
            "tokens_per_second": total_tokens / total_time if total_time > 0 else 0,
            "samples_per_second": len(self.step_times) / total_time if total_time > 0 else 0,
            "total_tokens_processed": self.total_tokens,
            "avg_step_time_ms": (total_time / len(self.step_times)) * 1000,
            "effective_tokens_per_second": (
                total_tokens * 8 / total_time if total_time > 0 else 0
            ),  # effective batch size 下的 tokens/s
        }


# 使用示例
tracker = ThroughputTracker()

for step, batch in enumerate(dataloader):
    step_start = time.time()

    outputs = model(**batch)
    loss = outputs.loss
    loss.backward()

    if (step + 1) % grad_accum_steps == 0:
        optimizer.step()
        optimizer.zero_grad()

    step_time = time.time() - step_start
    tracker.update(batch_size=2, seq_len=2048, step_time=step_time)

stats = tracker.get_stats()
print(f"Training throughput: {stats['tokens_per_second']:.1f} tokens/s")
print(f"Samples per second: {stats['samples_per_second']:.2f}")
print(f"Avg step time: {stats['avg_step_time_ms']:.0f} ms")
```

```python
from torch.utils.data import Sampler

class BucketBatchSampler(Sampler):
    """按序列长度分桶，减少 padding 浪费"""
    def __init__(self, lengths, batch_size, bucket_boundaries):
        self.buckets = self._create_buckets(lengths, bucket_boundaries)
        self.batch_size = batch_size

    def _create_buckets(self, lengths, boundaries):
        buckets = {b: [] for b in boundaries}
        for idx, length in enumerate(lengths):
            for boundary in boundaries:
                if length <= boundary:
                    buckets[boundary].append(idx)
                    break
        return buckets

    def __iter__(self):
        # 从每个桶中随机取 batch
        for bucket in self.buckets.values():
            random.shuffle(bucket)
            for i in range(0, len(bucket), self.batch_size):
                yield bucket[i:i + self.batch_size]
```

## 12. Loss NaN 排查 / OOM 排查 / Checkpoint Resume

### 12.1 Loss NaN 排查决策树

```
Loss 突然变成 NaN:
├── 步骤 1: 检查是否是某个 batch 的问题
│   └── 用 torch.autograd.detect_anomaly() 定位
├── 步骤 2: 检查学习率是否过大
│   └── 尝试 lr/10 重新运行
├── 步骤 3: 检查数据是否有 NaN/Inf
│   └── 遍历 dataloader 检查每个 tensor
├── 步骤 4: 检查是否是 FP16 溢出
│   └── 换 BF16 或减小 loss scale
├── 步骤 5: 检查 attention mask 是否正确
│   └── padding token 是否被正确 mask
└── 步骤 6: 降低 max_grad_norm (如 1.0 → 0.3)
```

### 12.2 OOM 排查决策树

```
CUDA OOM 了:
├── 先看发生在哪个阶段
│   ├── forward → batch size 太大 → 减小 batch_size
│   ├── backward → 激活值太大 → 开 gradient_checkpointing
│   └── optimizer.step() → 优化器状态 → 换 paged_adamw_8bit
├── 如果 batch_size=1 还 OOM:
│   ├── DPO: pre-compute reference log-probs
│   ├── SFT: 减少 max_seq_len 或换更小模型
│   └── 检查是否意外加载了多个模型副本
└── 如果显存使用 < 90% 但 OOM:
    └── 碎片化 → PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True
```

## 13. 面试核心问答

### 13.1 "单卡 5090 怎么训练 8B"标准回答

> "我们使用 QLoRA 技术。核心思路是 4bit NF4 量化把 8B 参数从 16GB 压缩到约 4GB，只训练 LoRA adapter（约 5.4M 参数，占总参数 0.07%），优化器状态用 paged_adamw_8bit 进一步压缩和可选的 CPU offload，激活值通过 gradient checkpointing 省 50-70%。SFT 阶段 batch_size=2、grad_accum=8、max_seq_len=2048，显存峰值约 18GB。DPO 阶段 batch_size=1、grad_accum=8，通过 pre-compute reference log-probs 消除 reference model 加载，显存峰值约 22-24GB。32GB 显存还有约 8-10GB 的安全余量，训练非常稳定。这个配置不是'勉强能跑'，而是'运行在舒适区'。"

### 13.2 "DPO 为什么更吃显存"标准回答

> "DPO loss 需要 4 次前向传播：policy model 分别对 chosen 和 rejected response 计算 log-prob（2 次），reference model 分别对 chosen 和 rejected response 计算 log-prob（又是 2 次）。而 SFT 只需要 1 次前向。此外，reference model 本身额外占用显存（约 4GB in NF4）。因此 DPO 的显存需求是 SFT 的 1.5-2 倍。我们的优化方案是 pre-compute 所有 reference log-probs 并存入训练数据集，训练时完全不加载 reference model，把 DPO 的显存需求降到接近 SFT 水平。"

### 13.3 "如果给你 8 卡你怎么扩展训练"标准回答

> "如果扩展到 8 卡 A100/H100，我会考虑以下方案：
>
> **方案 A（保守，QLoRA + DDP）**：保持 QLoRA 配置不变，8 卡做数据并行（DDP）。每卡独立训练自己的数据分片，梯度通过 all-reduce 同步。effective batch size 可以做到 128（8卡 × 2 batch × 8 grad_accum），训练收敛更快。代码改动最小，适合快速验证。
>
> **方案 B（进阶，FSDP + 全量微调）**：如果有 8 卡 A100（80GB），可以做全参数微调。使用 FSDP（FULL_SHARD 策略）把 8B 模型的参数/梯度/优化器状态分片到 8 张卡上，每卡显存约 8-10GB（参数）+ 激活值 ~20GB，总计约 30GB，在 80GB 范围内容易容纳。设置 mixed precision = BF16，gradient checkpointing 开启。8 卡用 NCCL over NVLink 通信，带宽足够。
>
> **方案 C（扩展 70B+）**：如果是 Qwen3-72B 或更大的模型，需要用 3D 并行：TP（张量并行，单机 8 卡内）+ PP（流水线并行，如果跨节点）+ DP（数据并行，多节点间）+ ZeRO-3。使用 Megatron-LM 或 DeepSpeed + HuggingFace 集成。这种规模下通信拓扑设计（NVSwitch / InfiniBand）和数据加载优化变得至关重要。
>
> 对于我的项目场景（8B QLoRA），方案 A 是最务实的——代码改动最小，通信开销可忽略（LoRA 参数只有 5M，all-reduce 传输量极小），主要收益是 8x 的吞吐提升。"

## 14. 背诵版总结

### 核心概念速记表

| 概念 | 一句话 | 本项目状态 |
|------|--------|-----------|
| DDP vs DP | DDP 多进程 all-reduce，DP 多线程主卡汇聚 | 未使用 |
| DistributedSampler | 每卡分配不重叠数据子集 | 掌握理论 |
| NCCL | NVIDIA GPU 通信后端，优化 all-reduce/broadcast | 掌握理论 |
| ZeRO-1 | 分片优化器状态 | 类比 paged optimizer |
| ZeRO-2 | 分片优化器状态 + 梯度 | 掌握理论 |
| ZeRO-3 | 分片参数 + 梯度 + 优化器 | 掌握理论 |
| FSDP | PyTorch 原生 ZeRO-3 | 掌握理论 |
| TP / PP | 张量并行 / 流水线并行 | 了解 |
| BF16 vs FP16 | BF16 动态范围大，无需 loss scaling | 项目使用 |
| AMP | 前向反向半精度，master weights FP32 | 项目使用 |
| Gradient Checkpointing | 反向时重算激活值，省 50-70% 显存 | 项目使用 |
| Gradient Accumulation | 多次 forward/backward 换等效大批次 | 项目使用 |
| QLoRA 为啥省显存 | NF4 4bit + 只训 LoRA adapter | 项目核心 |
| DPO 为啥更吃显存 | 4 次 forward + reference model | 项目验证 |

### 重要数字速记

| 项目 | 数值 |
|------|------|
| 8B BF16 全参训需要显存 | ~64GB+ (不含激活) |
| 8B QLoRA SFT 显存 (本项目) | ~18GB |
| 8B QLoRA DPO 显存 (本项目) | ~22-24GB |
| LoRA 可训练参数占比 | 0.07% (5.4M / 8B) |
| Gradient Checkpointing 节省 | 50-70% 激活显存 |
| ZeRO-3 显存节省 | N 倍 (N=GPU 数) |
| BF16 dynamic range | ~10^38 (同 FP32) |
| FP16 dynamic range | ~65504 |
