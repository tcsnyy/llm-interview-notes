## 面试 1 分钟 / 3 分钟回答版本

### 1 分钟版

> 大模型训练的并行策略分为四类：数据并行（每卡一份模型副本，不同数据）、张量并行（单层切分到多卡）、流水线并行（不同层放不同卡）、序列并行（长序列切分）。显存优化方面，ZeRO-1/2/3 分别对优化器状态、梯度、参数做分片，FSDP 是 PyTorch 原生实现。混合精度训练（BF16/FP16+FP32 master weights）、梯度检查点（用计算换显存）、梯度累积（用时间换大批次）是单卡场景的核心技巧。我的项目在 RTX 5090 单卡上用 QLoRA 完成了 8B 模型的 SFT 和 DPO 训练，如果扩展到 8 卡，我会使用 FSDP + gradient checkpointing + BF16 混合精度做全参数微调。

### 3 分钟版（含项目细节）

> 并行训练要解决的核心问题是"单卡放不下"。8B 模型全参数 BF16 训练需要约 64GB 显存（参数 16GB + 梯度 16GB + 优化器 32GB），远超单卡 32GB 上限。解决方案有四条路径。
>
> 第一，数据并行（DDP）。每卡独立进程，用 all-reduce 通信。关键概念包括 rank（全局进程序号）、world_size（总进程数）、local_rank（单机内 GPU 序号）、DistributedSampler 做数据分配。
>
> 第二，模型并行。张量并行（TP）把一个矩阵乘法切成多块分到多卡并行计算再合并，通信量极大；流水线并行（PP）把模型按层切分，存在"气泡"空闲问题。
>
> 第三，ZeRO/FSDP。ZeRO-1 分片优化器状态（省 4x），ZeRO-2 加分片梯度（省 8x），ZeRO-3 连参数都分片（省 N 倍）。FSDP 是 PyTorch 原生实现。
>
> 第四，混合精度与显存优化。BF16 前向反向 + FP32 master weights，gradient checkpointing 省 50-70% 激活显存，gradient accumulation 用多次 forward/backward 换等效大批次。
>
> 在我的项目中，由于使用 QLoRA（4bit 量化 + 仅训 LoRA），base model 只需约 4GB，总显存在 18-24GB 范围内，单卡 RTX 5090 即可完成。这是经过计算后的技术选型，不是"只有一张卡"的妥协。但我掌握了分布式训练的理论知识，如果面试官问"8 卡怎么扩展"，我能给出具体的配置方案和通信策略设计。

## 1. 为什么大模型训练需要并行

### 1.1 四大瓶颈

| 瓶颈类型 | 具体表现 | 8B 模型示例 |
|---------|--------|------------|
| **显存瓶颈** | 单卡放不下模型+优化器+激活 | BF16 全参训练需 ~64GB，单卡 32GB 不够 |
| **计算瓶颈** | 单卡算力不够导致训练时间不可接受 | 8B 全参训练单卡可能需要数月 |
| **通信瓶颈** | 多卡间梯度同步成为延迟主要来源 | all-reduce 在大 batch 下通信量可达 GB 级 |
| **数据加载瓶颈** | CPU 预处理跟不上 GPU 消费 | tokenization 成为 pipeline 瓶颈 |

### 1.2 显存需求定量分析

```
全参数 BF16 训练 8B 模型的显存需求:
  模型参数 (Φ):        8B × 2 bytes = 16 GB
  梯度:                8B × 2 bytes = 16 GB
  优化器状态 (AdamW):  8B × 8 bytes = 64 GB  (m:4 bytes + v:4 bytes)
  激活值:              取决于 batch_size × seq_len, 通常 20-80 GB
  ─────────────────────────────────────────
  总计:                             116+ GB

对比 QLoRA (r=16, NF4):
  模型参数 (NF4):      8B × 0.5 bytes =  4 GB
  LoRA 权重 (BF16):    ~5.4M × 2     ≈  0.01 GB
  优化器状态 (8bit):   ~5.4M × 2     ≈  0.01 GB
  激活值 (grad ckpt):                 ~8-12 GB
  ─────────────────────────────────────────
  总计:                    ~18 GB  ← 单卡 32GB 可跑
```

## 2. 数据并行：DataParallel vs DDP

### DDP (DistributedDataParallel) 核心原理

每个 GPU 独立进程有完整模型副本，处理不同 micro-batch。反向传播时 `loss.backward()` 自动触发 all-reduce 同步梯度。各 GPU 独立 optimizer.step()（因梯度相同，参数更新一致）。用 NCCL 后端通信，支持多机多卡。

**核心区别**：DP 用多线程 + 主卡聚合（有单主卡瓶颈 + Python GIL 限制），DDP 用多进程 + all-reduce（无主卡瓶颈）。

### DDP 训练伪代码

```python
import torch
import torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP

def setup(rank, world_size):
    dist.init_process_group(backend="nccl", init_method="env://",
                            rank=rank, world_size=world_size)
    torch.cuda.set_device(rank)

def train_one_epoch(model, dataloader, optimizer, rank):
    model.train()
    for batch in dataloader:
        input_ids = batch["input_ids"].to(rank)
        labels = batch["labels"].to(rank)
        outputs = model(input_ids=input_ids, labels=labels)
        loss = outputs.loss
        optimizer.zero_grad()
        loss.backward()  # DDP 在 backward 时自动 all-reduce 梯度
        optimizer.step()
        if rank == 0 and batch_idx % 100 == 0:
            print(f"Step {batch_idx}, Loss: {loss.item():.4f}")

if __name__ == "__main__":
    world_size = torch.cuda.device_count()
    mp.spawn(main_worker, args=(world_size,), nprocs=world_size)
```

### torchrun 启动命令

```bash
# 从节点: torchrun --nproc_per_node=8 --nnodes=2 --node_rank=1 --master_addr=192.168.1.100 --master_port=29500 ddp_training.py
```

## 3. 模型并行：张量并行 (TP) 与流水线并行 (PP)

### 张量并行 (Tensor Parallelism)

将单层 Transformer 的权重矩阵按列或行切分到多 GPU。每层计算时 GPU 间 all-reduce/all-gather 通信。通信量极大，适合 NVLink 高速互联。Megatron-LM 是经典实现。

### 流水线并行 (Pipeline Parallelism)

将模型按层切分到不同 GPU，存在"气泡"问题（下游 GPU 等待上游完成前向）。优化技术：GPipe（按 micro-batch 流水）、1F1B 调度。

### 3D 并行

Megatron-LM 提出的组合方案：3D 并行 = TP × PP × DP。例如 256 张 GPU：TP=8（单机 8 卡）× PP=4（4 台机器）× DP=8（8 组）。

## 4. ZeRO / FSDP / DeepSpeed

### ZeRO-1/2/3 逐级对比

| ZeRO 阶段 | 分片内容 | 每卡显存节省 | 通信量 | 实现复杂度 |
|-----------|---------|-------------|--------|-----------|
| ZeRO-1 | 优化器状态 (m, v) | ~4x | 低 | 低 |
| ZeRO-2 | 优化器状态 + 梯度 | ~8x | 中 | 中 |
| ZeRO-3 | 优化器状态 + 梯度 + 参数 | ~N 倍 (N=GPU数) | 高 | 高 |

## 5. FP32 / FP16 / BF16 / INT8 / INT4 与 AMP

### 数值精度对比

| 精度 | 总位数 | 符号 | 指数 | 尾数 | 动态范围 | 典型用途 |
|------|--------|------|------|------|---------|---------|
| FP32 | 32 | 1 | 8 | 23 | ~10^38 | 训练 master weights |
| BF16 | 16 | 1 | 8 | 7 | ~10^38 | 训练前向/反向计算（主流） |
| FP16 | 16 | 1 | 5 | 10 | ~65504 | 推理加速 |
| INT8 | 8 | 1 | — | 7 | 256 级 | 推理量化 |
| INT4 | 4 | — | — | — | 16 级 | 训练量化（QLoRA）/ 推理 |

### 为什么 BF16 比 FP16 更适合训练

> "FP16 的指数位只有 5 位，动态范围 [-65504, 65504]，小梯度容易 underflow 为 0，需要用 loss scaling。BF16 用 8 位指数（和 FP32 一样），动态范围约 10^38，小梯度不会 underflow，训练不需要 loss scaling，代码更简洁，训练更稳定。代价是尾数精度从 10 位降到 7 位，但实践证明这对深度学习训练的收敛基本没有影响。"

### AMP 代码

```python
import torch.cuda.amp as amp

def amp_training_step_bf16(model, batch, optimizer):
    with amp.autocast(device_type="cuda", dtype=torch.bfloat16):
        outputs = model(**batch)
        loss = outputs.loss
    optimizer.zero_grad()
    loss.backward()
    torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
    optimizer.step()
    return loss.item()
```

**本项目使用 BF16**：RTX 5090 原生支持 BF16 Tensor Core 计算。

## 6. Gradient Checkpointing / Gradient Accumulation / Gradient Clipping

### Gradient Accumulation

```python
def training_loop_with_grad_accum(model, dataloader, optimizer, grad_accum_steps=8):
    model.train()
    optimizer.zero_grad()
    for step, batch in enumerate(dataloader):
        outputs = model(**batch)
        loss = outputs.loss / grad_accum_steps  # 缩放 loss
        loss.backward()
        if (step + 1) % grad_accum_steps == 0:
            torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
            optimizer.step()
            optimizer.zero_grad()
```

### Gradient Checkpointing

无 checkpointing：激活值显存 ≈ batch_size × seq_len × hidden_size × num_layers ≈ 32 GB。有 checkpointing：减少 50-70%，总计 ≈ 10-16 GB。

## 7. 显存分解：参数 / 梯度 / 优化器状态 / 激活值

### 本项目 QLoRA SFT 显存分布


## 8. QLoRA 为什么省显存（与分布式对比视角）

| 方法 | 原理 | 显存节省 | 代价 |
|------|------|---------|------|
| **QLoRA (本项目)** | 4bit 量化 + 只训 adapter | 约 5x | 精度略降，表达能力有限 |
| **ZeRO-3** | 参数/梯度/优化器全分片 | 约 N 倍 | 大量通信，需要高速互联 |
| **Gradient Checkpointing** | 不存激活值，反向重算 | 约 2x (激活部分) | 20-30% 额外计算 |
| **CPU Offload** | 优化器/参数放 CPU | 随 CPU 内存而定 | PCIe 带宽瓶颈 |

> "单卡 + QLoRA 组合不是因为'只有一张卡'，而是经过计算的合理技术选型。8B 级别的 QLoRA 训练，单卡显存已足够，引入分布式反而增加了通信开销和代码复杂度。这体现了'用合适的工具解决合适的问题'的工程思维。如果扩展到 70B 模型或全量微调，分布式就是必需的。"

## 9. DPO 为什么比 SFT 更吃显存

> "DPO 的核心 loss 需要同时计算 4 次前向传播：policy model 对 chosen response、policy model 对 rejected response、reference model 对 chosen response、reference model 对 rejected response。而 SFT 只需要 1 次前向。此外 reference model 本身额外占用显存（约 4GB in NF4）。因此 DPO 的显存需求是 SFT 的 1.5-2 倍。"

**解决策略（本项目采用）**：Pre-compute reference log-probs → 消除 reference model 加载；micro_batch_size=1；gradient_checkpointing=True；max_seq_length=2048。

```python
# Pre-compute Reference Log-probs
ref_logps_chosen = compute_logprobs_in_batches(ref_model, dataset["chosen"])
ref_logps_rejected = compute_logprobs_in_batches(ref_model, dataset["rejected"])
# 存入 dataset → 训练时不加载 reference model
```

## 10. Loss NaN 排查 / OOM 排查 / Checkpoint Resume

### Loss NaN 排查决策树

```
Loss 突然变成 NaN:
├── 步骤 1: 检查是否是某个 batch 的问题 → torch.autograd.detect_anomaly()
├── 步骤 2: 检查学习率是否过大 → 尝试 lr/10 重新运行
├── 步骤 3: 检查数据是否有 NaN/Inf
├── 步骤 4: 检查是否是 FP16 溢出 → 换 BF16 或减小 loss scale
├── 步骤 5: 检查 attention mask 是否正确
└── 步骤 6: 降低 max_grad_norm (如 1.0 → 0.3)
```

### OOM 排查决策树

```
CUDA OOM 了:
├── forward → batch size 太大 → 减小 batch_size
├── backward → 激活值太大 → 开 gradient_checkpointing
├── optimizer.step() → 优化器状态 → 换 paged_adamw_8bit
├── batch_size=1 还 OOM:
│   ├── DPO: pre-compute reference log-probs
│   └── SFT: 减少 max_seq_len
└── 显存使用 < 90% 但 OOM → 碎片化 → PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True
```

## 11. 面试核心问答

### Q: 单卡 5090 怎么训练 8B？⭐⭐⭐⭐⭐

> "我们使用 QLoRA 技术。核心思路是 4bit NF4 量化把 8B 参数从 16GB 压缩到约 4GB，只训练 LoRA adapter（约 5.4M 参数，占总参数 0.07%），优化器状态用 paged_adamw_8bit 进一步压缩和可选的 CPU offload，激活值通过 gradient checkpointing 省 50-70%。SFT 阶段 batch_size=2、grad_accum=8、max_seq_len=2048，显存峰值约 18GB。DPO 阶段 batch_size=1、grad_accum=8，通过 pre-compute reference log-probs 消除 reference model 加载，显存峰值约 22-24GB。32GB 显存还有约 8-10GB 的安全余量，训练非常稳定。这个配置不是'勉强能跑'，而是'运行在舒适区'。"

### Q: 如果给你 8 卡你怎么扩展训练？⭐⭐⭐⭐⭐

> "如果扩展到 8 卡 A100/H100，我会考虑以下方案：
>
> **方案 A（保守，QLoRA + DDP）**：保持 QLoRA 配置不变，8 卡做数据并行（DDP）。每卡独立训练自己的数据分片，梯度通过 all-reduce 同步。effective batch size 可以做到 128（8卡 × 2 batch × 8 grad_accum）。代码改动最小，适合快速验证。
>
> **方案 B（进阶，FSDP + 全量微调）**：如果有 8 卡 A100（80GB），可以做全参数微调。使用 FSDP（FULL_SHARD 策略）把 8B 模型的参数/梯度/优化器状态分片到 8 张卡上。设置 mixed precision = BF16，gradient checkpointing 开启。8 卡用 NCCL over NVLink 通信。
>
> **方案 C（扩展 70B+）**：需要用 3D 并行：TP（单机 8 卡内）+ PP（跨节点）+ DP（多节点间）+ ZeRO-3。使用 Megatron-LM 或 DeepSpeed + HuggingFace 集成。
>
> 对于我的项目场景（8B QLoRA），方案 A 是最务实的——代码改动最小，通信开销可忽略（LoRA 参数只有 5M），主要收益是 8x 的吞吐提升。"

| 项目 | 数值 |
|------|------|

> "全参训不动上 QLoRA，单卡通吃 8B 大模型。DP 要淘汰，DDP 是标配，ZeRO 分三级，FSDP 是原生的。激活存不下开 ckpt，batch 太大做累积，精度不行换 BF16。DPO 四遍前向吃显存，pre-compute logprobs 来救场。"
